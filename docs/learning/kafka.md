# Part 1. 4주 차 전에

## ⭐ 1. 토픽 · 파티션 · 오프셋

- 💡 **토픽** = 이벤트 종류별 통 (`transfer-events`). 토픽은 **파티션** 여러 개로 쪼개진다. 파티션 하나는 **추가만 되는 로그 파일**(append-only)이고, 메시지마다 **오프셋**(0, 1, 2…) 번호가 붙는다.
  - 메시지를 읽어도 지워지지 않는다 (보관 기간까지 남음). 그래서 여러 컨슈머 그룹이 같은 메시지를 각자 읽을 수 있고, 오프셋을 되돌려 **다시 읽을** 수도 있다
  - 큐(RabbitMQ)와 가장 큰 차이: 큐는 읽으면 빠지고, Kafka는 "어디까지 읽었나(오프셋)"를 읽는 쪽이 기억한다
- 🎤 Kafka와 RabbitMQ의 차이? / 메시지를 읽으면 지워지나요? / 파티션은 왜 나누나요? (병렬 처리의 단위)
- 🔬 토픽을 만들고 메시지 3개를 넣은 뒤, 컨슈머로 처음부터 읽기 → 같은 메시지를 또 읽기 (지워지지 않음 확인)

## ⭐ 2. 파티션 키와 순서 보장

- 💡 순서는 **파티션 안에서만** 보장된다. 토픽 전체 순서는 없다. 같은 **키**를 가진 메시지는 항상 같은 파티션으로 간다 (`hash(key) % 파티션 수`).
  - 우리 원칙 "파티션 키는 계좌 ID" (CLAUDE.md 2장)의 이유: 한 계좌의 이벤트(입금 → 출금)가 순서대로 처리되어야 하니까
  - 함정: **파티션 수를 나중에 늘리면** `hash % N`이 바뀌어 같은 키가 다른 파티션으로 간다 → 그 순간 순서가 깨질 수 있다. 그래서 파티션 수는 처음에 넉넉히 정한다
  - 함정: 키 하나에 트래픽이 몰리면 그 파티션만 바쁘다 = **핫 파티션** (16주 차)
- 🎤 Kafka는 순서를 보장하나요? / 송금 이벤트의 키는 무엇으로? 송금 ID? 계좌 ID? (송금 하나는 두 계좌에 걸친다 — 4주 차 설계 질문) / 파티션을 늘리면 무슨 일이?
- 🔬 키 없이 10개, 같은 키로 10개 보내고 각각 어느 파티션에 들어갔는지 보기

## ⭐ 3. 컨슈머 그룹

- 💡 같은 **그룹 ID**를 쓰는 컨슈머들이 파티션을 **나눠 맡는다.** 파티션 하나는 그룹 안에서 **한 컨슈머만** 읽는다 → 그래서 순서가 지켜진다.
  - 파티션 3개에 컨슈머 4개면 1개는 논다 → **컨슈머 수의 상한 = 파티션 수**
  - 다른 그룹은 같은 메시지를 독립적으로 다 받는다 (notification 그룹, 나중의 감사 로그 그룹…)
  - 그룹 멤버가 늘거나 죽으면 파티션을 다시 나눈다 = **리밸런싱** (16주 차)
- 🎤 컨슈머를 10개로 늘리면 10배 빨라지나요? / notification 파드를 2개로 늘리면 알림이 두 번 가나요? (같은 그룹이면 아니다)
- 🔬 notification을 2개로 늘리고 파티션이 어떻게 나뉘는지 보기 (`kafka-consumer-groups --describe`)

## ⭐ 4. 브로커 · 리더 · 팔로워 · ISR · 복제

- 💡 **브로커** = Kafka 서버 한 대. 파티션은 여러 브로커에 **복제**된다 (replication factor).
  - 복제본 중 하나가 **리더**: 읽기·쓰기는 리더만 받는다. 나머지는 **팔로워**: 리더를 따라 복사한다
  - **ISR** (In-Sync Replicas) = 리더를 충분히 따라잡은 복제본 목록. 리더가 죽으면 **ISR 중에서** 새 리더를 뽑는다 = **리더 선출**
  - 복제 계수 1(브로커 1대)이면 그 브로커가 죽는 동안 토픽을 못 쓴다. 학습 초반엔 감수, 17주 차 장애 실험엔 3대 필요
- 🎤 브로커 하나가 죽으면 메시지가 사라지나요? / ISR이 뭔가요? / ISR이 아닌 복제본을 리더로 뽑으면? (`unclean.leader.election` — 가용성 vs 유실)
- 🔬 (3대일 때) 리더 브로커 파드를 지우고, 파티션 리더가 다른 브로커로 바뀌는 것 보기

## ⭐ 5. 프로듀서 acks: "보냈다"의 의미

- 💡 프로듀서가 "전송 성공"으로 보는 기준:
  | acks | 성공 기준 | 위험 |
  | --- | --- | --- |
  | `0` | 보내기만 함 | 브로커가 못 받아도 모름 |
  | `1` | 리더가 받음 | 팔로워가 복사하기 전에 리더가 죽으면 유실 |
  | `all` | ISR 전부가 받음 | 느리지만 안전. `min.insync.replicas`와 짝 |
  - 돈 이벤트는 `acks=all` + 멱등 프로듀서(`enable.idempotence=true`, 재시도해도 브로커가 중복을 걸러 줌). 최신 Kafka 클라이언트는 이게 기본값이다
  - 우리 원칙 "타임아웃 ≠ 실패"(pitfalls 6)가 여기도 그대로: 전송 타임아웃은 "브로커에 들어갔는지 모름"이다
- 🎤 acks=all이면 절대 유실이 없나요? (min.insync.replicas=1이면 사실상 acks=1) / 프로듀서 재시도로 중복이 생기는 이유?

# Part 2. 해당 주차에

## 6. 오프셋 커밋 시점: 유실 vs 중복 (6주 차)

- 💡 컨슈머는 "어디까지 처리했나"를 오프셋으로 **커밋**한다.
  - 처리 **전에** 커밋 → 처리 중 죽으면 그 메시지는 **유실** (at-most-once)
  - 처리 **후에** 커밋 → 커밋 직전 죽으면 재시작 후 **다시 받음 = 중복** (at-least-once)
  - 실무 기본은 at-least-once + **멱등 컨슈머** (CLAUDE.md 7장: 모든 컨슈머는 멱등, 이벤트에 `eventId`)
  - "exactly-once"는 Kafka 안에서 읽고 쓰는 경우(트랜잭션)에만 성립한다. DB·외부 API가 끼면 결국 멱등으로 푼다
- 🎤 Kafka는 exactly-once를 보장하나요? / 알림이 두 번 가면 어떻게 막나요?

## 7. 커밋과 발행 사이 (6주 차, Outbox)

- 💡 "DB에 송금 완료 커밋 → Kafka 발행" 사이에 죽으면 이벤트가 **유실**된다. 순서를 바꿔도(발행 → 커밋) 반대 문제(유령 이벤트)가 생긴다. → 이벤트를 **같은 DB 트랜잭션으로 outbox 테이블에** 쓰고, 별도 발행기가 읽어서 보낸다 (Transactional Outbox)
- 🎤 DB와 Kafka에 동시에 쓰는 걸 원자적으로 할 수 있나요? / Outbox 발행 방식: 폴링 vs CDC(Debezium)?

## 8. 리밸런싱 · 컨슈머 랙 · 핫 파티션 (16주 차)

- 💡 **랙** = 마지막 메시지 오프셋 − 컨슈머가 커밋한 오프셋 (밀린 양). 리밸런싱 중엔 그룹 전체가 잠깐 멈춘다(기존 방식). 처리가 느려 `max.poll.interval.ms`를 넘기면 "죽은 컨슈머"로 보고 리밸런싱 → 또 느려짐 → 반복 (리밸런싱 폭풍)
- 🎤 컨슈머 랙이 계속 늘면 어떻게 하나요? / 컨슈머를 늘려도 랙이 안 줄면? (핫 파티션, 파티션 수 상한)

## 9. 컨트롤러(KRaft) · 롤링 재시작 (17주 차)

- 💡 **컨트롤러** = 클러스터 메타데이터(어떤 브로커가 살아 있나, 각 파티션의 리더는 누구)를 관리하고 리더 선출을 지휘한다. 예전엔 ZooKeeper가 이 역할, Kafka 4.0부터는 **KRaft**(Kafka 내부의 Raft 합의)만 쓴다. 컨트롤러도 과반수가 살아 있어야 해서 보통 3대
  - **롤링 재시작** (설정 변경·버전업): 브로커를 **한 대씩**, 그 브로커가 리더인 파티션을 다른 브로커로 옮긴 뒤 재시작, 따라잡을 때까지 기다렸다 다음. Strimzi가 이 순서를 대신 지켜 준다 (손으로 하면 사고 나는 부분)
  - 앱 롤링 배포(2주 차 공통 차트의 `maxSurge`/`maxUnavailable`, preStop)와 비교해 보면 좋다: 상태 없는 앱은 아무거나 먼저 죽여도 되지만, Kafka는 "리더를 먼저 옮기고"가 필요하다
- 🎤 Raft에서 왜 홀수 대(3, 5)인가요? / Kafka 브로커를 무중단으로 업그레이드하려면?
