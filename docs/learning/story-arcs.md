# 이야기 줄기 (블로그·면접 얼개)

> 2026-11-23 개발자 결정: 자기 말 요약과 블로그는 **20주 차까지 다 한 뒤 몰아서**, 주차별이 아니라 **주제의 줄기**로 엮어 쓴다 (예: 락 경합 → 벌크헤드·요청 제한).
> Claude는 세션마다 새 장면을 해당 줄기에 한 줄씩 붙인다. 장면 = 주차 · 무엇을 봤나 · 문서 링크. ⏳ = 앞으로 올 장면 (로드맵 기준).
> 한 줄기가 글 한 편(또는 시리즈)이 된다. 줄기끼리 겹치는 장면은 양쪽에 둔다.

---

## 1. 기다림은 공짜가 아니다: 대기가 쌓여 시스템이 무너지는 법과 막는 법

질문: 느린 곳 하나가 왜 전체를 죽이나? 기다리는 동안 무엇이 쌓이나? 어디서 끊어야 하나?

- 5주 · k6 stress: DB 커넥션 풀 고갈 → 대기 스레드 증가 → 힙 밖 메모리 → OOMKilled → 앞단 gateway까지 전파 (`docs/experiments/week-05-k6-baseline.md`)
- 4주 · Kafka가 죽으면 `send()`가 60초 막힌다 = 부수 기능이 핵심 기능을 멈춤 (pitfalls 20)
- 7주 · 핫 계좌: 처리 한계(1 ÷ 락을 쥔 시간)를 넘으면 줄이 끝없이 는다. Redis 락은 한계가 낮아 먼저 줄이 생기고, 대기자마다 Netty 버퍼 비용 → 같은 스레드 200개인데 혼자 OOMKilled. "어디서 기다리느냐가 비용" (`week-07-locks.md` 판독 1, pitfalls 37, `2026-11-23.md` 3-1)
- 7주 · Redis 락은 DB의 일이 아니라 기다림(커넥션 점유)을 덜어 준다 = 격리 (`2026-11-23.md` 3-2)
- 7주 · 느린 성공(비관적 락) vs 빠른 실패(낙관적 락) vs 전체 장애(Redis) = 업무 판단 (`2026-11-23.md` 5)
- 기초: 스레드가 기다리는 세 가지 모양, 이벤트 루프 (`io-and-event-loop.md`)
- ⏳ 14주 · 게이트웨이 MVC / 가상 스레드 / WebFlux: 기다리는 스레드의 비용 자체를 바꾸기, 이벤트 루프 블로킹
- ⏳ 15주 · 외부 은행 지연 → 장애 전파 → 타임아웃·서킷 브레이커·**벌크헤드**·백오프+지터 (대기 제한의 정답지)
- ⏳ 16주 · 컨슈머 랙: 비동기에서도 줄은 쌓인다
- ⏳ 17주 · 카오스: graceful shutdown, readiness

## 2. "모른다"를 다루는 법: 결과 불명과 멱등

질문: 응답이 안 왔을 때 돈은 나갔나? 다시 보내도 되나? 누가 언제 확정하나?

- 3주 · core 송금 ID 멱등 (UNIQUE + 재시도), 동시 중복 요청 재현
- 3-2주 · 타임아웃·5xx = 결과 불명(UNKNOWN), "응답 없음 = 실패" 오판의 이중 송금 경로 (transfer 어댑터)
- 3-2주 · 고객 멱등 키: 처리 중 재요청, UNKNOWN 뒤 재시도, 키 범위(사용자별) (pitfalls 17)
- 5주 · 사가 의도 상태: 호출 전에 커밋, 결과 불명이면 보상 금지 (`2026-11-20.md` 1, pitfalls 27)
- 6주 · Outbox: 발행 타임아웃 ≠ 미발행, at-least-once + eventId 고정 (pitfalls 29·30)
- 7주 · 라이브러리 안의 멱등 키: Redisson 풀기 기록 (`io-and-event-loop.md` 8)
- 8주 · 당행 결과 불명 해소 설계: "다시 보내면 되지" → 늦은 실행(멱등은 늦은 실행을 못 막음) → 조회만 → 조회의 "없음"은 "아직 하는 중"일 수도 → 트랜잭션 타임아웃(시작부터 잰다) + 대사 → 기준 시각 `createdAt`. 설계가 장애 질문 하나마다 바뀐 과정 자체가 글 (`design-drills/08-unknown-resolution.md` "설계가 바뀐 과정", ADR-0005, pitfalls 38, `timeouts-and-deadlines.md`)
- ⏳ 8주 · 해소 스케줄러 구현·재현, 타행 결과 불명(외부 은행 조회), 일일 대사

- (2026-11-25, 8주 차) 마지막 그물: 해소 일꾼이 외부 조회 "없음"을 믿고 출금을 취소했는데 외부는 입금 → 원장은 완벽히 맞는데 은행은 5만 원을 두 번 냈다. 외부 정산 파일과의 양방향 대사만 이걸 잡는다 (`DOUBLE_PAYMENT`, `docs/experiments/week-08-reconciliation.md`). "모른다"를 다루는 장치는 상대의 약속에 기대고, 약속이 깨지는 걸 잡는 건 대사
- (2026-11-25) 오늘 실제 데이터: 합계로 보면 transfer 40억 vs core 2만 8천 원, 건별로 보면 265건 전부 정상 (실패 송금은 전표가 없어야 정상). 총액 대사가 왜 보조인지

## 3. 원장이 진실, 잔액은 캐시

질문: 같은 돈을 두 군데에 적으면 어느 쪽을 믿나? 틀어진 걸 어떻게 찾나?

- 3주 · 복식부기 원장 + 잔액을 한 트랜잭션으로 (`docs/domain/README.md`)
- 5주 · 미정산 임시 계정, 보상 = 역분개 (원래 전표를 가리킴, 한 번만)
- 7주 · 락 없음: 원장 합은 정확, 잔액만 +8,507원 (INSERT는 덮어쓰지 않는다) (`2026-11-23.md` 2)
- ⏳ 8주 · 일일 대사: 불일치 분류, 수작업 조정 전표
- ⏳ 13주 · 패널의 잔액 정합성 지표

## 4. 동시성: 검사와 행동 사이의 틈

> ⭐ 개발자가 "진짜 정리 멋지게, 블로그 빡세게" 하겠다고 한 줄기 (2026-11-23). 1번 줄기(기다림)와 7주 장면을 공유한다 → 시리즈로: ① lost update 재현 → ② 전략 6개 실측 → ③ Redis 락은 왜 혼자 죽었나 → ④ 그래서 무엇을 고르나

질문: 확인하고 행동하면 왜 틀리나? 틈을 없애는 방법들은?

- 3-2주 · BOLA 검사를 출금 트랜잭션 안으로 (TOCTOU 제거)
- 6주 · Outbox 릴레이 `FOR UPDATE SKIP LOCKED`, MySQL 갭 락 함정
- 7주 · lost update 재현, 전략 6개 (조건부 UPDATE·비관·낙관·Redis pub/sub·스핀), 락 범위는 트랜잭션 바깥 (pitfalls 32~34, `concurrency.md`)
- 7주 · Redis 풀기 전 확인 제거: 막지도 못하는 확인 대신 예외로 (`2026-11-23.md` 4)
- 7주 · 기본 전략 선택(ATOMIC_UPDATE)과 "락은 작업마다 고른다", 섞어도 안전한 조건(version +1) (`week-07-locks.md` 적용한 해결책)
- 7주 · "비관적 락은 언제?" 답변 연습 2회: 이점은 빠름이 아니라 다 성공, 짧은 타임아웃이어도 낙관과 다른 이유(헛수고, 초당 성공 460 vs 300) (`concurrency.md` 3절)
- ⏳ 8주 · 해소 스케줄러와 고객 재시도의 경합

## 5. 측정을 믿을 수 있게: 실험이 조건을 만들었나

질문: 숫자가 거짓말하는 경우는? 대조군 없이 "안전하다"고 할 수 있나?

- 5주 · coordinated omission: VU 루프는 느린 구간을 덜 잰다 → arrival-rate (`week-05-k6-baseline.md`)
- 5주 · 고객 위치(k6) vs 서버 지표의 차이
- 7주 · 균일 도착은 경합을 안 만든다: 락 없음이 안 깨짐 → 대조군으로 발견 (pitfalls 36, `2026-11-23.md` 1·6)
- 7주 · 카운터가 음수 = 측정 중 재시작
- ⏳ 14·15주 · 전후 비교 실험들

- (2026-11-25, 8주 차) 메모리 테스트의 기준점: 대사 추출을 커서로 바꾼 뒤 "첫 줄 vs 마지막 줄" 메모리를 비교하는 테스트를 썼는데 커서를 빼도 통과했다 (커서가 없으면 첫 줄 전에 30만 줄을 다 받아 둬서 두 시점이 똑같이 높다). 기준을 "조회 전"으로 바꾸자 커서 없음 91MB / 있음 20MB 미만으로 갈렸다. 고친 것을 일부러 빼서 테스트가 실패하는지 보지 않았으면 몰랐다

## 7. 보이게 만들기: 요청 한 건을 끝까지 따라가기

질문: 지표로는 "나쁘다"만 안다. 이 요청 한 건은 어디서 시간을 썼고, 어디서 길을 잃었나?

- 7주 · OOM 판독은 전부 지표로 (`observability.md` 7-5)
- 9주 · 트레이싱 부품: 에이전트(송장)·Collector(집하장)·Tempo(창고), AWS·Datadog 대응 (`observability.md` 5-0)
- 9주 · Outbox에서 트레이스가 끊김 → traceparent를 행에 저장, 묶음은 부모가 될 수 없어 행마다 자식 (pitfalls 39). 대기 951ms가 트레이스 빈칸으로 보임
- ⏳ 9주 · 느린 송금 트레이스 읽기, 로그에 traceId
- ⏳ 10주 · 로그 ↔ 트레이스, exemplar, RED 대시보드
- ⏳ 11주 · SLO·알림
- (2026-11-26) **판독 연습 1**: bank-mock 간헐 지연에서 RED(딱 3초 = 타임아웃) → 부르는 쪽 vs 받는 쪽(3초 vs 10초) → 워터폴의 "삐져나온 막대" = 결과 불명이 생기는 순간 → 로그 → 송금 ID로 이으려다 해소 로그의 공백 발견. 줄기 2("모른다"를 다루는 법)와 만나는 장면. 덤: transfer 호출 지표가 아예 없었던 것(트레이스만 보고 계측됐다고 착각, pitfalls 40), CI 초록인데 배포 안 됨(pitfalls 44)
