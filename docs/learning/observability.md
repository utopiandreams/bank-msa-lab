# Part 1. 읽는 법

## ⭐ 1-1. 세 가지 틀: RED · USE · Golden Signals

- 💡 **RED** (서비스·API를 볼 때): **R**ate(초당 요청) / **E**rrors(에러율) / **D**uration(지연, p50·p95·p99). "사용자가 느끼는 것"
- 💡 **USE** (자원을 볼 때: CPU, 메모리, 커넥션 풀, 스레드 풀, 디스크): **U**tilization(얼마나 쓰나) / **S**aturation(대기열이 생겼나) / **E**rrors. "왜 그렇게 느끼는가"
- 💡 **Golden Signals** (구글 SRE): 지연 · 트래픽 · 에러 · 포화. RED + USE의 포화를 합친 것
- 💡 순서가 중요하다: **RED로 "어디가 아픈지" → USE로 "왜 아픈지"**. 자원부터 보면 정상인 고사용률에 낚인다 (CPU 90%여도 응답이 빠르면 문제 아님)
- 🎤 대시보드를 처음 만든다면 무엇부터 넣나요?

## ⭐ 1-2. 퍼센타일과 히스토그램

- 💡 **평균은 거짓말한다.** 99개가 10ms, 1개가 5초면 평균 60ms. 그 1%가 화난 고객이다. 그래서 p99 (100번 중 가장 느린 1번 직전의 값)
  - p50 = 보통 사용자, p95 = 운 나쁜 사용자, p99 = 가장 운 나쁜 사용자 (그리고 대개 가장 많이 쓰는 VIP — 요청이 많으면 꼬리를 자주 밟는다)
- 💡 **퍼센타일은 평균 낼 수 없다.** 파드 3개의 p99를 평균 내도 전체 p99가 아니다 → Prometheus는 **히스토그램**(구간별 개수)을 합친 뒤 `histogram_quantile`로 계산한다
- 💡 **히스토그램 구간(bucket)이 정밀도를 정한다.** 구간이 100ms, 500ms면 p99가 "100~500 사이 어딘가"로만 나온다. SLO 경계값(예: 300ms)에 구간을 둔다
- 📈 **히트맵**: 시간 × 지연 구간 × 개수를 색으로. 평균선에서 안 보이는 "두 갈래 분포"(캐시 히트는 5ms, 미스는 200ms)가 보인다
- 🎤 p99를 서비스 인스턴스별로 구한 뒤 평균 내면 왜 안 되나요?

## ⭐ 1-3. 대시보드 30초 판독 순서

1. **사용자 영향**: 에러율, p99, SLO 소진율. 영향이 없으면 급하지 않다
2. **언제부터**: 그래프에서 꺾인 시점 → **그 시점에 무엇이 바뀌었나** (배포, 설정 변경, 트래픽 급증, 외부 장애). 장애 원인 1순위는 "변경"이다
3. **어디서**: 서비스별 RED → 가장 먼저 나빠진 곳 (나중에 나빠진 곳은 피해자일 가능성이 높다)
4. **왜**: 그 서비스의 USE (커넥션 풀, 스레드, GC, CPU 스로틀링) + 그 서비스가 부르는 의존성의 지연
5. **증거**: 느린 요청 하나의 트레이스 → 그 traceId로 로그

- 💡 "먼저 나빠진 곳이 원인, 나중에 나빠진 곳은 피해자"가 분산 시스템 판독의 핵심 감각

## ⭐ 1-4. 서비스 대시보드는 보통 어떻게 짜나 (2026-11-25 개발자 질문: "RED가 뭔지, 대시보드를 보통 어떻게 구성하는지")

- 💡 **RED는 서비스 하나를 세 숫자로 요약하는 방법이다.** 받은 일의 양(Rate, 초당 요청 수), 그중 실패한 비율(Errors, 에러율), 걸린 시간(Duration, p50·p95·p99)
  - 셋이 다 필요하다. 에러율만 보면 요청이 0건으로 떨어진 장애(앞단이 막힘)를 못 본다. 0건이면 에러도 0%라 "정상"으로 보인다. 지연만 보면 "빨리 실패하는" 장애를 놓친다. 실패는 대개 빠르다 (DB가 죽으면 즉시 예외)
  - 셋 다 **"고객이 느끼는 것"**이다. CPU·메모리는 고객이 못 느낀다. 그래서 RED가 위, 자원(USE)이 아래
- 💡 **"요청"은 HTTP만이 아니다.** 하는 일이 있으면 RED가 있다. Kafka 컨슈머의 R = 초당 처리한 메시지 수, E = 처리 실패율, D = 메시지 하나 처리 시간. 스케줄러는 실행 수 · 실패 수 · 실행 시간. 배치는 처리 건수 · 실패 건수 · 회차 소요 시간
- 💡 **대시보드는 위에서 아래로 "넓게 → 좁게"** (실무에서 가장 흔한 배치):
  1. **맨 위: 큰 숫자 카드 몇 개.** 고객 입구(gateway)의 TPS · 에러율 · p99. 기준값에 따라 초록/노랑/빨강. 3초 안에 "지금 괜찮나?"에 답한다
  2. **서비스 비교:** R · E · D 그래프 세 개, 서비스마다 선 하나. "어디가 아픈가, 누가 먼저 꺾였나"
  3. **서비스 하나 상세:** 상단 드롭다운(변수)으로 서비스를 고르면 엔드포인트별로 쪼개서 보여 준다. "그 서비스의 어떤 API가?"
  4. **의존성:** 이 서비스가 부르는 쪽(DB · 다른 서비스 · 외부)의 지연 · 에러. "내가 느린가, 내가 부르는 쪽이 느린가?"
  5. **자원(USE):** 커넥션 풀 · 스레드 · JVM · CPU. "왜?" 보통은 별도 대시보드(JVM · CNPG)로 링크를 걸어 넘긴다
  - 위쪽 행일수록 **자주, 빨리** 보고, 아래쪽은 **원인을 좁힐 때만** 본다. 판독 순서(1-3)와 대시보드 배치가 같다
- 💡 **흔한 실수**
  - 그래프 50개를 한 화면에 늘어놓기 ("graph wall"). 장애 때 어디를 볼지 모른다. **대시보드 하나 = 질문 하나**
  - 평균 지연만 그리기 → p99 (1-2)
  - 에러율에 4xx · 5xx 섞기 → 의미가 다르다 (Part 2). 5xx = 우리 잘못, 4xx = 고객 입력 · 업무 거절 · 계약 문제
  - 서비스마다 y축 단위 · 색이 제각각 → 같은 뜻은 같은 모양으로
  - 헬스 체크 · 지표 수집 요청을 걸러 내지 않기 → 아무도 안 쓰는데 "초당 0.3건, p50 1ms"로 보인다 (이 프로젝트에서 실제로 발견, 2026-11-25)
- 💡 **보통 대시보드를 여러 장 둔다.** 서비스 개요(RED, 매일 · 장애 첫 화면) / 서비스별 상세 / 자원(JVM · DB · Kafka, 원인 찾기) / 업무 지표(송금 완료 수 · UNKNOWN 체류). 첫 화면에서 아래 대시보드로 링크
- 🎤 대시보드를 처음 만든다면 어떤 패널부터 넣고 왜 그 순서인가요? (RED가 위, 자원이 아래: 고객 영향부터, 원인은 나중)
- 🎤 에러율 0%, p99 정상인데 장애일 수 있나요? (Rate가 0으로 떨어짐: 앞단 차단 · DNS · 라우팅. 그래서 R도 같이 본다)
- 🎤 Kafka 컨슈머의 RED는 뭔가요? 컨슈머 랙과 무엇이 다른가요? (RED는 처리하는 쪽의 속도 · 실패 · 시간, 랙은 "밀린 양" = 포화(USE의 S))
- 📎 이 프로젝트 대시보드: `deploy/grafana/dashboards/` (서비스 RED는 10주 차에 추가), 판독 순서: 1-3, 활용 장면: `monitoring-playbook.md`

# Part 2. 계층별로 매일 보는 지표

| 계층 | 매일 보는 것 | 경보를 거는 것 | 이 프로젝트의 출처 |
| --- | --- | --- | --- |
| **API** | RPS, 에러율(5xx·4xx 분리), p50/p95/p99 (엔드포인트별) | 5xx 비율, p99 SLO 소진 | Micrometer `http.server.requests` |
| **의존성 호출** | 호출 대상별 지연·타임아웃·에러 | 타임아웃 급증 | Micrometer `http.client.requests` (transfer → core) |
| **JVM** | GC 후 힙 사용량, GC 일시정지 시간·빈도, 스레드 수(BLOCKED), CPU | Old 영역이 GC 후에도 계속 증가, GC 시간 비율 | Micrometer `jvm.*` |
| **커넥션 풀** | active / idle / **pending**, 커넥션 획득 시간 p99, 타임아웃 수 | pending > 0 지속, 획득 타임아웃 | Micrometer `hikaricp.*` |
| **DB** | QPS, 상위 쿼리(총 시간 기준), 활성 커넥션/최대, 락 대기, 데드락, 캐시 히트율 | 커넥션 80%, 락 대기, 복제 지연 | `pg_stat_statements`, `pg_stat_activity`, CloudNativePG exporter |
| **Kafka** | 컨슈머 랙, 생산·소비 속도, 리밸런싱 횟수 | 랙이 계속 증가, under-replicated 파티션 | Strimzi exporter (4주 차~) |
| **쿠버네티스** | 파드 재시작, OOMKilled, **CPU 스로틀링**, readiness 실패, 노드 메모리 압박 | 재시작 루프, OOMKilled | kube-state-metrics, cAdvisor |
| **Redis** | 히트율, eviction, 지연, 메모리, slowlog | eviction 급증, 메모리 한계 | redis exporter (7주 차~) |

- 💡 **4xx와 5xx를 나눠 본다.** 4xx 급증은 대개 클라이언트·배포 호환성(계약 변경, pitfalls 18) 문제, 5xx는 우리 문제
- 💡 **"GC 후" 힙을 본다.** 힙 그래프는 원래 톱니 모양(쌓였다 GC로 떨어짐)이다. 문제는 **톱니의 바닥이 계속 올라갈 때** (누수)

# Part 3. 대표 트러블슈팅 10개

> 실무에서 가장 자주 만나는 순서대로. 각각 "그래프 모양"을 외우는 게 목표.

## ⭐ 3-1. 커넥션 풀 고갈

- 📈 p99가 절벽처럼 치솟는데 **CPU는 한가하다**. HikariCP **pending이 0 위로 올라가 머문다**, 획득 시간 p99가 커넥션 타임아웃(기본 30초) 근처. 곧 `Connection is not available, request timed out` 에러
- 🔎 원인 후보: ① 트랜잭션 안에서 원격 호출 (상대가 느려지는 동안 커넥션을 쥐고 있음, pitfalls 8) ② 느린 쿼리·긴 트랜잭션 ③ 트래픽 대비 풀이 작음 ④ 커넥션 누수 (반환 안 함)
- 🛠 원격 호출을 트랜잭션 밖으로, 쿼리 개선, 풀 크기는 **리틀의 법칙**(4-4)으로 계산. 무작정 늘리면 DB가 죽는다
- 🔬 **15주 차**: transfer의 트랜잭션 분리를 일부러 되돌리고(트랜잭션 안에서 core 호출) core에 지연 주입 → pending 그래프 관찰. "왜 T-1에서 트랜잭션을 나눴나"를 숫자로 증명
- 🎤 CPU는 낮은데 응답이 느려요. 무엇부터 보나요?

## ⭐ 3-2. 느린 쿼리 · 인덱스 누락

- 📈 **특정 엔드포인트만** p99 상승, DB CPU 상승, 데이터가 늘수록 점점 나빠짐 (어느 날 갑자기가 아니라 서서히)
- 🔎 `pg_stat_statements`를 **총 시간(total_exec_time) 순**으로 정렬 → 상위 쿼리 `EXPLAIN (ANALYZE, BUFFERS)` → `Seq Scan`, 예상 행 수와 실제 행 수의 큰 차이
- 🛠 인덱스, 쿼리 수정, N+1 제거
- 💡 **평균 시간이 아니라 총 시간 순**으로 본다: 1ms짜리라도 초당 1만 번이면 가장 비싼 쿼리
- 🔬 송금 내역 조회(계좌별)를 데이터 수십만 건으로 만들고 인덱스 유무 비교 (k6)
- 🎤 느린 쿼리를 어떻게 찾나요? / 실행 계획에서 무엇을 보나요?

## ⭐ 3-3. GC · 메모리 누수 · OOMKilled

- 📈 GC 후 힙의 **바닥이 계속 상승** → GC 빈도·일시정지 증가 → **GC 일시정지와 같은 시각에 p99 스파이크** → 결국 `OOMKilled`(컨테이너 한도) 또는 `OutOfMemoryError`(힙 한도)
- 🔎 힙 덤프, 크기 제한 없는 캐시·컬렉션, 스레드로컬
- 💡 **OOMKilled ≠ Java OOM**: OOMKilled는 커널이 컨테이너 메모리 한도를 넘은 프로세스를 죽인 것 (힙 외 메모리: 메타스페이스, 스레드 스택, 다이렉트 버퍼 포함). 그래서 힙을 limit의 75%로 둔다 (2주 차 차트의 `MaxRAMPercentage`)
- 🔬 크기 제한 없는 맵에 계속 넣는 엔드포인트를 실험 스위치로 → 톱니 바닥 상승 관찰
- 🎤 파드가 OOMKilled로 재시작돼요. 힙은 여유 있어 보이는데요?

## ⭐ 3-4. 장애 전파 (느린 의존성 → 스레드 고갈)

- 📈 **다운스트림 지연이 먼저** 오르고 → 호출하는 쪽의 스레드(Tomcat `busy` 스레드)가 최대치에 붙고 → 호출하는 쪽의 **모든** API가 느려짐 (상관없는 API까지)
- 🔎 "먼저 나빠진 곳"을 찾는다 (1-3). 의존성 호출 지연 그래프
- 🛠 타임아웃, 서킷 브레이커, 벌크헤드(의존성별 스레드·커넥션 격리)
- 🔬 **15주 차**: 패널 버튼 "외부 은행 3초 지연"
- 🎤 결제 API 하나가 느려졌는데 왜 전체 서비스가 멈췄나요?

## ⭐ 3-5. 재시도 폭주 (retry storm)

- 📈 장애 시작 후 의존성으로 가는 **요청 수가 오히려 몇 배로 증가** (재시도 × 계층 수). 회복된 뒤에도 몰린 재시도에 다시 쓰러짐
- 🛠 지수 백오프 + **지터**, 재시도 예산(전체의 몇 %까지만), 서킷 브레이커, 멱등이 아닌 요청은 재시도 금지
- 🔬 **15주 차**
- 🎤 재시도는 많이 할수록 좋은가요?

## ⭐ 3-6. 락 경합

- 📈 동시성을 올려도 **처리량은 평평**, p99만 상승. DB의 락 대기(`pg_stat_activity.wait_event_type = 'Lock'`) 증가, 최악은 데드락
- 🛠 락 범위·시간 축소, 낙관적 락으로 전환, 핫 로우(한 계좌에 몰림) 분산
- 🔬 **7주 차**: 동시 출금, 락 3종 비교. 이 그래프가 7주 차 실험 기록의 주인공
- 🎤 비관적 락과 낙관적 락은 언제 각각 쓰나요?

## ⭐ 3-7. 컨슈머 랙 증가

- 📈 랙이 **계속 우상향**. 리밸런싱 횟수가 같이 튀면 "처리가 느려 → 죽은 컨슈머로 판정 → 리밸런싱 → 더 느려짐" 루프
- 🛠 컨슈머 처리 개선, 파티션·컨슈머 증설(상한 = 파티션 수), `max.poll` 설정, 핫 파티션이면 키 설계
- 🔬 **16주 차**: "컨슈머 죽이기", "핫 파티션" 버튼
- 🎤 컨슈머를 늘렸는데 랙이 안 줄어요

## ⭐ 3-8. CPU 스로틀링 (쿠버네티스)

- 📈 CPU 사용률 그래프는 limit **아래**인데 p99가 주기적으로 튄다. `container_cpu_cfs_throttled_periods_total`이 증가
- 🔎 CPU limit은 100ms 단위 할당량이다. 순간적으로 몰아 쓰면 남은 시간 동안 멈춘다. 평균 그래프에는 안 보인다
- 🛠 CPU limit 제거(request만), 또는 넉넉히. JVM 기동·GC 스레드 수 조정
- 💡 이 프로젝트는 처음부터 CPU limit을 안 걸었다 (pitfalls 16). **일부러 걸어서** 재현해 보면 좋다
- 🎤 CPU 사용률은 50%인데 왜 느리죠?

## ⭐ 3-9. 배포할 때마다 에러 스파이크

- 📈 **배포 마커와 정확히 같은 시각**에 502·503 짧은 스파이크, 그리고 배포 직후 몇십 초간 p99 상승
- 🔎 502: 종료 중인 파드로 요청이 감 (preStop 없음, graceful shutdown 없음) / p99 상승: **JIT 워밍업** (JVM은 처음엔 인터프리터로 느리다), 캐시·커넥션 풀이 비어 있음
- 🛠 preStop + graceful shutdown + readiness (2주 차 차트에 이미 있음), 워밍업 요청, 롤링 속도 조절
- 🔬 **17주 차**: 부하 중 롤링 배포, preStop을 껐을 때와 비교
- 🎤 무중단 배포라는데 배포 때마다 에러가 나요

## 3-10. 타임아웃 종류 구분

- 📈 같은 "타임아웃"이라도 **connect timeout**이면 대상이 없거나 네트워크·DNS 문제, **read timeout**이면 대상이 느린 것. 둘을 섞어 보면 원인을 엉뚱하게 잡는다
- 💡 결과 불명과 연결된다: connect 실패는 "요청이 안 갔다"(재시도 안전), read 타임아웃은 "갔는데 모른다"(멱등 재전송·상태 조회 필요, pitfalls 6)
- 🔬 transfer의 `CorePostingAdapterTest`가 이미 둘을 따로 재현한다 (3-1주 차)

# Part 4. 알면 돋보이는 것

## ⭐ 4-1. Coordinated omission (측정 도구가 숫자를 속인다)

- 💡 "응답이 오면 다음 요청"을 보내는 부하 도구(닫힌 모델)는 서버가 느려지면 **요청도 덜 보낸다** → 정작 느린 구간의 표본이 빠져서 p99가 실제보다 좋게 나온다
- 🛠 k6의 **`constant-arrival-rate`**(열린 모델: 초당 N개를 무조건 보냄)로 측정. 이 프로젝트의 k6 시나리오는 기본을 이걸로
- 🎤 부하 테스트 결과의 p99를 믿을 수 있나요?

## ⭐ 4-2. 꼬리 지연 증폭

- 💡 요청 하나가 서비스 여러 개를 **순서대로** 거치거나, **여러 개에 동시에** 퍼지면(fan-out), 사용자 경험의 꼬리는 각 서비스의 p99보다 나빠진다. 100개에 fan-out하면 하나라도 p99를 밟을 확률이 63%
- 💡 gateway → transfer → core가 그 구조. 그래서 서비스별 p99와 **사용자 여정 전체(gateway 기준)** p99를 둘 다 본다

## ⭐ 4-3. 사용률과 대기 시간: 하키 스틱

- 💡 대기열 이론: 사용률이 70~80%를 넘으면 대기 시간이 **급격히** 늘어난다 (선형이 아니다). "CPU 80%면 아직 20% 남았다"가 틀린 이유
- 📈 부하를 올리며 p99를 그리면 어느 지점에서 하키 스틱처럼 꺾인다. 그 지점이 실제 용량

## ⭐ 4-4. 리틀의 법칙 (Little's Law)

- 💡 **동시에 처리 중인 수 = 초당 요청 × 평균 처리 시간** (L = λW)
  - 커넥션 풀 크기: 초당 200건 × 쿼리 50ms = **동시 10개**면 된다. 여유를 둬도 20개. "풀을 100으로 늘리자"가 대개 틀린 이유 (DB도 동시에 처리할 수 있는 수가 한정)
  - 반대로: 풀 10개에서 쿼리가 500ms로 느려지면 처리 가능한 건 초당 20건으로 떨어진다 → 3-1의 고갈
- 🎤 커넥션 풀 크기는 어떻게 정하나요? ← 이 질문에 리틀의 법칙으로 답하면 확실히 돋보인다

## 4-5. PostgreSQL 운영 함정

- 💡 **락 대기열 함정**: 긴 쿼리가 도는 중에 `ALTER TABLE`을 실행하면 ALTER가 락을 기다리고, **그 뒤에 오는 평범한 SELECT까지 전부** ALTER 뒤에 줄을 선다 → 순식간에 전체 장애. 마이그레이션에 `lock_timeout`을 거는 이유
- 💡 **idle in transaction**: 트랜잭션을 열어 둔 채 놀고 있는 세션이 락을 쥐고, vacuum도 막는다 (`idle_in_transaction_session_timeout`)
- 💡 **autovacuum과 bloat**: UPDATE가 많은 테이블(계좌 잔액!)은 죽은 행이 쌓여 커지고 느려진다. 극단적으로는 **트랜잭션 ID wraparound**로 DB가 쓰기를 거부한다 (대형 장애 사례로 유명)
- 💡 **HikariCP `maxLifetime`**: DB·방화벽·로드밸런서의 유휴 연결 끊기 시간보다 짧아야 한다. 아니면 이미 끊긴 커넥션을 받아서 간헐적 에러

## 4-6. 지표 자체가 장애를 낸다: 카디널리티 폭발

- 💡 지표 라벨에 사용자 ID, 계좌 ID, 송금 ID처럼 **값이 무한히 많은 것**을 넣으면 시계열이 폭증해 Prometheus가 메모리 부족으로 죽는다. Micrometer의 URI 라벨이 `/transfers/{id}` 패턴인 이유 (실제 ID가 아니라)
- 🎤 지표에 넣으면 안 되는 라벨은?

## 4-7. 지표 → 트레이스 → 로그 연결 (exemplar)

- 💡 p99 그래프의 튀는 점을 클릭하면 **그 시각의 느린 요청 트레이스**로 바로 간다 (exemplar). 트레이스의 traceId로 로그를 찾는다 (Loki). 10주 차 "로그 ↔ 트레이스 연결"의 목표
- 💡 트레이스 샘플링: 전부 저장하면 비싸다. **head 샘플링**(시작할 때 1%만)은 정작 느린·에러 요청을 놓친다 → **tail 샘플링**(끝난 뒤 느린 것·에러는 전부 보관)

## 4-8. 기타 단골

- 가상 스레드 **pinning** (`synchronized` 안에서 블로킹 → 캐리어 스레드를 붙잡음, Java 24+ JEP 491로 대부분 해결) → 14주 차
- WebFlux **이벤트 루프 블로킹** (`reactor-http-nio` 스레드에서 블로킹 호출) → 14주 차
- 쿠버네티스 **DNS `ndots:5`**: 외부 도메인 하나에 DNS 질의가 여러 번 나가 지연 (`api.bank.com.` 끝에 점, 또는 ndots 조정)
- **conntrack 테이블 가득 참**: 연결이 많은 노드에서 간헐적 패킷 드롭 (리눅스 네트워크 딥다이브 백로그와 연결)

# Part 5. APM 도구 화면 읽기

## ⭐ 5-0. 지표 · 트레이스 · 로그, 그리고 트레이싱 부품 (2026-11-23 개발자 질문: "템포는 뭐고 에이전트는 뭐지?")

- 💡 **지표(Prometheus)** = 전체를 합친 숫자 (p99 1.4초, 스레드 200). "얼마나 나쁜가"는 알려 주지만 **"이 요청 한 건이 어디서 썼나"는 모른다**. 7주 차 OOM 판독은 전부 지표로 했다
- 💡 **트레이스(Tempo)** = 요청 한 건의 여정 (택배 배송 조회). 구간(span)마다 시작·끝 시각 → 폭포 그림으로 "Redis 락 대기 1,390ms"가 바로 보인다
- 💡 **로그(Loki, 10주 차)** = 그 순간 무슨 일이 있었나의 문장. 트레이스 구간에서 클릭하면 같은 trace ID의 로그로 이동하게 잇는다
- 💡 트레이싱 부품:

  | 부품 | 하는 일 | 비유 |
  | --- | --- | --- |
  | **Java 에이전트** (OpenTelemetry) | JVM 시작 옵션 `-javaagent`로 붙어 Spring·JDBC·Kafka·Redisson 코드에 기록 코드를 끼워 넣는다(바이트코드 조작). 서비스끼리 부를 때 헤더(`traceparent`)에 trace ID를 실어 다음 서비스로 넘긴다. **우리 코드는 안 바뀐다** | 송장 |
  | **OTel Collector** | 서비스들이 보낸 구간을 받아 모으고(배치·샘플링) 저장소로 넘긴다. 앱이 저장소를 몰라도 되게 하는 중간층 | 집하장 |
  | **Tempo** | 트레이스 저장소. Grafana에서 trace ID로 조회 | 배송 기록 창고 |

- 💡 **AWS에서는** (2026-11-23 개발자 질문: "나중에 AWS를 쓰면 어디서 보나"):

  | 우리 구성 | AWS 관리형 | 콘솔에서 보는 곳 |
  | --- | --- | --- |
  | Prometheus | Amazon Managed Service for Prometheus (AMP) | 쿼리는 Managed Grafana. AWS 자원 지표는 CloudWatch Metrics |
  | Grafana | Amazon Managed Grafana | 워크스페이스 |
  | Tempo | AWS X-Ray | CloudWatch → X-Ray traces · Trace Map · Transaction Search |
  | OTel Collector | ADOT Collector (AWS Distro for OpenTelemetry) / CloudWatch Agent | EKS 애드온 |
  | Java 에이전트 | ADOT Java 에이전트 (OTel 에이전트의 AWS 배포판) | 같은 `-javaagent` |
  | Loki (10주 차) | CloudWatch Logs | CloudWatch → Logs Insights |

  **OpenTelemetry가 공통어**라서 저장소를 Tempo → X-Ray(또는 Datadog·New Relic)로 바꿔도 앱은 그대로, Collector의 보내는 곳(exporter)만 바꾼다 = Collector를 중간에 두는 이유. 🎤 "벤더 종속 없이 관측성을 구성하려면?"
- 💡 **Datadog · New Relic** (2026-11-23 개발자 질문: "그라파나·로키 기능을 다 포함하나?") → 네. 지표·대시보드·트레이스(APM)·로그·알림(+ RUM·외부 모니터링)을 **한 SaaS로 묶은 것**. 고르는 기준:
  - SaaS: 운영할 게 거의 없고 지표·로그·트레이스가 한 화면에서 이어진다 / **비싸다**(호스트·데이터양 과금, 특히 로그), 데이터가 회사 밖으로
  - 직접 운영(우리 구성 = Grafana LGTM: Loki·Grafana·Tempo·Mimir/Prometheus): 무료, 데이터가 안에 / 용량·업그레이드·장애를 직접 책임
  - 국내 금융권: 규제로 데이터를 못 내보내는 경우가 많아 설치형 APM(Pinpoint·Scouter·제니퍼·와탭 설치형)이나 직접 운영
  - OTel로 만들어 두면 SaaS로 옮길 때 Collector의 exporter만 바꾼다. 🎤 "Datadog 대신 직접 구축한 이유는?"
- 💡 에이전트는 **같은 처리 흐름 안에서** 송장을 넘긴다. Outbox처럼 요청 스레드는 INSERT만 하고 다른 스레드(릴레이)가 나중에 발행하면? → 9주 차 4단계의 질문
- 💡 **Outbox에서 끊긴 트레이스 잇기** (2026-11-24 개발자 답: "아웃박스에 트레이스 아이디 심어서"):
  - 심는 것은 trace ID 하나가 아니라 **`traceparent` 전체** = `00-<trace ID>-<부모 span ID>-<샘플링 플래그>`. span ID가 없으면 같은 트레이스여도 트리 어디에 붙을지 모르고, 플래그가 없으면 릴레이가 "기록하기로 한 요청인가"라는 결정을 이어받지 못한다
  - **흔한 방식인가** → 그렇다. Debezium Outbox 이벤트 라우터에는 이 용도의 컬럼(`tracingspancontext`)이 기본으로 들어 있다. 폴링 릴레이를 직접 만든 곳도 같다: INSERT 때 현재 컨텍스트를 컬럼에 적고 → 발행 때 꺼내 복원. DB 큐·배치·지연 작업 테이블처럼 **비동기로 끊기는 곳 전부**에서 해법은 같다: "컨텍스트를 데이터와 함께 저장한다"
- 💡 **트레이스는 언제 보나** (2026-11-24 개발자 질문: "잘못된 요청을 한눈에 보려고 해둔 건가?") → 맞다. 다만 평소에 트레이스를 훑지는 않고, **다른 신호에서 출발해 트레이스에 도착한다**
  - 쓰임 ① 느림: 요청 한 건의 시간이 어느 구간(DB? 외부 호출? 대기?)에 쓰였나 ② 실패: 여러 서비스 중 어디서 처음 에러가 났나 ③ 길 잃음: 비동기 뒤에서 이벤트가 어디서 멈췄나 (Outbox 대기 빈칸, 컨슈머 미처리) ④ 모르던 것 발견: N+1 쿼리, 쓸데없는 중복 호출, 예상과 다른 호출 순서
  - 도착하는 길: 알림·지표 급등 → **exemplar**(그래프의 점 하나 → 그 순간의 trace, 10주 차) / 에러 로그 한 줄의 **traceId**(10주 차) / 고객 문의의 송금 ID → **속성으로 검색**(TraceQL) / "느린 것만" 검색(`{ duration > 1s }`)
  - 운영에서는 비용 때문에 전부 남기지 않는다(샘플링). 그래서 "에러·느린 요청은 꼭 남기기"(꼬리 기반 샘플링, Collector)가 다음 고민
  - 첫 송금 트레이스에서 실제로 보인 것: 160ms 중 멱등 키 조회(`findByRequesterIdAndIdempotencyKey`)가 56ms. 지표(p99)로는 절대 안 보이는 구간 단위 내역
  - 🎤 "지표와 트레이스와 로그를 장애 때 어떤 순서로 보나요?" (지표로 이상 감지 → 트레이스로 위치 → 로그로 이유)
- 💡 **Datadog을 써도 같은 설계가 필요한가** (2026-11-24 개발자 질문) → 그렇다
  - Datadog의 Java 에이전트(`dd-java-agent`)도 OTel 에이전트처럼 HTTP·JDBC·Kafka에 자동으로 끼어들어 헤더로 송장을 넘긴다. 하지만 **"이 DB 행이 나중에 다른 스레드에서 발행된다"는 건 우리 업무 흐름이라 어떤 에이전트도 모른다**. outbox 컬럼에 적고 꺼내는 코드는 어느 벤더든 직접 쓴다
  - 그 코드를 **OTel API**(`io.opentelemetry.api`, 벤더 중립)로 쓰면 저장소가 Tempo든 Datadog이든 그대로 동작한다. Datadog 에이전트는 OTel API로 만든 구간을 받아들이고, 전파 헤더도 W3C `traceparent`를 지원한다. 벤더 전용 API(`dd-trace-api`)로 쓰면 그 벤더에 묶인다
  - 정리: **벤더를 바꾸면 바뀌는 것 = 에이전트 jar와 보내는 곳. 안 바뀌는 것 = 비동기 경계에서 컨텍스트를 들고 가는 설계**. 🎤 "Outbox를 쓰면 분산 트레이싱이 어떻게 되나요? 어떻게 이었나요?" / "APM 벤더를 바꾸면 코드를 얼마나 고쳐야 하나요?"
- 🎤 "지표와 트레이스는 각각 무엇을 답하나요?" / "분산 트레이싱에서 trace ID는 서비스 사이에 어떻게 전달되나요?" / "코드 수정 없이 어떻게 트레이스가 생기나요?"
- 📎 9주 차 실험 기록(예정), CLAUDE.md 2장 아키텍처 그림

| 도구 | 어디서 많이 쓰나 | 대표 화면 |
| --- | --- | --- |
| **Pinpoint** (네이버, 오픈소스) | 국내 대기업·금융권 | **서버맵**(서비스 간 호출 지도와 지연), **응답 시간 산점도**(점 하나 = 요청 하나, 위로 튄 점을 드래그하면 그 요청들의 호출 스택), 호출 스택 타임라인 |
| **Scouter** (LG CNS, 오픈소스) | 국내 SI·금융권 | **XLog**(Pinpoint 산점도와 같은 개념, 실시간), 액티브 서비스(지금 처리 중인 요청과 어디서 멈췄나) |
| **Datadog, New Relic** (상용) | 스타트업·글로벌 | 서비스 맵, 트레이스 플레임 그래프, 지표·로그·트레이스 한 화면 |
| **OpenTelemetry + Tempo + Grafana** (오픈 표준) | 이 프로젝트 (9~10주 차) | 트레이스 워터폴, 서비스 그래프, exemplar |

- 💡 **산점도(XLog) 읽는 법**: 가로 = 시간, 세로 = 응답 시간. 평소엔 아래쪽에 띠. ① 위쪽에 **가로 줄**이 생기면 = 특정 타임아웃 값에 걸림 (예: 3초 줄 = read-timeout 3s) ② **세로 기둥** = 그 순간 모두 멈춤 (GC 일시정지, 락, DB 순간 정지) ③ 띠 전체가 **서서히 올라감** = 자원 포화 (커넥션 풀, CPU)
- 💡 도구는 달라도 보는 것은 같다: **어떤 요청이 느렸나 → 그 요청의 시간이 어느 구간(DB? 외부 호출? 내부 로직?)에서 쓰였나**
- 💡 이 프로젝트는 OpenTelemetry로 한다. 면접에서 "국내에서 많이 쓰는 Pinpoint/Scouter와 원리가 같다(에이전트가 바이트코드에 끼어들어 구간 시간을 잰다)"고 연결하면 된다

# Part 7. CPU 사용률: 언제 정상이고 언제 장애인가

> 개발자 질문 (2026-11-17): "CPU가 올라가는데 어떨 땐 정상이고 어떨 땐 장애더라. 이것밖에 볼 줄 몰랐다."

## ⭐ 7-0. 제1원칙: CPU는 혼자 보면 아무 뜻이 없다

- 💡 CPU는 항상 **요청 수(RPS)와 지연(p99)과 나란히** 본다. 세 그래프의 조합이 답이다
- 💡 가장 쓸모 있는 파생 지표는 **요청 1건당 CPU** (= CPU 사용량 ÷ RPS). 이 값이 일정하면 CPU가 올라도 "일이 늘어서"고, 이 값이 오르면 "같은 일에 더 많이 쓴다" = 이상
- 💡 **CPU가 낮은 게 더 무서울 때가 있다** (7-3)

## ⭐ 7-1. 판독표

| CPU | RPS | p99 | 판정 | 무슨 일인가 |
| --- | --- | --- | --- | --- |
| ↑ | ↑ (같은 비율) | 평평 | ✅ **정상** | 트래픽이 늘어 일을 더 하는 중. 요청당 CPU 일정 |
| 매일 같은 시각에 ↑ | 평평 | 평평 | ✅ 정상 | 배치·스케줄 작업 (8주 차 대사·이자 배치가 이 모양) |
| 배포 직후 잠깐 ↑ | 평평 | 잠깐 ↑ | ✅ 정상 (주의) | JVM 기동 + JIT 컴파일 워밍업. 몇십 초 뒤 내려오면 정상 (3-9) |
| ↑ | **평평** | ↑ | ❌ **장애** | 요청당 CPU 증가 = **같은 일에 더 많이 씀**. 직전 배포의 비효율 코드(정규식, 직렬화, 메모리 안 루프), 또는 GC (7-2) |
| ↑ (GC 스레드) | 평평~↓ | ↑ | ❌ 장애 | **GC 폭주**: 힙이 꽉 차 GC만 계속 돈다. 메모리 문제가 CPU로 보이는 것 (3-3) |
| 코어 하나만 **100% 고정** | 무관 | 무관 | ❌ 장애 | 무한 루프·바쁜 대기. 전체 평균으로 보면 "12%"라 놓친다 → **코어별/스레드별**로 본다 |
| ↑ | ↑ | ↑ | 성공 RPS는 ↓ | ❌ 장애 | **재시도 폭주**: 요청은 많은데 대부분 실패·재시도 (3-5). 총 RPS가 아니라 **성공 RPS**를 본다 |
| **낮음 / ↓** | 평평 | ↑ | ❌ **장애** | **기다리는 중**: 커넥션 풀, 락, 느린 의존성, 디스크. 스레드가 일을 못 하고 서 있다 (7-3) |
| **0 근처로 ↓** | **↓** | — | ❌ 장애 | **트래픽이 안 들어옴**: 파드 다운, Ingress·DNS·LB 문제, 상위 서비스 장애 |
| limit 아래 | 평평 | **주기적으로 튐** | ❌ 장애 | **CPU 스로틀링** (3-8). 사용률 평균에는 안 보인다 |
| 노드는 ↑, 내 파드는 평범 | 평평 | ↑ | ❌ 장애 | **시끄러운 이웃**: 같은 노드의 다른 파드·VM이 CPU를 먹는다 (7-4의 steal) |

## ⭐ 7-2. CPU를 쪼개서 본다: user · system · iowait · steal

| 구성 | 높으면 | 이 프로젝트에서 |
| --- | --- | --- |
| **user** | 앱 코드가 계산 중. 대부분 정상 | JVM, 우리 코드 |
| **system** | 커널 일 (시스템 콜, 컨텍스트 스위칭). 스레드가 너무 많거나 작은 I/O를 너무 자주 | Tomcat 스레드 200개가 다 깨어날 때 |
| **iowait** | **디스크를 기다리는 중**. CPU가 바쁜 게 아니라 디스크가 느린 것 | DB 노드, etcd(노트북 HDD면 여기가 튄다) |
| **steal** | **가상화 호스트가 CPU를 다른 VM에 줬다**. 내 VM은 일하고 싶은데 못 함 | **Proxmox 위 VM들**. 호스트 코어보다 VM vCPU 합이 많으면 생긴다 |

- 💡 "CPU 90%"라도 iowait가 70%면 CPU 문제가 아니라 **디스크** 문제. steal이 높으면 앱이 아니라 **호스트** 문제. 쪼개 보지 않으면 엉뚱한 곳을 고친다
- 💡 **steal time은 클라우드에서도 똑같이 나온다** (AWS 버스터블 인스턴스 t3의 크레딧 소진). 온프레미스 VM에서 직접 보면 클라우드에서도 알아본다

## ⭐ 7-3. CPU가 낮은데 느리다 = "기다림"을 찾는다

- 💡 가장 흔한 실무 장애 패턴이고, CPU만 보는 사람이 가장 많이 놓치는 패턴
- 🔎 기다림의 종류와 보는 곳:
  | 무엇을 기다리나 | 보는 지표 |
  | --- | --- |
  | DB 커넥션 | HikariCP pending, 획득 시간 |
  | DB 락 | `pg_stat_activity.wait_event_type = 'Lock'` |
  | 느린 의존성 | 의존성 호출 지연 (`http.client.requests`) |
  | 스레드 풀 | Tomcat busy 스레드 = 최대치 |
  | 디스크 | iowait, 디스크 지연 |
  | GC 일시정지 | GC pause (일시정지 중엔 앱 CPU가 안 쓰임) |
- 💡 **스레드 덤프**가 결정적 증거: 대부분의 스레드가 `WAITING`/`BLOCKED` 상태로 같은 곳(커넥션 풀 `getConnection`, 소켓 `read`)에 서 있다

## 7-4. 이 프로젝트에서 CPU 판독을 연습하는 법

- 🔬 **정상 패턴**: k6로 RPS를 단계적으로 올리며 CPU·p99 → 요청당 CPU가 일정한 구간과, 어느 순간 p99가 꺾이는 하키 스틱 지점(4-3)
- 🔬 **요청당 CPU 증가**: 실험 스위치로 비효율 코드 경로를 켜기 (예: 응답마다 큰 JSON을 여러 번 직렬화) → RPS는 같은데 CPU만 오름
- 🔬 **CPU 낮음 + 느림**: 3-1 커넥션 풀 고갈 재현과 같은 실험에서 CPU 그래프를 같이 띄운다 → "CPU가 오히려 떨어지는" 장면
- 🔬 **steal time**: Proxmox에서 VM들의 vCPU 합을 호스트 코어보다 크게 잡고, 다른 VM에서 부하(`stress-ng`) → 앱 VM의 steal 증가. 온프레미스라서 할 수 있는 실험
- 🔬 **코어 하나 100%**: 무한 루프 스위치 → 전체 평균 vs 코어별 그래프 비교

# Part 8. 그래프 모양 도감

> 지표 종류와 상관없이 **모양**이 말해 주는 것. 대시보드를 보면 먼저 모양을 분류한다.

| 모양 | 이름 | 보통 뜻하는 것 | 예 |
| --- | --- | --- | --- |
| `/\/\/\/\` (바닥 일정) | **톱니** | 쌓였다 비워지는 정상 주기 | 힙(GC), 배치 큐 |
| `/\/\/\/\` (바닥 상승) | **바닥이 오르는 톱니** | 비워도 다 안 비워진다 = **누수** | 힙 누수, 디스크 사용량 |
| `____/‾‾‾‾` | **계단** | 어느 시점에 무언가 바뀌었다 → **배포·설정 마커와 맞춰 본다** | 배포 후 요청당 CPU 상승 (성능 퇴행) |
| `____|____|____` (주기적) | **정시 스파이크** | 스케줄 작업, 주기적 GC, 캐시 만료, cron | 매시 정각 배치, 캐시 TTL 동시 만료(thundering herd) |
| `____/‾‾‾‾‾‾‾` 천장에 붙음 | **평평한 천장** | **어떤 한계에 닿았다**. 수요는 더 있는데 더 못 받는다 | 커넥션 최대, 스레드 풀 최대, CPU limit, 레이트 리밋, 네트워크 대역 |
| `______/` 급격히 꺾임 | **하키 스틱 / 절벽** | 포화 지점을 넘었다. 대기열이 폭증 | 부하를 올릴 때 p99, 사용률 80% 이상 |
| `/` 끝없이 우상향 | **단조 증가** | 들어오는 것 > 나가는 것. 언젠가 터진다 | 컨슈머 랙, 대기열, 디스크, 누수 |
| `‾‾‾‾\____` 0으로 뚝 | **추락** | ① 정말 0이 됐다 (트래픽 끊김, 파드 다운) ② **데이터가 안 들어온다** (수집 장애). **둘을 구분**: 0이 찍히는가, 점 자체가 없는가 | 파드 다운 vs Prometheus 수집 실패 |
| `/\/\/\` 규칙적으로 출렁 | **진동** | 제어 루프가 흔들린다 | 오토스케일러 플래핑, 서킷 브레이커 열림·반열림 반복, 리밸런싱 루프, 재시도 물결 |
| 히트맵에서 띠가 두 개 | **두 갈래 분포** | 서로 다른 두 경로 | 캐시 히트/미스, 파드 하나만 느림, 특정 파티션만 느림 |
| 여러 선 중 **하나만** 튐 | **외톨이** | 전체 문제가 아니라 **한 인스턴스** 문제 | 나쁜 노드, 핫 파티션, 로드밸런싱 불균형, 그 파드만 GC |
| A가 꺾이고 **조금 뒤** B가 꺾임 | **시차** | **먼저 꺾인 A가 원인**, B는 피해자 | 의존성 지연 → 호출하는 쪽 스레드 고갈 (3-4) |
| 두 지표가 **정확히 같은 시각**에 튐 | **동기** | 같은 원인을 공유 | GC 일시정지와 p99 스파이크 (3-3), 배포와 502 (3-9) |

- 💡 판독 습관: **모양 분류 → 시각 확인(마커와 맞추기) → 다른 지표와 시차·동기 비교** → 원인 가설 → 증거(트레이스·로그·덤프)
- 💡 "평균 선 하나"만 그린 대시보드는 위 패턴의 절반을 숨긴다: 외톨이(인스턴스별로 쪼개야), 두 갈래(히트맵이어야), 코어 하나 100%(코어별이어야). **쪼개서 보는 습관**

## ⭐ 7-5. OOMKilled 판독 순서 (2026-11-23 7주 차에서 실제로 한 것)

> 개발자 소감: "대시보드는 아직 많이 어렵다". 오늘 막힌 곳은 "패널이 짜부돼서 안 보임" → Explore에서 쿼리 하나씩 크게 보기로 해결. 아래 순서를 그대로 다시 쓰면 된다.

1. **스레드가 상한에 붙었나** → 대시보드 **JVM (Micrometer)**, Application=`core`, Instance 전체(재시작하면 시계열이 나뉜다) → 행 **JVM Misc** → **Threads**. 상한(톰캣 200)에 붙었으면 "줄이 생겼다". 넘을 수는 없다 (넘으면 톰캣 말고 다른 범인)
2. **살아남은 회차와 비교** → 같은 상한에 붙었는데 한쪽만 죽었다면 "몇 개가 기다렸나"는 원인이 아니다 → "기다리며 무엇을 붙잡았나"로
3. **Explore**(왼쪽 메뉴) → Prometheus → **Code** 모드에서 하나씩:
   - 컨테이너 전체 (커널이 OOMKilled를 판단하는 숫자): `container_memory_working_set_bytes{namespace="bank",pod=~"core-.*",container!="",container!="POD"}`
   - 힙 밖 Netty 버퍼: `jvm_buffer_memory_used_bytes{application="core", id="direct"}`
   - DB 커넥션을 기다린 요청: `hikaricp_connections_pending{application="core"}`
4. 힙·논힙이 평평한데 컨테이너가 limit에 닿았다 = **힙 밖**. direct 버퍼, 스레드 스택, 대기열의 연결을 의심

- 💡 패널이 작으면 고생하지 말고 Explore로. 패널 제목 옆 메뉴 → **Explore**를 누르면 그 패널의 쿼리를 그대로 들고 간다
- 💡 OOMKilled ≠ `OutOfMemoryError`. 전자는 컨테이너(힙 + 힙 밖)가 limit을 넘어 커널이 죽인 것, 후자는 힙이 찬 것. 힙 그래프만 보면 전자를 놓친다
- 📎 `docs/experiments/week-07-locks.md` 판독 1, pitfalls 37

## ⭐ 0. 이렇게까지 해야 하나? 유의미한 순간은 언제 (2026-11-26 개발자 질문)

> "전 직장도, 대부분의 서비스 회사도 이렇게까지 안 해도 잘 굴러간다. 이런 게 유의미한 순간은 장애 때인가, 일상에서도 생기나?"

- 💡 **맞는 관찰이다.** 대부분은 없어도 굴러간다. 대신 그 비용을 **사람이 몸으로** 낸다: CS 문의마다 개발자가 DB를 뒤지고, 장애 나면 재시작하고 원인은 모른 채 넘어가고, 시스템을 아는 몇 명이 기억으로 버틴다. 규모가 작고 틀려도 싸면 이게 합리적인 선택이다.
- 💡 **장애 때보다 일상에서 더 자주 쓴다:**
  1. **고객 문의** "돈은 빠졌는데 송금이 안 됐어요" (핀테크에선 매일): 송금 ID 하나로 트레이스·상태·전표를 따라가면 몇 분, 없으면 몇 시간 + 서비스마다 로그 grep
  2. **배포 직후**: 매 배포가 작은 실험이다. 에러율·p99가 배포 전후로 바뀌었나 (카나리)
  3. **조용한 저하 (gray failure)**: 장애는 아닌데 p99가 조금씩 오르고, 커넥션 풀이 80%를 넘고, 외부 은행 하나가 느려진다. 고객이 먼저 알기 전에
  4. **돈이 맞나 (대사)**: 은행·PG에선 일일 대사가 법·감사 요구라 "선택"이 아니다. 이중 지급처럼 **원장은 완벽한데 돈이 새는** 일은 대사 말고는 아무도 못 찾는다. 없으면 몇 달 뒤 회계 감사에서 발견
  5. **용량 계획**: 이벤트·월급날 대비 "지금 몇 % 쓰고 있나"
  6. **사후 분석**: 장애 때는 MTTR(복구 시간)을, 장애 뒤엔 "재발하나"를 결정한다
- 💡 **없이 버티던 회사가 무너지는 시점:** 팀이 커져 "아는 사람"이 부족해질 때 / MSA로 요청 하나가 서비스 5개를 건널 때 (로그만으로 못 이음) / 돈처럼 되돌릴 수 없고 감사받는 것을 다룰 때 / 온콜 피로
- 💡 **이 프로젝트에서 무엇이 보편이고 무엇이 과한가:**
  - 거의 모든 회사: RED 지표, 로그에 traceId, 증상 기반 경보, 결제 멱등
  - 금융·결제 도메인: 원장, 결과 불명 해소, 일일 대사 (은행엔 다 있다. 보통 별도 배치·정산 팀)
  - 규모가 클 때: 분산 트레이싱·꼬리 샘플링, 카오스 실험
  - 학습용으로 일부러 과한 것: 대사 서비스 분리, 장애 패널
- 🎤 "모든 서비스에 이 정도 관측성이 필요한가요?" → "아니다. 틀렸을 때의 비용(돈·되돌릴 수 있나)과 시스템 복잡도(홉 수, 팀 크기)로 정한다. 최소한은 RED + traceId 로그 + 증상 경보, 돈을 다루면 대사·멱등은 필수"
- 🎤 "관측성이 없던 팀에 처음 하나만 넣는다면?" (답의 방향: 고객 문의를 가장 많이 받는 흐름의 요청 ID를 로그에 → 그다음 RED)

## ⭐ 0-1. 모니터링 대시보드 vs 관리자 화면(백오피스) (2026-11-26 개발자 질문: "원래 이렇게 보는 게 맞아? 관리자 대시보드를 말한 건데")

💡 **둘은 다른 물건이고, 실무에선 둘 다 있다.** 묻는 질문이 다르다.

| | 모니터링 (Grafana) | 관리자 화면 (백오피스·어드민·운영 단말) |
| --- | --- | --- |
| 묻는 것 | "지금 시스템이 건강한가, 언제부터 이상한가" | "**이 송금**은 어떻게 됐나, 이걸 어떻게 처리하나" |
| 단위 | 집계 (건수·비율·나이·추이) | 레코드 한 건 (송금 ID, 고객, 상태 이력) |
| 데이터 | 지표 (Prometheus): 숫자만, 라벨은 적게 (송금 ID 못 넣음, 4-6 카디널리티) | 서비스 DB를 **서비스 API로** 조회 |
| 행동 | 보기 + 경보 | 조회·검색 + **처리** (대사 항목 닫기, 조정 전표, 환불, 재시도) |
| 사용자 | 개발자·SRE·당직 | 운영팀·CS·정산 담당 (개발자 아님) |
| 꼭 필요한 것 | 시간축, 경보 | 권한(역할), **감사 로그**(누가 언제 무엇을), 작성자·승인자 분리 |

- 이번에 만든 "Bank · 은행 운영"은 **모니터링** 쪽이다. 카운팅 지표는 Grafana만을 위한 게 아니라 **경보의 재료**다 ("결과 불명이 10분 넘게 5건 이상" → 11주 차). 관리자 화면이 있어도 이건 필요하다: 사람이 화면을 계속 보고 있지 않으니까
- 관리자 화면은 "경보가 울린 뒤 그 건을 찾아 처리하는 곳". 흐름: **Grafana 경보 → 몇 건·언제부터 → 관리자 화면에서 그 송금들 목록 → 한 건 열어 상태 이력 → 처리 버튼**
- 전 직장의 "수작업 대사·환불"이 하던 일이 바로 관리자 화면의 일이다 (지금 이 프로젝트엔 아직 없다: 백로그 "불일치를 찾은 뒤의 처리")
- DataGrip으로 DB를 직접 보는 건 개발자의 임시방편이다. 운영팀에게 DB 접속을 주지 않는 이유: 권한을 잘게 못 나누고, 누가 무엇을 봤는지 남지 않고, 실수로 UPDATE하면 원장이 깨진다. 그래서 백오피스는 **서비스 API를 거친다**

🎤 꼬리 질문
- "결과 불명 송금을 운영자가 강제로 성공 처리하는 버튼을 만든다면, 무엇을 지켜야 하나?" (서비스 도메인 메서드로만, 원장·외부와 대조한 근거, 감사 로그, 2인 승인)

## 이 프로젝트에서 익숙해지는 방법

- 실험 기록(`docs/experiments/`)에 **"대시보드 판독"** 칸을 둔다: 어느 그래프가 먼저 꺾였고, 무엇이 피해자였나. 재현 → 그래프 캡처 → 판독 → 해결 → 다시 캡처
