# Part 1. 읽는 법

## ⭐ 1-1. 세 가지 틀: RED · USE · Golden Signals

- 💡 **RED** (서비스·API를 볼 때): **R**ate(초당 요청) / **E**rrors(에러율) / **D**uration(지연, p50·p95·p99). "사용자가 느끼는 것"
- 💡 **USE** (자원을 볼 때: CPU, 메모리, 커넥션 풀, 스레드 풀, 디스크): **U**tilization(얼마나 쓰나) / **S**aturation(대기열이 생겼나) / **E**rrors. "왜 그렇게 느끼는가"
- 💡 **Golden Signals** (구글 SRE): 지연 · 트래픽 · 에러 · 포화. RED + USE의 포화를 합친 것
- 💡 순서가 중요하다: **RED로 "어디가 아픈지" → USE로 "왜 아픈지"**. 자원부터 보면 정상인 고사용률에 낚인다 (CPU 90%여도 응답이 빠르면 문제 아님)
- 🎤 대시보드를 처음 만든다면 무엇부터 넣나요?

## ⭐ 1-2. 퍼센타일과 히스토그램

- 💡 **평균은 거짓말한다.** 99개가 10ms, 1개가 5초면 평균 60ms. 그 1%가 화난 고객이다. 그래서 p99 (100번 중 가장 느린 1번 직전의 값)
  - p50 = 보통 사용자, p95 = 운 나쁜 사용자, p99 = 가장 운 나쁜 사용자 (그리고 대개 가장 많이 쓰는 VIP — 요청이 많으면 꼬리를 자주 밟는다)
- 💡 **퍼센타일은 평균 낼 수 없다.** 파드 3개의 p99를 평균 내도 전체 p99가 아니다 → Prometheus는 **히스토그램**(구간별 개수)을 합친 뒤 `histogram_quantile`로 계산한다
- 💡 **히스토그램 구간(bucket)이 정밀도를 정한다.** 구간이 100ms, 500ms면 p99가 "100~500 사이 어딘가"로만 나온다. SLO 경계값(예: 300ms)에 구간을 둔다
- 📈 **히트맵**: 시간 × 지연 구간 × 개수를 색으로. 평균선에서 안 보이는 "두 갈래 분포"(캐시 히트는 5ms, 미스는 200ms)가 보인다
- 🎤 p99를 서비스 인스턴스별로 구한 뒤 평균 내면 왜 안 되나요?

## ⭐ 1-3. 대시보드 30초 판독 순서

1. **사용자 영향**: 에러율, p99, SLO 소진율. 영향이 없으면 급하지 않다
2. **언제부터**: 그래프에서 꺾인 시점 → **그 시점에 무엇이 바뀌었나** (배포, 설정 변경, 트래픽 급증, 외부 장애). 장애 원인 1순위는 "변경"이다
3. **어디서**: 서비스별 RED → 가장 먼저 나빠진 곳 (나중에 나빠진 곳은 피해자일 가능성이 높다)
4. **왜**: 그 서비스의 USE (커넥션 풀, 스레드, GC, CPU 스로틀링) + 그 서비스가 부르는 의존성의 지연
5. **증거**: 느린 요청 하나의 트레이스 → 그 traceId로 로그

- 💡 "먼저 나빠진 곳이 원인, 나중에 나빠진 곳은 피해자"가 분산 시스템 판독의 핵심 감각

# Part 2. 계층별로 매일 보는 지표

| 계층 | 매일 보는 것 | 경보를 거는 것 | 이 프로젝트의 출처 |
| --- | --- | --- | --- |
| **API** | RPS, 에러율(5xx·4xx 분리), p50/p95/p99 (엔드포인트별) | 5xx 비율, p99 SLO 소진 | Micrometer `http.server.requests` |
| **의존성 호출** | 호출 대상별 지연·타임아웃·에러 | 타임아웃 급증 | Micrometer `http.client.requests` (transfer → core) |
| **JVM** | GC 후 힙 사용량, GC 일시정지 시간·빈도, 스레드 수(BLOCKED), CPU | Old 영역이 GC 후에도 계속 증가, GC 시간 비율 | Micrometer `jvm.*` |
| **커넥션 풀** | active / idle / **pending**, 커넥션 획득 시간 p99, 타임아웃 수 | pending > 0 지속, 획득 타임아웃 | Micrometer `hikaricp.*` |
| **DB** | QPS, 상위 쿼리(총 시간 기준), 활성 커넥션/최대, 락 대기, 데드락, 캐시 히트율 | 커넥션 80%, 락 대기, 복제 지연 | `pg_stat_statements`, `pg_stat_activity`, CloudNativePG exporter |
| **Kafka** | 컨슈머 랙, 생산·소비 속도, 리밸런싱 횟수 | 랙이 계속 증가, under-replicated 파티션 | Strimzi exporter (4주 차~) |
| **쿠버네티스** | 파드 재시작, OOMKilled, **CPU 스로틀링**, readiness 실패, 노드 메모리 압박 | 재시작 루프, OOMKilled | kube-state-metrics, cAdvisor |
| **Redis** | 히트율, eviction, 지연, 메모리, slowlog | eviction 급증, 메모리 한계 | redis exporter (7주 차~) |

- 💡 **4xx와 5xx를 나눠 본다.** 4xx 급증은 대개 클라이언트·배포 호환성(계약 변경, pitfalls 18) 문제, 5xx는 우리 문제
- 💡 **"GC 후" 힙을 본다.** 힙 그래프는 원래 톱니 모양(쌓였다 GC로 떨어짐)이다. 문제는 **톱니의 바닥이 계속 올라갈 때** (누수)

# Part 3. 대표 트러블슈팅 10개

> 실무에서 가장 자주 만나는 순서대로. 각각 "그래프 모양"을 외우는 게 목표.

## ⭐ 3-1. 커넥션 풀 고갈

- 📈 p99가 절벽처럼 치솟는데 **CPU는 한가하다**. HikariCP **pending이 0 위로 올라가 머문다**, 획득 시간 p99가 커넥션 타임아웃(기본 30초) 근처. 곧 `Connection is not available, request timed out` 에러
- 🔎 원인 후보: ① 트랜잭션 안에서 원격 호출 (상대가 느려지는 동안 커넥션을 쥐고 있음, pitfalls 8) ② 느린 쿼리·긴 트랜잭션 ③ 트래픽 대비 풀이 작음 ④ 커넥션 누수 (반환 안 함)
- 🛠 원격 호출을 트랜잭션 밖으로, 쿼리 개선, 풀 크기는 **리틀의 법칙**(4-4)으로 계산. 무작정 늘리면 DB가 죽는다
- 🔬 **15주 차**: transfer의 트랜잭션 분리를 일부러 되돌리고(트랜잭션 안에서 core 호출) core에 지연 주입 → pending 그래프 관찰. "왜 T-1에서 트랜잭션을 나눴나"를 숫자로 증명
- 🎤 CPU는 낮은데 응답이 느려요. 무엇부터 보나요?

## ⭐ 3-2. 느린 쿼리 · 인덱스 누락

- 📈 **특정 엔드포인트만** p99 상승, DB CPU 상승, 데이터가 늘수록 점점 나빠짐 (어느 날 갑자기가 아니라 서서히)
- 🔎 `pg_stat_statements`를 **총 시간(total_exec_time) 순**으로 정렬 → 상위 쿼리 `EXPLAIN (ANALYZE, BUFFERS)` → `Seq Scan`, 예상 행 수와 실제 행 수의 큰 차이
- 🛠 인덱스, 쿼리 수정, N+1 제거
- 💡 **평균 시간이 아니라 총 시간 순**으로 본다: 1ms짜리라도 초당 1만 번이면 가장 비싼 쿼리
- 🔬 송금 내역 조회(계좌별)를 데이터 수십만 건으로 만들고 인덱스 유무 비교 (k6)
- 🎤 느린 쿼리를 어떻게 찾나요? / 실행 계획에서 무엇을 보나요?

## ⭐ 3-3. GC · 메모리 누수 · OOMKilled

- 📈 GC 후 힙의 **바닥이 계속 상승** → GC 빈도·일시정지 증가 → **GC 일시정지와 같은 시각에 p99 스파이크** → 결국 `OOMKilled`(컨테이너 한도) 또는 `OutOfMemoryError`(힙 한도)
- 🔎 힙 덤프, 크기 제한 없는 캐시·컬렉션, 스레드로컬
- 💡 **OOMKilled ≠ Java OOM**: OOMKilled는 커널이 컨테이너 메모리 한도를 넘은 프로세스를 죽인 것 (힙 외 메모리: 메타스페이스, 스레드 스택, 다이렉트 버퍼 포함). 그래서 힙을 limit의 75%로 둔다 (2주 차 차트의 `MaxRAMPercentage`)
- 🔬 크기 제한 없는 맵에 계속 넣는 엔드포인트를 실험 스위치로 → 톱니 바닥 상승 관찰
- 🎤 파드가 OOMKilled로 재시작돼요. 힙은 여유 있어 보이는데요?

## ⭐ 3-4. 장애 전파 (느린 의존성 → 스레드 고갈)

- 📈 **다운스트림 지연이 먼저** 오르고 → 호출하는 쪽의 스레드(Tomcat `busy` 스레드)가 최대치에 붙고 → 호출하는 쪽의 **모든** API가 느려짐 (상관없는 API까지)
- 🔎 "먼저 나빠진 곳"을 찾는다 (1-3). 의존성 호출 지연 그래프
- 🛠 타임아웃, 서킷 브레이커, 벌크헤드(의존성별 스레드·커넥션 격리)
- 🔬 **15주 차**: 패널 버튼 "외부 은행 3초 지연"
- 🎤 결제 API 하나가 느려졌는데 왜 전체 서비스가 멈췄나요?

## ⭐ 3-5. 재시도 폭주 (retry storm)

- 📈 장애 시작 후 의존성으로 가는 **요청 수가 오히려 몇 배로 증가** (재시도 × 계층 수). 회복된 뒤에도 몰린 재시도에 다시 쓰러짐
- 🛠 지수 백오프 + **지터**, 재시도 예산(전체의 몇 %까지만), 서킷 브레이커, 멱등이 아닌 요청은 재시도 금지
- 🔬 **15주 차**
- 🎤 재시도는 많이 할수록 좋은가요?

## ⭐ 3-6. 락 경합

- 📈 동시성을 올려도 **처리량은 평평**, p99만 상승. DB의 락 대기(`pg_stat_activity.wait_event_type = 'Lock'`) 증가, 최악은 데드락
- 🛠 락 범위·시간 축소, 낙관적 락으로 전환, 핫 로우(한 계좌에 몰림) 분산
- 🔬 **7주 차**: 동시 출금, 락 3종 비교. 이 그래프가 7주 차 실험 기록의 주인공
- 🎤 비관적 락과 낙관적 락은 언제 각각 쓰나요?

## ⭐ 3-7. 컨슈머 랙 증가

- 📈 랙이 **계속 우상향**. 리밸런싱 횟수가 같이 튀면 "처리가 느려 → 죽은 컨슈머로 판정 → 리밸런싱 → 더 느려짐" 루프
- 🛠 컨슈머 처리 개선, 파티션·컨슈머 증설(상한 = 파티션 수), `max.poll` 설정, 핫 파티션이면 키 설계
- 🔬 **16주 차**: "컨슈머 죽이기", "핫 파티션" 버튼
- 🎤 컨슈머를 늘렸는데 랙이 안 줄어요

## ⭐ 3-8. CPU 스로틀링 (쿠버네티스)

- 📈 CPU 사용률 그래프는 limit **아래**인데 p99가 주기적으로 튄다. `container_cpu_cfs_throttled_periods_total`이 증가
- 🔎 CPU limit은 100ms 단위 할당량이다. 순간적으로 몰아 쓰면 남은 시간 동안 멈춘다. 평균 그래프에는 안 보인다
- 🛠 CPU limit 제거(request만), 또는 넉넉히. JVM 기동·GC 스레드 수 조정
- 💡 이 프로젝트는 처음부터 CPU limit을 안 걸었다 (pitfalls 16). **일부러 걸어서** 재현해 보면 좋다
- 🎤 CPU 사용률은 50%인데 왜 느리죠?

## ⭐ 3-9. 배포할 때마다 에러 스파이크

- 📈 **배포 마커와 정확히 같은 시각**에 502·503 짧은 스파이크, 그리고 배포 직후 몇십 초간 p99 상승
- 🔎 502: 종료 중인 파드로 요청이 감 (preStop 없음, graceful shutdown 없음) / p99 상승: **JIT 워밍업** (JVM은 처음엔 인터프리터로 느리다), 캐시·커넥션 풀이 비어 있음
- 🛠 preStop + graceful shutdown + readiness (2주 차 차트에 이미 있음), 워밍업 요청, 롤링 속도 조절
- 🔬 **17주 차**: 부하 중 롤링 배포, preStop을 껐을 때와 비교
- 🎤 무중단 배포라는데 배포 때마다 에러가 나요

## 3-10. 타임아웃 종류 구분

- 📈 같은 "타임아웃"이라도 **connect timeout**이면 대상이 없거나 네트워크·DNS 문제, **read timeout**이면 대상이 느린 것. 둘을 섞어 보면 원인을 엉뚱하게 잡는다
- 💡 결과 불명과 연결된다: connect 실패는 "요청이 안 갔다"(재시도 안전), read 타임아웃은 "갔는데 모른다"(멱등 재전송·상태 조회 필요, pitfalls 6)
- 🔬 transfer의 `CorePostingAdapterTest`가 이미 둘을 따로 재현한다 (3-1주 차)

# Part 4. 알면 돋보이는 것

## ⭐ 4-1. Coordinated omission (측정 도구가 숫자를 속인다)

- 💡 "응답이 오면 다음 요청"을 보내는 부하 도구(닫힌 모델)는 서버가 느려지면 **요청도 덜 보낸다** → 정작 느린 구간의 표본이 빠져서 p99가 실제보다 좋게 나온다
- 🛠 k6의 **`constant-arrival-rate`**(열린 모델: 초당 N개를 무조건 보냄)로 측정. 이 프로젝트의 k6 시나리오는 기본을 이걸로
- 🎤 부하 테스트 결과의 p99를 믿을 수 있나요?

## ⭐ 4-2. 꼬리 지연 증폭

- 💡 요청 하나가 서비스 여러 개를 **순서대로** 거치거나, **여러 개에 동시에** 퍼지면(fan-out), 사용자 경험의 꼬리는 각 서비스의 p99보다 나빠진다. 100개에 fan-out하면 하나라도 p99를 밟을 확률이 63%
- 💡 gateway → transfer → core가 그 구조. 그래서 서비스별 p99와 **사용자 여정 전체(gateway 기준)** p99를 둘 다 본다

## ⭐ 4-3. 사용률과 대기 시간: 하키 스틱

- 💡 대기열 이론: 사용률이 70~80%를 넘으면 대기 시간이 **급격히** 늘어난다 (선형이 아니다). "CPU 80%면 아직 20% 남았다"가 틀린 이유
- 📈 부하를 올리며 p99를 그리면 어느 지점에서 하키 스틱처럼 꺾인다. 그 지점이 실제 용량

## ⭐ 4-4. 리틀의 법칙 (Little's Law)

- 💡 **동시에 처리 중인 수 = 초당 요청 × 평균 처리 시간** (L = λW)
  - 커넥션 풀 크기: 초당 200건 × 쿼리 50ms = **동시 10개**면 된다. 여유를 둬도 20개. "풀을 100으로 늘리자"가 대개 틀린 이유 (DB도 동시에 처리할 수 있는 수가 한정)
  - 반대로: 풀 10개에서 쿼리가 500ms로 느려지면 처리 가능한 건 초당 20건으로 떨어진다 → 3-1의 고갈
- 🎤 커넥션 풀 크기는 어떻게 정하나요? ← 이 질문에 리틀의 법칙으로 답하면 확실히 돋보인다

## 4-5. PostgreSQL 운영 함정

- 💡 **락 대기열 함정**: 긴 쿼리가 도는 중에 `ALTER TABLE`을 실행하면 ALTER가 락을 기다리고, **그 뒤에 오는 평범한 SELECT까지 전부** ALTER 뒤에 줄을 선다 → 순식간에 전체 장애. 마이그레이션에 `lock_timeout`을 거는 이유
- 💡 **idle in transaction**: 트랜잭션을 열어 둔 채 놀고 있는 세션이 락을 쥐고, vacuum도 막는다 (`idle_in_transaction_session_timeout`)
- 💡 **autovacuum과 bloat**: UPDATE가 많은 테이블(계좌 잔액!)은 죽은 행이 쌓여 커지고 느려진다. 극단적으로는 **트랜잭션 ID wraparound**로 DB가 쓰기를 거부한다 (대형 장애 사례로 유명)
- 💡 **HikariCP `maxLifetime`**: DB·방화벽·로드밸런서의 유휴 연결 끊기 시간보다 짧아야 한다. 아니면 이미 끊긴 커넥션을 받아서 간헐적 에러

## 4-6. 지표 자체가 장애를 낸다: 카디널리티 폭발

- 💡 지표 라벨에 사용자 ID, 계좌 ID, 송금 ID처럼 **값이 무한히 많은 것**을 넣으면 시계열이 폭증해 Prometheus가 메모리 부족으로 죽는다. Micrometer의 URI 라벨이 `/transfers/{id}` 패턴인 이유 (실제 ID가 아니라)
- 🎤 지표에 넣으면 안 되는 라벨은?

## 4-7. 지표 → 트레이스 → 로그 연결 (exemplar)

- 💡 p99 그래프의 튀는 점을 클릭하면 **그 시각의 느린 요청 트레이스**로 바로 간다 (exemplar). 트레이스의 traceId로 로그를 찾는다 (Loki). 10주 차 "로그 ↔ 트레이스 연결"의 목표
- 💡 트레이스 샘플링: 전부 저장하면 비싸다. **head 샘플링**(시작할 때 1%만)은 정작 느린·에러 요청을 놓친다 → **tail 샘플링**(끝난 뒤 느린 것·에러는 전부 보관)

## 4-8. 기타 단골

- 가상 스레드 **pinning** (`synchronized` 안에서 블로킹 → 캐리어 스레드를 붙잡음, Java 24+ JEP 491로 대부분 해결) → 14주 차
- WebFlux **이벤트 루프 블로킹** (`reactor-http-nio` 스레드에서 블로킹 호출) → 14주 차
- 쿠버네티스 **DNS `ndots:5`**: 외부 도메인 하나에 DNS 질의가 여러 번 나가 지연 (`api.bank.com.` 끝에 점, 또는 ndots 조정)
- **conntrack 테이블 가득 참**: 연결이 많은 노드에서 간헐적 패킷 드롭 (리눅스 네트워크 딥다이브 백로그와 연결)

# Part 5. APM 도구 화면 읽기

| 도구 | 어디서 많이 쓰나 | 대표 화면 |
| --- | --- | --- |
| **Pinpoint** (네이버, 오픈소스) | 국내 대기업·금융권 | **서버맵**(서비스 간 호출 지도와 지연), **응답 시간 산점도**(점 하나 = 요청 하나, 위로 튄 점을 드래그하면 그 요청들의 호출 스택), 호출 스택 타임라인 |
| **Scouter** (LG CNS, 오픈소스) | 국내 SI·금융권 | **XLog**(Pinpoint 산점도와 같은 개념, 실시간), 액티브 서비스(지금 처리 중인 요청과 어디서 멈췄나) |
| **Datadog, New Relic** (상용) | 스타트업·글로벌 | 서비스 맵, 트레이스 플레임 그래프, 지표·로그·트레이스 한 화면 |
| **OpenTelemetry + Tempo + Grafana** (오픈 표준) | 이 프로젝트 (9~10주 차) | 트레이스 워터폴, 서비스 그래프, exemplar |

- 💡 **산점도(XLog) 읽는 법**: 가로 = 시간, 세로 = 응답 시간. 평소엔 아래쪽에 띠. ① 위쪽에 **가로 줄**이 생기면 = 특정 타임아웃 값에 걸림 (예: 3초 줄 = read-timeout 3s) ② **세로 기둥** = 그 순간 모두 멈춤 (GC 일시정지, 락, DB 순간 정지) ③ 띠 전체가 **서서히 올라감** = 자원 포화 (커넥션 풀, CPU)
- 💡 도구는 달라도 보는 것은 같다: **어떤 요청이 느렸나 → 그 요청의 시간이 어느 구간(DB? 외부 호출? 내부 로직?)에서 쓰였나**
- 💡 이 프로젝트는 OpenTelemetry로 한다. 면접에서 "국내에서 많이 쓰는 Pinpoint/Scouter와 원리가 같다(에이전트가 바이트코드에 끼어들어 구간 시간을 잰다)"고 연결하면 된다
