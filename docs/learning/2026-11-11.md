### 1. cloud-init
vm 프로비저닝시 초반 작업을 도와주는 오픈소스
처음으로 VM 을 부팅하게 되면 해당 VM 의 가상 CD-ROM 에 스크립트를 넣어주면 그걸 실행해주는 역할을 함
패키지 설치, 계정 설정 등 직접하면 번거로운 작업들을 싹다 처리
클라우드 VM 이미지에 설치가 되어있다.

> 💬 **리뷰:** 정확해요. 두 가지만 보태면 완성입니다.
> - **첫 부팅 때만** 실행된다 (instance-id 기준, 재부팅해도 다시 안 돎).
> - 가상 CD-ROM은 Proxmox 방식이고, AWS는 메타데이터 서버(`169.254.169.254`)에서 받는다. cloud-init은 같고 **설정 받는 곳(datasource)만 다르다** → 우리 user-data를 EC2에 거의 그대로 쓸 수 있다.
>
> 🎤 꼬리 질문: "`terraform apply`가 끝나면 k3s 설치도 끝난 건가요?" (아니요. Terraform은 VM 안 작업을 모른다 → `cloud-init status --wait`)

### 2. 쿠버네티스의 네트워크 관련 리소스 
#### kube-proxy
클러스터 내부의 파드간 네트워크 구성해주는 애 (ip-table 관리 등)

> 💬 **리뷰 (⚠️ 고칠 것):** 파드 간 네트워크(파드 A → 파드 B로 패킷이 가게 하는 것)는 **flannel(CNI)** 담당이에요. kube-proxy는 **Service를 구현**합니다. "ClusterIP·NodePort로 온 패킷을 실제 파드 IP 중 하나로 바꿔라(DNAT)"는 iptables 규칙을 노드마다 써 넣는 애예요.
> - 한 줄로: **flannel = 파드끼리 길을 놓는다 / kube-proxy = 대표번호(Service)를 실제 파드로 바꿔 준다**

#### ClusterIP
클러스터 내부에서 쓰이는 IP 특정 서비스의 대표 주소

> 💬 **리뷰:** 맞아요 (노트의 "회사 대표번호" 비유 그대로). 보탤 것: 이 IP를 가진 **장치는 어디에도 없다** (가상 IP). 패킷이 오면 각 노드의 iptables가 파드 하나를 골라 바꿔 준다 → 그래서 ClusterIP에 ping이 안 된다.

#### NodePort
클러스터 외부에서 트래픽을 받기위해 노드에 마다 공통의 포트를 뚫어서 특정 서비스로 인입 되도록 함
이때 위에서 언급한 kube-proxy 가 해당 노드 포트를 클러스터IP 로 연결해줌

> 💬 **리뷰:** 거의 맞아요. 세부 하나: ClusterIP **주소로** 한 번 더 보내는 게 아니라, ClusterIP와 **같은 처리 절차(iptables의 `KUBE-SVC` 체인)에 합류해서 바로 파드를 고른다.** 그리고 그 포트를 듣는 프로그램은 없다 (`ss -lntp`에 안 나옴). 프로그램에 닿기 전에 커널이 가로챈다.
>
> 📎 [네트워킹 노트](../infra/notes/k8s-service-networking.md) «주의: Service 타입 이름 `LoadBalancer` ≠ LB 장치», «파드가 없는 노드의 NodePort로 오면 어떻게 파드까지 가나»

#### MetalLB
쿠버네티스 클러스터에 트래픽 인입해주는 방식은
클러스터 외부에 실제 라우터 장비를 두고 로드밸런싱을 해주는 방식임
그러나 그런 장비를 설치할 환경이 되지 않으면 lb 를 별도 어플리케이션으로 둘 수 있다.
대표적으로 하나의 노드를 추가해서 거기서 인입을 먼저 받고, 쿠버네티스 클러스터로 로드밸런싱 해주는 방법이 있음
그런데 이렇게 노드를 생성하지 않고 기존 노드에서 lb 를 수행하도록 할 수 있는데 이게 metallb 의 역할임
metalLB 는 ARP 단계에서 클러스터의 노드중 하나의 노드를 트래픽 인입 지점이라고 속인다. (L2)
그러면 해당 노드에 요청이 꽂히는데 이때 해당 포트를 다른 ClusterIP 연결을 해줌. 그러다가 해당 노드가 죽게되면
다른 노드 중 하나에서 metalLB 파드가 다시 ARP 를 날려서 요청지를 속인다. (대부분의 LB 리던던시도 이런식으로 동작함)
장점은 노드를 하나 추가하지 않아도 되어서 리소스 부담이 없다는 점, 리던던시 구성이 자동으로 된다는점 
단점은 부하가 한곳으로 집중되어 로드밸런싱을 못한다는 점이 있다.

> 💬 **리뷰:** 오늘 쓴 것 중 제일 잘 썼어요. 장단점까지 정확합니다. 다듬을 곳 세 군데:
> - 31줄 "해당 포트를 다른 ClusterIP 연결을 해줌"의 주어가 MetalLB처럼 읽혀요. **MetalLB는 "`.240`은 이 노드예요"라고 알리기만 하고 트래픽 경로에는 끼지 않는다.** 노드에 도착한 다음은 kube-proxy(iptables) 몫. 면접에서 자주 헷갈리는 포인트라 명확히 써 두면 좋아요.
> - 노드가 죽으면 파드가 새로 뜨는 게 아니라, **speaker 파드가 이미 노드마다 떠 있다가** 다른 speaker가 이어받는다. 이때 보내는 ARP를 **Gratuitous ARP**라고 부른다. "대부분의 LB 리던던시도 이런 식"은 맞는 직관이고, 이름은 **VRRP / keepalived**.
> - 28줄 "노드를 하나 추가해서 인입을 먼저 받는" 방식 = 외부 LB VM(HAProxy 등).
>
> 🎤 꼬리 질문: "그럼 부하 분산은 어떻게 하나요?" → BGP 모드 (라우터가 ECMP로 여러 노드에 분산, BGP 지원 라우터 필요). "회사망에 깔아도 되나요?" → ARP 스푸핑과 같은 원리라 스위치의 DAI나 클라우드 VPC에서 막힐 수 있다 → 네트워크팀 협의, 클라우드는 ELB.
>
> 📎 [네트워킹 노트](../infra/notes/k8s-service-networking.md) «ARP와 MetalLB (쉬운 설명)», «MetalLB 정리», «4. MetalLB» (L2 vs BGP 표), «MetalLB 대신 외부 LB VM(HAProxy 등)은?»

#### Traefik
클러스터로 들어온 트래픽이 처음으로 맞는 게이트웨이임
Ingress 라는 리소스를 기반으로 라우팅을 해줌

> 💬 **리뷰:** 맞아요. "처음 맞는 **L7**(HTTP를 읽는) 관문"이라고 하면 더 정확해요 (그 앞의 MetalLB·kube-proxy는 HTTP를 안 본다). 이 프로젝트에선 Traefik이 **Host**(어느 시스템)로, 나중에 만들 Spring `gateway`가 **경로·JWT**(어느 서비스)로 나눈다. 둘 다 L7인데 역할이 다르다는 게 면접 포인트.
>
> 📎 [네트워킹 노트](../infra/notes/k8s-service-networking.md) «Ingress vs gateway: 이 프로젝트에서의 역할 분담», «레이어별 정리»

#### flannel
노드간 통신을 할 수 있도록 도와주는 애. 오버레이 네트워크라고 함.

> 💬 **리뷰:** 충분해요. 한 줄 보태면: 노드마다 파드 IP 대역(10.42.**N**.x)을 나눠 주고, 다른 노드의 파드로 가는 패킷을 노드 IP로 **포장(VXLAN)해서 터널로** 보낸다. 집 공유기는 10.42.x.x를 모르니까 포장이 필요한 것.

### 트래픽 인입 시나리오
외부 요청이 들어오면 우선 LB(AWS 에서는 ELB) 역할을 해주는 애가 필요한데, metalLB 가 그 인입구 역할을 한다.
metalLB 로 부터 유도되어 트래픽은 노드중 한 곳으로 들어가는데(요청은 거기가 다른 노드 인줄 안다)
그리고 해당 포트는 kube-proxy 에 의해 traefik 으로 다시 연결됨
traefik 은 Ingress 에 적힌 규칙대로 라우팅을 하여 (도메인 기반/요청 path 기반) 해당 서비스에 꽂히게 된다.

> 💬 **리뷰:** 흐름 맞아요. 빠진 마지막 구간: Traefik → 앱 **Service(ClusterIP)** → kube-proxy가 **또 한 번** 파드를 고름 → (파드가 다른 노드면 flannel 터널) → 앱 파드. 즉 kube-proxy는 두 번 등장해요.
> ```
> 맥북 → .240 (MetalLB: ARP로 "이 노드") → 노드 도착
>      → kube-proxy ① → Traefik 파드 (L7: Host 보고 판단)
>      → 앱 Service → kube-proxy ② → 앱 파드   (다른 노드면 flannel)
> ```
> 그리고 ① 구간에서 SNAT이 일어나서 **고객 IP가 사라진다** → 아래 "SNAT와 고객 IP 유실" 아이템으로 이어져요.

## GitOps와 Argo CD, App of Apps, self-heal 📝 `gitops-argocd.md`
뒤에꺼 두개는 뭐래...

> 💡 **답:**
> - **App of Apps:** Argo CD의 "앱"(Application)도 YAML이다. 그래서 **앱 목록을 관리하는 뿌리 앱 하나**(`deploy/argocd/root.yaml`)만 손으로 등록하고, 그 뿌리 앱이 `deploy/argocd/apps/` 폴더를 본다. 이 폴더에 `core.yaml` 같은 파일을 **추가하면 설치, 지우면 삭제.** 새 서비스 배포가 "파일 하나 커밋"이 된다.
> - **self-heal:** 누가 `kubectl`로 손대서 클러스터가 Git과 달라지면, Argo CD가 **Git 상태로 되돌린다.** 1주 차에 `kubectl delete` 했더니 몇 초 만에 다시 생긴 그것.
> - 🎤 "self-heal이 왜 좋나?" → 운영에서 손으로 고친 게 다음 배포 때 날아가는 사고(drift)를 구조적으로 막는다. 롤백도 `git revert` → 배포 이력 = Git 이력 (금융권 변경 관리·감사에 유리).
>
> 📎 [GitOps 노트](../infra/notes/gitops-argocd.md) «1. Argo CD의 동작», «4. 실무 포인트» / [인프라 README](../infra/README.md) «배포 구조 (GitOps)», «GitOps 함정 메모»
