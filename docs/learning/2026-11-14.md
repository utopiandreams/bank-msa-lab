## ⭐ 트랜잭션 나누기: 처리중 커밋 → 트랜잭션 밖에서 core 호출 → 결과 커밋

> 💡 **핵심**
> ```kotlin
> val processing = startInTransaction(...)        // 트랜잭션 ①: PROCESSING으로 저장, 커밋
> val result = corePostingPort.transfer(processing) // 트랜잭션 밖: DB 커넥션을 쥐고 있지 않다
> return applyResultInTransaction(processing, result) // 트랜잭션 ②: COMPLETED / FAILED / UNKNOWN
> ```
> - **트랜잭션 안에서 원격 호출하면:** ① 상대가 느려질 때 DB 커넥션을 쥔 채 기다림 → 풀(기본 10개) 고갈 → 송금과 무관한 조회까지 멈춤 ② 호출은 성공했는데 커밋이 실패하면 DB만 롤백되고 상대 쪽 일은 되돌릴 수 없음
> - **PROCESSING을 먼저 커밋하는 이유:** 호출 중에 죽어도 "처리하다 멈춘 송금"이라는 흔적이 남는다. 나중에 찾아서 해소할 수 있다
> - **PROCESSING의 진짜 의미는 "호출했다"가 아니라 "호출했을 수도 있다".** 커밋 직후 호출 전에 죽었는지, 호출 후 응답 전에 죽었는지 구분할 수 없다. 그래도 괜찮은 이유: core에 상태 조회가 있고, 같은 송금 ID로 다시 보내도 core가 멱등하게 한 번만 처리한다
> - **REQUESTED는 저장하지 않았다:** 동기 처리라 "REQUESTED로 남은 송금"은 PROCESSING과 구별되는 정보가 없고 커밋만 늘어난다
> - 실무에서 흔한 반례: 소규모 서비스의 `@Transactional` 안 PG 승인 호출. 트래픽이 적으면 버티지만 "승인은 됐는데 주문은 롤백"이 CS로 돌아온다. 단계별 대응: 실패 시 보상 취소 → 상태 먼저 커밋 → 타임아웃이면 조회 → 멱등 키 → 웹훅·대사
>
> 🎤 "core 호출이 트랜잭션 밖이라는 걸 어떻게 보장하나?" → 테스트 두 개: 가짜 core가 호출 순간 `TransactionSynchronizationManager.isActualTransactionActive()`가 false인지 확인, 같은 순간 DB를 따로 읽어 PROCESSING이 이미 커밋돼 있는지 확인
> 🎤 "core는 성공했는데 두 번째 트랜잭션(결과 반영)이 실패하면?" → PROCESSING으로 남고 고객은 500을 받는다. 돈은 움직였다. 8주 차 해소 스케줄러가 core 상태 조회로 COMPLETED로 확정한다 ("처리중인데 실제로는 완료"). 송금 ID가 든 에러 로그가 추적의 시작점
> 🎤 "그럼 그냥 `@Transactional` 하나로 감싸면 안 되나?" → 위의 ①② 때문. 다만 부작용 없는 짧은 조회 호출이면 실무적으로 허용할 수 있다 (트레이드오프)
>
> 📎 `transfer/application/TransferUseCaseImpl.kt` / `TransferUseCaseTest` «core를 호출하는 동안 DB 트랜잭션이 열려 있지 않다», «core를 호출하는 시점에 PROCESSING이 이미 커밋돼 있다»

## ⭐ 응답 분류: 완료 · 거절 · 결과 불명

> 💡 **핵심**
> - **기준 한 줄: "core가 처리하지 않았음이 확실할 때만 거절(FAILED). 조금이라도 애매하면 결과 불명(UNKNOWN)."** 거절을 잘못 확정하면 "돈은 나갔는데 실패 표시" → 고객이 다시 보내 이중 송금
>
>   | core 응답 | 분류 | 이유 |
>   | --- | --- | --- |
>   | 201 / 200 | 완료 | 200은 같은 키 재요청, 같은 원장 ID |
>   | 400 / 404 / 422 | 거절 | core가 업무 규칙으로 거절, 트랜잭션 롤백 → 확실히 처리 안 됨 |
>   | **409** | **결과 불명** | 같은 송금 ID로 **다른 거래가 이미 있다** = "처리 안 됨"이 아니다 |
>   | **5xx** | **결과 불명** | core가 커밋한 직후 응답을 만들다 터졌을 수 있다 |
>   | **2xx인데 body를 못 읽음** | **결과 불명** | 커밋은 확실한데 원장 ID가 없어 완료로 확정 불가 |
>   | 타임아웃 · 연결 실패 | 결과 불명 | 응답 자체가 없음 |
> - **UNKNOWN의 정의는 원인(타임아웃)이 아니라 "상태 조회로 확정해야 하는 송금".** 원인이 달라도 빠져나오는 방법(core 상태 조회)이 같아서 상태 하나로 묶는다
> - **포트는 예외 대신 sealed 결과를 돌려준다.** 타임아웃을 예외로 던지면 catch를 빠뜨렸을 때 "모름"이 조용히 사라진다. `when`으로 받으면 처리 누락을 컴파일러가 잡는다
>
> 🎤 "타임아웃이면 실패 아닌가?" → 응답을 못 받았을 뿐, core는 처리했을 수 있다. 네트워크에서 **답장만** 사라지는 경우도 있다 (아래 conntrack)
> 🎤 "409를 왜 거절로 안 봤나?" → 이 송금 ID로 무언가 처리돼 있다는 뜻이라. 정상이라면 일어날 수 없어서 우리 버그 신호 → 에러 로그
>
> 📎 `transfer/infrastructure/core/CorePostingAdapter.kt` `classify()` / `CorePostingAdapterTest`

## ⭐ HTTP 상태 코드: 400 · 404 · 409 · 422 · 5xx

> 💡 **핵심**
> - 4xx = 요청 쪽 문제, 5xx = 서버 쪽 문제
>
>   | 코드 | 의미 | 판단 질문 | 예 |
>   | --- | --- | --- | --- |
>   | 400 | 요청이 틀림 | 요청을 고치면 해결되나? | 금액 -1000, 같은 계좌 송금 |
>   | 404 | 대상이 없음 | | 없는 계좌, 없는 송금 |
>   | 409 | 다른 요청과 **충돌** | 먼저 처리된 무언가와 부딪혔나? | 같은 멱등 키에 다른 내용, 낙관적 락 버전 불일치 |
>   | 422 | 형식은 맞는데 **업무 규칙**상 불가 | 입금하고 나서 그대로 다시 보내면 되나? | 잔액 부족 |
>   | 5xx | 서버 잘못 | | 버그, DB 장애 |
> - 400 vs 422는 팀 컨벤션. 전부 400으로 주는 회사도 많다
> - **상태 코드는 굵다.** 그래서 body(ProblemDetail, RFC 9457)에 `code`(`INSUFFICIENT_BALANCE` 등)를 같이 준다. 어댑터는 상태 코드로 크게 나누고 `code`를 실패 사유로 저장
> - **transfer API 결정:** POST는 결과와 무관하게 201 + Location. 송금 기록(자원)은 어떤 결과든 만들어졌으니까. 결과는 body의 `status`. GET에서 없는 송금은 404 (core의 상태 조회가 "처리 안 됨"을 200으로 답하는 것과 다른 이유: 송금은 우리가 발급한 ID로 찾는 자원)
>
> 🎤 "에러 코드는 상태 코드만으로 부족한가?" → 404만으로는 "계좌 없음"과 "URL 오타"가 구분 안 된다
>
> 📎 `core/.../posting/api/PostingExceptionHandler.kt`, `AccountExceptionHandler.kt` / `transfer/api/TransferController.kt`, `TransferExceptionHandler.kt`

## ⭐ 송금 상태 머신

> 💡 **핵심**
> ```
> REQUESTED ──▶ PROCESSING ──완료──▶ COMPLETED (끝)
>  (메모리만)               ├─거절──▶ FAILED (끝)
>                           └─모름──▶ UNKNOWN ──상태 조회(8주 차)──▶ COMPLETED / FAILED
> ```
> - 허용 전이는 `TransferStatus.canTransitTo` 한곳에 표처럼 모았다
> - 공개 API는 **의도별 메서드**: `startProcessing()`, `completeProcessing(coreEntryId)`, `failedProcessing(code)`, `markUnknown()`. 범용 `transitTo(to, entryId?, code?)`를 열면 "FAILED인데 원장 ID 있음" 같은 잘못된 조합을 컴파일러가 못 막는다. 의도별 메서드는 "완료엔 원장 ID 필수"를 **타입이** 보장한다
> - `markUnknown()`은 인자가 없다: 응답을 못 받았으니 원장 ID가 있을 수 없다
> - `updatedAt`은 전이마다 갱신: 해소 스케줄러가 "PROCESSING으로 N분 넘게 멈춘 송금"을 찾는 기준
>
> 🎤 "끝 상태에서 또 전이하려 하면?" → `check` 실패 → IllegalStateException → 500. 정상 흐름에선 일어날 수 없으니 버그로 보이는 게 맞다
>
> 📎 `transfer/domain/Transfer.kt`, `TransferStatus.kt`

## ⭐ Flyway 재기동 장애: search_path와 테스트 환경

> 💡 **핵심**
> - Flyway는 기록 테이블 위치를 안 정해 주면 **접속의 현재 스키마**를 쓴다. PostgreSQL의 현재 스키마 = `search_path`(`"$user", public`)에서 **실제로 존재하는 첫 스키마**. `"$user"` = 계정 이름과 같은 스키마
>
>   | | 현재 스키마 | Flyway 판단 |
>   | --- | --- | --- |
>   | 첫 기동 | `transfer` 스키마 없음 → `public` | 새 DB → `public`에 기록 만들고 V1 실행 → **V1이 `transfer` 스키마 생성** |
>   | 두 번째 기동 | `transfer` 생김 → `transfer` | 기록은 없는데 테이블은 있음 → 기동 거부 → CrashLoopBackOff |
> - **V1이 Flyway가 보는 위치 자체를 바꿨다.** 고침: `spring.flyway.default-schema: public`
> - **테스트가 못 잡은 이유:** Testcontainers 계정이 `test`(조건 불성립) + 매번 새 DB에서 한 번만 기동. 계정을 클러스터와 같은 `transfer`로 맞추고 `flyway.migrate()`를 한 번 더 불러 재기동을 흉내 → 같은 에러 재현 → 수정 확인 → 클러스터에서 파드를 지워 실제 재기동까지 확인
> - 쿠버네티스에서 "두 번째 기동"은 반드시 온다 (배포, 노드 재부팅, OOM)
>
> 🎤 "어떻게 찾았나?" → 파드 상태(CrashLoopBackOff 133회) → `kubectl logs --previous` → DB에서 `search_path`, `current_schema()`, 기록 테이블 위치를 직접 조회해 가설 확인 → 테스트로 재현 → 수정
> 🎤 교훈 한 줄 → 테스트 환경이 운영과 한 글자 다르면(계정 이름) 그 차이에서만 나는 버그는 못 잡는다
>
> 📎 `transfer/src/main/resources/application.yaml` `spring.flyway` / `FlywayRestartTest` / 커밋 `f6a6f60`

## `require` vs `check`

> 💡 **핵심**
> - 동작은 같고 예외 타입이 다르다: `require` → IllegalArgumentException ("넘어온 **인자**가 틀림"), `check` → IllegalStateException ("인자는 괜찮은데 **지금 상태**에서는 안 됨")
> - 생성자(`init`)는 `require`: 객체가 만들어지는 중이라 틀릴 수 있는 상태가 없다. 상태 전이는 `check`
> - 예외 타입 기준은 원인 추적이 아니라 **그 함수의 계약 중 무엇이 깨졌나**
> - 실무 차이: IllegalArgumentException을 전역 400으로 매핑하면 우리 버그가 "고객 잘못"으로 묻힌다 → 고객이 고칠 수 있는 오류는 **업무 예외**로 따로 던지고, `require`/`check`는 둘 다 500 (마지막 방어선)
>
> 📎 `Transfer.kt` `init`, `transitTo()` / `TransferExceptionHandler.kt` 주석

## 엔티티 vs 값 객체, 그리고 헥사고날의 이점

> 💡 **핵심**
> - **엔티티:** ID로 구분, 생애주기 동안 상태가 바뀜 → 가변 + 상태 변경은 도메인 메서드로만 (`Transfer`)
> - **값 객체:** 값이 같으면 같은 것 → 불변 (`Amount`)
> - 엔티티를 불변(`copy`)으로 만들면: `copy(status = COMPLETED)`로 전이 규칙 우회 가능, 반환값을 버리는 조용한 버그, `version` 누락 위험
> - **`Amount`를 도메인 필드로도 썼다 (core와 다름):** core는 JPA 엔티티 = 도메인이라 value class name mangling 때문에 필드는 Long. transfer는 헥사고날이라 도메인이 JPA를 모르고, 변환은 매퍼가 흡수 → "도메인과 저장 모델을 분리했더니 도메인을 더 표현력 있게 만들 수 있었다"
> - core의 `Amount`를 가져다 쓰지 않고 transfer에 따로 둔다: 서비스끼리 코드를 공유하면 같이 배포해야 한다
>
> 🎤 "왜 서비스마다 아키텍처가 다른가?" → core는 락·트랜잭션 실험이 JPA와 붙어 있어서 엔티티 = 도메인, transfer는 외부 의존이 많아 포트를 가짜로 바꿔 테스트하려고 헥사고날. 그 결과 중 하나가 위의 `Amount`
>
> 📎 `transfer/domain/Amount.kt`, `infrastructure/persistence/TransferMapper.kt`

## 로그 레벨 판단

> 💡 **핵심**
> - 질문 하나: **"사람이 봐야 하나?"** 그렇다 → `error`, 정상 흐름 → `info`, 이상하지만 스스로 회복 → `warn`
> - core 거절 400 → `error` (use case 입구에서 걸렀어야 하므로 우리 버그 신호), 404·422 → `info` (정상적인 업무 거절), UNKNOWN → `error` (사람이·스케줄러가 나중에 추적해야 하는 상태)
> - 추적용 로그엔 송금 ID를 꼭 넣는다
>
> 📎 `CorePostingAdapter.kt` `classify()`, `unknown()`

## HTTP 클라이언트와 타임아웃

> 💡 **핵심**
> - RestClient / HTTP Interface / Feign은 **모두 블로킹**이라 동작 차이는 작다. 실제 차이: 실패를 예외로 주나(Feign·HTTP Interface) 응답 코드로 직접 보나(RestClient `exchange`), 의존성(Feign은 Spring Cloud, 유지보수 모드)
> - 분류가 핵심이라 RestClient `exchange`: 4xx·5xx도 예외로 안 바꾸고 응답을 그대로 줘서 분류가 `classify` 한곳에 모인다
> - **connect 타임아웃** = 연결을 맺기까지 (넘으면 요청이 도달 안 함), **read 타임아웃** = 보낸 뒤 응답까지 (넘으면 처리했는지 모름 → UNKNOWN의 주된 원인). 안 걸면 JDK HttpClient 응답 대기는 무제한
> - core 응답 형식은 transfer에 DTO를 따로 둔다. DDD 용어로 **ACL(Anti-Corruption Layer)**: core 모델이 transfer 도메인으로 새어 들어오지 않게 어댑터가 번역
>
> 📎 `infrastructure/core/CoreClientConfig.kt`, `CoreApiDtos.kt`, `application.yaml` `core.*`

## 테스트: 무엇을 테스트해야 하나

> 💡 **핵심** (문법은 맡기고, 이걸 떠올릴 수 있으면 AI가 짠 테스트를 리뷰할 수 있다)
> - 분류표의 **모든 줄**에 테스트가 하나씩 있는가
> - "2xx인데 body가 깨짐"처럼 **돈이 걸린 애매한 경우**가 들어 있는가
> - **타임아웃은 가짜 응답으로 재현이 안 된다** (`MockRestServiceServer`는 소켓을 안 쓴다) → JDK `HttpServer`로 진짜 소켓을 열고 응답을 붙잡아 둔다. 고정 `sleep` 대신 래치로 붙잡아야 테스트가 느려지지 않는다 (2초 → 0.2초)
> - 보내는 계좌·받는 계좌가 뒤집히지 않았는가 (둘 다 UUID라 컴파일러가 못 잡음 → 포트는 `Transfer`를 통째로 받게 했다)
> - **가변 엔티티 함정:** 가짜 core가 저장한 `Transfer` 참조는 호출 뒤 use case가 COMPLETED로 바꾼다 → "호출 시점 상태"는 호출 순간에 기록해야 한다

## DB 커넥션: 주소 · 계정 · 커넥션 풀

> 💡 **핵심**
> - **주소·계정:** CloudNativePG `Cluster` 선언 → 오퍼레이터가 파드·PVC·Service(`-rw` 쓰기 / `-ro` 읽기 / `-r`)·Secret을 만든다 → Helm values가 `jdbc:postgresql://transfer-db-rw:5432/transfer` + Secret을 환경변수로. 페일오버 때 `-rw`가 새 primary를 따라가서 앱은 주소를 안 바꾼다
> - **커넥션 풀은 앱 안의 HikariCP** (쿠버네티스 리소스 아님). 기본 최대 10개, 트랜잭션 동안 1개를 쥔다. 풀이 바닥나면 `connectionTimeout`(기본 30초) 기다리다 실패
> - **스케일 아웃 계산:** 파드 수 × 풀 크기 ≤ Postgres `max_connections`(지금 100). 넘으면 PgBouncer 같은 풀러 (CloudNativePG `Pooler`)
>
> 🎤 "파드를 20개로 늘리면?" → 20 × 10 = 200 > 100 → 커넥션 거부. 풀 크기를 줄이거나 풀러를 둔다
>
> 📎 `deploy/platform/transfer-db/cluster.yaml`, `deploy/apps/transfer/values.yaml`

## DNAT · SNAT · conntrack (백엔드 개발자 수준까지만)

> 💡 **핵심**
> - **NAT** = 패킷이 지나가는 도중 헤더의 IP·포트를 바꿔 쓰는 것. **DNAT** = 목적지를 바꿈 (ClusterIP → 파드 IP), **SNAT** = 출발지를 바꿈 (파드 IP → 노드 IP, 집 공유기의 사설 IP → 공인 IP)
> - 들어오냐 나가냐가 아니라 **"이 주소 그대로면 도착하고 답장이 돌아오나"**가 기준. 라우터는 목적지만 보고 보내므로 나가는 건 된다. 문제는 답장: 출발지가 바깥에서 모르는 주소면 답장이 못 돌아온다 → SNAT
> - **답장은 conntrack이 되돌린다:** 커널이 연결의 첫 패킷에서 바꾼 내용을 5-튜플로 기억했다가 답장에 반대로 적용. NAT 규칙은 첫 패킷에서 한 번만 보므로 한 연결은 끝까지 같은 파드로 간다 (커넥션 풀 같은 긴 연결은 분산이 안 된다)
> - **SNAT 부작용:** 외부 요청이 다른 노드를 거치면 파드에서 고객 IP가 사라진다 → X-Forwarded-For, `externalTrafficPolicy: Local` (gateway 때)
> - 장애 사례 (이름만 알면 충분): conntrack 테이블 가득 참 → 랜덤 타임아웃, DNS 5초 지연, 낡은 기록이 죽은 파드를 가리킴 (롤링 배포). 앱에는 전부 **타임아웃**으로만 보인다 → transfer에선 UNKNOWN
>
> 🎤 "응답을 못 받았다 = 처리 안 됐다?" → 아니다. 요청은 도착해서 처리됐는데 답장만 네트워크에서 버려질 수 있다
>
> 📎 `docs/infra/notes/k8s-service-networking.md`
