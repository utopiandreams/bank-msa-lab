# 동시성 제어: 무엇을 언제 쓰나

> 2026-11-22 개발자 요청: "동시성 판단은 정말 잘 설명하고 빠삭하게 이해해야 한다." 목표는 "이 상황이면 뭘 쓰겠어요?"라는 질문에 **고려할 것 → 선택 → 트레이드오프** 순서로 답하는 것.
> 진행: Claude가 💡🎤📎 공부 자료 → 개발자가 맨 아래 "내 말로 요약"을 채움 → Claude 리뷰. 5번(분산 락)은 7주 차 Redis 구현과 k6 결과로 채운다.

## 0. 판단 순서 (면접 답변 뼈대)

```
1. 정말 동시성 문제인가?   같은 데이터를 동시에 읽고 쓰나. 틀리는 방식은 무엇인가 (1번 표)
2. 판단에 필요한 정보가 그 행 안에 다 있나?        → 예: 원자적 UPDATE
3. 아니면, 그 정보를 같은 행으로 끌어올 수 있나?    → 예: 컬럼 추가 + 원자적 UPDATE
4. 판단이 DB 안에서 끝나나?
     규칙 복잡 / 경합 높음          → 비관적 락
     경합 낮음                      → 낙관적 락
     읽기와 쓰기가 다른 요청에 걸침  → 낙관적 락 (version을 들고 다님)
5. 지킬 대상이 DB 밖인가?                         → 분산 락 (+ DB 쪽 안전망)
6. 그래도 한 행에 요청이 몰린다 (핫 계좌)          → 락으로 못 푼다. 구조를 바꾼다: 쪼개기, 모아서 처리, 단일 처리자 큐
```

## 1. 문제의 종류부터 구분한다

| 문제 | 장면 | 막는 것 |
| --- | --- | --- |
| lost update | 둘 다 10,000을 읽고 각자 9,000을 씀 → 출금 하나가 사라짐 | 상대값 SET(`balance = balance - :amt`), 락, version |
| 검사 후 행동 (TOCTOU) | 둘 다 "잔액 충분"을 확인하고 둘 다 뺌 → 음수 잔액 | 검사와 변경을 한 원자적 단위로 (조건부 UPDATE의 WHERE, 락) |
| 중복 요청 | 같은 요청이 두 번 와서 두 번 처리됨 | **락이 아니라 멱등 키** (UNIQUE) |

- 💡 상대값 SET만으로는 lost update만 막힌다. 음수 잔액은 WHERE 조건이 막는다. 둘은 다른 문제다
- 💡 중복 요청을 락으로 막으려 하면 안 된다. 락은 "동시에"만 막고, 1초 간격으로 두 번 오면 두 번 처리된다
- 🎤 "동시성 문제의 종류를 나눠 보세요" / "멱등성과 동시성 제어는 어떻게 다른가요?"
- 📎 `LockStrategyConcurrencyTest`의 NONE 재현 (원장 8,000 / 잔액 9,000), pitfalls 33

## 2. 원자적 UPDATE (조건부 UPDATE)

```sql
UPDATE account SET balance = balance - :amt, version = version + 1
 WHERE id = :id AND balance >= :amt      -- 0행 = 조건 불만족
```

- 💡 **왜 안전한가:** UPDATE는 행 잠금을 건다. 두 번째 요청은 기다렸다가, 첫 번째가 커밋하면 **최신 값으로 WHERE를 다시 평가**한다 (PostgreSQL READ COMMITTED). 판단과 변경이 한 문장이라 틈이 없다
- 💡 **락이 없는 게 아니다:** UPDATE부터 커밋까지 행 잠금을 쥔다. 핫 계좌 처리량의 상한 = 1 / (UPDATE~커밋 시간). 두 행을 바꾸면 순서를 정해야 한다 (데드락)
- 💡 **갈림길은 하나:** 판단에 필요한 정보가 그 행 안에 다 있는가
  - 다른 행·테이블·외부 호출을 봐야 함 (일일 한도 = 오늘 원장 합계, 이상 거래 탐지) → 락
  - 새 값을 SET 식 하나로 못 씀 (이자·수수료 구간) → 락
  - 요령: 필요한 값을 같은 행으로 끌어오면 다시 원자적 UPDATE로 된다 (`today_withdrawn` 컬럼 + 날짜 바뀔 때 초기화 처리)
- 💡 **다른 락으로 바꿀 이유가 아닌 것**
  - 바뀐 값이 필요함 → `RETURNING balance` (표준 JPQL에 없어 네이티브 쿼리)
  - 실패 원인이 필요함 → 0행이면 다시 조회. 그사이 상태가 바뀌어도 틀리는 건 메시지뿐, 돈은 안전
- 💡 **대가**
  - 규칙이 도메인 메서드와 SQL 두 곳에 생긴다. SQL 쪽 규칙은 DB 통합 테스트로만 검증된다
  - 0행은 오류가 아니다. 반환값 확인을 빠뜨리면 원장만 기록되고 잔액은 그대로 (조용한 불일치)
  - JPA 영속성 컨텍스트를 우회: 미리 읽은 엔티티는 옛 값, `@Version` 직접 +1, `@PreUpdate`·Auditing·Envers가 안 돈다
  - 격리 수준에 기댄다: REPEATABLE READ면 재평가 대신 직렬화 오류 → 재시도 필요
- 🎤 "재고 차감 동시성은 어떻게?" / "WHERE stock > 0이 왜 안전한가요? 락은 안 걸리나요?" / "단점은? 그럼 언제 못 쓰나요?" / "실패 원인은 어떻게 알려 주나요?"
- 📎 `AccountRepository.withdrawAtomically`, `AtomicUpdateBalanceChanger`, pitfalls 32·33

## 3. 비관적 락 (`SELECT ... FOR UPDATE`)

- 💡 읽는 순간 행을 잠그고 커밋까지 쥔다. 그 사이 앱이 아무리 복잡한 판단을 해도 남이 못 바꾼다 → **규칙이 복잡할 때의 기본 선택**
- 💡 **대기자가 DB 커넥션을 쥐고 기다린다.** 커넥션 풀이 10개인데 핫 계좌에 10명이 줄 서면 다른 계좌 요청까지 전부 멈춘다 → `lock_timeout`(또는 JPA 힌트 `jakarta.persistence.lock.timeout`)으로 상한을 둔다
- 💡 여러 행을 잠그면 **항상 같은 순서로** (계좌 ID 오름차순). 반대 순서 = 데드락
- 💡 PostgreSQL 행 잠금 대기열은 **도착 순서(FIFO)** → 공정하다
- 💡 잠금을 쥔 채 원격 호출을 하면 그 시간만큼 남이 기다린다. 트랜잭션 안에서 외부 호출 금지
- 🎤 "비관적 락의 위험은?" / "데드락은 어떻게 막나요?" / "락 대기 시간은 어떻게 제한하나요?"
- 📎 `PessimisticBalanceChanger`, `AccountRepository.findByIdForUpdate`, 데드락 재현 테스트, pitfalls 32
- 🎤 **"비관적 락은 언제 쓰나요?" 답변 연습 (2026-11-23)**
  - 개발자 첫 답: "구현이 간단하고 Redis보다 성능이 좋아서 동시성 경쟁이 많지 않을 때 / DB에서 기다리니 커넥션 여유가 필요"
  - 리뷰: ❌ **경쟁이 적을 때는 낙관적 락**(충돌 없으면 공짜). 비관적 락은 오히려 **경쟁이 많을 때** (실측: 핫 계좌 500건/초에서 낙관적 39% 실패, 비관적 실패 0). △ "구현이 간단"보다 **"판단에 행 하나 이상의 정보가 필요할 때"**가 핵심. ✅ 커넥션 여유는 정확 → 대책(짧은 트랜잭션, 락 중 외부 호출 금지, `lock_timeout`, ID 순서)까지 붙이면 완성
  - 다듬은 답 (언제 → 왜 → 대가 → 근거): "판단에 행 하나 이상의 정보가 필요하거나(일일 이체 한도처럼 오늘 거래 합산), 경합이 심해 낙관적 락이면 재시도가 폭발할 때 씁니다. 행을 잡아 둔 채 도메인 코드에서 규칙을 판단할 수 있고, 대기열이 도착 순서라 재시도 없이 공정하게 다 성공합니다. 대가는 대기자가 DB 커넥션을 쥔 채 기다린다는 것이라, 핫 계좌 하나가 풀을 다 잡으면 상관없는 요청까지 멈춥니다. 그래서 트랜잭션을 짧게, 락 중 외부 호출 금지, `lock_timeout`으로 상한, 여러 행은 ID 순서로 잡습니다. 실측에서 핫 계좌 500건/초에 낙관적 락은 39% 실패, 비관적 락은 실패 0에 p50 1.26초였고, 그래서 행 하나 조건은 조건부 UPDATE, 복잡한 규칙이 생기면 그 작업만 비관적 락으로 갑니다."
  - 짧게 말할 땐 첫 문장만, 꼬리 질문이 오면 대가로
  - 2차 답 (개발자): "여러 행을 먼저 락해 두니 복잡한 로직에 좋다 / 낙관적 락은 재시도로 지연이 길어지니 경합이 많으면 비관적 락이 지연을 줄인다 / 대기 위치가 DB라 커넥션을 차지하니 커넥션 풀 조정을 잘 해야 한다"
  - 리뷰: ✅ 구조(언제 → 왜 → 대가) 잡힘. 1문장은 "기준 행(계좌)을 잠가 그 계좌를 바꾸는 요청을 줄 세운다"가 정확. ❌ **2문장이 실측과 반대**: 500건/초에서 낙관 p50 30ms·실패 39%, 비관 p50 1.26s·실패 0 → 비관의 이점은 지연이 아니라 **"재시도 없이 다 성공"**, 대가로 느려진다. △ 3문장 처방은 풀 키우기보다 **대기 제한**(짧은 트랜잭션, `lock_timeout`): 풀을 키우면 잠금 대기자가 더 많이 쥘 뿐
  - 꼬리 의심 (개발자): "비관적 락은 쓸 상황이 제한적인 것 같다. 지연이 길어지니 타임아웃을 짧게 걸면 낙관적 락과 다를 게 없지 않나?"
    - 💡 주 무대는 경합보다 **규칙이 행 하나에 안 담길 때**. 계정계에서 "계좌 행 FOR UPDATE 후 처리"는 흔한 기본 패턴
    - 💡 짧은 타임아웃을 걸어도 다르다 = **헛수고의 차이**: 낙관은 모두 끝까지 일한 뒤 진 쪽이 처음부터 다시(일이 버려지고 재시도가 부하를 키움), 비관은 일을 시작하기 **전에** 기다려 버려지는 일이 없다. 실측 hot 500건/초 초당 성공: ATOMIC 약 500 / **PESSIMISTIC 약 460 / OPTIMISTIC 약 300**
    - 💡 실패 모양: 비관 + 타임아웃은 도착 순서로 처리하고 오래 기다린 뒤쪽만 실패(예측 가능), 낙관은 운 나쁜 요청이 계속 질 수 있다(불공정)
    - 💡 `lock_timeout` = 줄이 처리 한계를 넘으면 뒤쪽을 잘라내는 **대기 제한**(줄 최대 길이 ≈ 도착 속도 × 타임아웃). pitfalls 37과 같은 원리
    - 💡 경합이 행 처리 한계를 넘으면 어떤 락도 못 푼다 → 설계 변경: 점유 시간 줄이기(원자적 UPDATE), 줄 없애기(계좌별 단일 처리자 큐), 핫 계좌 쪼개기(잔액 여러 행)
  - 2차 고친 답: "비관적 락은 판단 기준이 되는 행을 먼저 잠그고 시작해, 그 안에서 여러 행을 읽어 복잡한 규칙을 판단하기 좋습니다. 낙관적 락은 경합이 심하면 재시도를 다 쓰고 실패하는데, 비관적 락은 줄을 세워 재시도 없이 모두 성공시킵니다. 대신 기다리는 만큼 느려질 수 있습니다 (실측: 핫 계좌 500건/초에서 낙관 39% 실패, 비관 실패 0에 p50 1.26초). 다만 대기자가 DB 커넥션을 쥔 채 기다려, 경합이 몰리면 상관없는 요청까지 커넥션을 못 얻습니다. 그래서 트랜잭션을 짧게, `lock_timeout`으로 대기 상한을 겁니다."

## 4. 낙관적 락 (`@Version`)

- 💡 `@Version`이 해 주는 일 세 가지: `AND version = ?` 붙이기, `version + 1`, 바뀐 행 수 확인 → 0행이면 예외. 직접 구현하면 셋 다 손으로 (예외는 `OptimisticLockingFailureException`을 직접 던지면 재시도 루프를 그대로 쓴다)
- 💡 충돌은 **커밋할 때** 드러난다 → 재시도는 트랜잭션 **밖**에서, 처음부터 새 트랜잭션으로 (실패한 트랜잭션과 엔티티는 못 살린다)
- 💡 재시도에는 지터. 같이 충돌한 요청들이 같은 순간에 또 부딪히지 않게
- 💡 경합이 높으면 불리: 잔액이 충분해도 "누가 건드렸다"는 이유만으로 실패하고, 재시도가 폭증한다. 공정성 없음 (계속 지는 요청)
- 💡 **낙관적 락만의 자리:** 읽기와 쓰기가 **다른 요청**에 걸칠 때 (화면에서 고치고 저장). 사용자가 고민하는 동안 잠금을 쥘 수 없으니 version을 들고 다닌다
- 🎤 "낙관적 락 충돌 나면 어떻게 하나요?" / "재시도는 어디서? 왜 트랜잭션 밖에서?" / "경합이 높으면 어떻게 되나요?" / "원자적 UPDATE와 메커니즘이 같은데 차이는?" (WHERE가 version을 묻나 업무 조건을 묻나)
- 📎 `PostingUseCaseImpl.retryOnOptimisticLock`, `OptimisticBalanceChanger`, 핫 계좌 테스트 (성공 20 / 충돌 실패 7 / 잔액 부족 13)

## 5. 분산 락 (Redis) — 7주 차 구현하며 채운다

- 💡 **락 범위는 트랜잭션 바깥.** DB 락은 커밋 때 풀리지만 Redis 락은 코드가 푸는 순간 풀린다. 커밋 전에 풀면 다음 요청이 커밋 안 된 옛 잔액을 읽는다 → lost update
- 💡 대기자가 DB 커넥션을 쥐지 않는다 (트랜잭션 밖에서 기다림). 비관적 락과의 핵심 차이
- 💡 Redisson pub/sub vs 스핀: 둘 다 스레드는 블로킹. 차이는 Redis 부하와 넘겨받는 속도. 경합이 심할수록 스핀이 불리 (Redis 스핀은 시도 한 번이 네트워크 왕복)
  - 동작 원리(세마포어로 재우기 → 해제 PUBLISH → Netty 이벤트 루프가 release로 깨움), 메시지가 안 올 때(남은 TTL만큼만 대기), epoll·연결 공유·구독 연결 분리는 `docs/learning/io-and-event-loop.md`
  - 구현: `REDIS`(getLock) / `REDIS_SPIN`(getSpinLock, 백오프 1ms×2 최대 128ms). 테스트 시간 기준 스핀이 2~4배 느렸음 (측정은 k6)
- 💡 TTL 딜레마: 짧으면 처리 중에 만료돼 둘이 들어오고, 길면 죽은 클라이언트의 락이 오래 남는다 → Redisson 워치독, 그래도 GC 멈춤이면 뚫린다 → DB 쪽 안전망(`@Version`) 또는 펜싱 토큰
- 💡 공정성: 기본 RLock은 불공정, `RFairLock`은 FIFO (대가: 명령 수, 죽은 대기자 때문에 뒷사람이 막힘)
- 🎤 "DB 락이 있는데 분산 락을 왜 쓰나요?" / "락이 만료됐는데 작업이 안 끝났으면?" / "Redis가 죽으면?" / "Lettuce 스핀 락과 Redisson 차이는?"
- 📎 `RedisAccountLocks`(대기 상한은 마감 시각 하나, ID 순서로 잡고 반대로 풂), `RedisLockScopeTest`, `RedisLockConcurrencyTest`(재시도 0), pitfalls 34, k6 결과 `docs/experiments/week-07-locks.md`
- 💡 (k6, 2026-11-23) **분산 락의 기본 요금:** 락 한 번 = 명령 13개, 왕복 4번 (경합 없어도). 송금당 약 0.6ms. hot 300건/초부터 REDIS 계열만 core OOMKilled (원인 판독은 실험 기록)

## 6. 공정성과 처리량

| 전략 | 공정성 | 이유 |
| --- | --- | --- |
| 비관적 락, 원자적 UPDATE | 있음 | PostgreSQL 잠금 대기열이 도착 순서 |
| 낙관적 락 | 없음 | 먼저 커밋한 쪽이 이김 |
| Redisson RLock, 스핀 | 없음 | 새로 온 쪽이 끼어들 수 있음 |
| Redisson RFairLock | 있음 | Redis에 대기열 |
| 계좌별 단일 처리자 큐 | 완전 | 한 처리자가 순서대로. 대신 API가 비동기 |

- 💡 공정성은 공짜가 아니다. 불공정 락은 실행 중인 스레드가 풀린 락을 바로 채 가서(barging) 처리량이 높고, 대신 운 나쁜 요청의 대기가 길다 (`ReentrantLock(true)` Javadoc: 공정 락은 종종 훨씬 느리다)
- 💡 그래서 k6에서는 p99뿐 아니라 **최대 지연**을 같이 본다
- 🎤 "먼저 온 요청을 먼저 처리해야 한다면?" / "공정 락의 대가는?"

## 8. 트랜잭션이 길면 무엇이 문제인가 (2026-11-25 질문, 8주 차 2부 타행 해소 일꾼)

장면: 해소 일꾼이 한 회차를 한 트랜잭션으로 돈다 (`SKIP LOCKED`로 잡기 → 건마다 원격 호출 → 커밋). 타행은 한 건에 원격 호출이 둘(조회 + 취소)이라 최악 8초/건, 10건이면 80초.

| 문제 | 일반적으로 | 이 일꾼에서는 |
| --- | --- | --- |
| ① 커넥션 고갈 | 긴 트랜잭션이 **동시에 여러 개**면 풀이 빈다 (요청 스레드마다 트랜잭션 안 원격 호출 → pitfalls 8, T-1에서 트랜잭션을 나눈 이유) | 일꾼은 스레드 하나라 커넥션 **하나**만 쥔다 (Hikari 기본 10개 중 1). 고갈은 아님 |
| ② 잠금 대기 | 같은 행을 쓰려는 쪽이 커밋까지 기다린다 → 그쪽 지연 | 멈춘 타행 행에 쓰는 쪽이 일꾼뿐 (고객 재요청은 읽기만, 결정 5). 다른 일꾼은 SKIP LOCKED로 건너뜀. **거의 없음** |
| ③ 늦게 보인다 | 커밋 전까지 바뀐 상태가 안 보인다 | 회차 끝에 한꺼번에 커밋 → 1번 건이 해소돼도 고객 조회·완료 이벤트(outbox)·알림이 회차 끝까지 늦는다 |
| ④ 죽으면 통째로 다시 | 중간에 죽거나 타임아웃이면 전부 롤백 | 원격에선 이미 취소됐는데 기록은 롤백 → 다음 회차가 다시 조회·취소. 멱등이라 돈은 안전, 일만 버림. 회차가 길수록 버리는 양이 커진다 |
| ⑤ 종료와 충돌 | 배포·스케일 다운 때 graceful shutdown 대기(30s)보다 길면 강제 종료 → ④ | 80초 회차는 30초 안에 못 끝난다 → 배포마다 ④가 날 수 있다 |
| ⑥ MVCC 청소 지연 (PostgreSQL) | 열린 트랜잭션(특히 쓰기로 트랜잭션 ID를 받은 뒤)보다 뒤에 죽은 행은 VACUUM이 못 지운다 → 테이블 부풀음. 분·시간 단위면 사고 (`idle in transaction`으로 잊힌 세션) | 수십 초라 거의 무시. 단, outbox처럼 갱신이 잦은 테이블과 같은 DB라는 건 기억 |

- 💡 "긴 트랜잭션은 나쁘다"가 아니라 **누가 그 잠금·커넥션을 기다리나**로 따진다. 기다리는 상대가 없으면 ①②는 비용이 거의 없고, 남는 건 ③④⑤(커밋 단위가 크다)
- 💡 ③④⑤는 회차 길이가 아니라 **커밋 단위**의 문제 → 회차는 그대로 두고 **건마다 커밋**(한 건 = 한 트랜잭션, SKIP LOCKED로 1건씩 반복)하면 잠금을 쥐고도 거의 사라진다. 잠금을 쥐는 시간은 건당 최대 8초로 같다
- 💡 정합성은 락이 아니라 멱등성(조회는 읽기, 취소는 `reverses_entry_id` UNIQUE)이 지킨다 → 어떤 락을 고르든 효율·운영 비용의 선택이다
- 🎤 "트랜잭션 안에서 원격 호출하면 왜 안 되나요?" → 무조건이 아니라 ① 동시에 여러 개면 풀 고갈 ② 같은 행을 기다리는 쪽 지연 ③~⑤ 커밋 단위. 이 일꾼은 스레드 하나·경합 없음이라 ③~⑤만 남고, 건마다 커밋으로 줄였다
- 🎤 "PostgreSQL에서 긴 트랜잭션이 특히 위험한 이유는?" → MVCC: VACUUM이 그 트랜잭션보다 뒤의 죽은 행을 못 지워 테이블이 부푼다. `idle_in_transaction_session_timeout`·`transaction_timeout`(17+)으로 막는다
- 📎 `TransferResolutionUseCaseImpl` (회차 = 한 트랜잭션), ADR-0005 결정 5, `docs/design-drills/08-unknown-resolution.md` 2부, pitfalls 8, `timeouts-and-deadlines.md` (transaction_timeout)
