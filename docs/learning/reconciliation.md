# 대사 (reconciliation)

질답 모음 (CLAUDE.md 6장 7-1-0). 8주 차 일일 대사 설계(설계 연습 09) 중에 나온 질문들. 설계 결정은 `docs/design-drills/09-reconciliation.md`

## 1. 대사는 무엇이고, 원장 자체 검증과 무엇이 다른가 (2026-11-25)

- 💡 **대사:** 같은 돈의 움직임을 **서로 다른 두 장부**가 같게 기록했는지 기간(보통 하루) 단위로 맞춰 본다. 해소 일꾼까지 놓친 것을 잡는 마지막 그물. 철학은 "완벽히 막기"가 아니라 "어긋나면 찾아서 맞춘다"
- 💡 **원장 자체 검증(시산표, trial balance):** 장부 **하나** 안의 규칙. 복식부기라 모든 전표가 차변 합 = 대변 합 → 원장 전체도 같아야 한다. 계좌 잔액 = 그 계좌 전표 합도 같은 부류 (7주 차 k6 "잔액 vs 원장"). 쿼리 하나로 싸고, 한쪽만 기록되는 버그·DB 직접 수정을 잡는다 → 대사와 같이 돌린다
- 💡 장부 쌍은 **두 시스템이 같은 사실을 따로 기록하는 경계**에서 고른다 (여기서만 어긋날 수 있다). 이 프로젝트: transfer ↔ core 원장, core 원장(미정산) ↔ 외부 은행
- 🎤 "대사와 시산표는 뭐가 다른가요?"

## 2. 불일치 여지가 있는 곳만 보나, 싹 다 보나

- 💡 **쌍은 골라도, 고른 쌍 안에서는 그 기간의 기록 전부를 양쪽에서** 맞춘다. 대사는 예상 못 한 곳(버그)을 찾으려는 것이라 "여긴 괜찮겠지"로 빼면 구멍
- 💡 **양방향:** 우리 쪽에서만 출발하면("송금마다 전표가 있나") **상대에게만 있는 기록**을 못 찾는다. "생길 수 없는 일"이 대사가 확인하는 대상. 실제 원인: 내부망에서 core 직접 호출(7주 차 k6가 실제로 core `/postings/transfers`를 직접 불러 송금 없는 전표 수천 건이 있다), 서비스별 DB를 **서로 다른 시점으로 복구**(MSA의 대표적 불일치 원인), 버그
- 🎤 "우리 기록에 없는 외부 거래는 어떻게 찾나요?" → 상대 쪽에서도 출발한다 (상대의 일자별 전체 내역)

## 3. 전표에서 송금 전표만 어떻게 고르나

- 💡 core `ledger.journal_entry`의 **`type`**(TRANSFER · INTERBANK_WITHDRAWAL · INTERBANK_WITHDRAWAL_CANCEL)으로 고르고, **`idempotency_key` = 송금 ID**로 짝을 맞춘다 (취소는 `{송금ID}-cancel` + `reverses_entry_id`)
- 💡 구멍: "누가 만든 거래인가"를 기록하지 않아 k6 전표도 TRANSFER로 보인다. 실무는 거래마다 **채널 코드**(인터넷뱅킹·창구·배치·대외 …)를 남기고 대사 범위를 그걸로 자른다
- 📎 `services/core/src/main/resources/db/migration/V2__create_ledger_schema.sql`, `V3__interbank_transfer.sql`

## 4. 외부 기록은 어떻게 받나: 정산 파일

- 💡 외부 기관(금융결제원 등)은 **영업일 단위 거래 내역(정산) 파일**을 준다: 그날 그 은행 이름으로 처리된 거래 전부
- 💡 구조: **건별 내역**(거래 고유번호·금액·받는 계좌·처리 시각·결과) + **합계(trailer: 총 건수·총 금액)**. 합계는 ① 파일이 다 왔나 확인 ② 차액결제 금액의 근거
- 💡 대사는 **총액 대사**(빠른 이상 감지) → **건별 대사**(우리만 / 외부만 / 금액 다름). **합계만으론 안 된다: 오류가 상쇄된다** (우리만 있는 3만 + 외부만 있는 3만 → 합계 같음, 실제 불일치 2건)
- 💡 단건 조회 API로 대사하면 우리 쪽에서만 출발 → 외부에만 있는 거래를 못 찾고, N건이면 N번 호출
- 🎤 "정산 파일 합계는 왜 있나요?" / "합계가 맞으면 대사 끝인가요?"

## 5. 날짜 경계

- 💡 23:59:59에 보내 외부가 00:00:02에 처리 → 양쪽이 **다른 날짜로 묶어서** 생기는 가짜 불일치. 단건 조회로 "시차"를 확인해도 다음 날 대사에서 "외부에만 있음"으로 또 잡힌다 → 뿌리는 날짜 기준이 둘이라는 것
- 💡 실무 도구: ① **한 날짜로 묶는다** (보통 외부가 정한 처리일·정산일을 응답으로 받아 우리 기록에 저장) ② **시차 차이는 오류가 아니라 이월(미결)**: 다음 날 다시 보고, 며칠이 지나도 안 맞을 때만 진짜 불일치. 아직 해소 중인 건(결과 불명)도 미결로 넘긴다

## 6. 하루 100만 건이면?

- 💡 **크기 자체는 작다:** 한 줄 100바이트면 100만 건 ≈ 100MB. 배치로는 평범한 크기 (실제 정산 파일이 이 규모 이상). 그래서 API 페이지 넘기기보다 **파일**(SFTP·전용선)로 주고받는다
- 💡 **비교는 건마다 조회하지 않고 집합으로 한다:** 양쪽 데이터를 대사용 저장소의 **스테이징 테이블**에 일괄 적재(PostgreSQL `COPY`) → 거래 ID로 **`FULL OUTER JOIN`** 한 번 → 한쪽이 NULL이면 "우리만/외부만", 금액이 다르면 "금액 다름". 100만 × 100만 해시 조인은 수 초~수십 초
- 💡 **DB per service라 다른 서비스 DB를 직접 조인하지 않는다:** transfer·core·외부 각각에서 그날 데이터를 **추출**(API·내보내기)해 대사가 사는 곳에 모은다 → "대사는 어느 서비스에 사나"가 설계 질문
- 💡 더 커지면: 날짜 파티션, 양쪽을 ID로 정렬해 한 줄씩 비교(sort-merge, 메모리 적게), 분산 처리(Spark). 재실행은 그날 스테이징을 지우고 다시 적재 (멱등)
- 🎤 "하루 100만 건 대사를 어떻게 하나요?" → 파일 수신 → 스테이징 적재 → FULL OUTER JOIN 한 번, 건마다 조회하지 않는다. 서비스별 DB는 추출해서 모은다

## 7. 대사를 별도 시스템으로 두면, 그 시스템은 모든 서비스 DB에 붙나? (2026-11-25)

- 💡 **왜 별도로 두나:** 독립성. 검사받는 쪽(transfer)이 검사를 겸하면 같은 코드의 버그를 못 볼 수 있다. 실무 은행은 정산·대사 시스템(또는 정보계)이 따로 있다
- 💡 **데이터를 모으는 방법 4가지:**

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| ① 서비스마다 일자별 내역 **API** | DB per service를 지킨다 | 서비스에 부하, 페이지 처리. 데이터가 **그 서비스 코드를 거쳐** 나온다 (버그가 내역에도 묻을 수 있음) |
| ② 서비스마다 일자별 **추출 파일**을 저장소(S3 등)에 떨굼 | 대량에 강함, 시간 분리(서비스는 떨구고 끝), 정산 파일과 같은 모양 | 파일 형식이 계약이 됨, 떨구는 배치 관리 |
| ③ **이벤트·CDC**로 대사 시스템이 자기 사본을 계속 쌓음 | 실시간에 가까움, DB에 실제로 커밋된 행을 읽음(CDC) | 이벤트 유실·중복을 다시 대사해야 하는 역설, 인프라(Debezium 등) |
| ④ 각 DB의 **읽기 복제본·DW에 직접** 붙음 | 가장 빠르게 만듦, 실제 저장된 값을 봄 | DB per service 위반, **스키마 결합**(core가 컬럼 이름을 바꾸면 대사가 깨짐). 실무에선 데이터 플랫폼·정보계로 흔히 함 |

- 💡 독립성과 결합의 줄다리기: 서비스 코드를 덜 거칠수록(④·CDC) 독립적이지만 스키마에 묶이고, API(①)는 경계를 지키지만 서비스 코드의 버그를 같이 볼 수 있다
- 🎤 "MSA에서 여러 서비스 데이터를 대사하려면?" → 방법 넷과 트레이드오프, 이 프로젝트의 선택과 이유
