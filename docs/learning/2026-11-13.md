## ⭐ posting 모듈: 원장 기록 + 잔액 변경을 한 트랜잭션으로

> 💡 **핵심**
> ```
> posting ──▶ ledger.recordXxx()   (원장 INSERT, 멱등 판정)
>    └──────▶ account.xxx()        (잔액 변경)        ← 둘을 TransactionTemplate 하나로 감쌈
> ```
> - **account와 ledger는 서로를 모른다.** 둘을 지휘하는 posting이 위에 있다 (의존 방향: posting → account, posting → ledger)
> - **한 트랜잭션이라:** 원장 INSERT 뒤에 잔액 부족·계좌 없음으로 실패하면 **원장 기록도 롤백.** "원장은 있는데 잔액은 안 바뀐" 상태가 안 남는다
> - **송금 1건 = 거래 1건(분개 2줄).** 출금 + 입금 거래 2건으로 쪼개면 둘이 한 송금이라는 연결이 원장에서 사라진다 (대사 불가)
>
> 🎤 "account가 ledger를 직접 부르면 안 되나?" → account가 ledger를 알게 되고, 송금(계좌 2개)은 account 하나의 일도 아니다. 여러 모듈을 엮는 유스케이스는 위에 따로 둔다 (DDD 용어로 애플리케이션 서비스)
> 🎤 "그걸 어떻게 증명했나?" → "받는 계좌가 없으면 보낸 쪽 출금도 롤백" 테스트: 원장 INSERT → 출금 성공 → 받는 계좌 조회 실패 → 출금·원장 모두 되돌아감
>
> 📎 `posting/application/PostingUseCaseImpl.kt` / `PostingUseCaseTest` «받는 계좌가 없으면...», «잔액보다 많이 출금하면...»

## ⭐ 멱등 키: replayed / IdempotencyConflict, `isSameRequestAs`

> 💡 **핵심**
> - **멱등 = 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같다.** 네트워크 타임아웃으로 클라이언트가 재시도해도 **이중 출금이 안 난다**
>
>   | 같은 키로 다시 오면 | 결과 |
>   | --- | --- |
>   | 같은 내용 | 기존 거래 ID + `replayed = true`, 잔액은 안 바꿈 |
>   | 다른 내용 (금액·받는 계좌가 다름) | `IdempotencyConflictException` (→ 409) |
> - **같은 내용 판정:** 해시를 따로 저장하지 않고 "거래 종류 + 분개 줄 구성(계정·계좌·방향·금액)"을 비교. 요청 정보가 분개 줄에 전부 남아 있어서 가능
> - 최종 방어선은 DB `UNIQUE (idempotency_key)`
>
> 🎤 "다른 내용인데 그냥 성공으로 응답하면?" → 클라이언트는 "20만 원 보냈다"고 믿는데 실제로는 처음 10만 원만 처리됨. 돈이 어긋난다
> 🎤 "멱등 키는 누가 만드나?" → 요청하는 쪽(입출금은 채널의 요청 ID, 송금은 transfer의 송금 ID). 재시도할 때 **같은 키를 다시** 보내야 의미가 있다
>
> 📎 `ledger/application/LedgerUseCaseImpl.kt` `record()`, `JournalEntry.isSameRequestAs()`

## ⭐ 동시 중복 요청과 UNIQUE 위반, 트랜잭션 밖 재시도

> 💡 **핵심**
> ```
> 요청 A                         요청 B (같은 키)
> 조회 → 없음                     조회 → 없음          ← 둘 다 "처음"이라고 판단
> INSERT 성공 → 커밋              INSERT → UNIQUE 위반 💥 (A 커밋까지 기다렸다가)
>                                → 트랜잭션 밖에서 잡고, 새 트랜잭션으로 한 번 더
>                                → 조회 → A의 거래 발견 → replayed
> ```
> - **실패한 트랜잭션 안에서는 수습 불가:** PostgreSQL은 에러 후 그 트랜잭션의 모든 쿼리를 거부(`current transaction is aborted`), Spring은 rollback-only로 표시. 그래서 **밖에서** 잡는다
> - **`TransactionTemplate`을 쓴 이유:** 같은 클래스 안의 `@Transactional` 메서드를 `this`로 부르면 프록시를 안 거쳐서 트랜잭션이 안 걸린다 (**self-invocation 함정**). 템플릿은 경계가 코드에 그대로 보인다
> - **재시도는 한 번만:** 두 번째엔 먼저 커밋된 거래가 반드시 보이므로 더 할 필요가 없다
>
> 🎤 "그 재시도의 한계는?" → `DataIntegrityViolationException`이면 다 잡아서, CHECK 제약 위반 같은 다른 무결성 오류도 한 번 재시도된다 (두 번째도 실패해서 그대로 올라가긴 함). 65자 멱등 키가 여기 잘못 잡혔던 게 그 예
> 🎤 "락으로 막으면 안 되나?" → 가능하지만, 아직 없는 행은 잠글 수 없다. UNIQUE 제약이 가장 단순하고 확실한 방어선
>
> 📎 `PostingUseCaseImpl.retryOnceOnDuplicateKey()` (KDoc)

## ⭐ 동시성 테스트: `CountDownLatch`, `Future`, spy, `verify(times(3))`

> 💡 **핵심**
> - **`CountDownLatch(2)` = "2명 다 타야 출발하는 놀이기구".** `countDown()`으로 숫자를 줄이고, `await()`은 0이 될 때까지 기다린다
> - **조회 직후에 맞물리기:** spy로 `findByIdempotencyKey`를 가로채서 진짜 조회 → `countDown()` → `await()`. 두 스레드 모두 "거래 없음"을 본 상태가 **반드시** 만들어진다
> - **"출발 신호" 방식과의 차이:** 동시에 출발만 시키면 한쪽이 조회→INSERT→커밋을 먼저 끝내 버려서 경합이 운에 달린다. 스레드 2개로는 재현이 잘 안 됨
> - **`Future`:** `submit`으로 일을 다 맡긴 뒤 `get()`으로 결과를 모은다. 하나씩 맡기고 기다리면 동시가 아니다. 스레드 안 예외는 `get()`에서 다시 던져진다 → **안 부르면 예외가 묻혀서 테스트가 그냥 통과**
> - **`verify(times(3))`:** 조회 2번 + 재시도 조회 1번 = 경합이 **실제로 일어났다**는 증거. 없으면 "운 좋게 통과"와 구분이 안 된다
>
> 🎤 "래치를 1로 두면?" → `countDown()` 하자마자 0이라 안 기다린다 = 래치가 없는 것과 같다. 3이면 영원히 0이 안 돼서 타임아웃(5초)까지 대기
> 🎤 "`callRealMethod()`가 왜 실패했나?" → Spring Data 리포지토리는 **인터페이스의 JDK 프록시**라 부를 구현이 없다. `@MockitoSpyBean`이 걸어 둔 기본 응답("원래 빈에 위임")을 꺼내 썼다
> 🎤 "재현 → 해결은 어떻게 보여 주나?" → 재시도 로직을 빼면 이 테스트가 `DataIntegrityViolationException`으로 실패, 넣으면 통과
>
> 📎 `PostingUseCaseTest` «같은 키로 동시에 입금해도...»

## ⭐ 400 vs 500, 검증 위치 (값 객체 / 유스케이스 입구 / 도메인 `require`)

> 💡 **핵심**
> - **기준: "누가 고칠 수 있나"** → 클라이언트가 요청을 바꿔서 해결되면 **4xx**, 서버(우리)가 고쳐야 하면 **5xx**
>
>   | 규칙 | 어디서 | 응답 |
>   | --- | --- | --- |
>   | 금액 > 0, 멱등 키 길이 (값 하나) | 값 객체 생성 시 | 400 |
>   | `from == to` (필드 여러 개) | posting 입구 | 400 |
>   | 없는 계좌 | account | 404 |
>   | 같은 키 다른 내용 | ledger | 409 |
>   | 잔액 부족 (DB 상태를 봐야 앎) | Account 도메인 | 422 |
>   | 차변 ≠ 대변, 원장에 0원 | 도메인 `require` | **500 (우리 버그)** |
> - **같은 규칙이 두 군데 있는 이유:** 값 객체는 고객에게 친절하게 거절, 원장의 `require`(+ DB CHECK)는 **검증을 빼먹은 경로가 생겨도 원장을 지키는 마지막 방어선**
>
> 🎤 "고객 입력 실수가 500이 되면 뭐가 문제?" → 500은 보통 **알람** 대상. 새벽에 엉뚱한 알람이 울리고, 진짜 버그가 그 소음에 묻힌다 (11주 차 SLO와 연결)
> 🎤 "잔액 부족은 입구에서 못 막나?" → DB의 현재 잔액을 봐야만 안다. 그래서 도메인이 업무 예외로 던진다. 예방은 못 해도 고객이 해결할 수 있으니 4xx
>
> 📎 `account/api/AccountExceptionHandler.kt` (상태 코드 매핑)

## ⭐ 값 객체, parse don't validate, Kotlin value class vs Java record, 공유 커널

> 💡 **핵심**
> - **parse, don't validate:** 검증 함수는 "검사하고 원래 값(Long)을 계속 씀" → 빼먹은 경로가 생길 수 있다. 값 객체는 "검사를 통과해야만 `Amount`가 생김" → **`Amount`를 갖고 있다는 것 자체가 검증됐다는 증거.** 안쪽 계층은 다시 검사 안 한다
> - **엔티티 필드·API DTO에는 원시 타입:** 엔티티는 value class의 name mangling을 Hibernate가 잘 못 다룸 / DTO는 외부 계약이라 내부 모델이 바뀌어도 흔들리면 안 됨 + 역직렬화 중 예외는 에러 응답 통제가 어려움 → **컨트롤러에서 `Amount(req.amount)`로 변환**
> - **Kotlin value class vs Java record**
>
>   | | value class | record |
>   | --- | --- | --- |
>   | 런타임 | `long`으로 풀림 (객체 생성 없음) | 진짜 객체 (힙 할당) |
>   | 필드 | 1개만 | 여러 개 |
>   | JPA | 필드로 쓰기 어려움 | `@Embeddable` 가능 (Hibernate 6.2+) |
>   → Java도 Project Valhalla(JEP 401)로 value class를 준비 중 (아직 정식 아님)
> - **공유 커널(`lab.bank.core.shared`):** 여러 모듈이 합의하고 같이 쓰는 작은 모델. **작게 유지가 조건** → 안 그러면 "공통" 폴더가 쓰레기통이 되고 모든 모듈이 엮인다
>
> 🎤 "검증 함수 방식에서 왜 바꿨나?" → 검증을 빼먹는 경로를 컴파일 단계에서 없애려고. 같은 규칙이 컨트롤러·Kafka 컨슈머 등 여러 입구에서 자동으로 지켜진다
>
> 📎 `shared/Amount.kt`, `shared/IdempotencyKey.kt` / CLAUDE.md 7장 값 객체 컨벤션 / 커밋 `0478940` (검증 → 값 객체 diff)

## 리뷰에서 잡힌 버그: 받는 쪽 `withdraw`, 0원 입금 500, 65자 멱등 키 500

> 💡 **핵심**
> - **받는 쪽도 출금:** `transfer`에서 받는 계좌에 `withdraw`를 호출. **타입이 같아서 컴파일되고, 송금 테스트가 없어서 통과.** 원장은 맞게 기록되니 **잔액과 원장이 서로 다른 말** → 일일 대사 전엔 안 드러나는 종류. "송금 후 합계 불변" 테스트로 고정
