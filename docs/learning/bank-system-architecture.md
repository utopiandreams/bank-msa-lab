# 은행 시스템 구조 (계정계·채널계·대외계·정보계)

질답 모음 (CLAUDE.md 6장 7-1-0). 8주 차 대사에서 "외부 내역은 누가 받나"를 이야기하다 나온 질문들.

## 1. 대외 요청은 실무에서 항상 대외계를 거치나? (2026-11-25)

- 💡 **국내 은행 시스템은 보통 역할별 "계"로 나뉜다** (은행마다 이름·경계는 조금씩 다르다):

| 계 | 하는 일 | 이 프로젝트에서 |
| --- | --- | --- |
| **계정계** | 계좌·잔액·원장. 돈이 실제로 움직이는 곳. 가장 보수적으로 운영 | `core` (account·ledger) |
| **채널계** | 고객 접점: 인터넷·모바일뱅킹, ATM, 창구 단말 | `gateway`, `transfer`(고객 요청 접수) |
| **대외계** | 바깥 기관과의 연계: 금융결제원, 타행, 카드사, VAN, 신용정보원, 국세청 … | `BankMockAdapter`(송금 요청), 대사 서비스의 수신 작업(정산 파일) |
| **정보계** | DW, 분석, 리포트, 규제 보고. 계정계 데이터를 복제해 따로 쓴다 | (없음. 대사의 "읽기 복제본·DW" 선택지가 여기) |

- 💡 **대체로 그렇다: 바깥으로 나가고 들어오는 건 대외계를 거친다.** 대외계(대외 연계 시스템, FEP: Front-End Processor라고도 부른다)가 하는 일:
  1. **형식 변환:** 기관마다 다른 전문(고정 길이 레코드 등)·파일 형식 ↔ 은행 내부 표준. 내부 시스템은 기관별 규격을 모른다 (DDD 용어로는 ACL을 한 곳에 모은 것)
  2. **연결 관리:** 전용선·VPN·SFTP, 기관별 접속·재접속, 타임아웃·재전송 규칙
  3. **보안과 규제:** 금융권 망분리 때문에 내부망 시스템이 인터넷·외부망에 직접 나가지 못하게 한다 → 나가는 문을 하나로
  4. **전문 로그:** 주고받은 전문·파일 원본을 전부 남긴다. 분쟁("보냈다/안 받았다")과 감사의 증거
- 💡 **왜 한 곳에 모으나:** 통제 지점이 하나면 보안·감사·장애 대응이 쉽고, 기관 규격이 바뀌어도 대외계만 고친다. 대가는 대외계가 **단일 장애점이자 병목**이 될 수 있다는 것 (그래서 이중화가 기본)
- 💡 **예외도 있다:** 오픈뱅킹·오픈API는 별도 API 게이트웨이 플랫폼으로 두기도 하고, 클라우드 전환이 진행된 곳은 경계가 다르다. "항상"이라기보다 "원칙적으로 외부 연결 통로는 통제된 한 곳"
- 💡 내부 시스템끼리의 연계도 중계 계층을 두는 경우가 많다: **MCI**(채널계 ↔ 계정계 중계), **EAI**(내부 시스템 간 연계). MSA의 API 게이트웨이·메시지 브로커와 비슷한 자리
- 🎤 "은행 시스템 구조를 설명해 보세요" → 계정계·채널계·대외계·정보계, 이 프로젝트의 서비스가 각각 어디에 해당하는지
- 🎤 "외부 기관 연계를 각 서비스가 직접 하면 안 되나요?" → 망분리·전문 로그·형식 변환·통제 지점. 우리 프로젝트는 서버를 늘리지 않으려고 transfer의 어댑터와 대사 서비스의 수신 작업이 대외계 역할을 나눠 맡는다 (타협)
