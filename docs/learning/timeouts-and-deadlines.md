## 1. 트랜잭션 타임아웃은 왜 "트랜잭션 시작"부터 재나 (2026-11-23)

**💡 핵심**
- 도구의 한계다. 트랜잭션 타임아웃(Spring `@Transactional(timeout)`, DB 설정)은 **자기가 맡은 트랜잭션만** 안다. 요청이 서버에 언제 도착했는지, 톰캣 대기열·커넥션 풀에서 얼마나 기다렸는지는 모른다.
- 그래서 "트랜잭션 **안**의 지연"(락 대기, 느린 쿼리)은 막지만, 그 **앞**의 대기(톰캣 대기열, HikariCP 커넥션 대기, 기본 최대 30초)는 못 막는다.
- 8주 차 장면: transfer 4초 타임아웃 → UNKNOWN → 5초에 해소 일꾼이 조회해 "없음" → FAILED 확정 → core가 커넥션을 늦게 얻어 5.5초에 커밋 = 이중 송금 위험. 이 빈틈은 대사가 잡는다.

**🎤 면접 꼬리 질문**
- "트랜잭션 타임아웃을 3초로 걸면 요청이 3초 안에 끝난다고 보장되나요?" → 아니다. 시작 전 대기는 안 센다
- "조회했더니 기록이 없으면 처리 안 된 게 확실한가요?" → "아직 하는 중"과 구분 못 한다

**📎** `docs/design-drills/08-unknown-resolution.md` 1부, pitfalls 38

## 2. 데드라인 전파를 다루는 도구가 있나, 직접 구현하기도 하나 (2026-11-23)

**💡 핵심**

데드라인 전파 = "이 요청은 이 시각(또는 앞으로 N ms)까지만 의미 있다"를 호출 체인 끝까지 실어 보내고, 각 홉이 남은 시간으로 자기 타임아웃을 정하고, 이미 지났으면 시작하지 않는 것.

| 도구 | 어떻게 | 📖 |
| --- | --- | --- |
| **gRPC** | 클라이언트가 deadline을 정하면 `grpc-timeout` 헤더로 **남은 시간(상대값)**을 보낸다. 서버는 그걸 자기 Context의 deadline으로 받고, 그 안에서 다시 gRPC를 부르면 남은 시간이 자동으로 이어진다. 넘으면 `DEADLINE_EXCEEDED` | 📖 |
| **Go `context.Context`** | `context.WithTimeout`으로 만든 ctx를 함수 인자로 끝까지 넘긴다. HTTP 클라이언트·`database/sql`(`QueryContext`)이 ctx 취소를 존중해 쿼리까지 끊는다. 언어 차원의 표준이라 "데드라인 전파"의 교과서 | 📖 |
| **Envoy / Istio** | 프록시가 업스트림에 `x-envoy-expected-rq-timeout-ms`(남은 시간)를 붙여 줄 수 있다. 앱이 그 값을 읽어 쓸지는 앱 몫 | 📖 |
| **Finagle (Twitter)** | RPC 컨텍스트에 Deadline을 실어 자동 전파 | 📖 |
| **Spring / Java REST** | **표준 없음.** Resilience4j `TimeLimiter`, 코루틴 `withTimeout`은 프로세스 안에서만 유효하고 다음 홉으로 안 넘어간다 | 📖 |

**직접 구현하는 경우: 흔하다.** REST 기반 MSA(특히 Java/Spring)는 표준이 없어서 큰 회사들이 자체 규약을 만든다. 모양은 거의 같다.
1. 입구(gateway)가 헤더에 남은 시간을 싣는다 (예: `X-Request-Timeout-Ms: 2900`)
2. 서비스의 필터가 "도착 시각 + 남은 시간"을 **자기 시계 기준 데드라인**으로 바꿔 요청 범위(ThreadLocal, 코루틴 컨텍스트)에 둔다
3. 나가는 HTTP 클라이언트 인터셉터가 남은 시간을 다시 헤더에 싣고, 그 값으로 read timeout을 정한다
4. DB 쿼리 타임아웃도 남은 시간으로 건다 (`Statement.setQueryTimeout`, PostgreSQL `SET LOCAL statement_timeout`)
5. 일을 시작하기 전에 이미 지났으면 바로 거절한다 (빠른 실패)

**절대 시각이 아니라 남은 시간(상대값)을 보내는 이유:** 서버마다 시계가 조금씩 다르다(clock skew). 상대값을 받아 각자 자기 시계로 데드라인을 다시 계산하면 시계 차이 문제가 사라지고, 오차는 네트워크 전송 시간만 남는다. (앞에서 "서버 간 시계 차이 문제가 생긴다"고 한 건 절대 시각을 보낼 때 이야기. gRPC가 상대값을 쓰는 이유가 이것)

**실무에서 주된 목적은 정합성이 아니라 낭비 줄이기:** 호출한 쪽이 이미 포기한 요청을 아래 서비스들이 끝까지 처리하면 CPU·커넥션만 쓰고 결과는 버려진다. 장애 때 이게 쌓여 부하가 커지고 회복이 늦어진다 (15주 차 장애 전파와 연결). 정합성 보장으로는 한계가 있다: "커밋 직전에 검사 → 통과 → 커밋" 사이에도 시간이 흐르고, 커밋 자체도 시간이 걸린다. **검사와 커밋이 원자적이지 않아서 빈틈이 0이 되지는 않는다** → 돈 문제의 마지막 보장은 여전히 대사.

**이 프로젝트에서는:** 8주 차 범위 밖 (결정 5: core 트랜잭션 타임아웃 + 대사). 15주 차(외부 은행 지연, 타임아웃 계층)에서 "gateway 5초 → transfer → core" 타임아웃 예산을 다룰 때 후보.

**🎤 면접 꼬리 질문**
- "서비스 A → B → C로 호출할 때 타임아웃을 각각 어떻게 잡나요?" → 아래로 갈수록 짧게(예산), 이상적으로는 남은 시간을 전파
- "데드라인을 절대 시각으로 보내면 무슨 문제가 있나요?" → clock skew. 상대값으로 보내고 받는 쪽이 자기 시계로 환산
- "데드라인 전파를 하면 결과 불명이 사라지나요?" → 아니다. 검사와 커밋 사이 빈틈, 응답 유실은 그대로. 낭비를 줄이는 장치
- "Spring에서 구현한다면?" → 필터(입구) + 요청 범위 컨텍스트 + RestClient 인터셉터(전파) + 쿼리 타임아웃(DB). 가상 스레드·코루틴이면 ThreadLocal 대신 해당 컨텍스트에 실어야 함

**📎** `services/gateway`(다운스트림 타임아웃 5s), `services/transfer/src/main/resources/application.yaml`(connect 1s / read 3s), pitfalls(타임아웃 계층), 15주 차 로드맵

## 3. 결과 불명에서 재전송을 쓰는 경우도 있나 (2026-11-23)

**💡 핵심**
- 있다. 재전송이 안전한 조건은 **"받는 쪽이 그 키의 결과를 실패까지 포함해 기억한다"**이다. 그러면 몇 시간 뒤 재전송해도 새로 실행되지 않고 처음 결과(거절이면 거절)가 그대로 돌아온다. 재전송 = 조회 + (안 왔으면) 실행이 된다.
  - 📖 Stripe 멱등 키: 첫 요청의 응답(상태 코드·본문, 실행이 시작된 뒤의 오류 포함)을 저장해 두고 같은 키 재요청엔 그걸 돌려준다 (24시간). 그래서 Stripe는 네트워크 오류 시 "같은 키로 재시도하라"고 안내한다.
  - 📖 AWS SDK: 클라이언트 토큰(멱등 토큰)을 붙여 자동 재시도.
- **짧은 시간 안의 자동 재시도**(수백 ms~수 초, 백오프)는 흔하다. 의사가 바뀔 시간이 없어서 "늦은 실행" 문제가 거의 없다.
- **이 프로젝트 core는 거절을 기억하지 않는다** (거절 = 롤백 = 흔적 없음). 그래서 재전송이 "나중에 다른 결과로 실행"이 될 수 있고, 8주 차는 재전송을 버리고 조회만 하기로 했다 (ADR-0005 결정 2).
- 금융권 도메인 사실: 결과를 모르면 같은 거래를 다시 보내지 않고 **조회 전문**으로 확인하거나, 카드·VAN 쪽은 **망취소**(타임아웃 난 거래를 무효화하는 취소 전문)를 보낸다. "모르면 다시 실행"보다 "모르면 확인하거나 무효화"가 기본.
- 대안으로 남겨 둔 것: core가 거절도 키별로 기록하게 바꾸면(거절 이력 테이블) 재전송이 언제나 안전해진다. 대신 core 쓰기가 늘고, 늦은 커밋(아직 하는 중) 문제는 그대로다.

**🎤 면접 꼬리 질문**
- "타임아웃 나면 같은 멱등 키로 재시도하면 되지 않나요?" → 상대가 실패까지 기억하는지에 달렸다. 성공만 기억하면 늦은 재시도가 다른 결과로 실행될 수 있다
- "Stripe는 왜 재시도를 권하나요?" → 실패 응답까지 저장해 두니까
- "그럼 우리 core도 거절을 저장하면?" → 재전송이 안전해진다. 비용과, 그래도 남는 '아직 하는 중' 문제

**📎** ADR-0005 결정 2·대안, pitfalls 38, `PostingUseCaseImpl`(멱등 판정)
