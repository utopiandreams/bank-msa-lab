## 보안·API

### 1. BOLA: 남의 객체 ID를 넣으면 뚫린다

**BOLA** = Broken Object Level Authorization (객체 수준 인가 실패). 예전 이름은 **IDOR** (Insecure Direct Object Reference). **OWASP API Security Top 10 1위.** (OWASP는 보통 "오와스프"라고 읽는다)

- **장면 (2026-11-14):** gateway JWT 인증을 붙인 뒤에도, 영희 토큰으로 `fromAccountId = 철수 계좌`를 넣어 송금 요청을 보낼 수 있었다. 키만 바꿔 보내면 철수 돈이 빠진다.
- **함정:** "로그인했으니 안전하다"고 착각한다. 인증(누구인가)은 통과했지만 **인가(이 객체를 건드려도 되나)**를 아무도 안 했다.
  - 요청에 들어오는 **객체 ID**(계좌 ID, 주문 ID, 송금 ID, 파일 ID…)는 전부 공격자가 마음대로 바꿀 수 있는 값이다
  - "UUID라서 못 맞힌다"는 방어가 아니다. ID는 URL·로그·거래 내역·다른 API 응답으로 새어 나간다
  - 목록 API는 막았는데 단건 조회(`GET /accounts/{id}`)나 수정 API를 빼먹는 경우가 가장 흔하다
- **원칙:**
  - 객체 ID를 받는 **모든** API에서 "이 객체가 요청자 것인가"를 확인한다. 조회도 포함
  - 검사는 **데이터를 가진 쪽이**, 가능하면 **변경과 같은 트랜잭션 안에서** 한다 (→ 9. TOCTOU)
  - 인증은 한곳(gateway)에서 끝낼 수 있지만, 인가는 업무 데이터가 필요해서 서비스가 한다 ("인증은 gateway, 인가는 서비스")
  - 남의 것이면 "없다"(404)로 답한다 (→ 2)
  - 재현 테스트를 먼저 만든다: "A의 토큰으로 B의 객체에 접근 → 성공하면 안 됨"
- 🎤 "로그인한 사용자가 URL의 ID만 바꿔서 남의 데이터를 보면 어떻게 막나요?" / "인가 검사를 gateway에서 하면 안 되나요?" (gateway는 계좌 주인을 모른다) / "권한 검사와 출금 사이에 소유자가 바뀌면?"
- 📎 ADR-0002 구현 전 결정 2, G-4 티켓

### 2. 존재 여부 누출: 403 대신 404

- **장면 (2026-11-14):** G-4 설계 중. 남의 계좌에 `NOT_ACCOUNT_OWNER`, 없는 계좌에 `ACCOUNT_NOT_FOUND`를 주면 둘이 구분된다.
- **함정:** 에러를 친절하게 나누면, 공격자가 ID를 하나씩 넣어 보며 "어떤 계좌가 **존재하는지**"를 알아낸다 (enumeration). 로그인 화면의 "아이디가 없습니다 / 비밀번호가 틀립니다"도 같은 문제다.
- **원칙:** 밖으로는 "남의 것"과 "없음"을 **같은 응답**으로 준다 (GitHub는 남의 private 레포에 404). 구분은 **내부 로그에만** 남긴다 (보안 감사용).
- 🎤 "권한이 없을 때 403 대신 404를 주는 이유는?" / "그럼 디버깅은 어떻게 하나요?" (내부 로그, traceId)

### 3. 신뢰 경계: 누가 붙인 헤더인가

- **장면 (2026-11-14):** 철수 토큰 + 손으로 붙인 `X-User-Id: younghee` → gateway가 영희로 그대로 넘겼다 (테스트로 재현, `expected [chulsoo] but was [younghee]`).
- **함정:**
  - 검증만 하고 **들어온 헤더를 지우지 않으면**, 유효한 토큰을 가진 사람이 남의 행세를 한다
  - 서비스가 헤더를 믿는 구조는 **"gateway를 거치지 않고는 서비스에 닿을 수 없다"는 전제**가 있어야만 안전하다. Ingress를 열어 두면 무너진다
  - 쿠버네티스 기본 네트워크는 모든 파드가 서로 통한다. 파드 하나가 뚫리면(취약 라이브러리, SSRF) 내부에서 헤더를 위조할 수 있다 (횡적 이동)
- **원칙:** 경계에서 들어온 신원 헤더는 **무조건 지우고 다시 쓴다**. 외부 진입점은 하나만 연다. 내부까지 막으려면 NetworkPolicy, 또는 서비스도 토큰을 검증한다 (제로 트러스트).
- 🎤 "gateway 뒤 서비스는 사용자 헤더를 그냥 믿나요?" / "파드 하나가 털리면요?"
- 📎 `services/gateway/.../UserIdRelayFilter.kt`, `GatewayAuthTest`, 백로그 "NetworkPolicy · 제로 트러스트"

### 4. JWT는 암호화가 아니다, 알고리즘은 고정한다

- **장면 (2026-11-14):** 발급받은 토큰의 가운데 조각을 base64로 풀자 `{"sub":"chulsoo",...}`가 그대로 보였다.
- **함정:**
  - JWT는 **서명**(안 바뀌었음 보장)이지 **암호화**가 아니다. 계좌번호·개인정보를 넣으면 누구나 읽는다
  - 헤더의 `alg`를 믿는 검증 구현은 `alg: none`(서명 없음)이나 알고리즘 바꿔치기에 뚫린다
  - JWT는 발급하면 만료 전엔 회수가 어렵다 (탈취 대응이 어려움)
- **원칙:** 페이로드엔 식별자만. 검증 쪽에서 알고리즘을 **고정**한다. 수명은 짧게(15분) + 리프레시(인증 서버 몫). 직접 짜지 말고 검증된 라이브러리를 쓴다.
- 🎤 "JWT에 무엇을 넣으면 안 되나요?" / "JWT를 강제로 만료시키려면?" / "HS256 vs RS256?"
- 📎 `services/gateway/.../SecurityConfig.kt`, `TestJwt.kt`, ADR-0002 결정 2

### 5. 멱등 키의 범위: 전역 키는 정보를 흘린다

- **장면 (2026-11-14, 클러스터 재현):** 멱등 키가 전역 UNIQUE일 때, 영희가 철수와 우연히 같은 키를 쓰자 ① 내용이 다르면 영희의 정상 송금이 409 ② 내용까지 같으면 **철수의 송금이 영희에게 200으로** 돌아왔다.
- **함정:** 멱등 키는 클라이언트가 만드는 값이라 겹칠 수 있다. 범위가 전역이면 남의 요청과 엮인다.
- **원칙:** 멱등 키는 **요청자(또는 계정) 범위**로 유일하게 한다. Stripe도 계정별이다. → `(requester_id, idempotency_key)` UNIQUE
- 🎤 "멱등 키를 전역으로 두면 무슨 문제가 있나요?"
- 📎 transfer Flyway V3, `TransferIdempotencyTest` "키 범위"

## 분산

### 6. 타임아웃 ≠ 실패

- **장면 (2026-11-14):** transfer → core 호출 결과를 완료·거절·**결과 불명**으로 나눴다.
- **함정:** 응답이 안 왔다고 실패로 처리하고 재시도하면, core에선 이미 처리됐을 수 있다 → **이중 송금**. 반대로 실패로 확정하면 돈은 나갔는데 고객에겐 실패로 보인다.
- **원칙:** 타임아웃·5xx는 "모름"(UNKNOWN)이다. **같은 ID로 재전송**(받는 쪽이 멱등해야 함)하거나 **상태 조회**로 확정한다.
- 🎤 "외부 호출이 타임아웃 났을 때 어떻게 처리하나요?"
- 📎 `docs/learning/2026-11-14.md` "응답 분류", `CorePostingAdapter`

### 7. 바깥 타임아웃 > 안쪽 타임아웃

- **장면 (2026-11-14):** gateway의 응답 타임아웃(5s)을 transfer의 core 대기(3s)보다 길게 잡았다.
- **함정:** 바깥이 더 짧으면 안쪽은 아직 처리 중인데 바깥이 먼저 504를 낸다. 고객은 실패로 알고 재시도하고, 안쪽에서는 일이 계속 진행된다.
- **원칙:** 호출 사슬의 타임아웃은 바깥으로 갈수록 길게. 단 무한정 길게는 안 된다 (스레드·커넥션 점유).
- 🎤 "타임아웃 값은 어떻게 정하나요?" (p99 근거, 10주 차에 실측)
- 📎 `services/gateway/src/main/resources/application.yaml`

### 8. 트랜잭션 안에서 원격 호출하지 않는다

- **장면 (2026-11-14):** transfer는 "처리중 커밋 → 트랜잭션 밖에서 core 호출 → 결과 커밋"으로 나눴다.
- **함정:** `@Transactional` 안에서 원격 호출을 하면, 상대가 느려지는 동안 **DB 커넥션을 쥐고 있다.** 커넥션 풀(기본 10개)이 금방 바닥나고, 상관없는 API까지 멈춘다 (장애 전파).
- **원칙:** 원격 호출은 트랜잭션 밖에서. 대신 "처리중" 상태가 생기고, 그 상태에서 죽으면 복구할 방법(상태 조회, 해소 스케줄러)이 필요하다.
- 🎤 "트랜잭션 안에서 외부 API를 부르면 무슨 문제가 생기나요?"
- 📎 `docs/learning/2026-11-14.md` "트랜잭션 나누기", `TransferUseCaseImpl`

### 9. TOCTOU: 검사와 사용 사이의 틈

TOCTOU = Time-of-check to time-of-use.

- **장면 (2026-11-14):** G-4 설계. transfer가 core에 "이 계좌 주인 누구야?"를 먼저 묻고 송금하면, 묻는 시점과 출금 시점 사이에 틈이 생긴다.
- **함정:** "확인하고 → 실행"을 두 단계(두 호출, 두 트랜잭션)로 나누면, 그 사이에 상태가 바뀐다. 잔고 확인 후 출금, 재고 확인 후 주문, 권한 확인 후 수정 전부 같은 모양이다.
- **원칙:** 검사와 실행을 **같은 트랜잭션 안에서**, **데이터를 가진 쪽이** 한다. 원격 호출도 한 번으로 줄어든다. 나눌 수밖에 없으면 락이나 조건부 갱신(`UPDATE ... WHERE balance >= ?`)으로 막는다.
- 🎤 "잔고를 확인하고 출금하는 사이에 다른 출금이 끼어들면?" (7주 차 동시 출금 실험과 같은 문제)

## 데이터

### 10. 운영 테이블에 NOT NULL 컬럼 추가와 백필

- **장면 (2026-11-14):** transfer V2(멱등 키), V3(요청자). 기존 송금엔 값이 없었다.
- **함정:**
  - 처음부터 `NOT NULL`로 추가하면 기존 행 때문에 마이그레이션이 실패한다
  - 진짜 값으로 채우려 해도 그 값이 **다른 서비스의 DB**에 있으면 SQL로는 못 가져온다 (DB per service). 서비스 간 백필은 API를 부르는 별도 배치가 필요하다
- **원칙:** NULL 허용으로 추가 → 기존 행 채우기(백필) → NOT NULL. 진짜 값을 모르면 표시값(`legacy`)으로 채우고 문서에 남긴다. 큰 테이블이면 백필을 나눠서 한다 (한 번에 UPDATE하면 락·복제 지연).
- 🎤 "운영 중인 큰 테이블에 NOT NULL 컬럼을 어떻게 추가하나요?"
- 📎 `services/transfer/src/main/resources/db/migration/V2__*.sql`, `V3__*.sql`

### 11. Flyway: 적용된 파일은 고치지 않는다, 재기동 때만 터지는 장애

- **장면 (2026-11-14):** 첫 기동은 됐는데 재시작하자 CrashLoopBackOff (PostgreSQL search_path와 스키마 이름이 계정 이름과 같아서 기록 테이블 위치가 바뀜).
- **함정:** 이미 적용된 마이그레이션 파일을 고치면 체크섬이 달라져 기동이 막힌다. 그리고 "처음 한 번은 되는" 설정 문제는 **재시작 때만** 드러난다.
- **원칙:** 고칠 게 있으면 새 버전 파일(V3)을 추가한다. 기동 테스트는 "두 번 기동"까지 한다. 운영과 같은 계정 조건으로 테스트한다.
- 📎 `docs/learning/2026-11-14.md` "Flyway 재기동 장애", `FlywayRestartTest`

### 12. 제약 위반은 제약 이름으로 구분한다

- **장면 (2026-11-13):** 65자 멱등 키가 컬럼 길이 위반으로 터졌는데, "UNIQUE 위반 = 중복 키"로 잡는 코드가 이걸 중복으로 오인해 엉뚱하게 재시도했다.
- **함정:** `DataIntegrityViolationException` 하나에 UNIQUE·길이·CHECK·FK 위반이 다 섞여 온다.
- **원칙:** 업무적으로 의미 있는 제약은 **이름을 붙이고**(`uq_transfer_requester_idempotency_key`), 그 이름으로만 골라낸다. 입력 길이는 DB에 가기 전에 값 객체로 막는다.
- 📎 `TransferPersistenceAdapter.violatedConstraint`, `docs/learning/2026-11-13.md`

### 13. 보이지 않는 기본값

- **장면 (2026-11-14):** Traefik이 레포 어디에도 없는데 동작하고 있었다. k3s가 설치할 때 함께 올리는 내장 애드온이었다.
- **함정:** 플랫폼이 깔아 주는 기본값은 코드에 안 보여서, 버전업으로 바뀌거나 설정을 바꿀 때 어디를 고쳐야 할지 모른다. 반대로 Spring Boot 기본값(actuator 노출, graceful shutdown)도 버전마다 바뀐다.
- **원칙:** 기대고 있는 기본값은 **명시**하거나 최소한 문서에 적는다. 그래서 `application.yaml`에 기본값과 같은 값도 적어 두었다 ("버전업으로 바뀌지 않게").
- 📎 `infra/terraform/templates/k3s-server.yaml.tftpl`, `docs/infra/README.md`

### 14. 모노레포 CI: 안 바뀐 서비스까지 재배포

- **장면 (2026-11-14):** gateway만 추가했는데 core·transfer 이미지도 다시 빌드되고 태그가 바뀌어 파드가 재시작됐다.
- **함정:** 고정 matrix는 "무엇이 바뀌었나"를 모른다. 서비스가 늘면 CI가 느려지고, 안 바뀐 서비스까지 롤링 재시작된다 (배포 위험이 쓸데없이 커짐).
- **원칙:** 바뀐 경로만 빌드한다. 단 공통 파일(빌드 설정, Dockerfile)이 바뀌면 전부 빌드한다.
- 📎 백로그 "CI 변경 감지"

### 15. GitOps 밖의 비밀값

- **장면 (2026-11-14):** gateway JWT 비밀키를 `kubectl create secret`으로 클러스터에서 직접 만들었다.
- **함정:** 비밀값을 Git에 그대로 넣으면 유출되고, 안 넣으면 "Git만 보면 클러스터를 재현할 수 있다"는 GitOps 약속이 깨진다. 클러스터를 다시 만들 때 빠뜨린다.
- **원칙:** 학습용으로는 생성 명령을 문서에 남긴다. 실무는 Sealed Secrets(암호화해서 커밋)나 External Secrets Operator(Vault 등에서 동기화).
- 📎 `docs/infra/README.md` "gateway JWT 비밀키"

### 16. JVM에 CPU limit을 걸면 기동이 느려진다

- **장면 (2026-11-12):** 공통 Helm 차트에서 메모리 limit만 걸고 CPU limit은 일부러 안 걸었다.
- **함정:** JVM은 기동할 때 CPU를 몰아 쓴다. limit이 있으면 스로틀링으로 기동이 몇 배 느려지고, startupProbe에 걸려 재시작 루프에 빠진다.
- **원칙:** CPU는 request만, 메모리는 limit을 건다 (메모리는 넘치면 OOMKilled라 상한이 필요). 힙은 `MaxRAMPercentage`로 limit의 비율로.
- 📎 `deploy/helm/spring-service/values.yaml`, `docs/learning/2026-11-12.md`

### 17. 멱등 재요청은 처음 판정을 다시 하지 않는다

- **장면 (2026-11-14, G-4):** core에 소유자 검사를 넣을 때, 검사를 원장 기록(멱등 판정) **앞**에 둘지 **뒤**에 둘지.
- **함정:** 앞에 두면, 이미 처리된 거래의 재전송(transfer의 UNKNOWN 해소, 요청자 `legacy`)이 소유자 검사에서 거절된다 → transfer는 FAILED로 확정 → **돈은 이미 빠졌는데 고객에겐 실패**. 규칙(권한, 한도, 영업시간)이 처음 요청과 재요청 사이에 바뀌어도 같은 일이 생긴다.
- **원칙:** 재요청이면 **원래 결과를 그대로** 돌려준다. 검사는 "새로 처리할 때만". 멱등 판정이 다른 모든 판정보다 먼저다.
- 🎤 "멱등 키로 재요청이 왔는데, 그사이 사용자 권한이 회수됐다면?"
- 📎 `services/core/.../PostingUseCaseImpl.transferInTransaction`, `PostingUseCaseTest` "이미 처리된 거래의 재요청은…"

### 18. 서비스 간 계약을 바꿀 때는 순서가 있다 (expand → contract)

- **장면 (2026-11-14, G-4):** core가 `X-User-Id`를 필수로 바꾸고, transfer가 그 헤더를 보내기 시작하는 변경을 한 번에 배포했다.
- **함정:** 롤링 배포 중엔 옛 버전과 새 버전이 **같이 돈다.** 새 core + 옛 transfer 조합이면 헤더가 없어 송금이 401로 거절된다. DB 컬럼 이름 바꾸기, 이벤트 필드 삭제도 같은 모양이다.
- **원칙:** ① 받는 쪽이 새 것을 **선택으로** 받게 하고(expand) ② 보내는 쪽이 새 것을 보내게 배포하고 ③ 다 바뀐 뒤 받는 쪽이 **필수로** 바꾼다(contract). 한 번의 배포로 양쪽 계약을 동시에 바꾸지 않는다.
- 🎤 "API 필드를 무중단으로 바꾸려면?" / "DB 컬럼 이름을 무중단으로 바꾸려면?"
- 📎 커밋 `[core] 계좌 소유자 인가…` (트래픽이 없어 한 번에 배포했음)
