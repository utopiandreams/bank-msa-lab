## 보안·API

### 1. BOLA: 남의 객체 ID를 넣으면 뚫린다

**BOLA** = Broken Object Level Authorization (객체 수준 인가 실패). 예전 이름은 **IDOR** (Insecure Direct Object Reference). **OWASP API Security Top 10 1위.** (OWASP는 보통 "오와스프"라고 읽는다)

- **장면 (2026-11-14):** gateway JWT 인증을 붙인 뒤에도, 영희 토큰으로 `fromAccountId = 철수 계좌`를 넣어 송금 요청을 보낼 수 있었다. 키만 바꿔 보내면 철수 돈이 빠진다.
- **함정:** "로그인했으니 안전하다"고 착각한다. 인증(누구인가)은 통과했지만 **인가(이 객체를 건드려도 되나)**를 아무도 안 했다.
  - 요청에 들어오는 **객체 ID**(계좌 ID, 주문 ID, 송금 ID, 파일 ID…)는 전부 공격자가 마음대로 바꿀 수 있는 값이다
  - "UUID라서 못 맞힌다"는 방어가 아니다. ID는 URL·로그·거래 내역·다른 API 응답으로 새어 나간다
  - 목록 API는 막았는데 단건 조회(`GET /accounts/{id}`)나 수정 API를 빼먹는 경우가 가장 흔하다
- **원칙:**
  - 객체 ID를 받는 **모든** API에서 "이 객체가 요청자 것인가"를 확인한다. 조회도 포함
  - 검사는 **데이터를 가진 쪽이**, 가능하면 **변경과 같은 트랜잭션 안에서** 한다 (→ 9. TOCTOU)
  - 인증은 한곳(gateway)에서 끝낼 수 있지만, 인가는 업무 데이터가 필요해서 서비스가 한다 ("인증은 gateway, 인가는 서비스")
  - 남의 것이면 "없다"(404)로 답한다 (→ 2)
  - 재현 테스트를 먼저 만든다: "A의 토큰으로 B의 객체에 접근 → 성공하면 안 됨"
- 🎤 "로그인한 사용자가 URL의 ID만 바꿔서 남의 데이터를 보면 어떻게 막나요?" / "인가 검사를 gateway에서 하면 안 되나요?" (gateway는 계좌 주인을 모른다) / "권한 검사와 출금 사이에 소유자가 바뀌면?"
- 📎 ADR-0002 구현 전 결정 2, G-4 티켓

### 2. 존재 여부 누출: 403 대신 404

- **장면 (2026-11-14):** G-4 설계 중. 남의 계좌에 `NOT_ACCOUNT_OWNER`, 없는 계좌에 `ACCOUNT_NOT_FOUND`를 주면 둘이 구분된다.
- **함정:** 에러를 친절하게 나누면, 공격자가 ID를 하나씩 넣어 보며 "어떤 계좌가 **존재하는지**"를 알아낸다 (enumeration). 로그인 화면의 "아이디가 없습니다 / 비밀번호가 틀립니다"도 같은 문제다.
- **원칙:** 밖으로는 "남의 것"과 "없음"을 **같은 응답**으로 준다 (GitHub는 남의 private 레포에 404). 구분은 **내부 로그에만** 남긴다 (보안 감사용).
- 🎤 "권한이 없을 때 403 대신 404를 주는 이유는?" / "그럼 디버깅은 어떻게 하나요?" (내부 로그, traceId)

### 3. 신뢰 경계: 누가 붙인 헤더인가

- **장면 (2026-11-14):** 철수 토큰 + 손으로 붙인 `X-User-Id: younghee` → gateway가 영희로 그대로 넘겼다 (테스트로 재현, `expected [chulsoo] but was [younghee]`).
- **함정:**
  - 검증만 하고 **들어온 헤더를 지우지 않으면**, 유효한 토큰을 가진 사람이 남의 행세를 한다
  - 서비스가 헤더를 믿는 구조는 **"gateway를 거치지 않고는 서비스에 닿을 수 없다"는 전제**가 있어야만 안전하다. Ingress를 열어 두면 무너진다
  - 쿠버네티스 기본 네트워크는 모든 파드가 서로 통한다. 파드 하나가 뚫리면(취약 라이브러리, SSRF) 내부에서 헤더를 위조할 수 있다 (횡적 이동)
- **원칙:** 경계에서 들어온 신원 헤더는 **무조건 지우고 다시 쓴다**. 외부 진입점은 하나만 연다. 내부까지 막으려면 NetworkPolicy, 또는 서비스도 토큰을 검증한다 (제로 트러스트).
- 🎤 "gateway 뒤 서비스는 사용자 헤더를 그냥 믿나요?" / "파드 하나가 털리면요?"
- 📎 `services/gateway/.../UserIdRelayFilter.kt`, `GatewayAuthTest`, 백로그 "NetworkPolicy · 제로 트러스트"

### 4. JWT는 암호화가 아니다, 알고리즘은 고정한다

- **장면 (2026-11-14):** 발급받은 토큰의 가운데 조각을 base64로 풀자 `{"sub":"chulsoo",...}`가 그대로 보였다.
- **함정:**
  - JWT는 **서명**(안 바뀌었음 보장)이지 **암호화**가 아니다. 계좌번호·개인정보를 넣으면 누구나 읽는다
  - 헤더의 `alg`를 믿는 검증 구현은 `alg: none`(서명 없음)이나 알고리즘 바꿔치기에 뚫린다
  - JWT는 발급하면 만료 전엔 회수가 어렵다 (탈취 대응이 어려움)
- **원칙:** 페이로드엔 식별자만. 검증 쪽에서 알고리즘을 **고정**한다. 수명은 짧게(15분) + 리프레시(인증 서버 몫). 직접 짜지 말고 검증된 라이브러리를 쓴다.
- 🎤 "JWT에 무엇을 넣으면 안 되나요?" / "JWT를 강제로 만료시키려면?" / "HS256 vs RS256?"
- 📎 `services/gateway/.../SecurityConfig.kt`, `TestJwt.kt`, ADR-0002 결정 2

### 5. 멱등 키의 범위: 전역 키는 정보를 흘린다

- **장면 (2026-11-14, 클러스터 재현):** 멱등 키가 전역 UNIQUE일 때, 영희가 철수와 우연히 같은 키를 쓰자 ① 내용이 다르면 영희의 정상 송금이 409 ② 내용까지 같으면 **철수의 송금이 영희에게 200으로** 돌아왔다.
- **함정:** 멱등 키는 클라이언트가 만드는 값이라 겹칠 수 있다. 범위가 전역이면 남의 요청과 엮인다.
- **원칙:** 멱등 키는 **요청자(또는 계정) 범위**로 유일하게 한다. Stripe도 계정별이다. → `(requester_id, idempotency_key)` UNIQUE
- 🎤 "멱등 키를 전역으로 두면 무슨 문제가 있나요?"
- 📎 transfer Flyway V3, `TransferIdempotencyTest` "키 범위"

## 분산

### 6. 타임아웃 ≠ 실패

- **장면 (2026-11-14):** transfer → core 호출 결과를 완료·거절·**결과 불명**으로 나눴다.
- **함정:** 응답이 안 왔다고 실패로 처리하고 재시도하면, core에선 이미 처리됐을 수 있다 → **이중 송금**. 반대로 실패로 확정하면 돈은 나갔는데 고객에겐 실패로 보인다.
- **원칙:** 타임아웃·5xx는 "모름"(UNKNOWN)이다. **같은 ID로 재전송**(받는 쪽이 멱등해야 함)하거나 **상태 조회**로 확정한다.
- 🎤 "외부 호출이 타임아웃 났을 때 어떻게 처리하나요?"
- 📎 `docs/learning/2026-11-14.md` "응답 분류", `CorePostingAdapter`

### 7. 바깥 타임아웃 > 안쪽 타임아웃

- **장면 (2026-11-14):** gateway의 응답 타임아웃(5s)을 transfer의 core 대기(3s)보다 길게 잡았다.
- **함정:** 바깥이 더 짧으면 안쪽은 아직 처리 중인데 바깥이 먼저 504를 낸다. 고객은 실패로 알고 재시도하고, 안쪽에서는 일이 계속 진행된다.
- **원칙:** 호출 사슬의 타임아웃은 바깥으로 갈수록 길게. 단 무한정 길게는 안 된다 (스레드·커넥션 점유).
- 🎤 "타임아웃 값은 어떻게 정하나요?" (p99 근거, 10주 차에 실측)
- 📎 `services/gateway/src/main/resources/application.yaml`

### 8. 트랜잭션 안에서 원격 호출하지 않는다

- **장면 (2026-11-14):** transfer는 "처리중 커밋 → 트랜잭션 밖에서 core 호출 → 결과 커밋"으로 나눴다.
- **함정:** `@Transactional` 안에서 원격 호출을 하면, 상대가 느려지는 동안 **DB 커넥션을 쥐고 있다.** 커넥션 풀(기본 10개)이 금방 바닥나고, 상관없는 API까지 멈춘다 (장애 전파).
- **원칙:** 원격 호출은 트랜잭션 밖에서. 대신 "처리중" 상태가 생기고, 그 상태에서 죽으면 복구할 방법(상태 조회, 해소 스케줄러)이 필요하다.
- 🎤 "트랜잭션 안에서 외부 API를 부르면 무슨 문제가 생기나요?"
- 📎 `docs/learning/2026-11-14.md` "트랜잭션 나누기", `TransferUseCaseImpl`

### 9. TOCTOU: 검사와 사용 사이의 틈

TOCTOU = Time-of-check to time-of-use.

- **장면 (2026-11-14):** G-4 설계. transfer가 core에 "이 계좌 주인 누구야?"를 먼저 묻고 송금하면, 묻는 시점과 출금 시점 사이에 틈이 생긴다.
- **함정:** "확인하고 → 실행"을 두 단계(두 호출, 두 트랜잭션)로 나누면, 그 사이에 상태가 바뀐다. 잔고 확인 후 출금, 재고 확인 후 주문, 권한 확인 후 수정 전부 같은 모양이다.
- **원칙:** 검사와 실행을 **같은 트랜잭션 안에서**, **데이터를 가진 쪽이** 한다. 원격 호출도 한 번으로 줄어든다. 나눌 수밖에 없으면 락이나 조건부 갱신(`UPDATE ... WHERE balance >= ?`)으로 막는다.
- 🎤 "잔고를 확인하고 출금하는 사이에 다른 출금이 끼어들면?" (7주 차 동시 출금 실험과 같은 문제)

## 데이터

### 10. 운영 테이블에 NOT NULL 컬럼 추가와 백필

- **장면 (2026-11-14):** transfer V2(멱등 키), V3(요청자). 기존 송금엔 값이 없었다.
- **함정:**
  - 처음부터 `NOT NULL`로 추가하면 기존 행 때문에 마이그레이션이 실패한다
  - 진짜 값으로 채우려 해도 그 값이 **다른 서비스의 DB**에 있으면 SQL로는 못 가져온다 (DB per service). 서비스 간 백필은 API를 부르는 별도 배치가 필요하다
- **원칙:** NULL 허용으로 추가 → 기존 행 채우기(백필) → NOT NULL. 진짜 값을 모르면 표시값(`legacy`)으로 채우고 문서에 남긴다. 큰 테이블이면 백필을 나눠서 한다 (한 번에 UPDATE하면 락·복제 지연).
- 🎤 "운영 중인 큰 테이블에 NOT NULL 컬럼을 어떻게 추가하나요?"
- 📎 `services/transfer/src/main/resources/db/migration/V2__*.sql`, `V3__*.sql`

### 11. Flyway: 적용된 파일은 고치지 않는다, 재기동 때만 터지는 장애

- **장면 (2026-11-14):** 첫 기동은 됐는데 재시작하자 CrashLoopBackOff (PostgreSQL search_path와 스키마 이름이 계정 이름과 같아서 기록 테이블 위치가 바뀜).

### 12. 제약 위반은 제약 이름으로 구분한다

### 14. 모노레포 CI: 안 바뀐 서비스까지 재배포

### 16. JVM에 CPU limit을 걸면 기동이 느려진다

### 17. 멱등 재요청은 처음 판정을 다시 하지 않는다

### 18. 서비스 간 계약을 바꿀 때는 순서가 있다 (expand → contract)

### 19. 2대로는 HA가 안 된다: 과반수와 장애 영역

- **장면 (2026-11-17):** 물리 호스트가 2대가 되자 "컨트롤 플레인을 2대로 이중화하면 되나?"가 나왔다. Proxmox를 클러스터로 묶을지 고민할 때도 같은 문제였다.
- **함정:**
  - Raft·etcd·Proxmox corosync·Redis Sentinel은 **과반수**가 살아 있어야 결정한다. 2대면 과반수가 2라서 1대만 죽어도 멈춘다 → 1대일 때보다 나을 게 없고 고장 날 곳만 늘어난다
  - 3대를 띄워도 **물리 장애 영역이 2개**(호스트 2대에 2+1)면, 2대 있는 쪽이 죽는 순간 과반수를 잃는다
- **원칙:** 합의 시스템은 홀수(3, 5)로, 그리고 **장애 영역도 3개 이상**에 나눈다. 장애 영역이 2개뿐이면 세 번째 곳에 작은 중재자(witness)를 둔다. 그럴 수 없으면 차라리 1대로 두고 한계를 문서로 남긴다.
- 🎤 "etcd를 2대로 하면 안 되나요?" / "데이터센터 2곳으로 HA를 하려면?" / "스플릿 브레인이 뭔가요?"
- 📎 `docs/learning/consensus.md`, `docs/infra/README.md` (두 번째 호스트: 클러스터로 묶지 않음)

### 20. Kafka가 죽으면 프로듀서 send()가 60초 멈춘다 (max.block.ms)

- **장면 (2026-11-18, 4주 차 K-2):** transfer가 송금 완료 후 Kafka로 이벤트를 보내는 어댑터를 만들 때. "send()는 비동기라 송금 API를 안 붙잡는다"고 생각하기 쉽다.
- **함정:** send()는 브로커 응답은 비동기로 기다리지만, **브로커 주소(메타데이터)를 모르면 send() 호출 자체가 막힌다.** 그 상한이 `max.block.ms`이고 **기본값 60초.** Kafka가 죽으면 "알림 보내기" 때문에 **송금 API가 건마다 60초씩 멈추고**, 톰캣 스레드가 다 묶여 송금 전체가 장애가 된다 (부수 기능이 핵심 기능을 죽이는 장애 전파). `delivery.timeout.ms`(기본 2분)도 길다.
- **send()가 막히는 두 경우:** ① 메타데이터(파티션 리더)를 모를 때 ② 프로듀서 버퍼(`buffer.memory`, 기본 32MB)가 꽉 찼을 때 (브로커가 느려 전송이 밀림). 둘 다 상한이 `max.block.ms`
- **구조:** 비동기의 정체는 Spring KafkaTemplate이 아니라 `KafkaProducer`의 버퍼(RecordAccumulator) + **전송 전담 스레드 하나**(`kafka-producer-network-thread`, 내부는 논블로킹 I/O·epoll). 콜백(`whenComplete`)도 그 스레드에서 돈다 → **콜백에서 블로킹하면 모든 전송이 멈춘다** (이벤트 루프 블로킹과 같은 원리). 콜백은 로그 정도만
- **원칙:** 외부 호출의 **모든** 타임아웃을 명시한다 (CLAUDE.md 7장). 프로듀서는 `max.block.ms`·`request.timeout.ms`·`delivery.timeout.ms`를 서비스 응답 시간 예산에 맞춘다. 부수 기능(알림)의 실패가 핵심 기능(송금)을 막지 않게 포트 계약을 "예외를 던지지 않는다"로.
- 🎤 "Kafka가 죽으면 이벤트를 발행하는 API는 어떻게 되나요?" / "send()는 비동기인데 왜 막히죠?"
- 📎 `services/transfer/.../KafkaTransferEventPublisher.kt`, `KafkaTransferEventPublisherTest` "Kafka에 못 붙어도…", `application.yaml` `spring.kafka.producer.properties`

### 21. 지표 엔드포인트가 인터넷에 열린다: 관리 포트를 나눠도 보안 체인은 따라온다

- **장면 (2026-11-18, 관측성 기본 스택):** 서비스에 `/actuator/prometheus`를 붙이려는데, gateway는 Ingress로 밖에 열린 유일한 입구다.
- **함정 1:** actuator를 앱 포트(8080)에 두면 지표가 **인터넷에 노출된다.** 경로별 호출 수·에러율·라이브러리 버전·커넥션 풀 크기가 다 보여 공격자에게 지도가 된다. 실제로 Spring Boot actuator 노출(`/env`, `/heapdump`)은 흔한 침해 경로다.
- **함정 2:** 그래서 관리 포트(8081)로 나눴더니, **WebFlux의 Spring Security 체인은 관리 포트에도 그대로 걸려** Prometheus가 401을 받았다 (`ManagementPortTest`가 잡음). "포트를 나누면 보안 설정과 무관하다"는 가정이 틀렸다.
- **함정 3:** 프로브까지 관리 포트로 옮기면, 앱 포트(Tomcat·Netty)가 고장 나 요청을 못 받는데도 관리 포트는 살아 있어 **Ready로 보인다** → 죽은 파드에 트래픽이 계속 간다.
- **원칙:** ① 지표·관리 엔드포인트는 외부 경로(Service·Ingress)에 없는 포트로 ② 보안 체인이 어느 포트에 걸리는지 **테스트로 확인** ("밖에서는 404", "관리 포트에서는 200") ③ 프로브는 실제 트래픽이 들어오는 포트로 (`add-additional-paths`).
- 🎤 "actuator를 운영에서 어떻게 노출하나요?" / "readiness를 관리 포트로 받으면 뭐가 문제죠?" / "Prometheus는 어떻게 파드를 찾아 긁나요?"

### 22. 처리 안 된 실패가 "모름"으로 보인다: 매핑 안 된 예외 → 500 → 결과 불명

- **장면 (2026-11-18, k6 기준선):** 계좌 200개에 초당 60건 송금 중 0.3초 사이 3건이 UNKNOWN. core 로그는 `ObjectOptimisticLockingFailureException`(낙관적 락 충돌: 두 송금이 같은 계좌를 동시에 수정).
- **함정 1:** 계좌가 많아도 **충돌은 생긴다.** 생일 문제와 같다: 200개 중 하나가 겹칠 확률은 동시 요청 수가 늘수록 빠르게 커진다. "계좌가 많으니 경합은 없겠지"는 틀린 가정이다.
- **함정 2:** core가 이 예외를 매핑하지 않아 **500**이 나갔다. transfer는 500을 규칙대로 **결과 불명**으로 분류했다 (pitfalls 6: 응답 없음·5xx ≠ 실패). 안전한 쪽으로 판단한 것은 맞지만, 실제로는 **롤백이 끝난 확정된 실패**였다. 고객은 "모름"을 받고, 송금은 해소 스케줄러가 생기기 전까지 UNKNOWN에 머문다.
- **원칙:** 서버는 "**처리 안 했음이 확실한 실패**"(락 충돌, 검증 실패)와 "**모름**"(타임아웃, 진짜 버그)을 응답 코드로 구분해 준다. 예: 락 충돌은 409 + 재시도 가능 표시. 호출하는 쪽이 안전하게 재시도하거나 바로 실패로 확정할 수 있게. 500은 정말 모를 때만.
- 🎤 "낙관적 락 충돌이 나면 클라이언트에게 무엇을 돌려주나요?" / "5xx를 받으면 실패인가요?" / "충돌을 서버 안에서 재시도할지, 클라이언트에게 돌려줄지 어떻게 정하나요?"
- 📎 `docs/experiments/week-05-k6-baseline.md` "예상 못 한 발견", `services/core/.../account/domain/Account.kt` (`@Version`), `services/transfer/.../CorePostingAdapter.kt` (5xx → 결과 불명). 처리 방향은 7주 차 설계 결정

### 23. 지표 라벨에 ID를 넣으면 모니터링이 죽는다 (카디널리티 폭발)

### 24. 힙은 여유인데 컨테이너가 죽는다 (OOMKilled ≠ OutOfMemoryError)

- **장면 (2026-11-18, k6 stress 800건/초):** transfer 힙은 최대 139Mi인데 컨테이너 메모리 506Mi → 한도 512Mi를 넘어 OOMKilled. 앞에서 DB 커넥션 풀(10개)이 막히자 요청을 기다리는 스레드가 343개까지 늘어난 상태였다.
- **함정 1:** 컨테이너 메모리 = 힙 + **힙 밖**(메타스페이스·코드 캐시 등 비힙, **스레드마다 스택**, 네이티브·다이렉트 버퍼, GC 자료구조). 힙만 보고 "여유 있다"고 판단하면 틀린다. 스레드가 늘면 힙 밖이 늘어난다.
- **함정 2:** 한도를 넘으면 JVM이 아니라 **리눅스 커널이 강제 종료**(exit 137, `OOMKilled`)한다. 자바 예외도, 힙 덤프도, 마지막 로그도 없다. `kubectl describe pod`의 Last State에서만 보인다.
- **함정 3:** `MaxRAMPercentage=75`는 힙에 한도의 75%(384Mi)까지 허락한다. 힙이 그만큼 커지면 힙 밖에 남는 건 128Mi뿐 → 스레드가 조금만 늘어도 넘친다.
- **함정 4 (연쇄):** 병목(커넥션 풀) → 대기 스레드 증가 → 메모리 증가 → 강제 종료 → 앞단(gateway)에 연결이 쌓여 앞단도 죽는다. 원인은 DB 커넥션인데 증상은 메모리 장애로 보인다.
- **원칙:** ① 메모리 한도는 힙 + 힙 밖(스레드 수 × 스택 포함)으로 잡는다 ② 요청을 무한히 받지 말고 못 받을 건 빨리 거절한다 (Tomcat 최대 스레드·대기열, 백프레셔) ③ 커넥션 풀 크기와 스레드 수를 같이 본다 (풀 10에 스레드 200이면 190개는 기다리기만 한다)
- 🎤 "OOMKilled와 OutOfMemoryError의 차이는?" / "JVM 컨테이너 메모리 한도는 어떻게 잡나요?" / "커넥션 풀이 막히면 왜 메모리 장애가 나죠?"
- 📎 `docs/experiments/week-05-k6-baseline.md` "2차", `deploy/helm/spring-service/values.yaml` (메모리 limit, `MaxRAMPercentage`), pitfalls 16


### 25. IaC에서 "설정 한 줄"이 서버 재생성이 된다 (Terraform replace)

- **장면 (2026-11-18, 노드 확장):** 새 노드에 `topology.kubernetes.io/zone` 라벨을 주려면 k3s 설치 명령(cloud-init 스니펫)에 한 줄 추가하면 된다. 같은 템플릿을 기존 노드 4대도 쓴다. 그대로 고치면 기존 4대의 스니펫 내용이 바뀌고, 스니펫은 VM 생성 때만 쓰이는 값이라 Terraform은 **VM을 지우고 새로 만드는 것**(replace)으로 계획한다. 로컬 디스크에 있는 DB·Kafka 데이터가 같이 사라진다.
- **함정 1:** "생성 때만 쓰는 값"(cloud-init·user-data, AMI, 서브넷, 디스크 이미지)은 바꾸면 그 자리 수정이 아니라 **교체**다. AWS에서 `user_data`·`ami`를 고치면 EC2가, RDS 일부 설정을 고치면 DB가 다시 만들어지는 것과 같다.
- **함정 2:** 코드를 정리한다고 리소스를 모듈로 옮기거나 이름을 바꾸면, Terraform은 "옛 주소 삭제 + 새 주소 생성"으로 본다. `moved` 블록으로 "이름만 바뀌었다"고 알려 줘야 한다.
- **원칙:** ① apply 전에 **plan을 읽는다**. `must be replaced`·`forces replacement`·`to destroy`가 하나라도 있으면 멈춘다 ② 이미 떠 있는 서버의 설정은 IaC 템플릿이 아니라 그 서버를 관리하는 도구로 바꾼다 (이번엔 `kubectl label`) ③ 템플릿을 고쳐야 하면 기존 대상의 출력이 **바이트 단위로 같은지** 먼저 확인한다 (이번엔 `terraform console`로 옛/새 렌더 비교 → `true`) ④ 리팩터링은 `moved`와 함께. 결과: `9 moved, 5 to add, 0 to change, 0 to destroy`
- 🎤 "Terraform apply로 운영 서버를 날린 적이 있거나 막아 본 적 있나요?" / "Terraform에서 리소스 이름을 바꾸면 무슨 일이 생기나요?" / "plan에서 무엇을 확인하나요?"
- 📎 `infra/terraform/main.tf` (`extra_labels = []` 주석, `moved` 블록), `infra/terraform/templates/k3s-agent.yaml.tftpl`, `docs/infra/README.md` "노드 확장"

### 26. DB 재시작이 몇 분씩 걸린다: 스마트 종료는 커넥션 풀을 기다린다

- **장면 (2026-11-18, 라이트사이징):** DB 메모리 설정을 바꾸자 CNPG가 파드를 재시작했는데 core-db가 약 4분 Terminating에 머묾. 로그에 "the database system is shutting down"만 반복
- **함정:** Postgres 종료에는 단계가 있다. CNPG는 먼저 **스마트 종료**(새 접속 거절, 기존 클라이언트가 스스로 끊을 때까지 기다림)를 하는데, 앱의 커넥션 풀(HikariCP)은 커넥션을 **계속 열어 두는 게 일**이라 스스로 끊지 않는다 → `smartShutdownTimeout`(기본 180초)을 다 채운 뒤에야 강제 종료로 넘어간다. 인스턴스가 하나면 그동안 DB가 통째로 안 된다. "설정 하나 바꾸면 수십 초"라는 예상이 틀린다
- **원칙:** ① 단일 인스턴스 DB의 설정 변경은 **다운타임 작업**이다. 레플리카를 두고 전환(switchover) 후 바꾸거나, 점검 시간을 잡는다 ② 종료 대기 시간(`smartShutdownTimeout`)은 "기다릴 가치가 있는 클라이언트"가 있을 때만 길게 ③ 앱은 DB가 사라졌다 돌아올 때 커넥션 풀이 알아서 다시 붙는지 확인한다 (17주 차 DB 다운 실험)
- 🎤 "DB 설정 변경을 무중단으로 하려면?" / "Postgres의 smart / fast / immediate 종료 차이는?" / "커넥션 풀이 있으면 DB 재시작이 왜 느려지나요?"

### 27. 외부 호출 전에 "보낼 거다"를 먼저 커밋한다: 요청 중 상태는 곧 결과 불명

- **장면 (2026-11-20, 5주 차 S-3):** 타행 사가 상태를 나누다가 `EXTERNAL_BANK_REQUESTED`와 `EXTERNAL_BANK_UNKNOWN`을 따로 뒀다. 개발자 질문: "API 호출과 트랜잭션을 못 묶으니, 요청함 상태는 어차피 불분명한 것 아닌가?" → 맞다.
- **함정:**
  - 호출 전에 의도를 커밋하지 않고 "호출 → 결과 커밋"만 하면, 그 사이에 죽었을 때 DB엔 이전 상태(`WITHDRAWN`)가 남는다. 복구 로직이 "아직 출금만 됐네" 하고 **보상하면 이중 지급** (상대 은행엔 입금됐는데 고객 돈도 돌려줌)
  - 반대로 "요청함"과 "모름"을 다른 상태로 나누면, 복구 입장에선 구별할 수 없는 둘을 다르게 처리하는 코드가 생긴다
- **원칙:** 되돌릴 수 없는 외부 호출 **전에** 의도 상태를 커밋한다 (write-ahead). 그러면 "이전 상태에 있다 = 확실히 안 보냄"이 보장된다. "모름"은 따로 만들지 않고 의도 상태에 남긴다. 상태를 나눌지는 **"멈춘 이 송금을 복구 로직이 발견하면 무엇을 하나"**가 다를 때만.
- 🎤 "외부 호출 직후 서버가 죽으면 그 송금은 어떻게 되나요?" / "결과 불명인데 보상하면 안 되는 이유는?" / "상태를 몇 개로 나눌지는 어떻게 정하나요?"

### 28. 한 테이블을 여러 종류가 같이 쓰면, 조회는 되는데 매핑이 깨진다

- **장면 (2026-11-20, 5주 차 S-3):** 당행·타행 송금이 공통 테이블 `transfer`를 같이 쓴다 (고객 멱등 키 UNIQUE를 둘을 통틀어 걸려고). 같은 사용자가 타행에 쓴 멱등 키로 당행 송금을 보내면?
- **함정:**
  - 당행 조회가 `(요청자, 키)`로 **타행 행을 찾아 버리고**, 그 상태(`WITHDRAWN`)를 당행 상태 enum으로 읽다가 매핑 예외 → **500**. 고객 실수가 서버 장애로 보인다
  - 종류별로 조회를 제한(`kind = 'DOMESTIC'`)하기만 하면 이번엔 "없음 → INSERT → UNIQUE 위반 → 다시 찾아도 없음"이 되어 **"중복인데 없음"**이라는 수수께끼 500이 된다
- **원칙:** 같은 테이블을 쓰는 엔티티는 **종류(구분 컬럼)로 읽기를 제한**하고, 키 충돌인데 같은 종류로 안 보이면 **다른 종류가 쓰는 키로 판정(소거법)**해 원인이 적힌 409로 돌려준다. PostgreSQL은 상대 행이 커밋된 뒤에만 UNIQUE 위반을 확정하므로 이 판정은 확실하다. JPA 단일 테이블 상속(`@DiscriminatorColumn`)도 같은 문제를 구분 컬럼으로 푼다.
- 🎤 "공통 테이블 + 상세 테이블로 나눈 이유는요? 그 대가는?" / "멱등 키가 다른 종류의 요청에 재사용되면?"

### 29. 메시지 발행 타임아웃 ≠ 미발행: Kafka에도 결과 불명이 있다

- **장면 (2026-11-21, 6주 차 유실 재현):** "커밋 뒤 발행 실패로 이벤트가 사라진다"를 재현하려고, 프로듀서가 연결된 뒤 Kafka 컨테이너를 일시정지(`docker pause`)했다. 프로듀서는 `delivery.timeout.ms`(5초) 뒤 콜백으로 **"발행 실패"**를 보고했는데, Kafka를 재개하자 그 메시지가 **토픽에 들어와 있었다** → 재현 실패
- **함정:**
  - 요청 바이트가 이미 소켓(커널 버퍼)으로 나갔으면, 브로커가 늦게라도 처리해 기록한다. 프로듀서의 타임아웃은 "응답을 못 받았다"일 뿐 "안 들어갔다"가 아니다. core 호출 타임아웃(pitfalls 6)과 같은 구조다
  - 그래서 "실패라고 떴으니 다시 보내자"(Outbox 릴레이의 재시도)는 **같은 이벤트를 두 번** 보낼 수 있다. eventId를 보낼 때마다 새로 만들면 컨슈머가 둘을 다른 이벤트로 보고 알림이 두 번 간다
- **원칙:** ① 발행은 "최소 한 번"으로 설계한다: Outbox + **컨슈머 멱등**은 짝이다 ② eventId는 **이벤트가 생길 때(outbox INSERT 때) 한 번** 정하고, 재시도해도 같은 값으로 보낸다 ③ 유실을 재현하려면 바이트가 아예 나가지 않는 장애를 만든다 (메타데이터를 받기 전에 브로커를 멈춰 `send()`가 `max.block.ms` 뒤 예외)
- 🎤 "Kafka 프로듀서가 타임아웃 났으면 메시지는 안 들어간 건가요?" / "Outbox가 있으면 중복 발행은 없나요?" / "exactly-once는 어떻게 보장하나요?" (프로듀서 멱등은 한 프로듀서 세션 안의 재시도 중복만 막는다, 앱 재시작·릴레이 재시도는 못 막음 → 컨슈머 멱등)
- 📎 `TransferEventLossTest` 주석, `KafkaTransferEventPublisher` (지금은 send 때 `UUID.randomUUID()`), notification `event_id` UNIQUE, pitfalls 6

### 30. "커밋 전에 보내고 ack 받으면 되지 않나?": dual write는 없앨 수 없고, 순서로 결과를 고른다

- **장면 (2026-11-21, 6주 차 Outbox):** 개발자 질문: "릴레이도 Kafka 전송과 DB 표시가 트랜잭션으로 안 묶이는 건 마찬가지다. 그러면 원래 흐름에서 커밋 전에 Kafka로 보내고 ack를 받은 뒤 커밋하면 유실이 없지 않나?"
- **함정:**
  - ack를 받은 뒤 커밋이 실패하면 (파드 종료, DB 연결 끊김, 낙관적 락 충돌) **유령 이벤트**: 송금은 롤백됐는데 "완료" 알림이 나갔다. Kafka에 나간 메시지는 회수할 수 없다 → 유실처럼 복구 불가
  - Kafka 왕복 동안 DB 커넥션 점유, **Kafka 장애 = 송금 API 장애** (알림 때문에 송금이 실패, ADR-0003 원칙 위반)
- **원칙:** 두 시스템에 걸친 쓰기는 원자적으로 만들 수 없다. 할 수 있는 건 **순서를 정해 장애 결과를 고르는 것**: 되돌릴 수 없는 쪽(Kafka, 외부 은행)보다 **우리 DB에 먼저 확정**한다. Outbox의 최악은 "중복"(컨슈머 멱등으로 복구)이고, 커밋 전 전송의 최악은 "유령"(복구 불가)이다. outbox 행 = 이벤트판 의도 상태 (pitfalls 27과 같은 구조)
- 🎤 "그냥 커밋 전에 보내면 안 되나요?" / "Outbox 릴레이도 원자적이지 않은데 왜 괜찮죠?" / "Kafka 트랜잭션(exactly-once)으로 DB와 묶을 수 있나요?" (Kafka 트랜잭션은 Kafka 안의 읽기-처리-쓰기만 묶는다. 외부 DB는 못 묶음)
- 📎 `TransferEventPublisher` KDoc (계약 변경), `TransferEventLossTest`, pitfalls 27 (의도 상태 먼저), 29 (발행 타임아웃 ≠ 미발행)

### 31. GitOps selfHeal은 손으로 일으킨 장애도 "어긋남"으로 보고 되돌린다

- **장면 (2026-11-21, 6주 차 중복 수신 재현):** 컨슈머 오프셋을 되감으려면 컨슈머 그룹에 활성 멤버가 없어야 한다 → `kubectl scale deploy/notification --replicas=0`. 그런데 Argo CD 앱이 `selfHeal: true`이고 차트가 `replicas`를 관리해서, 몇 초 만에 다시 1로 되돌아간다. 자식 앱의 자동 동기화만 끄면 상위 앱(app-of-apps, 역시 selfHeal)이 자식 앱 설정을 다시 원래대로 덮는다.
- **함정:** GitOps 환경에서 장애 대응이나 실험으로 손댄 것(스케일 다운, 설정 핫픽스, 파드 격리)이 **아무 경고 없이 원래대로 돌아간다.** 장애 중에 "분명히 줄였는데 왜 다시 떠 있지?"가 되고, 반대로 실험 뒤 되돌리는 걸 잊는 일은 없다
- **원칙:** ① 손으로 바꿔야 하면 **상위 앱부터** 자동 동기화를 끄고 (app-of-apps면 root → 자식 순), 끝나면 root만 다시 켜면 나머지가 selfHeal로 복구된다 ② 오래 갈 변경은 Git에 커밋한다 (그게 GitOps) ③ 장애 주입은 Argo가 관리하지 않는 리소스로 한다 (Chaos Mesh의 PodChaos·NetworkChaos는 별도 CR이라 충돌 없음, 12주 차) ④ HPA처럼 replicas를 다른 주체가 바꾸면 차트에서 `replicas`를 빼거나 Argo `ignoreDifferences`로 제외한다
- 🎤 "Argo CD 쓰는 환경에서 장애 때 급하게 kubectl로 고치면 어떻게 되나요?" / "selfHeal을 켜는 이유와 대가는?"

### 32. 두 행을 잠그는 코드는 잠그는 순서를 하나로 정한다 (데드락)

- **장면 (2026-11-21, 7주 차 비관적 락):** 당행 송금은 보내는 계좌와 받는 계좌 두 행을 바꾼다. A→B와 B→A가 동시에 오고 둘 다 "보내는 계좌부터" 잠그면, 각자 첫 행을 쥔 채 상대가 쥔 행을 기다린다. `LockStrategyConcurrencyTest`로 재현: PostgreSQL이 `deadlock_timeout`(1초) 뒤 원을 감지해 한쪽 트랜잭션을 죽인다 → 그 고객은 500
- **함정:**
  - `SELECT ... FOR UPDATE`만의 문제가 아니다. **조건부 UPDATE도 행 잠금**이라 두 행을 반대 순서로 UPDATE하면 똑같이 데드락. 낙관적 락도 커밋 때 flush하는 UPDATE 순서가 엇갈리면 생길 수 있다 (Hibernate `order_updates`로 PK 순 정렬)
  - 부하가 낮으면 안 보이다가 트래픽이 몰리는 날 터진다
- **원칙:** 여러 행을 잠그는 코드는 **항상 같은 순서**(ID 정렬)로 잠근다. 원(cycle)이 생길 수 없게 만드는 것이 감지·재시도보다 낫다. 기준은 아무거나 같기만 하면 된다 (자바 UUID 비교와 DB uuid 정렬은 다르지만 모든 파드가 같은 코드면 상관없음)
- 🎤 "데드락은 어떻게 막나요?" / "DB가 데드락을 감지하면 무슨 일이 생기나요?" / "UPDATE만 쓰는데도 데드락이 날 수 있나요?"
- 📎 `PessimisticBalanceChanger.transfer`, `AtomicUpdateBalanceChanger.transfer`, `LockStrategyConcurrencyTest` "재현 - 반대 순서로 잠그면 데드락"

### 33. 읽고-계산하고-쓰기 대신 조건부 UPDATE 한 문장: 단순 증감은 락이 필요 없을 수 있다

- **장면 (2026-11-21, 7주 차):** 잔액 차감은 "읽기(SELECT) → 앱에서 잔액 확인·계산 → 쓰기(UPDATE)"라 그 사이에 다른 트랜잭션이 끼면 lost update. 락 세 가지(낙관·비관·분산)를 비교하기 전에, 판단과 변경을 DB 한 문장으로 합치면 틈 자체가 없다: `UPDATE accounts SET balance = balance - :amt WHERE id = :id AND balance >= :amt`
- **함정:**
  - "락을 안 쓴다"가 아니다. UPDATE도 커밋까지 행 잠금을 쥔다. 동시에 오면 두 번째는 기다렸다가 **커밋된 최신 값으로 WHERE를 다시 평가**한다 (PostgreSQL READ COMMITTED). REPEATABLE READ에서는 재평가 대신 직렬화 오류로 실패한다 → 격리 수준에 따라 동작이 다르다
  - JPA 벌크 업데이트는 영속성 컨텍스트를 거치지 않는다: 미리 읽어 둔 엔티티는 옛 값, `@Version`은 직접 올려야 함
  - 업무 규칙(잔액 ≥ 금액)이 도메인과 SQL 두 곳에 생긴다. 실패 이유가 "0행"으로 뭉개져 조회를 한 번 더 해야 가린다
  - **0행 확인을 빠뜨리면 조용히 깨진다:** DB는 0행이어도 오류를 내지 않는다. 우리는 원장을 먼저 기록하므로 `if (updated == 0)`을 잊으면 원장엔 출금, 잔액은 그대로 → 대사에서야 드러나는 불일치. 반환값 확인이 곧 잔액 검사다
  - 바뀐 결과를 모른다: 거래 후 잔액(통장 거래내역)이 필요하면 PostgreSQL `UPDATE ... RETURNING balance` (표준 JPQL에는 없음 → 네이티브 쿼리)
  - 새 값을 SET 식 하나로 못 쓰면(이자·수수료 구간처럼 잔액에 따라 계산이 갈림, 다른 애그리거트나 외부 호출을 봐야 하는 규칙) 다시 읽고-계산하고-쓰기 → 락으로 돌아간다
- **원칙:** 단순한 증감·조건(재고 차감, 잔액 차감, 좌석 수)은 **조건부 UPDATE**가 가장 싸고 안전하다. 규칙이 복잡해지면(한도·여러 행 조합) 락 + 도메인 메서드. 분산 락은 DB 밖 자원을 묶을 때. 낙관적 락만의 자리는 읽기와 쓰기가 **다른 요청**에 걸칠 때(화면에서 고치고 저장): 사용자가 고민하는 동안 잠금을 쥘 수 없으니 version을 들고 다닌다
- 🎤 "재고 차감 동시성은 어떻게 처리하나요?" / "UPDATE ... WHERE stock > 0이 왜 안전한가요?" / "격리 수준에 따라 달라지나요?" / "조건부 UPDATE의 단점은? 그럼 낙관적 락은 언제 쓰나요?"
- 📎 `AccountRepository.withdrawAtomically` 주석, `AtomicUpdateBalanceChanger`, pitfalls 32

### 34. 분산 락은 트랜잭션 **바깥**에서 잡고 커밋 **뒤**에 푼다

- **장면 (2026-11-22, 7주 차):** Redis 분산 락을 잔액 변경 코드(트랜잭션 안) 근처에서 잡고 풀면 자연스러워 보인다. `@Transactional` 메서드 안에서 `lock() → 잔액 변경 → unlock()`
- **함정:**
  - DB 행 잠금은 **커밋할 때 DB가** 푼다. Redis 락은 **코드가 unlock()을 부르는 순간** 풀린다. 트랜잭션 안에서 풀면 "락은 풀렸는데 내 변경은 커밋 전"인 틈이 생기고, 다음 요청이 그 틈에 커밋 안 된 옛 잔액을 읽는다
  - 재현 (`RedisLockScopeTest`): 버전 검사 없이 덮어쓰면 출금 2건 성공에 잔액은 1건만 빠짐 (10,000 → 9,000). `@Version`이 있으면 늦은 커밋이 `OptimisticLockingFailureException`으로 거절된다 = 락이 뚫렸다는 신호
  - `@Transactional` 메서드 안에 락 코드를 넣으면 프록시 구조상 커밋은 메서드가 **끝난 뒤**에 일어난다 → `finally { unlock() }`도 커밋 전이다. 같은 실수
  - 락 저장소가 잠깐이라도 두 대가 되면(Deployment 롤링의 maxSurge) 같은 락을 둘이 잡는다 → 락 저장소는 StatefulSet replicas 1, 또는 합의 기반
- **원칙:** 순서는 `락 → 트랜잭션 시작 → 변경 → 커밋 → 락 해제`. 락은 트랜잭션 바깥에 둔다: 우리는 account가 감싸는 함수(`AccountLocks.around`)를 공개하고, 트랜잭션을 여는 `PostingUseCaseImpl`이 그 안에서 트랜잭션을 연다 (전략 판단은 account에, 위치는 posting이). 분산 락이 뚫릴 때(TTL 만료, GC 멈춤, Redis 재시작)를 대비해 DB 쪽 안전망(`@Version`, 조건부 UPDATE)을 남긴다. 락이 제대로면 안전망은 한 번도 안 터진다 → 그 카운터가 락의 건강 지표
- 🎤 "분산 락을 트랜잭션과 같이 쓸 때 주의점은?" / "@Transactional 메서드 안에서 unlock하면 왜 안 되나요?" / "Redis 락이 만료됐는데 작업이 안 끝났으면?"
- 📎 `RedisLockScopeTest`, `RedisGuardedBalanceChanger`, `deploy/platform/redis/redis.yaml`, pitfalls 33, `docs/learning/concurrency.md` 5번

### 35. 원격 접속할 집 대역이 흔한 사설 대역이면, 밖의 LAN과 겹쳐서 못 들어간다

- **장면 (2026-11-23):** Tailscale 서브넷 라우터로 집 `172.30.1.0/24`를 광고했다. 집 안에서 맥북 라우팅 테이블을 보니 `172.30.1/24`가 `en0`(와이파이)과 `utun6`(Tailscale) 두 줄이었고, `en0`가 이겼다.
- **함정:** "지금 붙은 LAN이 이긴다"는 규칙 때문에, 밖에서 붙은 네트워크도 `172.30.1.0/24`이면 (KT 공유기 기본 대역이라 카페·친구 집에서 흔하다) 그쪽 LAN으로 가 버려 집에 못 들어간다. 증상이 "Tailscale은 연결됨인데 클러스터만 타임아웃"이라 원인 찾기가 어렵다. 회사 VPN에서 사내 대역과 집 대역(`192.168.0.0/24` 등)이 겹치는 장애와 같은 모양이다.
- **원칙:** 원격으로 들어가야 할 망은 처음부터 흔하지 않은 대역(예: `10.87.0.0/24`)으로 잡는다. 이미 늦었으면 ① 겹치는 곳에서는 `100.x` 주소로 노트북에 붙어 점프 ② Tailscale 4via6(같은 대역을 다른 주소로 노출) ③ 집 대역 변경(큰 공사: MetalLB 풀, nip.io 주소, 노드 IP 전부 바뀜).
- 🎤 "VPN은 붙었는데 특정 서버만 안 될 때 무엇부터 보나요?" → 라우팅 테이블(`route get <IP>`)에서 어느 인터페이스로 나가는지
- 📎 `docs/learning/tailscale-and-nat.md` 4절

### 36. 고정 속도 부하는 경합을 만들지 않는다: 같은 "초당 50건"도 도착 모양이 다르다

- **장면 (2026-11-23, 7주 차 k6):** 핫 계좌 1개에 초당 50건을 넣었는데 락 없음(NONE)도 잔액이 안 깨졌다. 재시도 2회, 동시에 기다리는 요청이 한 번도 안 늘었다.
- **함정:** k6 `constant-arrival-rate`는 요청을 **정확히 같은 간격**으로 보낸다. 초당 50건 = 20ms마다 한 건인데 처리가 5ms면 앞 요청이 끝난 뒤에 다음이 도착해 **아무것도 안 겹친다.** 실제 트래픽은 몰려서 온다(무작위·버스트). "초당 N건에서 문제없음"이 실서비스의 초당 N건을 보장하지 않고, 동시성 버그는 테스트를 통과한다.
- **원칙:** 동시성 실험은 먼저 "겹침이 실제로 생겼나"를 확인한다 (대조군 NONE이 깨지나, 재시도·대기·동시 요청 수가 느나). 안 깨지면 실험이 틀린 것이다. 경합을 만들려면 속도를 **행 하나의 처리 한계(≈ 1 ÷ 락을 쥔 시간)** 근처 이상으로 올리거나 버스트(같은 순간 N개)를 쓴다.
- 🎤 "부하 테스트에서 동시성 문제가 안 나왔으면 안전한 건가요?" / "k6 arrival-rate와 VU 방식의 차이는?"
- 📎 `docs/experiments/week-07-locks.md` "1차 측정 실패", `load-test/lock-compare.js`

### 37. 대기는 공짜가 아니다: 같은 스레드 200개라도 어디서 기다리느냐가 메모리를 가른다

- **장면 (2026-11-23, 7주 차 k6):** 핫 계좌 300건/초에서 REDIS 락만 core가 OOMKilled. 살아남은 PESSIMISTIC 500건/초와 비교하니 톰캣 스레드는 둘 다 상한 200, 힙도 같았다. 차이는 기다린 위치: PESSIMISTIC은 히카리 풀에서 잠들어 있었고, REDIS는 Redisson Netty 쪽에서 구독·타이머·재시도 메시지가 오가며 direct 버퍼 풀이 늘었다.
- **함정:** "스레드 수에 상한을 걸었으니 메모리도 안전하다"고 생각하기 쉽다. 하지만 대기자 한 명이 붙잡는 것(버퍼, 구독, 타이머, 대기열의 연결)은 대기 방식마다 다르고, 처리 한계를 넘으면 대기자가 끝없이 쌓여 그 작은 차이가 곱해진다. OOMKilled는 JVM 힙 에러가 아니라 컨테이너 전체(힙 + 힙 밖)가 limit을 넘은 것이라 힙 그래프만 보면 원인을 놓친다.
- **원칙:** 대기를 **제한**한다: 대기자 수 상한(벌크헤드·세마포어), 짧은 대기 상한과 빠른 거절(503), 컨테이너 메모리에 힙 밖 여유. 장애 분석은 "몇 개가 기다렸나"에서 멈추지 말고 "기다리는 동안 무엇을 붙잡고 있었나"까지.
- 🎤 "스레드 수가 같은데 왜 한쪽만 OOM이 나죠?" / "OOMKilled인데 힙은 여유였다면 어디를 보나요?" / "부하가 처리 한계를 넘으면 시스템은 어떻게 무너지나요?"
- 📎 `docs/experiments/week-07-locks.md` 판독 1, pitfalls 13(보이지 않는 기본값), 5주 차 stress(`week-05-k6-baseline.md`)

### 38. 해소 일꾼이 "모름"을 재전송으로 풀면, 고객 없이 옛날 송금이 지금 실행된다

- **장면 (2026-11-23, 8주 차 결과 불명 해소 설계):** 멈춘 당행 송금(`PROCESSING`·`UNKNOWN`)을 해소 일꾼이 같은 송금 ID로 core에 재전송하면 멱등이라 안전하다고 생각했다. 그런데 core는 **거절을 기억하지 않는다** (롤백 → 원장에 흔적 없음, 조회하면 `NOT_PROCESSED`).
- **함정:** 10시에 잔액 부족으로 거절된 송금이 결과 저장 전에 transfer가 죽어 `PROCESSING`으로 남았고, core 장애가 2시간 이어졌다. 12시에 core가 살아났을 때 그사이 월급이 들어와 있으면 재전송이 **성공**한다. 고객은 없는데 2시간 전 의사로 돈이 움직인다. 멱등은 "두 번 실행 방지"이지 "늦은 실행 방지"가 아니다. 잔액은 시간에 따라 바뀌어서 짧은 지연(1분)도 다른 판단이 될 수 있다.
- **원칙:** 고객이 없는 해소 일꾼은 **새로 돈을 움직이지 않고 확인만** 한다 (상태 조회 → 처리됨이면 반영, 안 됐으면 실패로 확정). 재전송(=지금 실행)은 실행 의사가 지금 있는 쪽(고객의 같은 키 재요청)만 한다. "처리 안 됨"으로 포기할 때는 원래 요청이 뒤늦게 커밋되지 않는다는 보장도 필요하다.
