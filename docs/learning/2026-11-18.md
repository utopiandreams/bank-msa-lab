## ⭐ 브로커와 파티션
- 💡 파티션은 브로커들에 나눠 저장되고, 파티션마다 **리더 브로커**가 하나. 쓰기·읽기는 리더가 받는다. 리더를 브로커마다 골고루 → 일을 파티션 단위로 나눠 맡는다
- 💡 프로듀서는 메타데이터(파티션별 리더)를 **캐시**해 두고 리더에게 **직접** 보낸다 (중앙 라우터 없음). 처음·주기적(5분)·에러 때만 새로 받는다. `bootstrap-servers`는 "처음 물어볼 곳"
- 💡 리더가 둘: **컨트롤러 리더**(클러스터에 하나, Raft로 뽑음, 누가 파티션 리더인지 결정) / **파티션 리더**(파티션마다 하나, 실제 쓰기·읽기)
- 💡 컨슈머는 당겨 간다(pull). 느리면 덜 가져가고 쌓인다 = 랙
- 🎤 브로커가 죽으면 그 브로커가 리더였던 파티션은? / 프로듀서는 매번 리더를 물어보나요?

## ⭐ 프로듀서의 비동기 구조
- 💡 비동기의 정체는 `KafkaProducer`의 **버퍼 + 전송 전담 스레드 하나**(내부는 논블로킹 I/O, epoll). send()는 버퍼에 붙이고 바로 돌아온다. 묶음(batch) 단위로 전송
- 💡 콜백은 그 전송 스레드에서 돈다 → 콜백에서 블로킹 금지 (이벤트 루프와 같은 원리)
- 💡 send()가 막히는 두 경우: 메타데이터를 모를 때, 버퍼(32MB)가 찼을 때 → `max.block.ms`
- 📎 `KafkaTransferEventPublisher.kt`, pitfalls 20

## ⭐ 멱등 컨슈머와 poison pill
- 💡 Kafka는 at-least-once: 처리 후 오프셋 커밋 전에 죽으면 다시 받는다 → `event_id` UNIQUE로 INSERT 시도, 위반이면 중복 (먼저 조회하고 INSERT하면 동시 중복을 못 막는다. T-2와 같은 결론)
- 💡 깨진 메시지에 예외를 던지면 재시도하느라 **그 파티션 전체가 멈춘다** → 건너뛰고 기록 (나중에 Dead Letter Topic)
- 💡 발행은 커밋 **뒤**에: 커밋 전에 보내면 롤백됐는데 알림이 나가는 유령 이벤트. 대신 사이에 죽으면 유실 → 6주 차 Outbox
- 🎤 Kafka는 exactly-once인가요? / 알림이 두 번 가면 어떻게 막나요? / 컨슈머가 계속 같은 메시지에서 실패하면?
- 📎 `NotificationService.kt`, `TransferEventListener.kt`, `NotificationIntegrationTest`

## NVMe vs SATA, etcd와 디스크
- 💡 모양(2.5인치 / M.2) · 통로(SATA / PCIe) · 대화 방식(AHCI / NVMe)은 별개. M.2에도 SATA가 있다. NVMe는 대기열이 많고 PCIe 직결이라 빠르다
- 💡 etcd·DB 커밋 로그에 중요한 건 처리량(MB/s)이 아니라 **fsync 지연과 IOPS**. 보급형 SSD는 전원 손실 보호가 없어 fsync p99 꼬리가 길다
- 📎 `docs/infra/README.md` "etcd 디스크 적합성 측정"

## ⭐ 지표가 Grafana까지 오는 길 (pull 방식)
- 💡 앱은 지표를 **보내지 않는다.** Micrometer가 메모리에 카운터를 들고 있다가 `/actuator/prometheus`에 텍스트로 보여 줄 뿐. **Prometheus가 15초마다 가져간다** (pull)
- 💡 Prometheus는 받은 값을 시간과 함께 디스크에 쌓는다(7일). **Grafana는 저장하지 않는다.** 화면을 열 때마다 Prometheus에 PromQL로 물어서 그린다
- 💡 "누구를 긁을지"는 **PodMonitor·ServiceMonitor 선언** → prometheus-operator가 Prometheus 설정으로 바꿔 준다. 파드 IP가 바뀌어도 라벨로 따라간다 (CloudNativePG가 `Cluster` 선언을 보고 DB를 만드는 것과 같은 오퍼레이터 패턴)
- 💡 **relabeling** = 저장 전에 라벨 고쳐 쓰기. node-exporter의 `instance`를 IP → 노드 이름으로, Kafka의 `strimzi.io/cluster` → `strimzi_io_cluster`로
- 💡 Kafka·DB도 같은 구조: 자기 안의 숫자(JMX, `pg_stat_*`)를 누군가 Prometheus 형식으로 번역한다 (Strimzi Metrics Reporter, CNPG 인스턴스 매니저). **컨슈머 랙은 브로커에 없다** → Kafka Exporter가 "마지막으로 쓰인 오프셋 − 커밋한 오프셋"으로 계산 (커밋한 적 없는 파티션은 -1)
- 🎤 Prometheus는 push인가요 pull인가요? 장단점은? / 파드가 재시작돼 IP가 바뀌면 수집은? / Grafana가 죽으면 지표가 사라지나요?
- 📎 `deploy/helm/spring-service/templates/podmonitor.yaml`, `deploy/platform/monitoring/`, `deploy/argocd/apps/kube-prometheus-stack.yaml`, `docs/infra/README.md` "관측성 기본 스택"

## ⭐ actuator 관리 포트 분리
- 💡 파드 하나가 문을 두 개 연다: **8080 고객용**(Service·Ingress에 연결) / **8081 관리용**(Service에 없음 → 밖에서 길이 없음, Prometheus만 파드 IP로 직접)
- 💡 막은 게 아니라 **옮겼다.** 8080에 두고 규칙으로 막으면 규칙 하나 빠뜨릴 때 뚫린다. 처음부터 길이 없는 쪽이 안전
- 💡 함정 1: 포트를 나눠도 **WebFlux Spring Security 체인은 관리 포트에도 걸린다** → Prometheus 401. 테스트(`ManagementPortTest`)가 잡았다
- 💡 함정 2: 프로브를 관리 포트로 받으면 앱 포트가 고장 나도 Ready → 프로브는 앱 포트의 `/livez`·`/readyz` (`add-additional-paths`)
- 💡 **kubelet의 프로브는 Ingress를 거치지 않는다** (노드에서 파드 IP로 직접). 그래서 Ingress에서 경로를 막아도 프로브는 안 깨진다
- 🎤 actuator를 운영에서 어떻게 노출하나요? / readiness를 관리 포트로 받으면? / ServiceMonitor 대신 PodMonitor를 쓴 이유는?

## ⭐ taint와 toleration
- 💡 **taint** = 노드의 "관계자 외 출입 금지" 표지판, **toleration** = 파드의 출입증. 표지판을 떼는 게 아니라 출입증 있는 파드만 들어간다
- 💡 `CriticalAddonsOnly` = "클러스터 운영에 꼭 필요한 부가 기능만". 4GB 컨트롤 플레인에 앱이 올라와 API 서버까지 같이 죽는 걸 막으려고 1주 차에 걸었다
- 💡 node-exporter는 앱이 아니라 **노드 검진 도구**라 모든 노드에 있어야 한다 → `tolerations: [{operator: Exists}]` (어떤 taint든 통과). 컨트롤 플레인이야말로 가장 지켜봐야 할 노드
- 🎤 taint와 nodeSelector·affinity의 차이는? / DaemonSet이 특정 노드에만 안 뜨면 무엇부터 보나요?

## ⭐ p99는 어떻게 재나
- 💡 p99 = 느린 순으로 줄 세운 99% 지점. 평균은 소수의 느린 요청을 가린다
- 💡 **k6**: 요청 시간을 전부 기록해 정확히 정렬. **서버**: 전부 기록할 수 없어 "몇 ms 이하가 몇 건" **칸(버킷)**만 센다 → `histogram_quantile`이 칸 안에서 고르게 퍼졌다고 가정하고 추정
- 💡 버킷 방식의 장점: 파드 여러 개의 칸을 **더하기만 하면** 전체 p99. 파드별 p99의 평균은 진짜 p99가 아니다 (그래서 앱 안에서 계산하는 `percentiles`는 안 씀)
- 💡 PromQL: `histogram_quantile(0.99, sum by (le, application) (rate(http_server_requests_seconds_bucket{...}[1m])))` — Prometheus 수집·프로브 요청은 `uri!~`로 뺀다
- 🎤 p99와 평균 중 무엇을 보나요? / 파드 3개의 p99를 합치려면? / 히스토그램 버킷을 잘못 잡으면?

## ⭐ 어디서 재느냐에 따라 숫자가 다르다

## ⭐ 부하 테스트 숫자를 실무로 옮기는 법
- 💡 홈랩의 **절대값**("초당 300건")은 운영으로 못 옮긴다. 옮길 수 있는 건 **같은 환경의 전후 비교**, **병목 위치**(무엇이 먼저 막히나), **근거 있는 설정값**(p99 기반 타임아웃)
- 💡 실무 목표는 비즈니스에서: 피크(급여일·명절) × 여유분. 운영과 같은 사양의 성능 환경에서 **파드당 처리량** + **공유 자원(DB·Kafka) 한계**를 따로 잰다 (파드를 늘려도 DB가 하나면 DB가 먼저 막힌다)
- 💡 `constant/ramping-arrival-rate`: 응답을 기다리지 않고 정해진 속도로 보낸다. 응답을 기다리는 방식은 서버가 느려지면 요청도 덜 보내서 느린 구간을 덜 잰다 (coordinated omission)
- 🎤 홈랩 수치가 운영에서 의미가 있나요? / 용량 계획은 어떻게 하나요? / coordinated omission이 뭔가요?

## ⭐ 기준선 판독과 예상 못 한 발견
- 💡 60건/초까지 꺾이지 않음 (CPU 22%, core DB 커넥션 최대 1). 하키 스틱은 수백 건/초에서 찾아야 한다
- 💡 부하가 늘수록 빨라짐 (서버도) → 가설: CPU 절전 상태에서 깨어나는 비용, JIT. 검증 안 함
- 💡 **UNKNOWN 3건**: 같은 계좌를 동시에 건드린 두 송금 → core 낙관적 락 충돌(`@Version`) → 매핑 안 돼 500 → transfer가 규칙대로 결과 불명. 돈은 안전(한 트랜잭션이라 통째로 롤백). 하지만 **확정된 실패가 "모름"으로 보였다**
- 💡 잔액 합 검증(2억 = 2억)은 "돈이 생기거나 사라지지 않았다"만 증명한다. 각 송금이 맞게 처리됐는지는 아님 (당행 송금은 성공해도 합이 같다)
- 💡 UNKNOWN 뒤에 **새 키로 재시도하면 이중 송금 위험**. 같은 키로 재시도 → 같은 송금 ID로 core 재전송 (3주 차 T-2 설계)
