# 모니터링 활용 플레이북: 상황이 오면 어디를 어떤 순서로 보나

> 2026-11-24 개발자 요청: "모니터링을 활용하는 방법 같은 건 최대한 잘 정리해 줬으면". 배관(설치·연결)은 Claude가 빠르게 하고, 개발자는 **실무에서 어떻게 쓰나**에 익숙해지는 데 시간을 쓴다.
>
> 이 문서는 **활용법** (상황 → 신호 → 클릭 경로 → 판단). 개념(지표란, 퍼센타일, 트러블슈팅 원리)은 `observability.md`, 실무 사고는 `pitfalls.md`.
> 표시: ✅ = 이 클러스터에서 실제로 해 봄 / ⏳ = 해당 주차에 채움. 장면이 쌓일 때마다 Claude가 갱신한다.

---

## 0. 제1원칙: 신호에서 출발해 좁혀 간다

```
알림·고객 문의·배포    →   지표          →   트레이스         →   로그
"뭔가 이상하다"            "얼마나, 언제부터"   "어느 요청이, 어디서"   "왜"
```

- **트레이스와 로그는 훑어보는 게 아니라 도착하는 곳.** 평소에 열어 보지 않는다. 택배 배송 조회처럼, 문제가 생긴 한 건을 찾아 들어간다
- **지표는 넓게, 트레이스는 한 건을 깊게.** 지표로 "p99가 14:02부터 3배"를 보고 → 그 시간대의 느린 트레이스 몇 개 → 공통으로 긴 구간
- **"언제부터"가 절반이다.** 배포·설정 변경·트래픽 변화 시각과 겹치는지 먼저 본다 (장애의 대부분은 무언가를 바꾼 직후)
- **피해자와 원인을 구분한다.** 가장 먼저 꺾인 그래프가 원인 쪽, 나중에 따라 꺾인 쪽은 피해자 (5주 차: DB 커넥션 고갈 → gateway 타임아웃은 피해자)

## 1. 상황별 플레이북

각 항목: **첫 질문 → 볼 곳(클릭 경로) → 무엇을 보나 → 흔한 결론**.

### 1-1. "송금이 느려요" (고객 문의 · p99 상승 알림)

1. **첫 질문:** 전부 느린가, 일부만 느린가? 언제부터?
2. **지표:** Grafana → JVM/앱 대시보드 → API별 지연(p50·p99) → p50도 올랐나(전체 포화) / p99만 올랐나(일부 요청·일부 자원)
3. **트레이스:** Explore → 데이터 소스 **Tempo** → TraceQL `{ resource.service.name = "gateway" && duration > 1s }` → 느린 것 몇 개를 열어 **공통으로 긴 막대**를 찾는다
4. **판단:**
   - 긴 막대가 DB 쿼리 하나 → 느린 쿼리·인덱스 (`observability.md` 3-2)
   - 막대는 짧은데 사이에 **빈칸** → 기다림 (커넥션 풀, 락, 스레드). 빈칸 앞뒤 구간 이름이 단서
   - 외부 호출(bank-mock) 막대가 김 → 의존성 지연 → 타임아웃·서킷 브레이커 (15주 차)
   - 같은 쿼리가 계단처럼 수십 번 → N+1
   - 첫 요청만 느림 → 워밍업 (커넥션·JIT·클래스 로딩). ✅ 9주 차 첫 송금: 160ms 중 멱등 키 조회 56ms

### 1-2. "송금은 됐는데 알림이 안 와요" (비동기에서 길 잃음) ✅

1. **첫 질문:** 이벤트가 나갔나? 나갔으면 소비됐나?
2. **트레이스:** 송금 ID로 찾는다. TraceQL `{ span.outbox.aggregate_id = "<송금 ID>" }` (발행 구간에 송금 ID를 속성으로 달아 둠)
   - 아무것도 안 나옴 → **아직 발행 전.** outbox에 남아 있다 → Kafka 장애? 릴레이 정지?
   - `outbox publish`는 있는데 notification 구간이 없음 → 소비 쪽 문제 (컨슈머 랙, 컨슈머 에러, poison pill)
   - 다 있음 → 알림은 처리됨. 발송(가짜) 단계·고객 쪽 확인
3. **보조 지표:** 컨슈머 랙 (Grafana → Strimzi Kafka Exporter 대시보드 → consumer group lag). ⏳ outbox 미발행 수·가장 오래된 미발행 나이 (13주 차)
4. **팁:** 트레이스의 `outbox publish` 구간 속성 `outbox.wait_ms` = INSERT부터 발행까지 기다린 시간. 평소 1초 안쪽(릴레이 주기), 늘어나면 릴레이나 Kafka가 밀리는 중

### 1-3. 에러율이 튄다 (5xx 알림)

1. **첫 질문:** 어느 서비스·어느 API에서? 언제부터? 배포가 있었나?
2. **지표:** API별 에러율 → 한 API만인가 전부인가
3. **트레이스:** `{ status = error }` (서비스로 좁히려면 `&& resource.service.name = "transfer"`) → 트리에서 **가장 깊은 곳의 빨간 구간**이 처음 터진 곳. 위쪽 빨간 구간들은 그 에러가 올라온 것(피해자)
4. **판단:** 가장 깊은 에러가 DB 연결 실패 / 다운스트림 타임아웃 / 업무 예외(422 같은 정상 거절은 에러로 치지 않게 설계했는지도 확인)
5. ⏳ 로그: 그 구간의 traceId로 로그로 건너가 예외 메시지 (10주 차)

### 1-4. 파드가 재시작된다 (OOMKilled · CrashLoop) ✅

`observability.md` 7-5의 순서를 그대로: 재시작 사유(`kubectl describe pod` → Last State) → 컨테이너 메모리 vs limit → 힙 vs 힙 밖 → 스레드 수 → 무엇을 기다리느라 쌓였나. 7주 차 Redis 락 OOM이 이 순서로 풀렸다.

### 1-5. 배포 직후 이상 ⏳

배포 시각 마커(Argo CD 동기화 시각)와 그래프 꺾임이 겹치는지 → 새 버전 파드만 에러인가(`service.version` 속성으로 트레이스 구분 가능: 에이전트가 이미지 태그를 넣어 둠) → 롤백 판단. 13주 차 패널에 배포 마커

### 1-6. 컨슈머 랙이 쌓인다 ⏳ (16주 차)

랙 그래프 모양: 계속 오름(처리량 < 유입) / 계단(리밸런싱 중 멈춤) / 한 파티션만(핫 파티션). 트레이스로 소비 구간 하나가 느린지, 소비 사이 빈칸(폴링 지연)인지

## 2. 트레이스 워터폴 읽는 법 (모양 도감)

| 모양 | 뜻 | 다음 행동 |
| --- | --- | --- |
| 긴 막대 하나가 전체를 차지 | 그 구간이 범인 | 그 구간 종류(DB·HTTP·Kafka)별로 파고든다 |
| 짧은 막대들 사이 **빈칸** | 계측 안 된 곳에서 기다림 (풀 대기, 락, 큐, GC) | 빈칸 앞뒤 구간 이름, 같은 시각의 지표(풀 pending, GC 일시정지) |
| 같은 구간이 **계단처럼 반복** | N+1 쿼리 / 재시도 반복 | 반복 횟수 = 루프 크기인지 재시도 횟수인지 |
| 막대들이 **겹침** | 병렬 호출 | 전체 시간 = 가장 긴 것. 직렬이었다면 합 |
| 위에서 아래로 **빨간 구간 줄줄이** | 깊은 곳 에러가 위로 전파 | 가장 깊은 빨간 구간이 원인 |
| 트레이스가 **중간에 끝남** | 비동기 경계에서 문맥이 끊김 or 아직 처리 전 | 끊긴 배관인지(pitfalls 39) 진짜 멈춤인지 |
| ✅ 끝부분이 **1초쯤 떨어져** 이어짐 | Outbox 대기 (릴레이 주기) | 정상. 수 초 이상이면 릴레이·Kafka 확인 |

## 3. TraceQL 치트시트 (Grafana → Explore → Tempo → TraceQL)

> 2026-11-26 개발자 질문 "이건 어떤 언어야?": Grafana 계열은 **신호마다 질의 언어가 하나씩** 있다. 모양이 비슷해서 하나를 익히면 나머지가 쉽다
> | 신호 | 언어 | 생김새 |
> | --- | --- | --- |
> | 지표 (Prometheus) | **PromQL** | `rate(http_server_requests_seconds_count{application="transfer"}[1m])` |
> | 로그 (Loki) | **LogQL** | `{app="transfer"} |= "ERROR"` |
> | 트레이스 (Tempo) | **TraceQL** | `{ resource.service.name = "transfer" && duration > 2s }` |
> - `{ }` 안의 조건에 맞는 **구간(span)**을 고르고, 그 구간이 든 트레이스를 돌려준다
> - `resource.` = 어디서 실행됐나 (서비스·파드·버전), `span.` = 그 동작의 속성 (HTTP 경로, DB 문장, 송금 ID), 앞에 점이 없는 것 = 기본 항목 (`duration`, `name`, `status`)
> - 처음엔 손으로 안 써도 된다: Explore → Tempo → **Search** 탭의 드롭다운으로 고르면 아래에 TraceQL이 만들어진다 (로그·지표도 Builder 모드가 있다)

```
# 서비스의 느린 요청
{ resource.service.name = "transfer" && duration > 500ms }

# 에러 난 구간이 있는 트레이스
{ status = error }

# 송금 ID로 (발행 구간의 속성)
{ span.outbox.aggregate_id = "<송금 ID>" }

# Outbox에서 오래 기다린 이벤트
{ name = "outbox publish" && span.outbox.wait_ms > 5000 }

# HTTP 경로로
{ span.http.route = "/transfers" && duration > 1s }

# 구조: gateway에서 시작해 notification까지 간 트레이스 (>> = 자손)
{ resource.service.name = "gateway" } >> { resource.service.name = "notification" }

# 특정 버전(이미지 태그)만: 배포 전후 비교
{ resource.service.version = "<태그>" && status = error }
```

- 속성 앞의 `resource.`(서비스·파드·버전처럼 프로세스 단위) vs `span.`(구간마다 다른 값)를 구분한다
- 검색 기본 범위는 최근 시간대. 오래된 건 오른쪽 위 시간 범위를 넓힌다 (보관 72시간)

## 4. 실무 팁 모음 (장면에서 건진 것)

- **비동기 경계는 트레이스가 끊기는 곳이다.** Outbox·DB 큐·배치는 직접 이어야 한다. 처음 붙였을 때 "요청부터 소비까지 한 트레이스인가"부터 확인 ✅ (pitfalls 39)
- **잡음부터 지운다.** 프로브·지표 수집·1초 스케줄러·커넥션 풀 관리 스레드가 검색 결과를 덮는다. 찾는 법: TraceQL `{ }`로 최근 트레이스를 보고 **루트 이름이 반복되는 것**을 연다 (이번에 Hikari housekeeper를 이렇게 찾음: `thread.name` 속성). 구간 단위는 Collector `filter`, 트레이스 통째는 `tail_sampling` ✅ (`otel-collector.yaml`)
- **운영에선 전부 남기지 않는다.** 꼬리 기반 샘플링으로 "에러·느린 것은 100%, 정상은 몇 %". 지금 학습 환경은 전부 남김
- **검색할 값을 구간 속성으로 달아 둔다.** 고객 문의는 송금 ID로 온다. 속성이 없으면 시간대로 뒤져야 한다 (지금 송금 ID는 발행 구간에만 → ⏳ 요청 구간에도 달기)
- **관측 도구도 자원을 먹는다.** 에이전트를 붙이니 유휴 메모리 +70~90Mi. 전후 실험 수치를 비교할 땐 이 조건 차이를 적는다 ✅
- **로컬에서 렌더링된 설정 ≠ 클러스터에 적용된 설정.** 실제 리소스를 확인한다 ✅ (pitfalls 38)
- **도구는 달라도 질문은 같다.** Datadog·Pinpoint·X-Ray 어디서든 "어떤 요청이 → 어느 구간에서 → 왜". 벤더를 바꿔도 남는 건 이 순서와 비동기 문맥 설계
