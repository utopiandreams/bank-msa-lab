## Gradle 멀티모듈, build-logic 컨벤션 플러그인, 버전 카탈로그

> 💡 **핵심**

## Dockerfile 레이어 분리, 멀티스테이지, 비root

> 💡 **핵심**
> - **jar는 Gradle이, Docker는 포장만:** CI가 이미 빌드·테스트한 jar를 넣는다. Docker 안에서 또 빌드하면 캐시가 없어 느리고 같은 일을 두 번 한다
> - **레이어 분리:** fat jar를 `dependencies`(수십 MB, 거의 안 바뀜) → `application`(우리 코드, 수십 KB) 순으로 풀어서 복사. **코드만 바뀌면 마지막 레이어(12KB)만 새로 push·pull** (의존성 27.6MB는 재사용)
> - **멀티스테이지:** 1단계에서 jar를 풀고, 2단계(실행 이미지)에는 풀린 결과만 복사
> - **비root (uid 10001):** 컨테이너가 뚫려도 노드 권한까지 넘어가기 어렵게
> - **`MaxRAMPercentage=75`:** 힙을 고정값이 아니라 메모리 limit의 75%로. 나머지 25%는 메타스페이스·스레드 스택 몫 (100%면 OOMKilled)
>
> 🎤 "레이어 순서를 반대로 하면?" → 우리 코드가 바뀔 때마다 그 뒤 레이어(의존성)까지 캐시가 깨져서 매번 수십 MB 전송
> 🎤 "Jib나 Buildpacks는?" → 편하지만 내부가 감춰짐. 설명할 수 있는 쪽을 골랐다
>
> 📎 `deploy/docker/spring-boot.Dockerfile` (주석이 곧 설명) / [인프라 README](../infra/README.md) «구성 요소» 표의 "컨테이너 이미지" 행

## CI: 테스트 → amd64 이미지 → GHCR → values 태그 커밋 (배포 = 커밋)

> 💡 **핵심**
> ```
> push → 테스트 → amd64 이미지 → ghcr.io/.../core:<커밋해시>
>      → deploy/apps/core/values.yaml의 tag를 CI가 커밋 → Argo CD가 감지 → 롤링 업데이트
> ```
> - **CI(이미지 만들기)와 CD(Git대로 맞추기)를 분리.** CI는 클러스터에 직접 손대지 않는다 (클러스터 접속 권한이 CI에 없어도 됨)
> - **태그 = 커밋 해시, `latest` 금지:** `latest`는 매니페스트 글자가 안 바뀌어서 Argo CD가 변화를 모르고, 지금 뭐가 떠 있는지 추적 불가
> - **amd64 지정:** 맥북은 arm64, 노드는 amd64 → 로컬 빌드 이미지는 노드에서 `exec format error`
> - 세부: `concurrency`(같은 브랜치 빌드는 **취소하지 않고 하나씩 줄 세움** → values 커밋끼리 충돌 방지), GHA 캐시, 그래도 충돌하면 `pull --rebase` 후 재시도 3회
>
> 🎤 "롤백은 어떻게?" → `git revert` → push. 배포 이력 = Git 이력 (누가 언제 무엇을, 금융권 감사 대응)
> 🎤 "Argo CD Image Updater는 왜 안 썼나?" → 구성 요소가 하나 늘고 메모리가 빠듯. CI 커밋 방식이 가장 흔하다
>
> 📎 `.github/workflows/services.yaml` / [GitOps 노트](../infra/notes/gitops-argocd.md) «3. 이미지가 바뀌는 배포» / [인프라 README](../infra/README.md) «배포 구조 (GitOps)»

## ⭐ 공통 Helm 차트: 프로브 3종, 메모리 limit만 걸고 CPU limit은 안 거는 이유

> 💡 **핵심**
> - **공통 차트 하나 + 서비스별 values:** 서비스 6개의 Deployment·Service·Ingress가 거의 같다 → 프로브·리소스 제한을 빠뜨린 서비스가 **구조적으로** 안 나온다
> - **프로브 3종**
>
>   | 프로브 | 실패하면 | 용도 |
>   | --- | --- | --- |
>   | startup | (기동 끝날 때까지 나머지 프로브 보류) | JVM 기동이 느려서 liveness가 먼저 죽이는 것 방지 |
>   | liveness | **재시작** | 재시작으로 낫는 문제만 (데드락 등). DB 장애를 여기 넣으면 전 파드가 재시작 폭주 |
>   | readiness | **Service에서 제외** (트래픽 안 받음) | 잠깐 못 받는 상태 (기동 중, 종료 중, 과부하) |
> - **CPU limit 없음, 메모리 limit만:** JVM은 기동 때 CPU를 많이 쓴다 → CPU limit이 있으면 스로틀링 → 기동이 몇 배 느려짐 → startupProbe 실패 → 재시작 루프. 메모리는 넘치면 노드 전체가 위험하니 limit을 건다
>
> 🎤 "liveness에 DB 연결 체크를 넣으면?" → DB가 잠깐 죽으면 **모든 파드가 동시에 재시작**. 재시작해도 DB는 안 살아난다. 장애를 키우는 대표적 실수
> 🎤 "CPU limit을 안 걸면 한 파드가 노드 CPU를 다 먹지 않나?" → requests로 스케줄링·우선순위는 보장된다. 남는 CPU를 빌려 쓰는 것뿐
>
> 📎 `deploy/helm/spring-service/` (values.yaml 주석) / [인프라 README](../infra/README.md) «공통 차트의 실무 포인트»

## ⭐ 무중단 롤링(`maxSurge`/`maxUnavailable`)과 종료 순서(preStop → SIGTERM → graceful shutdown)

> 💡 **핵심**
> - **`maxSurge: 1`, `maxUnavailable: 0`:** 새 파드를 먼저 하나 띄우고, **Ready가 된 뒤에** 기존 파드를 내린다 → replicas 1이어도 무중단
> - **종료 순서**
>   ```
>   ① 파드 삭제 결정 → 엔드포인트에서 제거 시작 (Traefik·kube-proxy에 퍼지는 데 시간이 걸림)
>   ② preStop sleep 5초      ← 그동안 아직 들어오는 요청을 받아 준다
>   ③ SIGTERM → Spring graceful shutdown (새 요청 거절, 처리 중인 요청은 끝까지, 최대 30초)
>   ④ 45초(terminationGracePeriodSeconds)가 지나도 안 끝나면 SIGKILL
>   ```
> - preStop이 없으면: 엔드포인트 제거가 퍼지기 전에 앱이 먼저 닫혀서 **배포할 때마다 502가 몇 개씩** 난다
> - 숫자 관계: preStop 5 + graceful 30 < grace period 45
>
> 🎤 "송금 처리 중에 파드가 죽으면?" → graceful shutdown이 처리 중 요청을 끝까지 기다린다. 그래도 SIGKILL·노드 장애는 막을 수 없다 → 그래서 멱등 키·트랜잭션·결과 불명 처리가 필요 (17주 차 카오스 실험)
>
> 📎 `deploy/helm/spring-service/templates/deployment.yaml`, `services/core/src/main/resources/application.yaml` (`server.shutdown: graceful`, `timeout-per-shutdown-phase`) / [인프라 README](../infra/README.md) «공통 차트의 실무 포인트»

## PVC / PV / volumeMount, local-path의 한계

> 💡 **핵심**
> - **PVC = 요청서** ("5Gi 디스크 주세요") → **PV = 실제 디스크** (StorageClass가 만들어 줌) → **volumeMount = 컨테이너 안의 경로**에 연결
> - **local-path:** PV가 **특정 노드의 디스크 폴더**다. 가볍지만, 그 노드가 죽으면 데이터도 못 쓰고 파드도 다른 노드로 못 옮긴다
> - 실무 대안: 네트워크 스토리지(Ceph/Longhorn, 클라우드 EBS) 또는 DB 자체 복제(CNPG replica)
>
> 🎤 "DB 파드를 지우면 데이터는?" → PVC·PV가 남아서 새 파드가 같은 디스크를 붙인다. "DB가 있는 노드를 끄면?" → local-path라 못 옮긴다 → replica로 페일오버해야 함
>
> 📎 CLAUDE.md 백로그 "스토리지 복습" (실습: DB 파드 삭제, 노드 끄기) / `kubectl -n bank get pvc,pv`

## 업무 예외: sealed class + 에러 코드 + RFC 9457 Problem Details

> 💡 **핵심**
> - **sealed class:** 하위 예외가 한 파일 안에서만 생긴다 → 예외→HTTP 매핑의 `when`에서 **빠뜨리면 컴파일 에러**
> - **에러 코드(`INSUFFICIENT_BALANCE`):** 클라이언트(transfer 등)가 메시지 문자열이 아니라 코드로 분기. 메시지는 바뀌어도 코드는 안 바뀐다
> - **RFC 9457 Problem Details:** 에러 응답 JSON의 표준 형식 (`type`, `title`, `status`, `detail` + 확장 필드 `code`)
> - 도메인은 HTTP를 모른다. 상태 코드는 api 계층(`AccountExceptionHandler`)이 정한다
> - 잔액은 예외 메시지에 넣지 않는다 (로그·응답으로 퍼지는 민감 정보)
>
> 📎 `account/domain/exception/AccountException.kt`, `account/api/AccountExceptionHandler.kt`

## JPA: 앱이 만든 UUID와 `@Version` (새 엔티티 판단, INSERT vs merge), 더티 체킹

> 💡 **핵심**
> - **ID를 앱이 만드는 이유:** 저장 전에도 ID가 있어서 원장·이벤트에 바로 쓸 수 있다
> - **함정:** Spring Data의 `save()`는 "ID가 있으면 기존 엔티티"로 보고 SELECT 후 merge → 불필요한 쿼리. **`@Version`이 null이면 새 엔티티**로 판단해서 바로 INSERT
> - **더티 체킹:** 트랜잭션 안에서 조회한 엔티티의 필드를 바꾸면, `save()` 없이도 커밋 때 UPDATE가 나간다 (`version`도 +1)
>
> 🎤 "`save()`를 왜 안 불러요?" → 영속성 컨텍스트가 변경을 감지한다. 불러도 되지만 의미 없는 호출
>
> 📎 `account/domain/Account.kt` (`version` 주석), `AccountRepositoryTest` "version이 오른다" / [worklog](../worklog.md) 11-12 트러블슈팅 마지막 줄

## ⭐ 복식부기: 차변·대변, 계정(현금 / 고객예금), 입금·출금·송금 분개

> 💡 **핵심** (도메인 지식이라 정답)
> - 모든 거래를 **두 번** 적는다: 한쪽은 차변(왼쪽), 한쪽은 대변(오른쪽). **차변 합 = 대변 합**이 항상 성립해야 한다
> - 은행 입장에서 **고객 예금은 빚(부채)**이다. 부채는 늘면 대변, 줄면 차변. 현금(자산)은 그 반대
>
>   | 거래 | 차변 | 대변 |
>   | --- | --- | --- |
>   | 입금 1만 | 현금 +1만 | 고객예금(A) +1만 |
>   | 출금 1만 | 고객예금(A) −1만 | 현금 −1만 |
>   | 당행 송금 A→B | 고객예금(A) −1만 | 고객예금(B) +1만 ← **현금은 안 움직임** |
> - 잔액은 원장의 **결과(캐시)**이고, 원장이 **진실**. 일일 대사 = "계좌 잔액 = 그 계좌 분개 줄의 합"인지 확인
>
> 🎤 "그냥 잔액만 바꾸면 안 되나?" → 왜 바뀌었는지 기록이 없다. 틀렸을 때 추적·복구가 불가. 원장이 있으면 잔액은 언제든 다시 계산 가능
>
> 📎 `ledger/domain/JournalEntry.kt` (companion 팩토리 3개) / [도메인 노트](../domain/README.md) «2. 잔액과 원장»

## ⭐ 애그리거트 루트(JournalEntry)와 불변식(차변 합 = 대변 합), 거래 불변

> 💡 **핵심**
> - **애그리거트:** 함께 일관성을 지켜야 하는 객체 묶음. 거래(JournalEntry) + 분개 줄(JournalLine)이 하나
> - **루트를 통해서만:** 분개 줄 생성자가 `internal`, 줄 리포지토리는 만들지 않는다 → 줄을 따로 추가·수정해서 균형을 깨는 경로가 없다
> - **불변식은 생성 시 검사:** `init`에서 `require(debit == credit)`. 균형이 안 맞는 거래 객체는 **존재할 수 없다**
> - **거래 불변:** 잘못된 거래는 고치지 않고 **반대 거래를 새로 남긴다** (회계 원칙. 이력이 지워지지 않음)
>
> 🎤 "줄 하나만 수정하고 싶으면?" → 안 된다. 취소(반대) 거래 + 새 거래. 감사 추적을 위해 원장은 append-only
>
> 📎 `ledger/domain/JournalEntry.kt`, `JournalLine.kt` (클래스 주석)

## 양방향 1:N 매핑, 연관관계 주인, cascade, 지연 로딩

> 💡 **핵심**
> - **연관관계 주인 = FK를 가진 쪽 = `JournalLine.entry` (`@ManyToOne`).** `JournalEntry._lines`는 `mappedBy`로 읽기 전용 거울
> - **양쪽을 함께 맞춰야 한다:** 한쪽(리스트)만 넣으면 `entry_id`가 비어서 INSERT 실패 → `init`에서 `attachTo(this)`
> - **cascade PERSIST:** 거래를 저장하면 줄도 같이 저장
> - **지연 로딩(LAZY):** 거래를 조회해도 줄은 접근할 때 SELECT. 트랜잭션 밖에서 접근하면 `LazyInitializationException` (오늘 테스트에서 `TransactionTemplate`으로 감싼 이유)
>
> 📎 `JournalEntry.kt`, `JournalLine.kt` / `JournalEntryRepositoryTest` (지연 로딩 테스트 2개)

## 모듈 경계: 다른 모듈 엔티티 대신 ID만, 모듈 간 FK를 안 거는 이유

> 💡 **핵심**
> - `Account.withdraw(amount, ledgerEntryId: UUID)`: JournalEntry 객체가 아니라 **ID만** 받는다. account가 ledger의 클래스를 알면 모듈이 엉킨다
> - 분개 줄의 `account_id`에 **FK를 안 건다:** 다른 모듈(스키마)의 테이블이라서. 정합성은 앱 + 일일 대사로
> - 같은 애그리거트 안(거래 ↔ 줄)은 FK를 건다
> - 언젠가 모듈을 서비스로 떼어 낼 때, 이 경계가 지켜져 있으면 DB를 나누기 쉽다
>
> 🎤 "FK가 없으면 없는 계좌 ID가 원장에 들어가지 않나?" → posting이 같은 트랜잭션에서 계좌를 조회하므로 없는 계좌면 롤백된다 (오늘 테스트로 증명). 그 밖의 어긋남은 대사가 잡는다
>
> 📎 `V2__create_ledger_schema.sql` (FK 주석), CLAUDE.md 2장 "DB per service" 원칙
