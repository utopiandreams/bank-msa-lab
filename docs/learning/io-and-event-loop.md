# I/O 모델과 이벤트 루프: Redis 클라이언트로 들여다보기

> 2026-11-22 개발자 질문에서 시작 ("pub/sub 락은 스레드를 어떻게 재우고 누가 깨우나?" → "epoll로 여러 소켓을 보나?" → "pub/sub 메시지가 요청 사이에 끼면?"). 개발자 요청: 더 깊은 곳까지 공부하고, 나중에 다시 떠올릴 수 있게 남긴다.
> 사실 확인: Redisson 4.8.0 jar를 열어 확인한 것은 ✅ 표시. 14주 차(게이트웨이 MVC vs WebFlux, 이벤트 루프 블로킹 재현) 전에 다시 읽는다.

## 1. 스레드가 "기다린다"의 세 가지 모양

| | 무엇을 기다리나 | 누가 깨우나 | 예 |
| --- | --- | --- | --- |
| `Thread.sleep(n)` | 시간 | 타이머만. 기다리던 일이 먼저 끝나도 시간까지 잔다 | Redisson 스핀 락의 백오프 |
| 블로킹 소켓 읽기 | 내 소켓에 데이터 도착 | 커널 | JDBC 쿼리 응답 대기 |
| 동기화 도구에서 멈춤 (`Semaphore`, `Future.get`) | 다른 스레드의 신호 | 신호를 준 스레드 (`release`, 결과 설정) | Redisson pub/sub 락 대기 |

- 💡 셋 다 기다리는 동안 CPU는 0이다 (OS 스케줄러 목록에서 빠짐). 차이는 **깨어나는 조건**
- 💡 `sleep`은 "일이 끝났나"를 모른다 → 스핀 락은 락이 풀린 뒤에도 남은 sleep을 흘려보낸다 (핫 계좌 처리량 저하의 원인)

## 2. Redisson pub/sub 락은 어떻게 기다리고 누가 깨우나 ✅

```
[요청 스레드 A]                 [Redis]                         [쥔 쪽 B]
1. Lua로 획득 시도 ──────────▶ 키 있음 → 남은 TTL 반환
2. 채널 구독 ────────────────▶ SUBSCRIBE redisson_lock__channel:{키}
3. semaphore.tryAcquire(남은 TTL) → 멈춤
                                                               4. unlock Lua: 키 삭제 + PUBLISH "0"
                               ◀────────────────────────────
                               5. 구독 연결로 메시지를 밀어 보냄 (앱이 묻지 않아도)
[같은 JVM의 Netty 이벤트 루프 스레드]
6. 메시지 수신 → LockPubSub.onMessage → semaphore.release()  ← 허가증 1장 = 대기자 1명만 깨움
7. A가 깨어나 1번부터 다시 (그 사이 새로 온 요청이 먼저 잡았으면 다시 잠듦 = 불공정)
```

- ✅ 획득 Lua: `exists == 0 또는 hexists(내ID) == 1이면 hincrby(+1)·pexpire·return nil, 아니면 return pttl` → 재진입은 카운트, 실패하면 **남은 TTL**을 알려 준다
- ✅ 해제 Lua: `hincrby(-1)` → 0이면 `del` + 채널에 PUBLISH
- ✅ `RedissonLockEntry` 안의 `java.util.concurrent.Semaphore`가 대기 장치. `UNLOCK_MESSAGE`가 오면 `release()` (한 장)
- 💡 **메시지가 안 오면?** 쥔 쪽이 unlock 전에 죽으면 PUBLISH가 영영 없다 → 그래서 대기 시간을 "남은 TTL"로 잡는다. 키가 만료될 즈음 스스로 깨어나 다시 시도
- 💡 같은 JVM의 대기자들은 구독 하나를 공유하고 메시지 하나에 하나씩 깨어난다 → JVM 안에서는 우르르 몰려들기(thundering herd)가 없다
- 🎤 "Redisson 락은 기다리는 동안 Redis를 계속 두드리나요?" / "락을 쥔 서버가 죽으면 기다리던 쪽은 어떻게 되나요?" / "스핀 락과 처리량 차이가 나는 이유는?"

## 3. 이벤트 루프와 epoll ✅

- ✅ Redisson 기본값: 전송 `NIO`(자바 `Selector` → 리눅스에선 epoll, 맥에선 kqueue), Netty 이벤트 루프 스레드 `nettyThreads = 32`
- 연결(Netty `Channel`) 하나는 이벤트 루프 스레드 하나에 붙고, 스레드 하나가 여러 연결을 같이 본다

```
[이벤트 루프 스레드]
  epoll_wait(소켓 A, B, C, …)   ← 여러 소켓을 한 번에 걸어 두고 멈춤
  → 커널: "C에 데이터 왔음" → 읽기 → Redis 메시지로 해석 → 등록된 콜백 호출 → 다시 epoll_wait
```

- 💡 **이벤트 루프에서는 절대 오래 붙잡지 않는다.** 콜백은 `release()` 한 번 하고 돌아간다. 실제 일(락 재시도·트랜잭션)은 깨어난 요청 스레드가 한다. 이벤트 루프가 블로킹하면 그 스레드가 맡은 소켓 전부가 멈춘다 → **14주 차 "이벤트 루프 블로킹 재현"**, gateway(Spring Cloud Gateway)도 같은 Netty 구조
- 💡 요청 하나 안에 두 모델이 섞여 있다: Tomcat 요청 스레드가 `tryLock`에서 세마포어로 멈춤 → Netty가 깨움 → 같은 Tomcat 스레드가 JDBC로 자기 소켓을 블로킹으로 기다림
- 🎤 "epoll이 뭔가요? select와 차이는?" / "Netty 이벤트 루프에서 블로킹 호출을 하면?" / "thread-per-request와 이벤트 루프 모델의 차이는?"

## 4. Java Redis 클라이언트별 I/O

| 클라이언트 | I/O | pub/sub 대기 |
| --- | --- | --- |
| Redisson | Netty 이벤트 루프 | 이벤트 루프가 메시지 받아 콜백 |
| Lettuce (Spring Data Redis 기본) | Netty 이벤트 루프 | 같음 |
| Jedis | 블로킹 소켓 | `subscribe()`를 부른 스레드가 연결을 붙잡고 계속 읽음 = 구독마다 스레드 하나 |

- 💡 Redisson·Lettuce는 **동기 API도 속은 비동기**: `tryLock()`은 명령을 이벤트 루프에 넘기고 부른 스레드가 Future를 기다린다. 그래서 `tryLockAsync()`도 있다 (엔진 하나, 겉모양만 다름)
- 💡 같은 구조: Kafka 클라이언트(전용 네트워크 스레드), Spring WebClient, gateway

## 5. 동기 코드에서 속이 비동기면 뭐가 좋나 (스레드는 어차피 멈추는데)

- 💡 **부른 스레드 입장에서는 이점이 없다.** 이점은 연결과 뒤에서 도는 일에서 나온다
- **연결 공유 (가장 큰 이점):** 블로킹 클라이언트는 응답이 올 때까지 연결을 독점 → 동시 요청 수만큼 연결 필요, 모자라면 풀 대기 (Hikari 커넥션 풀 고갈과 같은 병목, 11/18 k6 stress). 이벤트 루프 클라이언트는 스레드 200개가 연결 몇 개를 같이 쓴다
- **뒤에서 도는 일에 스레드가 안 든다:** 구독, 락 워치독(TTL 연장), 재접속, 명령 타임아웃 → 이벤트 루프의 타이머로
- 엔진 하나로 동기·비동기·리액티브. 가상 스레드에서는 Future 대기 비용이 거의 없어 "겉은 동기, 속은 비동기"가 특히 잘 맞는다
- 대가: 스레드를 한 번 건너가는 비용(마이크로초), 예외 스택이 이벤트 루프에서 끊겨 디버깅이 어렵다

## 6. 연결 하나에 요청 여러 개: 짝은 어떻게 맞추나

- 💡 "채널"이 세 가지 뜻으로 쓰인다: **Netty Channel**(= 소켓 = TCP 연결, 적음) / **Redis pub/sub 채널**(구독 주제 이름, 락 키마다) / **기다리는 요청**(보내 놓은 명령의 Future, 많음)
- 많아지는 건 연결이 아니라 **메모리 안의 대기 항목**

```
소켓 1개
  보냄 → GET a, SET b, EVAL 락스크립트 ...      (응답 안 기다리고 줄줄이 = 파이프라이닝)
  대기열: [Future1, Future2, Future3, ...]
  받음 ← 응답1, 응답2, 응답3 ...                 (Redis는 한 연결 안에서 받은 순서대로 답한다)
         → 대기열 맨 앞 Future에 결과 → 주인 스레드를 깨움
```

- 💡 응답에 "누구 것" 표시가 없어도 **순서**로 짝을 맞춘다. 그래서 소켓을 늘릴 필요가 없다

## 7. pub/sub은 왜 연결을 따로 쓰나

- 💡 pub/sub 메시지는 요청 없이 아무 때나 온다 → 일반 명령 연결에 섞이면 순서로 짝 맞추기가 깨진다 (GET b의 Future에 해제 메시지가 들어감)
- RESP2: 연결에서 `SUBSCRIBE`하면 **구독 모드**가 되어 구독·구독 해제·PING 같은 몇 가지 명령만 받는다. 일반 명령은 오류
- 그래서 Redisson은 **명령용 연결 풀**과 **구독용 연결 풀**을 나눈다. 구독 연결로 오는 건 전부 "어느 주제의 메시지"라 이름표로 분배
- RESP3 (Redis 6+): push라는 별도 타입이 생겨 한 연결에 섞여도 구분 가능 (클라이언트 측 캐시 무효화 알림이 사용). Redisson 기본은 여전히 구독 연결을 따로 둔다
- 같은 이유로 `BLPOP`처럼 **서버 쪽에서 기다리는 명령**도 전용 연결이 필요하다 (공유 연결에서 쓰면 뒤 요청이 전부 막힘)
- 💡 원칙: 순서로 짝을 맞추는 일반 명령은 연결을 나눠 쓰고, 순서를 깨는 것(밀어 보내는 메시지, 서버 쪽 대기)은 연결을 따로 둔다
- 🎤 "한 연결로 여러 요청을 동시에 보내면 응답은 어떻게 구분하나요?" / "pub/sub 연결에서 GET을 하면?" / "RESP3는 뭐가 달라졌나요?"

## 8. 락 한 번에 Redis 명령이 몇 개 나가나 (13개, 왕복은 4번) ✅

> 2026-11-23 k6 락 비교에서 "송금 1건에 Redis 명령 약 26개"가 나와 시작. 개발자 질문: "Lua 스크립트가 아니라 단건 요청을 여러 번 한 거야?"
> 확인: Redisson 4.8.0 jar의 `RedissonLock`·`RedissonBaseLock` 상수 문자열(Lua)과 바이트코드, 우리 `RedisAccountLocks.kt:40`. 측정: `INFO commandstats` 전후 차이 (송금 약 101건 × 계좌 2개 = 락 약 203번)

- 💡 **Redis는 Lua 스크립트 안의 `redis.call`도 하나씩 센다.** `INFO commandstats`·`total_commands_processed`에 `evalsha` 1개와 그 안의 `exists`·`hincrby`… 가 모두 잡힌다 → "명령 26개 ≠ 네트워크 왕복 26번"
- 💡 락 하나(잡기 → 확인 → 풀기)의 실제 모습:

| 순서 | 누가 | 왕복 | 안에서 실행된 명령 |
| --- | --- | --- | --- |
| ① `tryLock` | Redisson Lua (`evalsha`) | 1 | `exists` → (없으니 `or` 뒤 `hexists`는 건너뜀) `hincrby +1` · `pexpire` |
| ② `isHeldByCurrentThread` | **우리 코드**, 단건 `HEXISTS` | 1 | `hexists` |
| ③ `unlock` | Redisson Lua (`evalsha`) | 1 | `get`(풀기 기록) · `hexists` · `hincrby -1` · `del` · `publish`(대기자 깨우기) · `set`(풀기 기록) |
| ④ 풀기 기록 정리 | Redisson 단건 `DEL` | 1 | `del` |
| 합 | | **4** | **13** (= evalsha 2 + 안쪽 9 + 단건 2) |

  송금 1건 = 계좌 2개 잠금 → 명령 26개, 왕복 8번. 측정값(명령 종류별 ÷ 101)과 정확히 맞는다
- 💡 **③의 `get`/`set KEYS[3]`은 "풀기의 멱등 키"다.** 풀기 요청의 응답이 유실돼 Redisson이 재시도하면, 이미 푼 락을 또 풀다 남의 락을 건드리거나 에러가 나지 않게 처음 결과를 기록해 두고 그대로 돌려준다 (요청 ID별 키, 짧은 만료). 이 프로젝트의 송금 멱등 키와 같은 발상이 라이브러리 안에도 있다
- 💡 **②는 우리가 넣은 왕복이다** (전체 왕복의 1/4). 목적은 "임대 시간(lease)이 지나 이미 풀린 락을 unlock하면 `IllegalMonitorStateException`"을 피하려는 것. 그런데 확인과 풀기 사이에도 만료될 수 있어서(TOCTOU) 완전히 막지도 못한다. 대안: 확인 없이 unlock하고 그 예외를 잡기 → 왕복 1번 절약, 안전성은 같음. (바꿀지는 개발자 판단, 아직 안 바꿈)
- 💡 경합이 없어도 이 비용은 그대로 든다 → spread(경합 거의 없음)에서도 송금당 26개였던 이유. DB 락(PESSIMISTIC·ATOMIC)은 이 왕복이 0이다 = **분산 락의 기본 요금**
