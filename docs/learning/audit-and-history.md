# 거래 이력과 감사 기록

질답 모음 (CLAUDE.md 6장 7-1-0). 8주 차 2부에서 "수작업으로 고쳤다는 기록"을 이야기하다 나온 질문들.

## 1. 송금 상태 이력을 실무에서는 다 쌓아 두나? (2026-11-25)

- 💡 **금융에서는 거의 다 쌓는다.** 송금 행은 현재 상태만 담고 덮어쓰지만, "언제 어떤 상태가 됐나"는 따로 추가만 하는(append-only) 이력으로 남긴다. 이유는 셋:
  1. **법적 보존 의무:** 전자금융거래법(제22조 전자금융거래기록의 생성·보존)이 거래 기록을 만들고 보존하게 한다. 시행령이 항목별로 기간을 정한다(거래 내용은 5년, 일부 항목은 1년). 보존 기간이 지나면 **파기**도 의무다 (개인정보)
  2. **민원·분쟁:** "이체했는데 돈이 안 갔어요" → 요청 시각, 출금 시각, 외부 전송 시각, 결과 불명, 해소 시각을 타임라인으로 보여 줘야 한다. 현재 상태(`CANCELLED`)만으로는 "왜 늦었나"에 답을 못 한다
  3. **장애 분석·감사:** 결과 불명에 얼마나 머물렀나(에이징), 누가 수작업으로 바꿨나
- 💡 **돈 쪽과 처리 쪽을 나눠 생각한다.** 돈이 움직인 기록은 이미 **원장**(복식부기 전표, 불변, 취소도 역분개)에 남는다. 상태 이력은 **처리 과정**(송금이 어떤 단계를 거쳤나)의 기록이다. 둘 다 덮어쓰지 않는다는 점이 같다
- 💡 **무엇을 쌓나:** 컬럼 하나하나의 변경이 아니라 **상태 전이** + 누가(시스템/해소 일꾼/담당자 ID) + 왜(사유 코드) + 언제. 송금 한 건에 행 4~6개 정도라 양은 송금 테이블의 몇 배 수준
- 💡 **양이 많아지면:** 날짜로 파티션을 나누고, 오래된 파티션은 싼 저장소로 옮기고(아카이빙), 보존 기간이 지나면 파티션째 지운다 (행 단위 DELETE보다 싸다). 조회는 최근 것만 빠르면 된다
- 💡 **꼭 같은 트랜잭션에 쓴다:** 상태는 바뀌었는데 이력이 없거나 그 반대면 기록을 믿을 수 없다 (outbox와 같은 dual write 문제, pitfalls 30)
- 🎤 "거래 상태를 덮어쓰면 과거를 어떻게 추적하나요?" → 현재 상태 테이블 + append-only 이력 테이블, 같은 트랜잭션. 돈의 기록은 원장(불변)이 따로
- 🎤 "이력 테이블이 계속 커지면요?" → 날짜 파티션, 아카이빙, 보존 기간 뒤 파티션째 파기
- 🎤 "이벤트 소싱으로 하면 되지 않나요?" → 이력이 곧 상태라 이력 누락이 구조적으로 없지만, 조회 모델·스냅숏·스키마 진화 비용이 크다. 상태 몇 개짜리 송금엔 이력 테이블로 충분
