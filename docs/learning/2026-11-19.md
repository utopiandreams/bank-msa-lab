## ⭐⭐ 1. 지표 보는 순서: 증상 → 범인 → 원인 → 근본

오늘 k6 stress 붕괴를 **직접** 쫓아간 경로를 일반화한 것. 장애 때 처음 보는 대시보드에서도 이 순서는 같다.

### 1-1. 네 단계

| 단계 | 질문 | 오늘 본 화면 | 오늘 찾은 것 |
| --- | --- | --- | --- |
| ① 증상 | 고객이 뭘 느끼나? (언제부터, 얼마나) | Explore: `http_server_requests` p99 (서비스별) | 17:24부터 p99 급등, transfer만 3.5초 |
| ② 범인 | **어느 서비스**인가? | 같은 쿼리를 서비스별로 나눠 봄 | core는 156ms, **transfer**만 튐 → 범인은 transfer |
| ③ 원인 | 그 서비스의 **어느 자원**이 막혔나? | Kubernetes / Compute Resources / Pod → 메모리·재시작 / JVM 대시보드 → 힙·스레드·Hikari | 메모리가 한도까지 → OOMKilled ×4. 힙은 여유, **스레드 WAITING 300**, **Hikari 10/10, 대기 183** |
| ④ 근본 | 왜 그 자원이 막혔나? 무엇이 **먼저** 꺾였나? | 시간축을 맞춰 여러 그래프의 "꺾인 시점" 비교 | **커넥션 풀이 먼저** 찼다 → 스레드가 줄 섬 → 힙 밖 메모리 → OOMKilled → gateway까지 전파 |

- 💡 **위에서 아래로.** 사용자가 느끼는 것(지연·에러)에서 시작해 서비스 → 파드 → 자원 순으로 좁힌다. 자원(CPU·메모리)부터 보면 "높은데 정상"인 값에 낚인다
- 💡 **"먼저 꺾인 것"이 원인 후보, "나중에 꺾인 것"은 피해자.** 오늘 메모리·재시작은 눈에 가장 띄었지만 피해자였고, 원인은 커넥션 풀이었다. 메모리만 늘렸으면 같은 장애가 조금 뒤로 밀렸을 뿐
- 💡 **한 서비스 안에서도 순서가 있다:** 요청이 들어오는 길을 따라간다. Tomcat 스레드(입구에서 줄 서나?) → 커넥션 풀(DB 앞에서 줄 서나?) → DB 자체(느린가?). 오늘은 DB는 멀쩡했고(core p99 156ms) **풀 앞에서** 줄이 섰다
- 💡 **증상 → 원인으로 가는 다리 = 포화(saturation) 지표.** "대기 중"을 세는 숫자(Hikari pending, Tomcat busy == max, 컨슈머 랙)가 0에서 올라가는 순간이 병목의 시작이다. 사용률(utilization)만 보면 놓친다: Hikari active 10/10은 "다 쓰는 중"일 뿐이고, **pending 183**이 "줄이 183명"이라는 증거

### 1-2. 4대 지표 (Golden Signals)와 우리 화면

| 신호 | 뜻 | 우리 화면에서 | 오늘 |
| --- | --- | --- | --- |
| **지연** (Latency) | 얼마나 느린가 (p50·p99) | `histogram_quantile(0.99, ... http_server_requests_seconds_bucket)` | transfer p99 26ms → 139ms → 3.5s |
| **트래픽** (Traffic) | 얼마나 들어오나 (초당 요청) | `rate(http_server_requests_seconds_count[1m])` / k6 단계 | 20 → 800건/초 |
| **에러** (Errors) | 얼마나 실패하나 | 5xx 비율, k6 실패율, UNKNOWN 수 | HTTP 실패 46.8%, core 5xx 0.3% → 4.9% |
| **포화** (Saturation) | 얼마나 꽉 찼나, **줄이 생겼나** | Hikari pending, Tomcat busy/max, 메모리/한도 | Hikari 대기 183, Tomcat 200/200, 메모리 506/512 |

- 💡 앞의 셋은 **증상**(사용자가 느끼는 것), 포화는 **원인 쪽**이다. 그래서 1-1의 ①②는 지연·에러, ③④는 포화
- 💡 RED(Rate·Errors·Duration) = 서비스 관점, USE(Utilization·Saturation·Errors) = 자원 관점. Golden Signals는 둘을 합친 것 (📎 `observability.md` 1-1)
- 💡 **홈 대시보드**(나중에 만들기로 한 것)는 이 네 개를 서비스별로 한 화면에. 오늘처럼 쿼리를 쳐 가며 찾지 않고 "어 지금 불안하다"를 한눈에 보려는 것. 오늘 찾은 쿼리들이 그 재료

## ⭐ 2. 붕괴 연쇄: 커넥션 풀 → 스레드 → 메모리 → OOMKilled → 전파

- 💡 커넥션 풀 10개가 다 차면 11번째 요청부터 **스레드를 쥔 채** 커넥션을 기다린다. 요청이 계속 들어오면 기다리는 스레드가 계속 늘어난다
- 💡 스레드마다 힙 **밖** 메모리(스택, 네이티브 할당 영역, 연결 버퍼)가 붙는다. 오늘 숫자: 스레드 +273개 ↔ 힙 밖 약 +190Mi = 스레드당 약 0.7Mi (추정, 15주 차에 NMT로 확인)
- 💡 컨테이너 한도를 넘으면 **커널이** 죽인다(OOMKilled, exit 137). JVM의 OutOfMemoryError가 아니라서 자바 로그·힙 덤프가 없다. `kubectl describe pod`의 Last State에서만 보인다
- 💡 transfer가 죽으면 앞단 gateway에 응답 못 받은 연결이 쌓여 gateway도 죽는다 = **장애 전파**. 15주 차 타임아웃·서킷 브레이커·벌크헤드의 "전" 상태
- 💡 해법은 메모리를 늘리는 게 아니라 **못 받을 요청을 빨리 거절**하는 것 (스레드 상한·대기열·429), 그다음 스케일 아웃. 다 받으려다 다 죽는다
- 🎤 "OOMKilled와 OutOfMemoryError의 차이는?" / "커넥션 풀이 막히면 왜 메모리 장애가 나죠?" / "커넥션 풀을 키우면 해결되나요?" (→ DB max_connections로 병목이 옮겨 감. 파드 수 × 풀 ≤ DB 한도)
- 📎 pitfalls 24, 실험 기록 "해결 선택지" 표

## 3. request · limit · 스로틀링

- 💡 **request = 예약**(스케줄러가 노드를 채우는 기준, 경합 시 CPU를 나누는 비율). **limit = 상한**
- 💡 **CPU는 압축 가능:** 모자라면 느려질 뿐. limit이 있으면 100ms마다 몫을 다 쓰면 다음 주기까지 강제로 멈춤 = **스로틀링** (노드가 한가해도). 평균 CPU는 낮은데 지연만 튀는 모양. 그래서 CPU는 request만, limit 없음
- 💡 **메모리는 압축 불가:** 돌려받을 방법이 없어 넘으면 죽는다. 그래서 request = limit (빌려 쓰는 구조면 노드가 빡빡할 때 먼저 쫓겨남)
- 💡 기준: CPU request = **평소 부하**에서의 사용량(유휴 0.005가 아니라 60건/초의 0.025), 메모리 = **감당하기로 한 부하**의 피크 + 여유
- 💡 AWS에서도 같다: EKS는 쿠버네티스 그대로, EC2 t3는 "평소 적게, 가끔 몰아 쓰기"를 상품으로(CPU 크레딧), Fargate만 request = 상한
- 🎤 "CPU limit을 거는 게 좋나요?" / "request를 너무 낮게 잡으면?" / "JVM 컨테이너 메모리는 어떻게 잡나요?"
- 📎 `deploy/helm/spring-service/values.yaml` 주석, pitfalls 16

## 4. 노드 확장과 스케줄러

- 💡 스케줄러는 **파드가 생길 때만** 노드를 고른다. 노드를 늘려도 기존 파드는 안 옮겨 간다 (옮기려면 재시작·descheduler)
- 💡 로컬 디스크(local-path)에 데이터가 있는 파드(DB·Kafka)는 재시작해도 원래 노드로 돌아간다 (디스크가 노드에 묶임)
- 💡 스케줄러는 물리 호스트를 나눠 주지 않는다 → 오늘 서비스가 전부 proxmox2로 몰림. 나누려면 `topology.kubernetes.io/zone` 라벨 + `topologySpreadConstraints` + replicas 2 이상 (17주 차)
- 💡 VM을 잘게 쪼개면 손해: VM마다 고정 비용(OS·kubelet·DaemonSet), 조각화, 같은 호스트라 호스트 장애엔 무력
- 🎤 "노드를 추가했는데 파드가 그대로입니다. 왜죠?" / "AZ 장애에 대비한 파드 배치는?"
- 📎 `docs/infra/README.md` "노드 확장", 실험 기록 "측정 뒤 바꾼 것"

## 5. 호스트가 사라졌을 때 (오늘 밤 사고)

- 💡 ping이 아니라 **ARP 단계에서 막힘**(`INCOMPLETE`) = 그 IP의 주인이 응답하지 않음. 맥북·노트북 둘 다에서 같으면 네트워크 쪽이 아니라 그 기계 쪽
- 💡 원인: proxmox 자기 랜 링크가 끊김(10Mbps/Half로 붙었다 끊김 = 접촉 불량 신호). **켜져 있는데 네트워크만 끊긴 상태라 Wake-on-LAN이 소용없었다** (WOL은 꺼진 기계를 깨우는 기능)
- 💡 확인 순서: 다른 기기에서도 안 보이나 → ARP → 물리(전원 LED, 랜 LED) → 복구 후 `journalctl -b -1`로 직전 부팅의 마지막 로그
- 🎤 "서버가 응답하지 않습니다. 무엇부터 확인하나요?"
- 📎 `docs/worklog.md` 2026-11-18 (밤) 트러블슈팅

## ⭐ 6. 사가: 피벗 트랜잭션과 보상

- 💡 단계를 **되돌릴 수 있는지**로 나눈다. 피벗(되돌릴 수 없는 지점, 외부 송금 성공) **앞은 보상**(뒤로 복구), **뒤는 재시도**(앞으로 복구). 되돌릴 수 없는 단계는 최대한 뒤에
- 💡 "보냈을 수도 있다"(INTERBANK_REQUESTED)에서 결과를 모르면 **보상 금지** → 확인 먼저. 실제로 입금됐다면 보상은 이중 지급
- 💡 FAILED(돈이 한 번도 안 움직임) ≠ CANCELLED(빠졌다 돌아옴): 원장 두 줄, 고객 거래 내역, 대사 대상이 다르다
- 💡 확실한 거절은 200 + REJECTED: 5xx로 주면 호출자가 결과 불명으로 보고 보상 대신 멈춘다
- 🎤 "분산 트랜잭션을 어떻게 처리했나요?" / "보상이 불가능한 단계는?" / "보상이 실패하면?" / "오케스트레이션과 코레오그래피 차이는?"
- 📎 `docs/adr/0004-interbank-transfer-saga.md`, `docs/design-drills/04-interbank-transfer.md`

## ⭐ 7. 멱등 키 vs 자연 키

- 💡 **멱등 키**: 요청한 쪽이 만든 ID. 요청자가 키를 제대로(재시도마다 같게) 만들어 줘야 한다
- 💡 **결정적 키**: 무작위가 아니라 규칙으로 만든 키 (`{송금ID}-cancel`). 재시도해도 같은 값
- 💡 **자연 키**: 데이터 자체가 유일함을 보장 (`reverses_entry_id` UNIQUE = 한 출금은 한 번만 취소). 요청자를 믿지 않아도 된다. 오늘 최종 선택
- 💡 같은 이유로 취소 요청은 금액을 보내지 않고 **원래 출금을 가리킨다** → 과다 환불이 구조적으로 불가능
- 💡 멱등 키는 **서비스마다, 동작마다 따로**: core 입장에서 출금과 취소는 다른 거래라 같은 키를 쓰면 취소가 출금의 재요청으로 보인다
- 🎤 "보상 트랜잭션의 멱등성은 어떻게 보장했나요?" / "동시에 두 번 취소 요청이 오면?"
- 📎 `services/core/.../ledger/domain/JournalEntry.kt` (`cancelOf`), `V3__interbank_transfer.sql`, `InterbankPostingTest` (동시 취소)

## 8. DB 재시작이 몇 분 걸린 이유 (스마트 종료)

- 💡 Postgres 종료는 세 가지: **smart**(새 접속 거절, 기존 클라이언트가 스스로 나갈 때까지 기다림) / **fast**(진행 중 트랜잭션을 끊고 종료) / **immediate**(즉시, 다음 기동 때 복구)
- 💡 CNPG는 smart부터 시도하는데, 앱의 커넥션 풀은 커넥션을 **계속 열어 두는 게 일**이라 스스로 안 나간다 → `smartShutdownTimeout` 180초를 다 기다린 뒤 fast. 그래서 메모리 설정 하나 바꿨는데 DB가 4분 멈춤
- 💡 단일 인스턴스 DB의 설정 변경 = 다운타임 작업. 운영이면 레플리카 + switchover, 또는 점검 시간
- 🎤 "DB 설정 변경을 무중단으로 하려면?"
- 📎 pitfalls 26

## 9. 모노레포 CI 변경 감지

- 💡 레포가 하나라 "푸시됐다"만으로는 무엇이 바뀌었는지 모른다 → 전부 빌드·재배포 (안 바뀐 서비스까지 재시작 = 배포 위험 증가)
- 💡 규칙: 서비스 폴더 → 그 서비스 / 공통 라이브러리 → **의존하는 서비스만** (의존성 그래프) / 빌드 공통 파일 → 전부 / 판단 불가 → 전부 (애매하면 많이 빌드하는 쪽이 안전)
- 💡 더 큰 규모: Bazel·Nx·Turborepo (그래프 계산 + 빌드 캐시)
- 🎤 "모노레포에서 CI를 어떻게 효율화했나요?" / "변경 감지가 틀리면?"
- 📎 `.github/scripts/changed-services.sh`, pitfalls 14

## 10. IaC·GitOps에서 "지우기"와 "바꾸기"의 함정

- 💡 **Terraform:** "생성 때만 쓰는 값"(cloud-init·user-data·AMI)을 바꾸면 그 자리 수정이 아니라 **교체**(서버 재생성). 리소스를 모듈로 옮기면 `moved`가 없을 때 삭제 + 생성. **apply 전에 plan에서 destroy/replace를 찾는다**
- 💡 **Argo CD:** Application 파일을 지워도 finalizer가 없으면 앱이 만든 리소스는 남는다. 반대로 DB 앱에 finalizer를 붙이면 파일 하나 지우는 실수가 DB 삭제가 된다
- 💡 **Flyway:** 이미 적용된 파일은 주석 한 줄도 고치지 않는다 (체크섬 → 기동 거부). 오늘 Claude가 실수로 고쳤다가 커밋 전에 되돌림
- 🎤 "Terraform apply로 운영 서버를 날린 적이 있거나 막아 본 적 있나요?" / "GitOps에서 리소스를 안전하게 지우려면?"
- 📎 pitfalls 11·25, `docs/infra/README.md` 트러블슈팅 2026-11-19
