## ⭐ 1. 왜 합의가 필요한가

- 💡 여러 대가 "같은 상태"를 가져야 한다 (클러스터 메타데이터, 누가 리더인가, 설정값). 한 대만 갖고 있으면 그게 죽을 때 끝 → 여러 대에 복제. 그런데 복제하면 **네트워크가 끊겼을 때 서로 다른 결정을 내릴 수 있다** (스플릿 브레인).
  - 스플릿 브레인 예: DB 두 대가 서로 상대가 죽었다고 생각하고 둘 다 "내가 마스터"로 쓰기를 받는다 → 데이터가 두 갈래로 갈라져 합칠 수 없다. **돈이면 이중 출금**
- 💡 해법: **과반수(majority, quorum)가 동의한 것만 결정으로 인정한다.** 과반수는 동시에 두 그룹이 가질 수 없으니까 (5대 중 3대 그룹은 하나뿐), 네트워크가 갈라져도 한쪽만 결정할 수 있다
- 🎤 스플릿 브레인이 뭔가요? / 왜 과반수인가요? (두 과반수는 반드시 겹친다 → 한 대라도 겹치면 두 결정이 충돌하지 않는다)

## ⭐ 2. 왜 홀수 대인가

| 대수 | 과반수 | 버틸 수 있는 장애 |
| --- | --- | --- |
| 1 | 1 | 0 |
| 2 | 2 | **0** (1대보다 나을 게 없고 고장 날 곳만 늘어남) |
| 3 | 2 | 1 |
| 4 | 3 | **1** (3대와 같음, 1대 더 돌릴 뿐) |
| 5 | 3 | 2 |

- 💡 짝수는 홀수보다 버티는 장애 수가 늘지 않는다. 그래서 3, 5대
- 💡 **물리 장애 영역**도 같이 봐야 한다: 서버 3대를 호스트 2대에 2+1로 나누면, 2대 있는 호스트가 죽는 순간 과반수를 잃는다. **장애 영역도 3개 이상**이어야 한다 (데이터센터 2곳이면 세 번째 곳에 작은 중재자(witness)를 둔다)
- 🎤 etcd를 4대로 하면 3대보다 좋은가요? / 데이터센터가 2개인데 HA를 하려면?
- 📎 이 프로젝트: Proxmox 2대를 클러스터로 안 묶음(`docs/infra/README.md`), k3s 컨트롤 플레인 1대 (아래 6)

## ⭐ 3. Raft: 리더 선출

- 💡 노드 상태는 셋: **팔로워**(기본) / **후보** / **리더**
  1. 팔로워는 리더의 **하트비트**를 기다린다. 일정 시간(election timeout, 노드마다 **랜덤**: 예 150~300ms) 안에 못 받으면 리더가 죽었다고 보고 **후보**가 된다
  2. 후보는 **임기(term) 번호를 1 올리고** 자기에게 투표한 뒤, 다른 노드들에게 투표를 요청한다
  3. 각 노드는 **한 임기에 한 표**만 준다 (먼저 요청한 후보에게). 과반수 표를 받으면 **리더**
  4. 리더는 하트비트를 보내 "내가 리더"를 알린다
- 💡 **랜덤 타임아웃**의 이유: 모두 같은 시간에 후보가 되면 표가 갈라져 아무도 과반수를 못 받는다(split vote). 랜덤이면 한 명이 먼저 나서서 대개 바로 정해진다
- 💡 **임기(term)**는 논리 시계다. 옛 임기의 리더가 살아나서 명령을 보내도, 받는 쪽은 "임기가 낮다"며 무시한다 → 옛 리더가 끼어드는 것을 막는다 (펜싱)
- 💡 **투표 조건**: 후보의 로그가 자기보다 **뒤처져 있으면 표를 안 준다** → 커밋된 데이터를 모르는 노드는 리더가 될 수 없다 (아래 4의 안전성)
- 🎤 리더가 죽으면 새 리더가 뽑히기까지 얼마나 걸리나요? (election timeout 수준, 그동안 쓰기 불가) / 두 후보가 동시에 나서면? / 옛 리더가 살아나면?

## ⭐ 4. Raft: 로그 복제와 커밋

- 💡 모든 쓰기는 **리더만** 받는다. 리더는 명령을 자기 로그에 붙이고 팔로워들에게 복제한다
- 💡 **과반수가 받았다고 답하면 커밋**: 그때 비로소 "확정"이고 클라이언트에게 성공을 답한다. 커밋된 것은 리더가 바뀌어도 사라지지 않는다 (과반수가 갖고 있고, 3의 투표 조건 때문에 그걸 가진 노드만 리더가 되므로)
- 💡 과반수가 죽으면? **쓰기를 거부한다** (가용성 포기). 일관성을 지키려고 멈추는 쪽을 택한 것 = CAP에서 **CP**
- 🎤 리더가 복제 도중 죽으면 그 쓰기는? (과반수 전에 죽었으면 클라이언트는 성공을 못 받았고, 결과 불명 → 재시도는 멱등해야 한다. pitfalls 6과 같은 이야기) / 과반수가 죽으면 읽기는 되나요?

## 5. 같은 원리, 다른 시스템

| 시스템 | 무엇을 합의하나 | 방식 | 이 프로젝트에서 |
| --- | --- | --- | --- |
| **etcd** | 쿠버네티스 클러스터 상태 전부 | Raft | k3s 컨트롤 플레인 HA (아래 6) |
| **Kafka KRaft** | 메타데이터, 파티션 리더 | Raft 변형 | 4주 차, 17주 차 (`kafka.md` 9) |
| ZooKeeper (옛 Kafka) | 메타데이터 | ZAB (Raft와 비슷) | — |
| **Redis Sentinel** | "마스터가 죽었나" + 장애 조치 지휘자 | 과반수 투표 + Raft에서 영감받은 리더 선출 | 7주 차 Redis 후보 |
| **Redis Cluster** | 레플리카 승격 | 가십 + 마스터들의 과반수 투표 (Raft 아님) | — |
| **Proxmox (corosync)** | 클러스터 멤버십, 설정 | 과반수 투표(votequorum) | 2대라 안 묶음 |
| DB (Patroni 등) | PostgreSQL 마스터 | etcd·Consul에 리더 락을 맡김 | CloudNativePG는 쿠버네티스 API를 리더 락으로 씀 |

- 💡 공통점: **과반수가 동의해야 리더가 되고, 과반수가 받아야 확정된다.** 다른 점은 "무엇을 합의하나"와 구현 디테일
- 🎤 Redis Sentinel은 왜 최소 3대인가요? / Kafka가 ZooKeeper를 버린 이유? (운영할 시스템이 하나 줄고, 메타데이터 규모 한계)

## ⭐ 6. 이 프로젝트의 컨트롤 플레인

- 지금: k3s 서버(컨트롤 플레인) **1대**, 저장소는 **SQLite** (서버 1대일 때 k3s 기본값). 단일 장애점
- **컨트롤 플레인이 죽으면**: 돌던 파드와 트래픽은 **계속된다** (데이터 플레인은 각 노드의 kubelet·iptables). 죽은 파드 재시작, 노드 장애 대응, 배포·스케일, `kubectl`은 **안 된다**. "관제탑이 꺼진 공항"
- HA로 가려면: k3s 서버 3대 + 내장 etcd. **물리 장애 영역 3개**에 하나씩 → 기존 서버 / 새 호스트 / 세 번째 장비 (라즈베리파이 등)
- 🔬 (17주 차) 컨트롤 플레인을 끄고 송금 부하를 계속 보내 보기 → 송금은 되는데, 그 상태에서 파드를 죽이면 다시 안 뜨는 것 확인
- 🎤 마스터 노드가 죽으면 서비스도 멈추나요? / etcd가 과반수를 잃으면 쿠버네티스는?
