## ⭐⭐ 1. "요청함" 상태는 원래 결과 불명이다: 호출 전에 의도를 커밋한다

- 💡 API 호출과 DB 커밋은 한 트랜잭션으로 묶을 수 없다. 그래서 단계마다 **① 의도 상태 커밋 → ② 원격 호출 → ③ 결과 커밋**. ①과 ③ 사이 어디서 죽어도 DB엔 의도 상태가 남고, 그때 실제로 보냈는지는 DB만 봐선 모른다 → "요청함"과 "응답이 모름"은 복구 입장에서 **같은 상태**
- 💡 의도 상태의 진짜 효용은 **그 앞 상태를 확실하게 만드는 것.** ①을 호출 전에 커밋하니까 `WITHDRAWN`으로 남은 송금은 "외부엔 확실히 안 나감" → 자동 보상이 안전해진다
- 💡 ①을 빼면: 호출 직후 죽었을 때 `WITHDRAWN`이 남고, 복구 로직이 "출금만 됐네, 보상" → **이중 지급** (상대 은행 입금 + 고객 환불)
- 💡 core 출금에도 의도 상태가 있다 (`WITHDRAW_REQUESTED`, 당행의 `PROCESSING`과 같은 자리). 피벗이라서가 아니라 **원격 호출마다** 하나
- 🎤 "외부 호출 직후 서버가 죽으면 그 송금은 어떻게 되나요?" / "결과 불명인데 보상하면 안 되는 이유는?" / "트랜잭션 안에서 외부 API를 부르면 안 되는 이유는?"
- 📎 pitfalls 27, `InterbankTransferUseCaseImpl.sendToExternalBank`, `InterbankTransferUseCaseTest` "외부 호출 순간에는 의도가 이미 커밋돼 있고…", "외부 결과 불명 - 보상하지 않는다"

## ⭐ 2. 상태를 몇 개로 나누나

- 💡 기준: **"이 상태에 10분째 멈춘 송금을 복구 로직이 발견하면 무엇을 하나?"** 답이 다르면 다른 상태, 같으면 합친다 (화면 표시용으로 나누지 않는다. 이력은 상태를 쪼개지 말고 이력 테이블로)
- 💡 종이 위에서 쓸 수 있는 신호: **두 상태 사이에 원격 호출이 없으면 의심** (`EXTERNAL_BANK_FAILED → CANCEL_REQUESTED` 사이에 호출이 없어서 합침)
- 💡 상태 하나에 두 축(단계 × 결과)을 담는 게 맞다. 컬럼 두 개(step, outcome)로 나누면 말이 안 되는 조합이 생긴다
- 💡 확정 (V5):

  | 상태 | 멈춰 있으면 복구 로직이 할 일 |
  | --- | --- |
  | `WITHDRAW_REQUESTED` | 같은 송금 ID로 출금 재전송 (core 멱등) |
  | `WITHDRAWN` | 외부 송금 진행 (외부엔 확실히 안 나감) |
  | `EXTERNAL_BANK_REQUESTED` | 외부에 **결과 조회**. 보상 금지 |
  | `EXTERNAL_BANK_REJECTED` (= 보상 의도) | 출금 취소 재시도 (취소 키 결정적) |
  | `COMPLETED` / `FAILED` / `CANCELLED` | 끝 (이벤트 한 번) |

- 💡 재시도 가능 여부 = **상대가 같은 키 재요청을 안전하게 처리해 주나.** core(우리 것, 멱등)는 재전송, 외부 결제망은 상대의 중복 판별을 100% 믿을 수 없어 **조회 전문으로 확인**이 원칙
- 🎤 "상태가 너무 많아지면 어떤 문제가 생기나요?" / "외부 결과 불명이면 왜 재전송 대신 조회하나요?"
- 📎 `InterbankTransferStatus`, `V5__interbank_saga_states.sql` 주석, `InterbankTransferTest`

## ⭐⭐ 3. 오케스트레이션 vs 코레오그래피, 그리고 "기다림"의 정체

- 💡 구분 기준은 동기/비동기가 아니라 **"다음 단계를 누가 정하나"**. 오케스트레이션 = 지휘자(transfer)가 순서·분기·보상 판단을 한 곳에, 코레오그래피 = 각자 이벤트를 보고 자기 일만 (판단이 흩어진다)
- 💡 **오케스트레이터 = 영속화된 상태 머신.** 지휘자는 ① 어디까지 왔나 ② 다음에 뭘 하나 ③ 죽었다 살아나도 ①②를 아나를 알아야 한다 → 상태가 DB에 있어야 한다 (사가 로그). 코레오그래피는 상태 머신이 없어지는 게 아니라 참여자들에게 **흩어진다** → "송금 전체가 지금 어디인가"가 어디에도 한 줄로 없다
- 💡 비동기 오케스트레이션의 "기다림"은 **스레드를 붙잡는 게 아니라 DB에 꽂아 둔 책갈피.** 상태 저장 후 스레드 반납 → 응답 이벤트가 오면 컨슈머가 상태를 읽어 이어 간다. 오늘의 `EXTERNAL_BANK_REQUESTED`가 이미 그 책갈피 (지금은 같은 스레드가 바로 이어 갈 뿐)
- 💡 지금의 동기 방식이 위험해지는 장면 = **15주 차**: 외부가 3초 지연되면 요청마다 톰캣 스레드가 3초 묶이고, 풀이 차면 당행 송금까지 멈춘다 (장애 전파). ADR-0004 "이번엔 동기"는 이걸 재현하려고 일부러 남긴 것
- 💡 실무는 **섞어 쓴다**: 돈이 걸리고 보상이 있는 핵심 흐름 = 오케스트레이션, 알림·포인트·통계 같은 부수 반응 = 이벤트. 이 프로젝트도 그렇다 (타행 사가는 오케스트레이션, 송금 알림은 Kafka 구독)
- 🎤 "왜 오케스트레이션을 골랐나요?" / "코레오그래피의 단점은?" / "비동기로 바꾸면 고객 응답은 어떻게 되나요?" (202 + 조회·알림, 혼합 방식)
- 📎 ADR-0004 대안 표, `InterbankTransferUseCaseImpl.runSaga`, S-4 비교 그림(예정)

## ⭐ 4. 워크플로 엔진 (Temporal 등)과 손으로 짠 사가

- 💡 반복되는 "상태 머신 + 재시도 + 타이머 + 멈춘 흐름 이어 가기"를 해 주는 게 워크플로 엔진: **Temporal**(코드 + 이벤트 이력 재생), **AWS Step Functions**(상태 머신 JSON), **Camunda/Zeebe**(BPMN, 사람 승인 단계), Netflix Conductor. Spring Statemachine은 메모리 상태 머신이라 사가 엔진이 아니다
- 💡 실무 사용은 늘고 있지만 다수는 아니다. **DB 상태 머신 + 멱등 키 + 결과 조회 + 대사**를 직접 만드는 게 결제·송금의 주류 → 지금 구현은 실무와 거리가 먼 방식이 아니다
- 💡 엔진 도입 시점: 흐름이 많고, 며칠짜리 대기·사람 승인이 있고, 엔진 인프라를 운영할 여력이 있을 때. 대가: 새 인프라, (Temporal) 워크플로 코드의 결정성 제약, 학습 비용
- 💡 **엔진을 써도 결과 불명은 안 사라진다.** 엔진은 "우리 흐름이 어디까지 갔나"를 기억할 뿐, 외부가 실제로 처리했는지는 모른다 → 결과 조회·대사는 여전히 직접 설계
- 🎤 "Temporal 같은 걸 왜 안 썼나요?" / "엔진을 쓰면 결과 불명 문제가 사라지나요?"

## 5. 한 테이블을 여러 종류가 쓸 때, 그리고 멱등 키 범위를 왜 안 바꾸나

- 💡 당행·타행이 공통 테이블을 쓰니, 당행 조회가 같은 키의 **타행 행을 찾아 매핑 예외(500)**. 종류 제한만 걸면 "중복인데 없음" 500. → 종류로 읽기 제한 + **소거법**("키 충돌인데 같은 종류로 안 보인다 = 다른 종류가 쓰는 키") → 원인이 적힌 409
- 💡 소거법이 확실한 이유: PostgreSQL은 상대 행이 **커밋된 뒤에만** UNIQUE 위반을 확정한다
- 💡 키를 `(요청자, 종류, 키)`로 바꾸면 더 깔끔해 보이지만 **더 나쁜 설계**: 재시도 버그로 은행 코드가 빠지면 한 의도로 당행·타행 두 번 송금된다. 멱등 키 = 고객 의도 하나
- 💡 API를 당행/타행으로 나눠도 이 문제는 그대로다 (DB 공통 테이블에서 나온 문제). 하나의 API로 둔 비용은 "DTO가 느슨해져 조합 검사가 필요한 것" 정도
- 🎤 "공통 + 상세 테이블로 나눈 이유와 대가는?" / "멱등 키가 다른 종류의 요청에 재사용되면?"
- 📎 pitfalls 28, `InterbankTransferControllerTest` "타행에 쓴 키로 당행 송금", V4 맨 위 주석

## 6. 은행 코드: enum이 아니라 값 객체

- 💡 기관 코드는 금융결제원이 부여하는 3자리 (004 국민, 088 신한, 090 카카오뱅크 …). 합병(외환 005 폐지)·신설(인터넷은행)로 **바뀌는 기준 정보** → 실무는 코드 테이블 + 캐시, 거래 행엔 문자열 그대로
- 💡 enum의 함정: 바뀔 때마다 재배포, **폐지된 코드로 저장된 과거 거래를 읽는 순간 매핑 예외** (거래는 불변이라 못 지움). 5번과 같은 종류의 함정
- 💡 지금은 값 객체로 **형식만**(parse, don't validate → 400), 존재 여부는 외부 결제망이 판단. "우리 은행이면 안 됨"은 값의 규칙이 아니라 타행 송금의 규칙이라 다른 곳에
- 🎤 "은행 코드를 왜 enum으로 안 했나요?"
- 📎 `domain/BankCode.kt`
