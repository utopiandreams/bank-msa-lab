# 결과 불명 처리 정책: 무엇을 고르면 무엇을 얻고 잃나

> 기술 질답 기록 (6장 7-1-0). 계기: 8주 차 당행 결과 불명 해소 구현 뒤 개발자 질문 (2026-11-24)
> "오늘 많은 걸 정했다. 재전송을 아예 막았지만 재전송을 허용하는 경우도, 해소에선 안 하고 고객 요청에만 허용하는 경우도 있을 것 같다. 그에 따라 시나리오를 어떻게 짜야 하고 무엇을 잃고 얻는지 이해하고 싶다."
> 블로그 글감: 줄기 2 "'모른다'를 다루는 법"의 정리 편. 우리 결정은 정답이 아니라 **조건에 맞춘 선택**이라는 걸 보여 주는 글.

---

## 1. 이게 어려운 이유

정답이 하나가 아니다. 같은 "응답이 안 왔다"도 **상대 시스템의 성질**과 **업무의 성질**에 따라 맞는 답이 다르다.
실무에서도 팀마다 다르게 하고, 결정 이유가 문서로 남지 않아 나중에 "왜 재시도를 안 하지?"로 다시 싸운다.
그래서 정책을 외우는 게 아니라, **아래 네 가지 질문에 답하면 정책이 거의 정해진다**는 걸 익히는 게 목표다.

## 2. 정책을 정하는 네 가지 질문

| # | 질문 | 우리 core의 답 | 왜 중요한가 |
| --- | --- | --- | --- |
| Q1 | **상대가 실패까지 기억하나?** (같은 키 재요청에 처음 결과를 돌려주나) | ❌ 성공만 기억. 거절은 롤백 = 흔적 없음 | 실패까지 기억하면 재전송 = 조회라 언제 보내도 안전. 성공만 기억하면 재전송이 "새로 실행"이 될 수 있다 |
| Q2 | **결과가 시간에 따라 달라지나?** (잔액·재고·환율·한도) | ✅ 잔액 의존 | 달라진다면 늦은 실행이 다른 결과를 낸다 (10시 거절 → 12시 성공) |
| Q3 | **되돌릴 수 있나?** | 당행 송금은 역분개로 되돌릴 수는 있지만, 고객 돈이 움직인 뒤라 사고 | 되돌리기 쉬우면 "일단 실행하고 틀리면 취소"도 선택지 |
| Q4 | **지금 실행 의사를 확인할 수 있나?** (고객이 앞에 있나) | 해소 일꾼: ❌ / 고객 재요청: ✅ | 의사가 지금 있으면 "지금 실행"이 정당해진다 |

## 3. 정책 스펙트럼

| 정책 | 어떻게 | 얻는 것 | 잃는 것 | 맞는 조건 | 실제 예 |
| --- | --- | --- | --- | --- | --- |
| **A. 재전송 없음, 조회만** (우리 선택) | 고객이든 일꾼이든 확인만. 안 됐으면 실패 확정 → 원하면 새 키로 새 요청 | 늦은 실행 0. 실행 경로가 하나라 단순. 기준 시각이 `createdAt` 하나로 끝남 | 실패로 끝난 건은 고객이 다시 해야 함 (UX). 확정까지 최소 5초 | Q1 ❌ + Q2 ✅ (실패를 기억 못 하고 결과가 시간에 따라 변함) | 금융권 "모르면 조회 전문" |
| **B. 고객 재요청만 재전송, 일꾼은 조회** | 고객이 같은 키로 오면 지금 실행 (T-2 원래 설계) | 고객 입장에선 "다시 누르면 된다"가 자연스러움 | 고객이 본 화면(금액·잔액)이 몇 시간 전 것일 수 있음. 실행 경로가 둘 → 시각 기준이 여러 개 | Q4 ✅를 중시하고, 고객 재요청이 보통 짧은 시간 안에 온다고 볼 때 | 많은 일반 API의 "같은 키로 재시도" |
| **C. 짧은 창 안에서만 재전송** | 보낸 지 N초 안 재요청은 재전송, 그 뒤는 조회 | 빠른 재시도는 결과를 바로 받음. 늦은 실행은 막음 | 경로 둘 + 경계 시간 근거가 필요 | Q2 ✅지만 몇 초 차이는 같은 의사로 볼 수 있을 때 | 클라이언트 라이브러리 자동 재시도(백오프) |
| **D. 일꾼도 재전송 (앞으로 복구)** | 멈춘 건을 끝까지 실행시킴 | 고객이 한 번 누르면 언젠가 반드시 처리됨 | Q1 ❌ + Q2 ✅면 늦은 실행 사고 | **Q1 ✅** (상대가 실패까지 기억) 또는 Q2 ❌ (결과가 시간과 무관) | Stripe(첫 응답을 오류까지 24시간 저장 → 재시도 권장), 메시징 at-least-once + 멱등 컨슈머 |
| **E. 모르면 무효화** | 결과 불명이면 "그 거래 취소"를 보냄 | 결과를 빨리 확정 (실패로) | 상대가 취소를 지원해야 함. 취소도 결과 불명이 될 수 있음 | 상대가 취소 전문을 받아 주고, 실패 확정이 빠를수록 좋을 때 | 카드·VAN **망취소** |

## 4. 조건이 바뀌면 답이 바뀐다 (우리 프로젝트에서)

- **core가 거절도 기록하면** (Q1 ✅로 바뀜): B·D가 안전해진다. 대가는 core 쓰기 증가와 스키마 변경. "아직 처리 중"(늦은 커밋) 문제는 여전히 남음 (ADR-0005 대안)
- **15주 차 비동기 응답** ("처리 중"을 먼저 주고 결과는 나중에): 고객이 결과를 기다리지 않으니 A의 UX 손해가 줄어든다. 해소 일꾼이 사실상 주 경로가 된다
- **타행 (8주 차 2부)**: 외부 은행은 우리가 못 바꾼다. 외부가 조회 API를 주나, 같은 키 재전송에 처음 결과를 주나(Q1)에 따라 A/D가 갈린다. 피벗(외부 송금) 뒤는 원래 "앞으로 복구"(ADR-0004)라 D 성격이 섞인다

## 5. 정책마다 시나리오를 어떻게 짜나

정책을 고르면 **그 정책이 잃는 것**이 곧 재현·검증해야 할 시나리오다.

| 정책 | 꼭 재현할 장면 (잃는 것) | 꼭 확인할 장면 (얻는 것) |
| --- | --- | --- |
| A | 고객이 FAILED를 받고 새 키로 다시 보냄 → 송금 1건만 처리됐나 / 조회 "없음"인데 core가 뒤늦게 커밋 (대사가 잡나) | 2시간 뒤 재요청이 실행되지 않음 (`TransferUnknownResolutionReproTest` 1번) |
| B | 오래된 UNKNOWN에 고객 재요청 → 늦은 실행이 일어남 (그걸 받아들일 수 있나) | 짧은 재요청이 결과를 바로 받음 |
| C | 경계 시간 직전/직후 재요청이 다르게 처리됨 | 창 안 재요청은 실행, 창 밖은 조회 |
| D | 거절된 건이 나중에 성공으로 바뀌는 장면 (Q1 ❌일 때 사고) | 고객 없이도 결국 처리됨 |
| E | 망취소가 결과 불명 → 취소의 취소? / 원거래가 취소보다 늦게 도착 | 결과 불명이 빨리 실패로 확정 |

## 6. 우리가 A를 고른 이유 (한 줄씩)

1. core는 실패를 기억하지 않는다 (Q1 ❌)
2. 송금 결과는 잔액에 따라 바뀐다 (Q2 ✅). 개발자 판단: "1분 차이도 다른 판단이 될 수 있다"
3. 실행 경로를 하나로 두면 기준 시각이 `createdAt` 하나로 끝나고 규칙이 단순하다 (B·C를 버린 이유: "재전송이 없는 게 일관적")
4. 잃는 것(실패 시 고객이 새로 보내야 함)은 은행 업무에서 받아들일 수 있다: 실패를 보고 고객이 다시 판단하는 게 오히려 안전

**💡 핵심:** 멱등은 "두 번 실행"을 막을 뿐 "늦은 실행"은 막지 못한다. 재전송이 안전한지는 **상대가 실패까지 기억하는지**와 **결과가 시간에 따라 변하는지**로 정해진다.

**🎤 면접 꼬리 질문**
- "타임아웃 나면 같은 멱등 키로 재시도하면 되지 않나요?" → Q1·Q2로 답한다. Stripe는 되고 우리 core는 안 되는 이유
- "고객이 다시 누르면 실행해 주는 게 UX상 낫지 않나요?" → B의 대가(오래된 의사로 실행, 경로 둘). 우리는 실패 확정 + 새 요청을 택했고, 15주 차 비동기 응답으로 UX를 보완할 계획
- "해소 배치는 재시도와 조회 중 무엇을 해야 하나요?" → 고객이 없으므로 기본은 조회. 상대가 실패까지 기억하면 재시도도 가능
- "결과 불명을 빨리 실패로 끝내고 싶다면?" → 망취소(E). 취소도 결과 불명이 될 수 있다는 점까지
- "이 결정이 바뀌는 조건은?" → core가 거절을 기록하게 되면, 응답이 비동기가 되면

**📎** ADR-0005 (결정 2·대안), `docs/design-drills/08-unknown-resolution.md` "설계가 바뀐 과정", pitfalls 38, `timeouts-and-deadlines.md` 3절, ADR-0004(피벗 뒤 앞으로 복구)

## ⭐ 트랜잭션 안에서 외부 결제를 부르는 서비스를 만나면 바꿔야 하나 (2026-11-26 개발자 질문)

> 전 직장은 지표·트레이스·로그는 Datadog을 달면 끝이었다. 다만 `BEGIN → 주문 저장 → PG 결제 호출 → 결제 완료로 수정 → COMMIT` 식이었다. "커밋(결제 중) → 결제 → 커밋(완료)"로 나눠야 할까?

- 💡 **Datadog이 주는 것과 못 주는 것:** 에이전트는 "몇 건, 얼마나 느림, 어디서 에러"(배관)를 공짜로 준다. "그 요청에서 **돈이 나갔나**"는 앱의 상태 설계만 답한다. 위 구조에선 트레이스가 완벽해도 답이 없다
- 💡 **한 트랜잭션 구조가 깨지는 세 장면:**
  1. PG는 승인했는데 그 뒤 COMMIT이 실패한다 (커넥션 끊김, 데드락, 트랜잭션 타임아웃, 배포로 파드 종료) → 롤백이 주문 기록까지 지운다. **고객 돈은 빠졌는데 우리 DB엔 흔적이 없다.** 찾을 실마리도 없다
  2. PG 응답이 타임아웃 → 실패로 보고 롤백 → 그런데 PG는 승인했을 수 있다 (같은 결과)
  3. PG가 느려지면 커넥션을 쥔 채 기다린다 → 풀 고갈 → 결제와 상관없는 API까지 멈춘다 (5주 차 k6 연쇄와 같은 모양)
- 💡 **바로 다 바꾸지 않는다. 판단 순서:**
  1. **실제로 얼마나 일어나나** 먼저 본다: PG 타임아웃 비율, "결제됐는데 주문 없음" CS 문의, PG 정산 내역과 우리 주문의 차이. 몇 달에 한 번이고 CS가 손으로 환불하고 있다면, 그게 그 회사의 (의식 못 한) 선택이다
  2. **이미 있는 안전망**: PG에 멱등 키(주문 ID)를 넘기나, PG 웹훅으로 나중에 맞추나, PG 정산 파일과 대사하나. 이게 있으면 구멍은 "못 찾음"이 아니라 "늦게 찾음"이다
  3. **싼 것부터 넣는다 (발견 → 예방 순):** ① PG 정산 대사(배치 하나, 기존 흐름 안 건드림) ② PG 멱등 키 ③ 호출 전에 "결제 시도" 한 줄을 **별도 트랜잭션으로** 남기기(롤백돼도 흔적이 남음) ④ 그래도 사고가 반복되면 그때 상태 분리 + 결과 불명 해소
  - 바꾸는 비용: 상태가 늘고(결제 중·결과 불명), 해소 일꾼이 생기고, 기존 주문 데이터와 화면이 새 상태를 알아야 한다. 운영 중 흐름을 바꾸는 위험도 있다
- 💡 **확실히 바꿀 때:** 거래량이 커서 "드문 일"이 매일 일어날 때 / PG 지연으로 풀 고갈 장애를 한 번이라도 겪었을 때 / 금액이 크거나 감사·규제를 받을 때
- 🎤 "외부 결제 호출을 DB 트랜잭션 안에 두면 무엇이 문제인가요?" → 커밋 실패·타임아웃 때 돈은 나갔는데 기록이 사라짐 + 외부 지연이 커넥션 풀로 번짐
- 🎤 "레거시가 그렇게 돼 있으면 바로 고치나요?" → 빈도·안전망부터 확인, 대사로 먼저 '찾을 수 있게' 만들고, 사고가 증명되면 구조를 바꾼다. 고칠 수 있다와 고쳐야 한다를 구분
- 📎 pitfalls 27 (외부 호출 전에 의도를 커밋), `timeouts-and-deadlines.md`, ADR-0004·0005, `docs/experiments/week-05-k6-baseline.md` (커넥션 풀 → OOM 연쇄)
