# ADR-0006. 일일 대사
- 상태: 초안 (2026-11-25, 설계 연습 09 리뷰에서 합의. 면접 30초 답변은 개발자 작성 예정)
- 날짜: 2026-11-25
- 설계 과정: `docs/design-drills/09-reconciliation.md` (결정 1~18), 질답: `docs/learning/reconciliation.md`

## 맥락

- 결과 불명 해소(ADR-0005, 설계 연습 08 2부)는 **멈춘 송금**을 푼다. 하지만 이미 끝 상태가 된 송금이 상대 장부와 어긋난 경우(예: 외부가 처리 상한을 어기거나 기록을 잃어 "없음" → 우리는 출금 취소, 외부는 입금 = 이중 지급)는 아무도 못 본다.
- 같은 사실을 **두 시스템이 따로 기록하는 경계**가 둘 있다: transfer ↔ core 원장, 타행 송금 ↔ 외부 은행(bank-mock). 원장 자체도 차변 = 대변이어야 한다.
- DB per service라 한 곳에서 여러 DB를 조인할 수 없다. 7주 차 k6가 core를 직접 불러 송금 없는 전표가 이미 있다 ("생길 수 없는 일"이 실제로 있다).

## 결정

### 1. 무엇을: 원장 자체 검증 + 두 경계의 양방향 대사
- 원장 자체: 차변 합 = 대변 합 (시산표). 대사는 아니지만 쿼리 하나라 같이 돈다.
- transfer ↔ core: core 전표는 `type`(TRANSFER·INTERBANK_WITHDRAWAL·INTERBANK_WITHDRAWAL_CANCEL)으로 고르고 `idempotency_key` = 송금 ID로 짝.
- 타행 송금 ↔ 외부: 외부 일자별 내역(건별 + 합계)과 짝.
- 고른 쌍 안에서는 그날 기록 **전부를 양방향으로** (한쪽에서만 출발하면 상대에게만 있는 기록을 못 찾는다).

### 2. 어디서: 별도 대사 서비스
- 독립성: 검사받는 쪽(transfer)이 검사를 겸하면 같은 코드의 버그를 못 본다. 실무도 정산·대사 시스템이 따로 있다.
- 파드 1개, 배포 중 겹침은 `Recreate` 또는 회차 행 잠금으로 막는다.

### 3. 데이터: 일자별 추출 파일 + 완료 이벤트 (인박스)
- **외부 내역은 대사 서비스 안의 수신 작업이 받아 온다** (2026-11-25 정정, 설계 연습 09 결정 19): 외부(bank-mock)는 우리 저장소·Kafka에 쓰지 않는다. bank-mock은 저쪽 형식의 일자별 내역 API(외부 기관의 파일 제공 채널)만 맡고, 수신 작업이 정해진 시각에 받아 원본 그대로 Garage에 보관하고 "외부 D일 도착"을 기록한 뒤 우리 모델로 번역(ACL). 원래는 별도 대외계 서비스 몫이지만 서버를 늘리지 않으려고 대사 서비스에 둔다
- core·transfer가 그날(D) 내역 파일을 **S3 호환 저장소(Garage)**에 올린 **뒤** "D 추출 완료" 이벤트(건수·금액 합계·체크섬)를 발행한다.
- 대사 서비스 컨슈머는 도착만 DB에 기록하고 바로 커밋한다 (인박스). 대사(수십 초~분)를 컨슈머 안에서 돌리면 `max.poll.interval.ms`를 넘겨 리밸런싱 → 같은 날짜가 동시에 돈다.
- 별도 일꾼이 "셋 다 도착, 완료 아님"인 날짜를 돈다. **하나라도 없으면 시작하지 않는다** (가짜 불일치 폭주). 파일이 이벤트의 건수·합계·체크섬과 안 맞으면 대사 불일치가 아니라 **파일 불량** → 회차 실패.
- 파일은 증거라 덮어쓰지 않는다. 다른 서비스 DB에 커넥션을 붙이지 않는다. API 대신 파일인 이유: 양, 시간 분리, 원본 보존(다시 돌려도 같은 결과).
- 추출이 아예 안 돌면 로그도 없다(신호의 부재) → 출처별 "마지막 추출 완료 시각" 지표 + 기한 알림 (dead man's switch).

### 4. 날짜와 이월
- 우리 날짜 = 송금 `createdAt` (안 바뀜). 외부 처리일은 받지 않는다.
- 짝 맞추기 대상 = 오늘 목록 + 이월된 미결 ↔ 오늘 상대 내역. 외부 → 우리 방향을 먼저 보며 이월과 짝지어 해소, 남은 건 이월. **양쪽 다** 이월 (시스템 간 시계 차이).
- 우리 쪽이 끝 상태가 아니면 판정하지 않고 이월.
- 이월 기한 **1일**: 다음 날에도 안 풀리면 불일치로 경보.

### 5. 판정 규칙 (우리 끝 상태별 외부 정상값)

| 우리 | 외부 정상 | 어긋나면 |
| --- | --- | --- |
| `COMPLETED` | ACCEPTED | 없음(이월 뒤)·REJECTED: 고객 손실 |
| `CANCELLED` (외부 거절) | REJECTED | ACCEPTED: 이중 지급 |
| `CANCELLED` (외부 조회 "없음") | 없음 | ACCEPTED: **이중 지급, 이월 없이 즉시 경보** |
| `CANCELLED` (`WITHDRAWN`에서) · `FAILED` | 없음 | 있음: 보낸 적 없는 송금이 외부에, 즉시 경보 |

### 6. 기록과 재실행
- 회차(기준일): 상태, 양쪽 건수·합계, 정상·이월·불일치 건수, 로직 버전, 들어온 이월. 예외 항목(이월·불일치): 송금 ID, 종류(우리만/외부만/금액 다름/결과 다름), 심각도, 상태, 처음 발견·해소일.
- **정상 건은 건별로 남기지 않는다** (파일로 다시 대사하면 된다).
- **전부 아니면 전무:** 스테이징(날짜별로 지우고 다시 적재)에서 비교를 끝낸 뒤 예외 항목 + 이월 해소 + 회차 완료를 한 트랜잭션으로. 죽으면 처음부터 다시.

## 결과

- 좋아지는 것: 해소 일꾼까지 놓친 불일치(이중 지급, 고객 손실, 송금 없는 전표)를 하루 안에 찾는다. 대사 결과가 회차·예외로 남아 증거가 된다.
- 나빠지는 것: 서비스 1개(대사) + 저장소 1개(Garage) + 추출 배치 3개 + 이벤트. 운영할 것이 늘어난다.
- 바뀌는 것: core·transfer·bank-mock에 일자별 추출(파일 + 완료 이벤트), 새 서비스 `reconciliation`(가칭), 클러스터에 Garage.

## 열린 것
- k6가 남긴 송금 없는 전표: 채널 칸 추가 / 알려진 예외 분류 / 기준 날짜 이후만 중 선택
- core 쪽 날짜(전표 `created_at`)와 transfer `createdAt`의 경계 차이 → 이월이 받는지 구현 때 확인
- 계속 실패하는 보상(수작업 대기 상태)과 대사 불일치의 수작업 처리(조정 전표, maker-checker): 설계 연습 08 2부 "보류"
- 파일 형식(CSV·JSON Lines), 배치 시각 세부, 서비스 이름
