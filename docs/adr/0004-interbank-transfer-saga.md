# ADR-0004. 타행 이체 사가
- 상태: 초안 (2026-11-19, 설계 연습 04 리뷰에서 합의. 면접 30초 답변은 개발자 작성 예정)
- 날짜: 2026-11-19
- 설계 과정: `docs/design-drills/04-interbank-transfer.md`

## 맥락

- 5주 차 목표: 타행 이체를 오케스트레이션 사가로 구현한다. core 출금 → `bank-mock` 송금 → 실패하면 출금 보상.
- ADR-0001: 사가는 **롤백할 수 없는 상대가 끼는 곳**에서 필요하다. 당행은 core 안의 로컬 트랜잭션이라 사가가 아니고, 타행에서 처음 생긴다.
- 5주 차 범위: `bank-mock`은 **성공 / 거절만** 답한다. 타임아웃, 결과 불명, 상태 조회, 대사는 8주 차에 이 설계 위에 얹는다. 그 자리는 지금 상태 머신에 남겨 둔다.
- 회계(도메인 사실): 외부로 나가는 돈은 정산 전까지 **미정산 임시 계정**에 둔다. 원장은 불변이라 취소도 반대 방향 전표(역분개)를 새로 쓴다. 정산은 송금마다가 아니라 하루치 배치다.

## 결정

### 1. 지휘자: transfer (오케스트레이션)
- 홉 3개: transfer → core 출금 / transfer → bank-mock 송금 / transfer → core 출금 취소(보상). core는 bank-mock을 모른다.
- 송금 상태 머신의 주인이 이미 transfer다 (ADR-0001). 흐름 전체가 한 곳(상태 칼럼 하나)에서 보인다.
- 코레오그래피(이벤트를 보고 각자 다음 일)는 구현하지 않고 같은 흐름으로 그려 비교만 한다 (아래 대안).

### 2. 피벗 트랜잭션: bank-mock 송금 성공
- **피벗 앞(core 출금)은 뒤로 복구:** 외부가 거절하면 출금을 보상(취소)한다.
- **피벗 뒤는 앞으로 복구:** 외부가 성공하면 B은행 고객에게 이미 돈이 갔다. 되돌리지 않고, 우리 쪽 기록이 실패해도 성공할 때까지 재시도한다.
- 그래서 되돌릴 수 있는 출금을 먼저, 되돌릴 수 없는 외부 송금을 마지막에 둔다.

### 3. 상태 머신

```
PROCESSING ──출금 성공──▶ WITHDRAWN ──외부 호출 직전 커밋──▶ INTERBANK_REQUESTED ──외부 성공──▶ COMPLETED
    │                                                              ├──외부 거절──▶ COMPENSATING ──취소 성공──▶ CANCELLED
    │                                                              │               ↺ 취소 실패 → 같은 키로 재시도
    │                                                              └──응답 없음──▶ 결과 불명 (8주 차: 확인 먼저)
    └──출금 거절──▶ FAILED
```

- **WITHDRAWN과 INTERBANK_REQUESTED를 나눈다.** WITHDRAWN은 "외부에 안 보낸 게 확실", INTERBANK_REQUESTED는 "보냈을 수도 있다". 여기서 죽으면 **보상하면 안 된다**: 외부가 실제로 처리했다면 이중 지급이다. 상태 조회 또는 같은 키 재전송으로 확인한 뒤 진행·보상 (8주 차).
- **FAILED와 CANCELLED를 나눈다.** FAILED는 돈이 한 번도 안 움직였다 (core 롤백, 원장에 흔적 없음). CANCELLED는 출금됐다가 돌아왔다 (원장에 출금 + 역분개 두 줄, 고객 거래 내역에도 둘 다 보임, 대사 대상). 이름 `CANCELLED`는 가칭.
- **COMPENSATING은 실패로 끝나지 않는다.** 보상은 성공할 때까지 재시도한다. 계속 안 되면 사람이 본다 (8주 차 에이징 리포트).
- 끝 상태로 바뀔 때 이벤트 발행 (ADR-0003): COMPLETED·FAILED에 **CANCELLED 추가**.

### 4. 멱등 키: 동작마다 따로, 재시도해도 같은 값
| 호출 | 중복을 막는 것 |
| --- | --- |
| core 출금 | 멱등 키 = 송금 ID (당행과 같음) |
| bank-mock 송금 | 멱등 키 = 송금 ID (bank-mock도 같은 키는 한 번만 처리) |
| core 출금 취소 | **자연 키: 원래 출금 전표** (`reverses_entry_id` UNIQUE). 요청은 `POST /postings/interbank-withdrawals/{송금ID}/cancel`, 바디·멱등 키 헤더 없음 |
- 출금 키를 취소에 그대로 쓰면 core는 "이미 처리한 키"로 보고 출금 결과를 다시 돌려준다. 취소는 실행되지 않는다. core 입장에서 출금과 취소는 다른 거래다.
- 처음 설계는 결정적 키 `{송금ID}-cancel`을 transfer가 보내는 것이었다 (무작위 키면 재시도마다 새 취소 → 두 번 환불). S-2에서 한 단계 더 나갔다 (2026-11-19 개발자 결정):
  - **취소 요청은 금액·계좌를 보내지 않고 원래 출금을 가리킨다.** core가 원래 전표를 찾아 정확히 반대로 쓴다 → 출금보다 많이 돌려주는 버그가 구조적으로 불가능. 원래 전표가 없으면 404 (없는 출금을 취소하면 미정산에서 들어온 적 없는 돈이 나간다), 타행 출금이 아니면 422
  - **"한 출금은 한 번만 취소"를 core가 원장 제약으로 보장한다.** 요청자가 키를 잘 만들어 주기를 믿지 않아도 된다. 동시에 두 번 와도 UNIQUE에 걸린 쪽은 기존 취소를 돌려받는다 (replayed)
  - 취소 전표의 원장 키는 core가 `{원래 키}-cancel`로 채운다 → 상태 조회 `GET /postings/{송금ID}-cancel`

### 5. 회계: 미정산 계정을 지금 넣는다
- core에 은행 내부 계정 `타행이체 미정산`을 둔다. 타행 출금은 고객 예금 → 미정산, 취소는 반대 방향.
- 8주 차로 미루면 그동안 원장이 회계적으로 틀린 상태가 된다. 8주 차 대사는 이 잔액을 그대로 쓴다 (정산 후 0).
- 정산 배치(미정산 → 한국은행 예치금)는 8주 차.

### 6. 고객 API: 같은 `POST /transfers` + 받는 은행 코드
- 요청에 `toBankCode` 추가. 우리 은행 코드면 당행, 아니면 타행 사가. 고객 입장에서 송금은 하나이고, 고객 멱등 키·조회 API를 그대로 쓴다.

### 7. 고객 응답: 이번엔 동기 (사가가 끝날 때까지 기다림)
- 설계로는 비동기가 맞다 (외부 처리 시간은 우리가 통제할 수 없다, 개발자 지적). 실제 은행은 혼합: 몇 초 기다려 끝나면 결과, 아니면 "처리 중" + 알림.
- **5주 차는 작게 동기로** 만들고 나중에 보강한다 (2026-11-19 개발자 결정, 포기가 아니라 순서). 비동기·혼합에 필요한 "사가를 이어 받는 일꾼"은 8주 차 해소 스케줄러와 같은 기계라 그때 만든다.
- 15주 차 "외부 은행 3초 지연"의 **전** 상태가 된다: 고객 요청 스레드가 외부를 기다리며 쌓이는 장면 (5주 차 k6 stress에서 본 스레드 → 메모리 연쇄와 같은 모양).

### 8. bank-mock: 수취 계좌 규칙 + 실험 스위치
- 수취 계좌번호가 정해진 패턴이면 거절 → 테스트가 결정적.
- 거절률(%)을 설정값으로 두어 실험 스위치로 바꿀 수 있게 (CLAUDE.md: 하드코딩 금지, 12주 차 패널 버튼과 연결).
- 같은 키 재요청은 처음 결과를 돌려준다 (8주 차 "같은 키 재전송으로 확인"의 전제).

## 대안

| 대안 | 고르지 않은 이유 |
| --- | --- |
| core가 bank-mock을 직접 호출 | 계정계 코어가 외부 연동·재시도·상태 머신까지 떠안는다. ADR-0001에서 코어는 단순하게, 송금 정책은 transfer에 두기로 했다 |
| 코레오그래피 (이벤트로 이어 달리기) | 단계가 3개뿐인 흐름에 지휘자 없이 이벤트를 늘리면 "지금 어디까지 왔나"를 한 곳에서 못 본다. 보상 순서도 각 서비스에 흩어진다. 비교 그림만 남긴다 |
| 외부 송금 먼저, 출금 나중 | 되돌릴 수 없는 단계가 앞에 오면, 뒤의 출금이 실패할 때 돈을 회수할 방법이 없다 |
| 워크플로 엔진 (Temporal 등) | 상태 저장·재시도·재개를 대신 해 준다. 손으로 구현해 원리를 익히는 게 이 프로젝트의 목적이라 정리만 한다 |

## 결과

- 좋아지는 것: 외부 거절 시 고객 돈이 자동으로 돌아온다. 이중 지급 경로(결과 불명에서 보상)를 상태로 막았다. 원장이 처음부터 회계적으로 맞다.
- 남기는 구멍 (의도): INTERBANK_REQUESTED·COMPENSATING에서 죽으면 멈춘 채로 남는다 → 8주 차 해소 스케줄러. 고객 요청이 외부를 기다린다 → 15주 차.
- 바뀌는 것: transfer 송금 테이블에 송금 종류·받는 은행 코드·새 상태, core에 미정산 계정·타행 출금·취소 API(Flyway V3: 거래 종류 2개, `reverses_entry_id`), 새 서비스 `bank-mock`.

## 변경 기록

- **2026-11-26 bank-mock 저장을 메모리 → DB로.** 처음엔 "남의 은행이라 내구성은 우리 몫이 아니다"로 메모리에 뒀다.
  그런데 재시작(배포·설정 변경)마다 그날 처리 기록을 잃어, 정산 파일에서 빠진 타행 12건이 대사에 MISSING_EXTERNAL로 떴다 (2026-11-25).
  가짜가 기억을 잃으면 대사가 **진짜 불일치와 가짜의 한계를 구분하지 못한다** → 늘 켜 두고 운영하는 모드(평소 트래픽 + 대사 관찰)에 맞지 않는다.
  "외부가 기록을 잃는" 장면은 실험 스위치(`lookupLiesNotFound`)로만 만든다. 함께: 실험 스위치를 재시작 없이 바꾸는 API(`/actuator/experiments`), 지연을 요청의 일부에만 주는 비율 스위치
