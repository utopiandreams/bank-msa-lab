# ADR-0001. 송금 유스케이스와 서비스 경계
- 상태: 승인 (면접 30초 답변만 남음)
- 날짜: 2026-11-11

## 맥락

- 이 프로젝트는 MSA의 분산 문제(분산 트랜잭션, 중복 메시지, 동시성, 결과 불명)를 재현하고 해결하는 것이 목적이다.
- 상품은 입출금 계좌 하나로 줄이고, "돈이 움직이는 방식"(복식부기 원장, 거래 불변, 결과 불명, 대사, 멱등성)을 실제처럼 만든다 (`docs/domain/README.md`).
- 전통 은행의 계정계(코어)는 대부분 모놀리스이고, 신규 기능은 그 주변에 MSA로 붙이는 추세다. 목표 직군은 전통 은행과 핀테크 양쪽이다.
- 정해야 할 것: 잔액(`account`)과 원장(`ledger`)을 서비스로 나눌 것인가, 그리고 분산 경계를 어디에 둘 것인가.

## 유스케이스 (정상 흐름, 상태 머신, 실패 시나리오)

### 범위
- **당행 송금**이 이 ADR의 중심이다. 타행 송금은 `bank-mock` 연동으로 나중에 추가한다 (아래 "결과"의 로드맵 참고).
- **입출금**은 송금의 재료다. ATM 같은 채널 장치는 만들지 않고 API로 흉내 낸다.
  - ATM도 "외부 장치의 결과를 확신할 수 없음 → 기록해 두고 대사로 맞춤"이라는 타행 이체와 같은 패턴이라, 타행 이체(`bank-mock`)로 대표해서 실험한다.

### 정상 흐름: 당행 송금 (A → B, 1만 원)

```
고객 ──송금 요청──▶ transfer
                    │ ① 송금 기록 생성 (상태: 요청됨, 송금 ID 발급)
                    │ ② 상태: 처리중
                    ├──송금 처리(송금 ID)──▶ core
                    │                         ┌ 하나의 로컬 트랜잭션 ───────────────┐
                    │                         │ ③ 출금·입금 계좌 확인 (상태, 잔고) │
                    │                         │ ④ A 잔액 -1만, B 잔액 +1만          │
                    │                         │ ⑤ 원장 2건 기록 (송금 ID 참조)      │
                    │                         └─────────────────────────────────────┘
                    ◀──────────성공────────────┘
                    │ ⑥ 상태: 완료
고객 ◀───완료───────┘
```

- 잔고 부족을 먼저 알아야 하므로 **잔액 갱신을 원장 기록보다 먼저** 한다.
  - 구현 노트 (2026-11-13): 실제로는 **원장 기록(멱등 판정 포함)을 먼저** 한다. 같은 키 재요청이면 잔액을 건드리기 전에 replayed로 끝내야 해서다. 한 트랜잭션이라 잔고 부족이면 원장 INSERT도 함께 롤백된다 (`PostingUseCaseTest`로 확인).
- 출금과 입금은 **한 트랜잭션으로 묶는다.** 둘은 짝이라서 같이 성공하거나 같이 롤백해야 한다. "출금 먼저, 입금 나중" 순서는 트랜잭션 안에서 지키면 된다. 순서 때문에 트랜잭션을 나눌 필요는 없다.

### 상태 머신: 송금 (`transfer`가 소유)

송금 테이블이 따로 필요한 이유: 고객 문의("제 송금 어떻게 됐어요?")에 답하고, 같은 요청의 중복을 알아보고, 중간에 죽었을 때 어디까지 했는지 기억하기 위해서다.

```
요청됨 ──▶ 처리중 ──코어 성공──▶ 완료
                 ├─코어 거절(잔고 부족 등)──▶ 실패
                 └─응답 없음(타임아웃)──▶ 확인필요 ──송금 ID로 상태 조회──▶ 완료 / 실패
```

- **규칙: 원격 호출 경계 하나마다 "보냈는데 아직 모름" 상태가 하나 생긴다.** 출금과 입금은 코어 안의 한 트랜잭션이라 별도 상태가 필요 없다. `transfer → core` 호출 경계에서 `확인필요`가 생긴다.
- `확인필요`에서 빠져나오는 방법은 **상태 조회**다. 코어는 출금·입금·원장에 송금 ID를 기록하므로, `transfer`는 "이 송금 ID로 처리된 거 있어?"라고 물어보면 된다.
- 조회 결과가 "없음"이어도 원래 요청이 아직 가는 중일 수 있다. 그래서 다시 보낼 때 두 번 처리되지 않도록 **코어는 송금 ID 기준으로 멱등하게 처리한다.**
- 끝 상태(`완료`, `실패`)는 바뀌지 않는다.

### 실패 시나리오: 당행 송금

A = 잔액(`account`)과 원장(`ledger`)이 다른 서비스, B = 같은 코어(DB 하나)

| # | 어디서 | 무슨 일 | A (전부 MSA) | B (코어 모놀리스) |
| --- | --- | --- | --- | --- |
| 1 | ③ | 잔고 부족 (업무 실패) | 거절, 돈 이동 없음 → `실패` | 같음 |
| 2 | ④ 출금 ↔ 입금 | 출금 직후 서버 다운 | 두 계좌 모두 `account` DB 안이라 한 트랜잭션 → 롤백, 돈은 A에 그대로 | 같음 |
| 3 | ④ 잔액 ↔ ⑤ 원장 | 잔액 갱신 후 원장 기록 전 다운 | 잔액은 바뀌었는데 원장이 없음 → **불일치.** 원장 기록 전까지 `처리 중` 상태로 관리하고 동시 요청엔 락, 원장 기록 리트라이 | 같은 트랜잭션 → 롤백. **불일치가 생기지 않음** |
| 4 | ④ → ⑤ 호출 | 원장 서비스 응답 없음 (타임아웃) | 원장이 기록됐는지 **모름.** 별도 DB에 기록해 두고 비동기로 상태를 맞춤 | 해당 없음 (원격 호출이 아님) |
| 5 | ② → core 호출 | 코어 응답 없음 (타임아웃) | 송금이 됐는지 모름 → `확인필요` → 송금 ID로 상태 조회 | 같음 |
| 6 | 고객 → transfer | 같은 송금 요청이 두 번 옴 (재시도, 더블 클릭) | 두 번 송금될 위험 → 멱등성 키로 한 번만 처리 | 같음 |

### 참고: 입출금 실패 (초안)

- 정상 흐름: 입금 요청 → 잔액 갱신 → 입출금 원장 생성
- 모놀리스(한 트랜잭션): 둘 중 하나라도 실패하면 롤백 → 입출금 실패
- MSA:
  - 잔액 갱신 실패 → 입출금 실패 (잔고 부족 또는 기술적 원인)
  - 잔액 갱신 성공 → 원장 생성 실패
    - 원장 생성 전까지 잔액에 `처리 중` 상태 관리가 필요 → 동시 요청엔 락
    - 원장 생성 리트라이
    - 타임아웃 등 확인 불가: 별도 DB에 기록 후 비동기로 상태를 맞춤

## 검토한 선택지

| | A. 전부 MSA | B. 코어 모놀리스(account + ledger 모듈, DB 하나) + 주변 MSA |
| --- | --- | --- |
| 당행 송금의 분산 경계 | `transfer ↔ account`, `account ↔ ledger` | `transfer ↔ core`만 |
| 잔액·원장 불일치 (시나리오 3, 4) | 생김 → 처리 중 상태, 리트라이, 비동기 정합화 필요 | 생기지 않음 (로컬 트랜잭션) |
| 출금 ↔ 입금 | 한 트랜잭션 (두 계좌가 같은 `account` DB) | 한 트랜잭션 |
| 실제 은행과의 유사성 | 낮음 (코어를 쪼갬) | 높음 (현재 전통 은행의 모습) |
| 새로 생기는 실무 주제 | - | 모듈 경계 지키기 (account·ledger 모듈이 서로의 테이블을 직접 건드리지 않게), 레거시 코어와 신규 MSA 연결 |

**실험별로 B에서 무엇이 남나**

| 실험 | B에서 |
| --- | --- |
| 5주 차 사가 (출금 → 입금 실패 → 보상) | **당행에서는 사라진다.** 출금과 입금이 한 트랜잭션이라 "입금 실패"가 없다 → 사가가 실제로 일어나는 **타행 이체**로 옮긴다 |
| 6주 차 Outbox, 중복 메시지 | 그대로 (코어 → `notification` 이벤트) |
| 7주 차 동시 출금, 락 비교 | 그대로 (원래 계좌 DB 안의 문제) |
| 8주 차 멱등성, 결과 불명, 대사 | 그대로. `transfer ↔ core`에서 당행부터 생긴다 |

## 결정

**B. 계정계 코어(account + ledger, 모듈형 모놀리스, DB 하나) + 주변 MSA**

- 실제 은행의 계정계 구조와 같고, 당행 이체를 실제처럼 로컬 트랜잭션으로 처리한다.
- B로도 이 프로젝트의 핵심 실험(Outbox, 동시성, 멱등성, 결과 불명, 대사)이 그대로 남는다. 잃는 것은 당행 사가 하나이고, 사가는 분산 트랜잭션이 실제로 생기는 타행 이체에서 다룬다.
- 분산 경계를 "쪼갤 수 있는 곳"이 아니라 **"실제로 갈라지는 곳"(채널 ↔ 코어, 코어 ↔ 외부 결제망)**에 둔다.

### 서비스별 책임과 데이터 소유

| 서비스 | 소유 | 하지 않는 것 |
| --- | --- | --- |
| `core` (가칭) | 계좌·잔액(account 모듈), 복식부기 원장(ledger 모듈). 송금 ID 기준 멱등 처리, 상태 조회 API | 송금 요청의 진행 상태 관리 |
| `transfer` | 송금 요청 기록과 상태 머신, 상태 조회로 `확인필요` 해소, (타행) 사가 지휘 | 잔액·원장 직접 수정 |
| `gateway` | 라우팅, JWT 인증, Idempotency-Key 검사 | 업무 로직 |
| `notification` | 송금 결과 알림 (Kafka 구독) | |
| `bank-mock` | 외부 결제망 전체(금융결제원 + 타행) 흉내 | |

### 통신 방식

| 구간 | 방식 | 이유 |
| --- | --- | --- |
| `transfer → core` | 동기 REST (3주 차) | 고객이 결과를 기다림. 타임아웃 → `확인필요` → 상태 조회 |
| `core → notification` | Kafka 이벤트 (4주 차), Outbox (6주 차) | 알림이 늦거나 실패해도 송금 결과는 바뀌지 않음 |
| `transfer → bank-mock` | 동기 REST + 타임아웃 | 외부 결제망. 결과 불명 처리 대상 |

### `transfer`를 코어 밖에 두는 이유
- 코어는 송금뿐 아니라 여러 채널(ATM, 창구, 이자 배치)이 함께 쓰는 시스템이다. 그래서 핵심 기능, 즉 **돈을 원자적으로 옮기는 API**에만 집중하게 한다.
- 송금 정책(한도, 예약 송금, 타행, 알림)은 자주 바뀐다. 역할을 나눠 두면 그때마다 가장 보수적으로 다뤄야 할 코어를 배포하지 않아도 되고, 코어를 단순하게 유지할 수 있다.
- 대가: `transfer → core` 호출 경계가 생겨 `확인필요` 상태, 상태 조회, 멱등 처리가 필요하다. 이 프로젝트는 이 경계를 실험 대상으로 삼는다.

### 잔액과 원장
- 잔액을 따로 저장하는 이유: 잔액을 알기 위해 매번 원장 전체를 합산할 수 없다. 또 잔액 행은 동시 출금을 막는 **락의 대상**이다 (7주 차).
- 원장은 **append-only**다. 수정하지 않고 반대 거래로 정정한다. 그래서 단순하고 신뢰할 수 있다.
- 둘이 어긋나면 **원장을 믿는다.** 어긋남은 **대사 배치**(잔액 vs 원장 합계 비교)로 발견한다. B에서는 같은 트랜잭션이라 어긋날 일이 드물지만, 버그나 수동 조작에 대비해 대사는 유지한다 (8주 차).

### 사가는 어디서
- **당행:** `transfer → core` 호출이 한 번이고 코어 안에서 한 트랜잭션으로 끝난다. 되돌릴 앞 단계가 없으므로 사가가 아니다. 대신 상태 머신, 상태 조회, 멱등성으로 처리한다.
- **타행:** ① 코어 출금(로컬 트랜잭션) → ② `bank-mock` 송금(외부, 롤백 불가) → ② 실패 시 ① 출금 취소(보상). `transfer`가 지휘하는 오케스트레이션 사가다. 사가는 **롤백할 수 없는 상대가 끼는 곳**에서 필요하다.

## 결과 (좋아지는 것 / 나빠지는 것 / 로드맵 영향)

**좋아지는 것**
- 잔액·원장 불일치가 구조적으로 생기지 않는다.
- 실제 은행 구조와 같아서 "왜 이렇게 나눴나"를 실무 근거로 설명할 수 있다.
- 서비스 수가 줄어 메모리와 운영 부담이 줄어든다 (부수 효과, 결정 이유는 아님).

**나빠지는 것**
- 당행 송금에서 사가를 실험할 수 없다 → 타행 이체로 옮김.
- 코어 안의 account·ledger 모듈 경계는 DB로 강제되지 않으므로 코드 규칙으로 지켜야 한다.

**로드맵 영향**

| 주차 | 기존 | 변경 |
| --- | --- | --- |
| 2주 | `account` 배포 | `core` 배포 (account 모듈부터) |
| 3주 | `transfer`·`ledger` 서비스 추가, 동기 REST | `transfer` 서비스 추가, ledger는 `core`의 모듈로 추가, `transfer → core` 동기 REST, `gateway` |
| 4주 | Kafka, `notification` | 변경 없음 (코어가 발행) |
| 5주 | 당행 사가 (출금 → 입금 → 원장) | **타행 이체 사가** (코어 출금 → `bank-mock` 송금 → 실패 시 출금 보상). `bank-mock`은 단순 성공/실패만 |
| 6주 | Outbox, 멱등 컨슈머 | 변경 없음 |
| 7주 | 동시 출금, 락 비교 | 변경 없음 |
| 8주 | 멱등성, 타행 이체 추가, 결과 불명, 대사 | 멱등성, 5주 차 타행 이체 위에 타임아웃·결과 불명·상태 조회·대사 추가 |

## 실제 은행과 다른 점

- 실제 계정계는 수십 년 된 거대한 시스템이다. 여기서는 작은 Spring 앱으로 "코어는 하나의 트랜잭션 경계"라는 구조만 흉내 낸다.
- 실제 은행은 채널(앱, ATM, 창구)과 코어 사이에 채널계·대외계 같은 중계 계층이 있다. 여기서는 `gateway`와 `transfer`가 그 역할을 단순화해서 맡는다.
- ATM, 창구 같은 채널 장치는 만들지 않는다.
- 영업일, 마감 시각, 결제망의 실제 전문 형식은 흉내만 내거나 생략한다.

## 생각해 볼 질문

1. (가장 중요) B를 고르면 당행 이체에서 출금·입금·원장 기록이 DB 하나 안의 로컬 트랜잭션으로 끝납니다. 그러면 5주 차 사가, 6주 차 Outbox, 7주 차 동시 출금 실험 중 무엇이 사라지고, 무엇이 남고, 무엇이 새로 생기나요? 사가가 의미 있으려면 분산 경계가 어디에 있어야 할까요?
2. B에서 transfer를 코어 밖에 두는 이유는 무엇일까요? 코어 안에 넣으면 무엇이 편해지고 무엇을 잃나요?
3. 출금은 성공했는데 입금 직전에 서비스가 죽었습니다. 고객 A의 돈은 지금 어디에 있고, 누가 언제 그 사실을 알아채나요?
4. 당행 이체에도 결과 불명 상태가 필요할까요? 외부 은행이 없는데도 "모른다"가 생기는 순간이 있을까요?
5. account의 잔액 컬럼과 ledger의 합계가 다르면 누구를 믿나요? 그런데 "출금 가능 여부"는 왜 원장 합계가 아니라 잔액으로 확인할까요?
6. 처음 MSA를 도입하는 실제 팀이라면 A와 B 중 무엇을 고를까요? 이 프로젝트는 학습용이라 판단이 달라도 괜찮습니다. 다만 그 차이를 ADR에 밝혀 두면 면접에서 오히려 강점이 됩니다.
