# ADR-0005. 당행 송금 결과 불명 해소
- 상태: 초안 (2026-11-23, 설계 연습 08 1부 리뷰에서 합의. 면접 30초 답변은 개발자 작성 예정)
- 날짜: 2026-11-23
- 설계 과정: `docs/design-drills/08-unknown-resolution.md` 1부
- 범위: **당행만** (transfer → core, 홉 1개). 타행(출금·외부 송금·보상)은 2부 → 별도 ADR

## 맥락

- 당행 송금이 끝 상태가 아닌 채로 멈추는 곳이 둘 있다.
  - `PROCESSING`: core 호출 **전에** transfer가 죽은 경우, 그리고 core가 **커밋한 뒤** transfer가 결과를 저장하기 전에 죽은 경우. 그래서 `PROCESSING`이라고 "core에서 처리 안 됨"이 아니다.
  - `UNKNOWN`: core 응답을 못 받음 (연결 실패, read 타임아웃, 5xx, 409).
- 지금은 `UNKNOWN`만 **고객이 같은 키로 재요청할 때** 재전송으로 풀린다 (3-2주 T-2). 고객이 다시 안 오면 영원히 `UNKNOWN`, `PROCESSING`은 아무도 풀지 않는다.
- core에는 상태 조회 API가 이미 있다: `GET /postings/{멱등 키}` → `COMPLETED` / `NOT_PROCESSED`.
- **core는 거절을 기억하지 않는다.** 잔액 부족 등으로 거절하면 롤백되어 원장에 흔적이 없고, 조회하면 `NOT_PROCESSED`다.

## 결정

### 1. 해소 일꾼: transfer 안의 스케줄러
- 대상: `PROCESSING`·`UNKNOWN`이고 **`createdAt`(= core에 보낸 시각) + 5초**가 지난 송금 (설정값).
- 기준 시각이 `updatedAt`이 아니라 `createdAt`인 이유 (2026-11-23 확정): `UNKNOWN`이 되면 `updatedAt`이 바뀌어 "보낸 시각"을 잃는다. 송금 생성과 `PROCESSING` 커밋·core 호출은 ms 차이라 `createdAt` ≈ 보낸 시각이고, **재전송이 없으므로(결정 2) core에 보내는 건 평생 한 번**이라 이 시각이 바뀌지 않는다. 덕분에 `PROCESSING`·`UNKNOWN`, 고객 재요청·해소 일꾼에 규칙 하나로 충분하다 (재전송이 있었다면 보낸 시각이 여러 번이라 불가능).
- **고객 재요청도 같은 규칙:** 5초가 지났으면 조회해서 확정, 안 지났으면 지금 상태(`PROCESSING`/`UNKNOWN`) 그대로 돌려준다.
- 5초 근거: transfer → core 최악 소요 = connect 1s + read 3s + 결과 커밋 ≈ 4.5s (`UNKNOWN`은 대개 보낸 지 약 4초 뒤에 생긴다 → `UNKNOWN`을 "바로 조회"하면 이 기준을 우회한다).
- 이 기준은 **정합성 장치다** (2026-11-23 정정: 처음엔 "헛일을 줄이는 장치"로 적었으나, 2번에서 재전송을 버리고 조회만 하기로 하면서 성격이 바뀌었다). 너무 일찍 조회하면 core가 아직 처리 중인데 `NOT_PROCESSED`를 보고 `FAILED`로 확정한다 → 늦은 커밋(3번). 그래서 기준 시간은 core 트랜잭션 타임아웃(3초)보다 **확실히 길어야** 한다. 10주 차 p99 지표로 조정하되 이 관계는 지킨다.

### 2. 해소 일꾼은 조회만 한다 (재전송하지 않는다)
- core 조회 결과에 따라:
  - `COMPLETED` → 송금 `COMPLETED` (완료 이벤트 outbox)
  - `NOT_PROCESSED` → 송금 `FAILED` (실패 이벤트 outbox)
  - 조회 자체가 실패 (core 장애) → 그대로 두고 다음 회차
- **이유:** 고객이 없는 일꾼이 재전송하면 옛날 송금이 **지금 잔액으로 지금 실행**된다. 10시에 잔액 부족으로 거절됐는데 결과 저장 전에 죽었고, core 장애가 2시간 이어지다 12시에 복구됐는데 그사이 월급이 들어왔다면, 재전송은 성공한다. 멱등은 "두 번 실행"을 막을 뿐 "늦은 실행"은 막지 못한다. 잔액은 계속 바뀌므로 1분 차이도 다른 판단이 될 수 있다 (pitfalls 38).
- **고객의 같은 키 재요청도 재전송하지 않고 조회한다** (2026-11-23 개발자 결정, T-2 변경). 이유: 재전송이 없는 쪽이 일관적이다. 송금을 지금 실행하는 경로는 "처음 요청" 하나뿐이 된다. 조회 결과가 `NOT_PROCESSED`면 고객은 실패를 받고, 원하면 **새 키로** 다시 보낸다 (그 시점의 잔액·의사로).
- 해소로 확정한 실패의 실패 코드: `CORE_NOT_PROCESSED` (core 조회 결과 "처리 안 됨". core가 거절을 기억하지 않아 원래 거절 사유는 알 수 없다).

### 3. 늦은 커밋: core 트랜잭션 타임아웃(예방) + 대사(마지막 그물)
- 문제: 조회의 "없음"은 **"진짜 안 됨"과 "아직 하는 중"을 구분하지 못한다.** core가 락 대기로 느려진 사이 일꾼이 `NOT_PROCESSED`를 보고 `FAILED`로 확정하고, 그 뒤 core가 커밋하면 → transfer는 실패, 돈은 이동 → 고객이 다시 보내면 이중 송금.
- **예방:** core 송금 트랜잭션에 타임아웃 3초 (해소 기준 5초보다 짧게). "시작하고 3초가 지나면 커밋하지 않는다"는 약속. 구현: Spring 트랜잭션 타임아웃(앱이 SQL마다 남은 시간을 거는 방식), 거래 전용 `TransactionTemplate`, 설정 `core.posting.transaction-timeout` (2026-11-24, `PostingTransactionTimeoutTest`로 재현·확인)
- **재시도 루프·트랜잭션 앞 대기 빈틈** (2026-11-24 개발자 결정): 기본 전략 `ATOMIC_UPDATE`에선 쓰는 트랜잭션이 사실상 하나라 작다. OPTIMISTIC(최대 3회 재시도)·REDIS(트랜잭션 앞 1초 대기) 실험 모드에서 커지는 빈틈은 재시도 예산을 두지 않고 대사에 맡긴다.
- **한계:** 타임아웃 시계는 **트랜잭션 시작**부터 돈다 (DB·Spring 트랜잭션은 요청 도착 시각을 모른다). 그 앞의 대기(톰캣 대기열, 커넥션 풀 대기)는 못 막는다.
- **마지막 그물:** 8-2 일일 대사가 "transfer `FAILED`인데 core에 그 송금 ID 전표가 있음"을 불일치로 잡는다.
- 빈틈까지 막는 데드라인 전파(gRPC deadline 방식)는 이번 범위 밖. 검사와 커밋이 원자적이지 않아 그것도 빈틈이 0은 아니다 (`docs/learning/timeouts-and-deadlines.md`).

### 4. 일꾼과 고객 재요청이 동시에 같은 송금을 쓰면
- 결과 쓰기는 기존 `@Version`(낙관적 락)이 하나만 통과시킨다. 진 쪽 트랜잭션은 outbox INSERT까지 함께 롤백되므로 **이벤트 중복은 없다.**
- 진 쪽이 **고객 요청**이면: 충돌 예외를 잡아 트랜잭션 밖에서 다시 읽고, 그 상태를 200으로 돌려준다 (`DuplicateIdempotencyKeyException` 처리와 같은 모양). 지금은 예외 처리가 없어 500이 나간다.
- 진 쪽이 **일꾼**이면: 다른 쪽이 이미 해소했다 → 넘어간다.

### 5. 일꾼이 여러 대면 (transfer 파드 여러 개)
- `FOR UPDATE SKIP LOCKED`로 몇 건 잡고 → 트랜잭션 안에서 core 조회 → 반영 → 커밋.
- 원격 호출 동안 트랜잭션을 쥐지만 일이 조회 한 번이라 짧다 (6주 차 Outbox 릴레이와 같은 모양). 회차당 건수 × 조회 타임아웃이 트랜잭션 최대 길이가 되므로 건수를 작게 둔다.
- 이건 정합성 장치가 아니라 **헛일을 줄이는 장치**다. 둘이 같은 건을 집어도 조회는 돈을 안 움직이고, 결과 쓰기는 4번이 지킨다.

## 대안

| 대안 | 안 고른 이유 |
| --- | --- |
| 일꾼이 같은 송금 ID로 **재전송** (앞으로 복구) | 멱등이라 이중 실행은 없지만, 고객 없이 늦은 실행이 된다 (결정 2) |
| core가 거절도 키별로 기록 (Stripe처럼 실패 응답까지 저장) → 재전송이 언제나 안전 | core 쓰기가 늘고 스키마 변경이 필요. '아직 하는 중'(늦은 커밋) 문제는 그대로. 이번엔 조회로 충분 |
| 고객 재요청만 재전송, 일꾼은 조회 (정책 B, 원래 T-2) | 보낸 시각이 여러 번이 되어 `createdAt` 기준이 깨진다: 고객 재전송이 core에서 처리 중일 때 일꾼이 조회 "없음"을 보고 FAILED → 재전송 커밋 = 늦은 커밋. 메우려면 `last_sent_at` 컬럼(보내기 전에 커밋) + 기준 변경 + 고객 경로의 늦은 실행 허용 결정이 필요. 2026-11-24 개발자 판단: 돈은 예민하니 실행 경로를 하나로 둔다 (`docs/learning/unknown-outcome-policy.md`) |
| 5초 안 재요청은 재전송, 뒤는 조회 | 돈 문제는 없지만(몇 초 안이라 의사가 그대로) 경로가 두 개가 된다 (2026-11-23 개발자 판단: 단순함 우선) |
| 오래된 건만 포기, 최근 건은 재전송 | 경계 시간을 정할 근거가 없다. 잔액은 1분 사이에도 바뀐다 |
| 결과 불명 송금이 있으면 고객의 새 송금을 **차단** | core 장애 동안 결과 불명 고객 전원이 송금 불가. 실무는 차단 대신 "처리 중" 표시 + 같은 수취인·같은 금액 재송금 시 **중복 이체 경고** |
| 늦은 커밋을 대사로만 잡기 | 대사는 하루 뒤에야 찾는다. 흔한 원인(트랜잭션 안 락 대기)은 타임아웃 한 줄로 싸게 막힌다 |
| 데드라인 전파 | 이번 범위에 과하다. 15주 차 타임아웃 예산 때 후보 |
| ShedLock(한 대만 실행) | 일이 멱등·조회뿐이라 여러 대가 동시에 돌아도 된다. SKIP LOCKED면 나눠서 처리도 된다 |

## 결과

- 좋아지는 것: 고객이 다시 오지 않아도 멈춘 당행 송금이 몇 초~몇 분 안에 끝 상태가 되고 알림이 나간다. 일꾼이 돈을 새로 움직이지 않아 늦은 실행이 없다.
- 남는 구멍 (의도): 트랜잭션 시작 전 대기로 생기는 늦은 커밋 → 대사(8-2). **조회 실패에서 회차를 멈추는 규칙의 head-of-line blocking:** 특정 송금 하나만 조회할 때마다 실패하면(core 버그·데이터 문제) 오래된 순 맨 앞에서 매 회차 멈춰 뒤 송금이 영영 안 풀린다 (개발자 실무 경험: 배치가 한 건 때문에 멈춘 적 있음). 해법 후보는 아래 "열린 질문". core가 오래 죽어 있으면 조회도 실패해 계속 멈춰 있다 → 13주 차 체류 시간 지표, 에이징 리포트.
- 필요한 변경 (구현 티켓에서 나눔):
  - transfer: core 상태 조회 포트·어댑터, 해소 스케줄러(SKIP LOCKED 조회 쿼리 + 기준 시간 설정값), 고객 재요청의 `@Version` 충돌 처리
  - core: 송금 트랜잭션 타임아웃
  - 재현 먼저 (6장 4번): "PROCESSING에 멈춘 송금이 안 풀린다", "늦은 커밋" 테스트

## 열린 질문

- head-of-line blocking 대응 (2026-11-23 발견, 구현 뒤 결정). 실무 후보:
  - **다음 시도 시각(`next_attempt_at`) + 백오프:** 실패한 건은 뒤로 미루고 나머지를 계속. 한 건이 줄 전체를 막지 않는다
  - **시도 횟수 상한 → 격리(park):** N번 실패하면 해소 대상에서 빼고 사람에게 (에이징 리포트·알림). 메시징의 DLQ와 같은 생각
  - **장애 구분:** 한 건 실패는 건너뛰고 계속, **연속 K건** 실패면 core 장애로 보고 회차 중단
- (해결) 고객 재요청이 5초 전이면 → 지금 상태 그대로 (결정 1)
