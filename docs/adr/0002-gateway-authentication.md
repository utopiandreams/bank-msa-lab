# ADR-0002. gateway 인증과 외부 노출 범위
- 상태: 승인 (2026-11-14, 면접 30초 답변만 남음)
- 날짜: 2026-11-14

## 맥락

- 지금은 서비스마다 Ingress가 하나씩 열려 있다 (`core.172.30.1.240.nip.io`, `transfer.…`). 누구나 core의 `/postings`를 직접 불러 잔액을 움직일 수 있다.
- 계좌에는 소유자(`ownerId`)가 있지만 개설 요청 바디로 받는다 (누구든 아무 userId로 개설 가능). transfer에는 요청자 개념이 없다. T-2 고객 멱등 키도 사용자 구분 없이 전역 UNIQUE로 두었다 ("gateway JWT 인증이 생기면 사용자별로").
- CLAUDE.md 2장의 원칙: **인증은 gateway, 인가는 서비스.**
- 이 프로젝트의 학습 목표는 분산 트랜잭션·장애다. 로그인 기능 자체는 면접 가치가 낮다. 대신 인증 서버 분리에서 생기는 질문들(키 배포·교체, 토큰 폐기, 인증 서버 장애)은 가치가 있어서 백로그로 남긴다.
- 제약: 클러스터는 메모리가 병목(32GB)이다. Keycloak은 1GB 가까이 쓴다.

## 결정

### 1. 발급: gateway의 학습용 엔드포인트 (의도한 타협)
- `POST /auth/token {"userId": "..."}` → JWT. **비밀번호 검증 없음.** k6 부하·패널 시연에서 사용자 여러 명의 토큰을 쉽게 뽑기 위해서다.
- 실무 정석은 **발급은 인증 서버(IdP: Keycloak, Auth0, Cognito), gateway는 검증만**이다. gateway가 발급까지 하면 비밀번호 검증 → 사용자 DB가 필요해져서 "얇은 정문"이 "회원 서비스"가 된다.
- 나중에 IdP로 갈아끼우기 쉽게, 검증은 표준 모듈(Spring Security OAuth2 Resource Server)로 한다. 교체할 때 바뀌는 건 발급 엔드포인트 삭제 + 검증 키 설정(`jwk-set-uri`)뿐이다.

### 2. 서명: HS256
| | HS256 | RS256 |
| --- | --- | --- |
| 키 | 비밀키 하나로 서명·검증 | 개인키로 서명, 공개키로 검증 |
| 누가 키를 아나 | 발급자·검증자 **모두** 비밀키 | 발급자만 개인키 (공개키는 유출돼도 위조 불가) |
| 맞는 상황 | 발급자 = 검증자 | 발급자 ≠ 검증자, 검증자가 여럿 |

- 지금은 발급자 = 검증자 = gateway라 비밀키를 gateway만 안다 → HS256으로 충분하다.
- 비밀키는 k8s Secret으로 주입한다. Git에 커밋하지 않는다.
- **RS256으로 바꾸는 시점:** IdP를 분리할 때, 또는 서비스도 토큰을 직접 검증할 때(제로 트러스트). 그때는 비밀키를 여러 곳에 나눠 주면 안 되기 때문이다.

### 3. 사용자 전달: gateway가 `X-User-Id`를 덮어쓴다
- 토큰 검증에 성공하면 `sub` 클레임을 `X-User-Id` 헤더로 서비스에 넘긴다.
- **들어온 `X-User-Id`는 토큰이 있든 없든 무조건 지운다.** 지우지 않으면 유효한 토큰을 가진 A가 `X-User-Id: B`를 붙여 B 행세를 할 수 있다.
- 서비스는 이 헤더를 믿는다. 이 신뢰는 **"서비스에 gateway를 거치지 않고는 닿을 수 없다"**는 전제 위에 있다 → 4번.

### 4. 외부 노출: gateway 하나만 연다
- Ingress는 gateway만 남기고 core·transfer의 Ingress를 닫는다. Argo CD는 운영 도구라 예외로 둔다.
- gateway 라우팅은 `/transfers/**` → transfer만 둔다. **core `/postings`는 gateway에도 열지 않는다.** 고객의 송금 입구는 transfer 하나이고, core는 내부 서비스(transfer)만 부른다.
- 토큰 없이 통과하는 경로: `/auth/token`, gateway 자신의 `/actuator/health`.

## 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| Keycloak (지금 바로) | 실무와 같은 구조, OIDC 학습 | 메모리 부담, 이번 주 목표(라우팅·인증 경계)보다 설정 학습이 커짐 → 노드 확장 뒤 백로그 |
| 서비스마다 JWT 직접 검증 | 내부 위조에도 안전 (제로 트러스트) | 키 배포 문제가 생겨 RS256·JWKS가 필요 → 백로그 |
| 손으로 짠 JWT 필터 | 라이브러리 없음 | 만료·서명 알고리즘 검증 같은 보안 코드를 직접 짜면 실수 위험, IdP 교체가 어려움 |

## 결과

- 좋아지는 것: 외부 진입점이 하나가 되어 인증·로그·(나중에) 레이트 리밋을 한곳에서 다룬다. 서비스는 인증 코드 없이 `X-User-Id`만 읽는다.
- 남는 위험: **클러스터 내부의 위조.** 쿠버네티스 기본 네트워크는 모든 파드가 서로 통한다. 파드 하나가 뚫리면(취약 라이브러리, SSRF) 그 안에서 `X-User-Id`를 위조해 transfer를 부를 수 있다 (횡적 이동). → 백로그 "NetworkPolicy · 제로 트러스트"에서 위조를 먼저 재현하고 막는다.
- 남는 위험: 학습용 발급은 누구나 아무 userId로 토큰을 받는다. 실제 인증이 아니다. → 백로그 "인증 서버 분리"
- 장애 관점: 검증은 gateway 안에서 로컬로 끝난다 (인증 서버에 묻지 않음). IdP를 분리한 뒤에도 공개키를 캐시하면 **IdP가 죽어도 기존 토큰의 송금은 계속된다.** 이걸 백로그에서 실험한다.

## 구현 전 결정 사항

1. ~~고객 멱등 키 범위~~ → **결정 (2026-11-14): 사용자별.** transfer에 `requester_id` 컬럼(Flyway V3), `(requester_id, idempotency_key)` UNIQUE. T-2에서 "gateway JWT 인증이 생기면 사용자별로"라고 미뤄 둔 것. 전역이면 다른 사용자의 키와 우연히 겹쳐 409를 받고, 그 409가 "누군가 이 키를 썼다"는 정보를 흘린다.
2. **"내 계좌에서만 송금" 인가 → 결정 (2026-11-14): G-4로 분리.** 지금은 유효한 토큰만 있으면 남의 `fromAccountId`로 송금할 수 있다 (**BOLA/IDOR**, OWASP API Security Top 10 1위). 계좌에는 이미 소유자(`ownerId`, 개설 때 바디의 `userId`)가 있다. 남은 일은 개설 API가 바디 대신 `X-User-Id`를 쓰게 하고, 송금 때 소유자를 검사하는 것이라 gateway 티켓과 나눈다. (처음엔 소유자가 없다고 잘못 판단했다가 G-1 클러스터 확인 중 정정, 2026-11-14) G-4는 "철수 토큰으로 영희 계좌 출금" 테스트로 뚫림을 먼저 재현한 뒤 막는다. 설계 질문: transfer가 core에 소유자를 먼저 묻는다(a) / core가 송금 처리 때 요청자를 받아 검사한다(b) — 원격 호출 횟수와 검사·출금 사이의 틈이 다르다.
