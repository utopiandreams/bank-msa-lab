# ADR-0003. 송금 이벤트와 notification
- 상태: 승인 (2026-11-18, 면접 30초 답변만 남음)
- 날짜: 2026-11-18

## 맥락

- 4주 차 목표: 송금이 끝나면 이벤트를 Kafka(Strimzi)로 보내고, `notification`이 받아서 알림을 기록한다.
- CLAUDE.md 2장: 서비스 간 비동기 통신은 Kafka, 파티션 키는 기본적으로 계좌 ID. 이벤트 발행은 **Phase 2(6주 차)부터** Transactional Outbox.
- CLAUDE.md 7장: 모든 Kafka 컨슈머는 멱등, 이벤트에는 고유 `eventId`.
- **의도적으로 남기는 구멍:** 이번 주는 Outbox 없이 커밋 뒤 바로 발행한다. 6주 차에 "커밋과 발행 사이 장애 → 이벤트 유실"을 재현하려면 이 구멍이 있어야 한다.

## 결정

### 1. 발행 주체: transfer
- "송금이 끝났다"는 사실의 주인은 송금 상태 머신을 가진 transfer다. UNKNOWN이 끝 상태로 확정되는 곳도 transfer다. core는 원장 기록만 안다.
- DDD 용어로는 Transfer 애그리거트의 **도메인 이벤트**.

### 2. 발행 시점: 끝 상태로 **바뀌는 순간**에만
- COMPLETED·FAILED로 전이될 때 발행한다. FAILED도 보낸다 (잔고 부족 같은 실패도 고객이 알아야 한다).
- UNKNOWN은 발행하지 않는다. UNKNOWN이 나중에 끝 상태로 확정되면 **그때** 발행한다.
- 같은 멱등 키 재요청에 기존 송금을 돌려줄 때는 발행하지 않는다. 기준은 "응답할 때"가 아니라 "상태가 바뀔 때" (응답마다 발행하면 알림이 중복된다).

### 3. 파티션 키: 송금 ID
- 같은 키끼리만 순서가 보장된다. 송금 완료 이벤트는 송금 하나당 한 번이라 송금 ID면 순서 문제가 거의 없고, 분산이 고르다.
- **CLAUDE.md의 "기본은 계좌 ID"를 이 이벤트에서는 따르지 않는다.** 계좌 ID로 하면 송금 하나가 두 계좌에 걸쳐 어느 쪽을 키로 할지 정해야 하고, 지금 계좌 단위 순서가 필요한 소비자가 없다.
- 포기하는 것: 같은 계좌의 송금 이벤트 순서. "계좌별 거래 내역", "이상 거래 탐지(계좌당 빈도)" 같은 소비자가 생기면 그 이벤트는 계좌 ID 키로 따로 낸다 (예: 출금됨 / 입금됨을 각 계좌 키로).

### 4. 이벤트 스키마: `libs/common`에 공유 클래스
- 모노레포라 공유가 편하다. **실무(서비스별 레포)라면 서비스별 클래스 + JSON 계약이 낫다**는 걸 알고 고른 타협이다 — 공유하면 생산자가 필드를 바꿀 때 소비자도 같이 배포해야 한다 (pitfalls 18).
- 완화: 소비자는 **모르는 필드를 무시**하고 읽는다, 이벤트에 **`schemaVersion`**을 둔다.

### 5. notification 멱등: 전용 DB
- Kafka는 같은 메시지를 다시 줄 수 있다 (at-least-once: 처리 후 오프셋 커밋 직전에 죽으면 재시작 후 다시 받음). 처리한 `eventId`를 기억해야 하고, 재시작에도 남아야 하므로 메모리가 아니라 DB.
- DB per service: notification 전용 PostgreSQL (CloudNativePG `notification-db`).
- 방식은 T-2와 같다: 알림 기록 행에 `event_id` UNIQUE. 기록과 중복 판별이 한 INSERT라 원자적.

### 6. 알림 발송: 최소 범위
- 진짜 문자·푸시도 외부 연동이라 transfer → core와 같은 결과 불명 문제가 생긴다 (개발자 지적). 그래서 알림 행에 **상태 칸**(대기 / 보냄 / 실패)은 지금부터 둔다.
- 이번 주는 **가짜 발송기**(로그만 남기고 바로 "보냄"). 외부 발송 업체의 지연·실패, 재시도는 15주 차(외부 장애)에.

## 대안

| 대안 | 버린 이유 |
| --- | --- |
| core가 발행 | core는 송금 상태(UNKNOWN 해소 등)를 모른다 |
| 응답할 때마다 발행 | 재요청마다 중복 이벤트 |
| 파티션 키 = 보내는 계좌 ID | 받는 쪽 순서는 어차피 포기, 지금 필요한 소비자 없음 |
| 멱등을 메모리로 | 중복은 하필 재시작 때 생기는데 재시작하면 잊는다 |
| 이번 주부터 Outbox | 6주 차에 유실을 재현할 수 없게 된다 |

## 결과

- 남기는 구멍 (6주 차 재현 대상): 송금 결과 커밋과 Kafka 발행 사이에 죽으면 이벤트가 사라진다. 발행 실패도 송금 응답에는 영향을 주지 않고 로그만 남긴다 → 같은 유실.
- 포기한 것: 계좌 단위 이벤트 순서.
- notification의 알려진 한계 (15주 차): 알림 INSERT(PENDING)와 SENT 커밋 사이에 죽으면 PENDING에 멈춘다. 같은 이벤트가 다시 와도 중복으로 건너뛰기 때문. PENDING이면 다시 보내게 하면 "실제로는 보냈는데 SENT 직전에 죽은" 경우 두 번 간다 (외부 발송의 결과 불명) → 재발송 스케줄러 + 발송 업체 쪽 멱등 키
- 깨진 메시지(poison pill)는 재시도 없이 로그만 남기고 건너뛴다 (예외를 던지면 그 파티션 전체가 막힌다). 일시 오류(DB 장애)는 1초 간격 3번 재시도 후 건너뛴다. 건너뛴 메시지는 유실 → 6주 차에 Dead Letter Topic 검토
