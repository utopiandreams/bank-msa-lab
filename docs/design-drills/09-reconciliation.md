# 09. 일일 대사 (8주 차)

> 진행 방식 (2026-11-25): 개발자가 먼저 채운다 → Claude가 장애 질문으로 하나씩 리뷰. 대사는 흐름(홉)이 아니라 **배치**라 템플릿을 대사용으로 바꿨다. 모르는 칸은 "모름"

## 0. 지금 시스템에 있는 것 (Claude 정리, 사실만)

- core 원장: 타행 출금 = 고객 예금 → `타행이체 미정산` 계정 (원장 키 = 송금 ID), 취소 = 역분개 (원장 키 = `{송금ID}-cancel`, `reverses_entry_id`로 원래 출금을 가리킴)
- transfer: 타행 송금 상태 (`COMPLETED` · `CANCELLED` · `FAILED` · 중간 상태들), 출금 전표 ID(`core_entry_id`)·취소 전표 ID(`cancel_entry_id`)
- bank-mock: 메모리에 송금 키별 판정(ACCEPTED/REJECTED) 저장, 송금 키 단건 조회 API. **하루치 거래 내역 API는 없다** (`docs/domain/README.md`의 "하루 거래 내역 제공(대사용)"은 아직 미구현). 재시작하면 기록이 사라진다 (결정 6)
- 차액결제(정산 자금 이동)는 흉내 내지 않기로 했다 (`docs/domain/README.md`) → 미정산 계정은 지금 계속 쌓이기만 한다 (S-4: "미정산 3만 남음 = 정상")

| 5 | 날짜 기준 | **우리 날짜 = 송금 `createdAt`**(요청 시각, 안 바뀜)으로 묶는다 (개발자). `updatedAt`은 해소 일꾼이 다음 날 처리하면 날짜가 바뀌어 같은 송금이 다른 날에 묶일 수 있다 | 외부 처리일을 받으려면 bank-mock 응답·transfer 테이블을 바꿔야 함 |
| 6 | 날짜 경계·시차 | **이월(미결)**: 짝 맞추기 대상 = 오늘 우리 목록 + 이월된 미결 ↔ 오늘 외부 내역. 외부 → 우리 방향을 먼저 보며 이월 건과 짝지어 해소(개발자), 남은 건 이월. **양쪽 다** 이월 (시스템 간 시계 차이로 외부가 먼저 보일 수 있음). N일 넘게 안 풀리면 진짜 불일치 (N 미정) | 자정 경계 송금은 양쪽이 다른 날로 묶는다. 이월 없이 단건 조회로 확인만 하면 다음 날 "외부에만 있음"으로 또 잡힌다 |
| 8 | 대사는 어디서 도나 | **별도 대사 서비스** (2026-11-25 개발자 결정, "대사 자체가 매우 중요해서") | 독립성: 검사받는 쪽(transfer)이 검사를 겸하면 같은 코드의 버그를 못 본다. 실무도 정산·대사 시스템이 따로 있다 |
| 9 | 데이터를 어떻게 모으나 | **일자별 추출 파일**을 오브젝트 저장소에 (core·transfer·bank-mock이 각자 떨구고, 대사 서비스가 읽어 자기 DB 스테이징에 적재 → 비교 → 결과 저장) | 양이 늘어도 강하고, 다른 서비스 DB에 커넥션을 붙이지 않고, 서비스와 시간이 분리되고, **파일 자체가 그날 내역의 증거**로 남아 재실행해도 같은 결과. API는 다시 부르면 그사이 데이터가 바뀔 수 있다. 저장소 선택은 미정 (MinIO 커뮤니티판은 2025-10부터 공식 이미지·바이너리 배포 중단) |
| 10 | 정상 건 기록 | **회차 요약(건수·합계) + 예외 항목(이월·불일치)만**. 정상 건은 송금마다 남기지 않는다 (개발자) | 그날 파일이 원본 증거로 남으니 "송금 X는 맞았나"는 그 파일로 다시 대사하면 된다. 건별 기록은 매일 수십만 행을 아무도 안 보는 데 쓴다. 재현 조건: 파일 불변(덮어쓰기 금지), 회차에 대사 로직 버전·들어온 이월 목록을 남김 (이월 때문에 하루치만 다시 돌리면 결과가 다를 수 있다) |
| 11 | 언제 돌리나 (시작 신호) | 각 서비스가 **파일을 다 올린 뒤** "D일 추출 완료" 이벤트(Kafka) 발행 → 대사 서비스가 날짜별로 도착을 기록하고 **셋 다 모이면** 시작. 하나라도 없으면 시작하지 않는다 (개발자) | 일부 파일로 돌리면 가짜 불일치가 수만 건 쏟아져 진짜가 묻힌다. 순서(업로드 → 이벤트)가 바뀌면 이벤트를 받았는데 파일이 없다. 이벤트 중복은 (날짜, 출처)로 멱등 |
| 12 | 파일 무결성 | 이벤트에 **건수·금액 합계·체크섬** → 대사 서비스가 파일과 대조, 안 맞으면 대사 불일치가 아니라 **파일 불량** → 회차 실패, 다시 받는다 (개발자) | S3 업로드는 원자적이라 반쯤 올라간 파일은 안 보이지만, "파일이 있다" ≠ "그날 거래가 다 들어 있다" (추출 버그). 정산 파일 trailer와 같은 역할 |
| 13 | 추출이 아예 안 돌면 | 1차: 서비스 안 에러 로그·알림. 2차: **대사 서비스가 기준 시각까지 안 오면 경보** (개발자) | 1차는 "돌다가 실패"만 잡는다: **아예 안 돈 배치는 로그를 남기지 않는다**(신호의 부재). 그래서 받는 쪽의 기한 감시(dead man's switch)가 본체. 구현은 출처별 "마지막 추출 완료 시각" 지표 + Prometheus 알림 규칙이 깔끔 (11주 차 Alertmanager) |
| 7 | 우리 끝 상태별 외부 내역 정상값 (개발자) | 아래 표. **우리 쪽이 끝 상태가 아니면 판정하지 않고 이월** | "있다/없다/금액"만으론 부족하고 **결과가 같은가**도 본다 |

| 우리 끝 상태 (어떻게) | 외부 내역 정상값 | 어긋나면 |
| --- | --- | --- |
| `COMPLETED` | ACCEPTED | 없음(이월 기한 뒤)·REJECTED: 고객 돈은 빠졌는데 받는 사람은 못 받음 → 고객 손실, 민원 |
| `CANCELLED` (외부 거절) | REJECTED | ACCEPTED: 이중 지급 |
| `CANCELLED` (외부 조회 "없음") | 없음 | ACCEPTED: **이중 지급** (외부 계약 위반 또는 우리 external-check-after 설정 실수) → 이월 없이 즉시 경보. 실무 처리는 받은 사람 은행에 반환 요청(착오송금 반환), 못 받으면 은행 손실 |
| `CANCELLED` (`WITHDRAWN`에서, 외부에 안 보냄) | 없음 | 있으면: 보낸 적 없는 송금이 외부에 있음 → 우리 버그 또는 ID 충돌, 즉시 경보 |
| `FAILED` (출금 거절·출금 조회 "없음") | 없음 | 위와 같음 |
