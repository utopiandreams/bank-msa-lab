## 7. 헷갈리는 것 / 질문

## 설계가 바뀐 과정 (블로그 재료, 2026-11-23)

> 블로그 글감: "결과를 모를 때 다시 보내면 안 되는 이유" / 줄기 2 "'모른다'를 다루는 법". 이 순서대로 쓰면 글이 된다: 처음 직관 → 장애 질문 하나마다 무너지는 지점 → 최종 규칙.

1. **첫 직관:** "멈춘 건 `PROCESSING`·`UNKNOWN` 둘. 둘 다 다시 진행하면 된다. 동시에 재전송돼도 core가 멱등이라 중복 처리는 안 된다." → 중복은 정말 안 난다. 여기까진 맞다.
2. **`PROCESSING`은 "안 보냄"이 아니다:** 보내기 전에 죽음 / core 커밋 뒤 저장 전에 죽음 / 타임아웃 뒤 저장 전에 죽음, 세 가지. 그래서 "`PROCESSING`이면 그냥 취소"는 돈은 나갔는데 실패 처리하는 길이 된다. → 취소 전에 확인이 필요.
3. **늦은 실행 (가장 큰 전환점):** core는 거절을 기억하지 않는다(롤백 = 흔적 없음). 10시 잔액 부족 거절 → 저장 전 죽음 → core 2시간 장애 → 12시 복구, 월급 입금 → 재전송이 성공. **멱등은 두 번 실행은 막지만 늦은 실행은 못 막는다.** 개발자 판단: "잔액은 계속 바뀐다. 1분 차이도 안 된다." → 해소 일꾼은 **조회만** (pitfalls 38).
4. **고객 재요청도 조회로:** "고객은 지금 의사가 있으니 재전송해도 된다"는 논리도 가능했지만, "재전송이 없는 게 일관적"이라 버림. 송금을 실행하는 경로는 처음 요청 하나뿐.
5. **조회의 "없음"은 두 뜻:** "진짜 안 됨"과 "아직 하는 중". 일꾼이 "없음"을 보고 실패 확정 → core가 뒤늦게 커밋 → 이중 송금. 개발자 첫 반응: "이건 대사에서 해야 하는 거 아니냐, 다 방어하기 어렵다" → **정답.** 실무 철학이 "다 막기"가 아니라 "어긋나면 찾아 맞춘다". 싼 예방책으로 core 트랜잭션 타임아웃(3초)을 더함.
6. **타임아웃은 어디서부터 재나:** 트랜잭션 시작부터. DB·Spring은 요청 도착 시각을 모른다(도구의 한계). 톰캣 대기열·커넥션 풀 대기는 못 막는다 → 남는 빈틈은 대사. 빈틈까지 막는 실무 방식 = 데드라인 전파(gRPC `grpc-timeout`은 남은 시간을 보내 시계 차이를 피함). 그래도 "검사와 커밋이 원자적이지 않아" 0은 아니다 (`timeouts-and-deadlines.md` 1·2).
7. **기준 시간의 성격이 바뀜 (Claude 정정):** 재전송일 땐 5초 기준이 "헛일 줄이기"였는데, 조회만 하게 되면서 "일찍 조회하면 오판" = **정합성 장치**가 됐다. 결정 하나가 다른 결정의 성격을 바꾼다.
8. **기준 시각:** `UNKNOWN`은 보낸 시각을 모른다(`updatedAt`이 바뀜). 개발자 첫 안 "`UNKNOWN`은 `updatedAt`+2초, `PROCESSING`은 5초" → 재전송이 없으니 보내는 건 한 번 → `createdAt` 하나로 통일. **4번의 단순화 결정이 8번을 가능하게 했다.**
9. **그럼 재전송은 언제 쓰나:** 상대가 실패까지 기억할 때(Stripe는 첫 응답을 오류까지 24시간 저장 → 재시도 권장), 그리고 아주 짧은 자동 재시도. 금융권 기본은 "모르면 다시 실행"이 아니라 "모르면 조회 전문 / 망취소" (`timeouts-and-deadlines.md` 3).

**한 줄 요약 (면접):** 결과 불명은 "다시 보내기"가 아니라 "확인하기"로 푼다. 멱등은 이중 실행을 막을 뿐 늦은 실행을 막지 못하고, 조회의 "없음"은 "아직 하는 중"일 수 있어서 확인 시점(보낸 시각 + 처리 상한)과 마지막 그물(대사)이 필요하다.

| 7 | 해소 회차의 트랜잭션 단위 (2026-11-25) | **잠금(`SKIP LOCKED`)은 그대로, 커밋은 건마다**: 1건 잡기 → 조회·(필요하면) 취소 → 커밋을 회차당 최대 N번 반복. 당행처럼 회차 = 한 트랜잭션으로 하지 않는다 | 타행은 한 건에 원격 호출이 둘(조회 + 취소)이라 최악 8초/건, 회차를 한 트랜잭션으로 묶으면 10건에 80초. 그런데 비용을 따져 보면 커넥션 고갈(일꾼은 스레드 하나)·잠금 대기(멈춘 행에 쓰는 쪽이 일꾼뿐, 고객 재요청은 읽기만)는 거의 없고, 남는 건 **커밋 단위가 큰 문제**(해소가 회차 끝까지 안 보임, 죽으면 통째로 다시, graceful shutdown 30s 초과)뿐 → 건마다 커밋으로 해결. 청크를 키워도 빨라지지 않는다: 건당 시간은 원격 호출이 차지하고, 묶어서 아끼는 건 SELECT·커밋(ms)뿐. 검토하고 버린 것: 트랜잭션 밖 호출 + `@Version`(잠금이 없으면 두 파드가 같은 "가장 오래된 N건"을 골라 일을 못 나눈다), 비동기 발사 후 다음 회차 확인(core가 느릴수록 진행 중 요청이 쌓임 = 스스로 만드는 재시도 폭주), 분산 락(행마다 = DB 잠금의 중복, 일꾼 전체 = ShedLock 추가). 정합성은 락이 아니라 멱등성이 지킨다 → 락은 효율 선택 (`docs/learning/concurrency.md` 8절) |
