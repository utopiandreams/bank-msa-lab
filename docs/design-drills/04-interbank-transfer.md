# 04. 타행 이체 (5주 차 사가 예습 → ADR-0004 초안)

> 2026-11-19 시작. **1~3절은 개발자가 채운다** (모르는 칸은 "모름"). 4~6절은 리뷰하면서 같이 채운다.
> 막히면 [00 예시](00-example-transfer-core.md)를 본다. 아래 "주어진 것"은 도메인 사실이라 정답으로 깔아 둔다.

## 주어진 것 (도메인 사실 · 지금 시스템)

**시나리오:** 고객 A(우리 은행)가 B은행의 계좌로 10만 원을 보낸다.

**지금 있는 것:**
- `transfer`: 고객 요청 기록, 상태 머신(PROCESSING → COMPLETED / FAILED / UNKNOWN), 고객 멱등 키, core 호출 결과 분류. 당행 송금은 core 호출 **한 번**으로 끝난다 (00 예시)
- `core`: `POST /postings/withdrawals`, `/deposits`, `/transfers` (Idempotency-Key = 송금 ID, 같은 키 재요청은 처음 결과 그대로), `GET /postings/{key}` (COMPLETED / NOT_PROCESSED). 원장(복식부기)과 잔액 변경이 한 트랜잭션
- `bank-mock`: **아직 없음.** 외부 결제망 전체(금융결제원 + B은행)를 대표하는 블랙박스. 우리가 롤백시킬 수 없다

**5주 차 범위 (CLAUDE.md 로드맵):** bank-mock은 **단순 성공 / 실패만** 돌려준다. 타임아웃·응답 없음·결과 불명·상태 조회·대사는 8주 차에 이 설계 위에 얹는다. 그래도 **8주 차에 얹을 자리**는 지금 설계에서 보이게 그린다

**회계 규칙 (정답):**
- 고객 돈은 외부로 나가는 순간까지 **미정산 임시 계정(가계정)**에 머문다. 고객 계좌에서 바로 "사라지게" 하지 않는다
  ```
  출금 시:   차변 고객 예금 -10만   / 대변 타행이체 미정산 +10만
  외부 성공 뒤 정산 (실제로는 다음 영업일 차액결제): 차변 타행이체 미정산 -10만 / 대변 한국은행 예치금 -10만
  외부 실패 → 보상: 출금 전표를 고치거나 지우지 않고, 반대 방향 전표를 새로 쓴다
             차변 타행이체 미정산 -10만 / 대변 고객 예금 +10만
  ```
- **원장은 불변.** 취소도 새 거래다 (역분개). 그래서 "보상"은 원장에 흔적이 두 줄 남는다
- 정상이라면 정산·보상이 끝난 뒤 미정산 잔액의 합은 0이 된다 → 대사 포인트

**핵심 용어:**
- **사가(Saga):** 여러 서비스에 걸친 작업을 각자 로컬 트랜잭션으로 나눠 순서대로 실행하고, 뒤에서 실패하면 앞 단계를 **보상 트랜잭션**으로 되돌리는 방식
- **오케스트레이션:** 지휘자 하나(transfer)가 "다음은 너" 하고 순서를 부른다 / **코레오그래피:** 지휘자 없이 각자 이벤트를 보고 다음 일을 한다

## 1. 흐름
누가 → 누구에게 → 무엇을 (홉마다 한 줄). 로컬 트랜잭션으로 묶이는 구간은 묶어서 표시

```
우선 해피패스
1. 타행 송금 row 추가 (tx1)
2. 코어 서버에 출금 요청을 보낸다.
3. 성공하면 타행 송금 상태를 임시 출금? 이런거로 바꾼다. (tx2) 
4. 타행 api (그런 별도 망이 있지 않을까?) 에다가 요청을 보냄 
5. 타행 api 요청이 성공하면 타행 처리 완료, 정산 진행중으로 상태를 바꾼다 (tx3)
6. 코어에 정산 요청을 보낸다.
7. 성공하면 완료 상태로 갱신 (tx4)

각각의 단계에서 UNKNOWN 상태가 있을 수 있고 이거는 사실 재확인하고, 이후 로직을 진행시키는 문제라서 생략하고
타행 api 에서 실패하거나 거절된 경우랑, 타행 api 는 성공했는데 우리쪽 문제로 보상을 해줘야 하는 경우는 고려해야함

전자의 상황
1~4 는 동일
5. 타행 api 요청에서 거절이 되면 타행 거절, 보상 트랜잭션 실행중 상태로 변경 (tx3) // 여기서 상태 머신이 복잡해서 더 컬럼을 나눠야 하는 가 생각이 드네
6. 코어에 임시 출금 상태를 다시 돌리는 보상 트랜잭션 요청
7. 코어에서 보상 트랜잭션이 성공하면 실패 상태로 갱신 (tx4)

후자의 상황
1~6 동일
7. 여기서 실패/거절 등이 되면 타행 api 보상 실행중 상태로 갱신 (tx4) >> 이건 신중하게 결정을 해야할 것 같다. 
8. 다시 타행 api 보상 실행
9. 타행 api 보상 성공 하면, 타행 보상 성공, 정산 진행중 으로 갱신 (tx5)
10. 출금 빠꾸 정산(?) 진행... 

```

## 2. 홉 분석표

| 홉 | ① 호출 전에 커밋할 흔적 | ② 응답을 못 받으면 상태 | ③ 재시도 멱등 키 | ④ 결과 확정 수단 | ⑤ 실패 시 앞 단계 되돌리기 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

이거 너무 복잡해서 이거 어떻게 씀...

> **리뷰 후 정리 (2026-11-19, 개발자 답변을 Claude가 표로 옮김)** — 홉은 3개, 지휘자는 transfer (오케스트레이션)

| 홉 | ① 호출 전에 커밋할 흔적 | ② 응답을 못 받으면 상태 | ③ 재시도 멱등 키 | ④ 결과 확정 수단 | ⑤ 실패 시 앞 단계 되돌리기 |
| --- | --- | --- | --- | --- | --- |
| transfer → core 출금 | 송금 행 PROCESSING | UNKNOWN (당행과 같음) | 송금 ID | core 상태 조회 / 같은 키 재전송 (이미 있음) | 앞 단계 없음. 거절이면 core가 롤백 → **FAILED** (원장에 흔적 없음) |
| transfer → bank-mock 송금 (**피벗**) | **INTERBANK_REQUESTED** ("보냈을 수도 있다") | 결과 불명 → **보상 금지**, 확인 먼저 | 송금 ID (bank-mock이 멱등하다는 전제) | bank-mock 상태 조회 / 같은 키 재전송 (**8주 차**). 5주 차는 이 상태에 멈춰 둔다 | 거절이면 출금 취소(보상) |
| transfer → core 출금 취소 (보상) | **COMPENSATING** | COMPENSATING 유지, **성공할 때까지 재시도** (보상은 실패로 끝날 수 없다) | **`{송금ID}-cancel`** (결정적 키: 출금과 다른 거래라 키가 달라야 하고, 재시도해도 같은 값이어야 한다) | core 상태 조회 / 같은 키 재전송 | 없음 (보상의 보상은 없다) |
| (피벗 뒤) transfer 완료 기록 | — | 외부 성공 확인 후 transfer DB 커밋 실패 | — | 다시 확인 → 기록 | **되돌리지 않는다. 앞으로만** (forward recovery) |

## 3. 상태 머신
상태 목록 + 전이 (끝 상태 표시, "모름" 상태가 홉마다 있는지, **보상 중** 상태가 필요한지)

```
STARTED > PROCESSING > 출금 완료 > WITHDRAWN > 타행 요청 > INTERBANK_REQUESTED > 성공 > COMPLETED > ( 정산 후 > SETTLED ?)
타행 요청 실패 > RECOVERYING? > 보상 요청 > 성공 > FAILED 

```

> **리뷰 후 정리 (2026-11-19)**

```
PROCESSING ──출금 성공──▶ WITHDRAWN ──외부 호출 직전 커밋──▶ INTERBANK_REQUESTED ──외부 성공──▶ COMPLETED (끝)
    │                    (외부에 안 보낸 게 확실)          (보냈을 수도 있다)        │
    │                                                                              ├──외부 거절──▶ COMPENSATING ──취소 성공──▶ CANCELLED (끝, 이름 미정)
    │                                                                              │               ↺ 취소 응답 없음/실패 → 같은 키로 재시도
    │                                                                              └──응답 없음/죽음──▶ (결과 불명: 확인 먼저, 8주 차)
    └──출금 거절──▶ FAILED (끝, 돈이 한 번도 안 움직임)
```

- 피벗 앞(출금)은 **뒤로 복구**(보상), 피벗 뒤는 **앞으로 복구**(재시도). 되돌릴 수 없는 단계는 최대한 뒤에 둔다
- `FAILED` ≠ `CANCELLED`: 원장(흔적 없음 vs 출금 + 역분개 두 줄), 고객 거래 내역, 대사 대상이 다르다
- SETTLED는 송금 상태가 아니다. 정산은 하루치 배치 → 미정산 계정 잔액으로 본다 (8주 차)

### 채우면서 생각해 볼 질문 (힌트, 답은 안 적어도 됨)
1. 당행은 홉이 1개였다. 타행은 홉이 몇 개인가? core 출금과 bank-mock 송금 사이에 transfer가 끼는가, core가 직접 bank-mock을 부르는가? (ADR-0001 "사가는 어디서"를 다시 볼 것)
2. 출금은 성공했는데 bank-mock이 "실패"라고 답했다. 고객 돈은 지금 어디(어느 계정)에 있나? 누가 무엇을 호출해서 돌려놓나?
3. 그 **보상 호출 자체가 실패**하면? 보상을 다시 보내도 두 번 돌려주지 않으려면 키를 무엇으로 하나? 출금 키와 같아도 되나?
4. 보상이 끝나면 송금 상태는 FAILED인가, 다른 이름이 필요한가? 고객 입장에서 "실패"와 "돈 빠졌다가 돌아옴"은 같은가?
5. 출금 전에 계좌가 외부에서 받을 수 있는 계좌인지(수취 조회) 먼저 물어보면 무엇이 줄어드나? (실제 은행은 한다. 5주 차에 넣을지는 선택)
