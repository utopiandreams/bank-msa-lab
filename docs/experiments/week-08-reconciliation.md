# Week 08. 일일 대사: 해소 일꾼까지 놓친 이중 지급을 찾는다

## 문제
타행 송금 결과 불명은 해소 일꾼이 외부 **조회**로 확정한다 (설계 연습 08 2부). 그런데 외부가 조회 계약을 어기면(처리했는데 "없음", 또는 기록을 잃었다가 정산 때 나타남) 일꾼은 출금을 취소하고, 외부는 입금한다 = **이중 지급**. 우리 원장(transfer ↔ core)만 보면 완벽하게 맞아서 **아무도 모른다**.

## 재현 (2026-11-25, 클러스터)
- bank-mock 실험 스위치를 GitOps로 켬: `BANK_MOCK_RESPONSE_DELAY=5s`(transfer read-timeout 3s보다 길게 → 결과 불명), `BANK_MOCK_LOOKUP_LIES_NOT_FOUND=true`(조회에 거짓 "없음", 정산 파일엔 나옴)
- gateway로 타행 송금 5만 원 (계좌 잔액 10만):
  - 응답 3.3초, `EXTERNAL_BANK_REQUESTED` (외부는 이미 입금 처리)
  - 약 18초 뒤 해소 일꾼이 조회 → "없음" → 출금 취소 → `CANCELLED`, 고객 잔액 100,000원 복구
- 이 시점의 상태: transfer = 취소, core = 출금 + 취소 전표(원장 정확), 외부 = **입금 5만 원**. 해소 일꾼·원장·알림 어디에도 이상 신호 없음

## 선택지 비교 (대사 구조, 설계 연습 09 결정 1~22)
| 방법 | 장점 | 단점 |
| --- | --- | --- |
| transfer 안에서 대사 | 서비스가 안 늘어남 | 검사받는 쪽이 검사를 겸함 (같은 코드 버그를 못 봄) |
| **별도 대사 서비스 + 일자별 추출 파일(S3) + 완료 이벤트(인박스)** | 독립성, 파일이 그날의 증거(다시 돌려도 같은 결과), 다른 서비스 DB에 안 붙음 | 서비스·저장소·추출 배치가 늘어남 |
| 대사 서비스가 각 DB 읽기 복제본에 직접 | 가장 빨리 만듦 | DB per service 위반, 스키마 결합 |
| 단건 조회 API로 맞춰 보기 | 쉬움 | 우리 쪽에서만 출발 → 외부에만 있는 거래를 못 찾음, N번 호출 |
| 합계(총액)만 비교 | 빠름 | 오류가 상쇄됨 (우리만 3만 + 외부만 3만 → 합계 같음) |

## 적용한 해결책과 이유
- **양방향 건별 대사** 두 쌍: transfer ↔ core 원장(+ 시산표), 타행 송금 ↔ 외부 정산 파일
- core·transfer는 매일 00:05 전날분을 CSV로 Garage에 올린 **뒤** 완료 이벤트(건수·합계·SHA-256). 외부 파일은 대사 서비스의 **수신 작업**이 받아 원본 그대로 보관 (외부는 우리 인프라에 쓰지 않는다 → 대외계 역할)
- 판정표(개발자 작성, 결정 7): 우리 끝 상태별로 외부 정상값을 정하고, 어긋나면 **이중 지급·고객 손실은 즉시 경보**, 자정 경계·시계 차이로 생길 수 있는 건은 **하루 이월**
- 결과는 회차 요약 + 예외 항목만, 한 트랜잭션 (전부 아니면 전무). 지표 + Prometheus 경보 규칙, 추출이 안 오면 기한 경보(dead man's switch)

## 결과 (전후 수치)
| 지표 | 전 (대사 없음) | 후 |
| --- | --- | --- |
| 이중 지급 5만 원 발견 | 영영 모름 (원장은 정확, 신호 없음) | 외부 파일 수신 후 **다음 대사 회차(≤ 60초)에 DOUBLE_PAYMENT 경보**, Prometheus `ReconciliationMoneyLoss` firing |
| 오늘 실제 데이터 transfer ↔ core | — | 265건(완료 249·실패 4·타행 완료 8·타행 취소 4) ↔ 전표 265건 **전부 정상**, 시산표 차변 = 대변 = 20,028,180원 |
| 합계로만 봤다면 | — | transfer 40억 vs core 2만 8천 원 → "40억 불일치"로 오판 (실패 송금은 전표가 없어야 정상) |
| 재추출 | — | 같은 날짜 새 추출이 오면 이전 회차 SUPERSEDED, 되돌린 뒤 다시 판정 (266 ↔ 267, 전부 정상) |

## 대시보드 판독
- 먼저 보인 곳: `reconciliation_items{kind="DOUBLE_PAYMENT", status="ESCALATED"}` = 1 → Alerts 탭 `ReconciliationMoneyLoss`
- 피해자: 은행(돈을 두 번 냄). 원장·송금·알림 대시보드는 전부 초록

## 배운 점 / 한계
- **원장이 맞다 ≠ 돈이 맞다.** 내부 장부끼리는 완벽해도 외부와 어긋날 수 있다. 결과 불명 해소가 "상대의 약속(처리 상한 + 조회)"에 기대는 한, 마지막 그물은 상대 쪽 원본과의 대사다
- **"S3 호환"은 SDK 기본값까지 호환되지 않는다**: AWS SDK 새 기본값(청크 서명 + 체크섬 트레일러)을 Garage가 거부 → 진짜 Garage 컨테이너 테스트로 재현·수정 (pitfalls 42)
- 한계: bank-mock은 기록을 메모리에 둬서 재시작하면 그날 기록을 잃는다 (결정 6). 실제로 오늘 배포 재시작으로 타행 12건이 외부 파일에서 빠져 MISSING_EXTERNAL로 이월됐다 → 내일 경보로 올라간다. 진짜 기관은 기록을 잃지 않는다는 전제의 한계
- 한계: 비교는 메모리에서 (하루 수천 건). 100만 건이면 스테이징 `COPY` + `FULL OUTER JOIN` (결정 22)
- 남은 것: 이중 지급을 찾은 **뒤**의 처리(착오송금 반환 요청, 수작업 조정 전표·승인자 분리), 계속 실패하는 보상의 격리(설계 연습 08 2부 보류)
