> **판독 칸(✍️)은 개발자가 채운다.** Claude는 사실과 원리만 적었다.

## 문제

같은 계좌를 동시에 바꾸는 요청이 겹치면, 각자 읽은 잔액에 자기 변경만 반영해 덮어써서 다른 요청의 변경이 사라진다(lost update). 은행에서는 출금이 사라지면 돈이 생기고, 입금이 사라지면 돈이 없어진다.

## 재현 (측정 방법)

### 질문 두 개, 시나리오 두 개

| 시나리오 | 모양 | 답하는 질문 |
| --- | --- | --- |
| **hot** | 계좌 1개 → 수신 계좌 200개로 1원씩 (이벤트 계좌, 월급 지급) | 경합이 최악일 때 전략별 정합성·처리량·지연은? |
| **spread** | 계좌 200개끼리 무작위 1~100원 (5주 차 기준선과 같은 모양) | 경합이 없을 때 락의 비용은? |

- **섞지 않았다.** 섞으면 나빠진 원인이 핫 계좌인지 데드락인지 구분이 안 된다 (한 번에 변수 하나). 서로 주고받는 데드락 모양은 테스트로 이미 재현·해결(PESSIMISTIC의 ID 순 잠금)
- **잔액은 넉넉히.** 잔액 부족 거절이 섞이면 실패 원인이 둘이 된다
- **core 직접** (`/postings/transfers`). gateway·transfer 구간이 섞이면 락 차이가 흐려진다. transfer가 503·500을 어떻게 분류하는지는 8주 차(결과 불명)로

### 실행기가 하는 일

1. 관리 포트(8081)로 전략 전환 (`POST /actuator/experiments`)
2. 전 지표: 낙관적 락 재시도 카운터, Redis `INFO stats`·`INFO commandstats`
3. **클러스터 안 k6 Job** (core와 다른 노드, podAntiAffinity). 맥북 Wi-Fi·Tailscale 흔들림이 섞이지 않게
4. k6 `setup()`이 **회차마다 새 계좌**를 만든다 (사용자 `lock-<RUN>-NNN`). NONE이 깨뜨린 잔액이 다음 회차에 섞이지 않게
5. `constant-arrival-rate`로 고정 속도 (응답을 기다리지 않음 = coordinated omission 회피)
6. 후 지표 + **DB 정합성**: 그 회차 계좌만 골라 잔액 합 / 원장 합 / 기대값, 잔액≠원장인 계좌 수

### 1차 측정 실패: 경합을 만들지 못했다

hot 50건/초에서 **NONE도 안 깨졌다** (재시도 2회, VU 50개에서 안 늘어남). 원인: `constant-arrival-rate`는 요청을 **정확히 같은 간격**으로 보낸다(포아송 도착이 아님). 50건/초 = 20ms마다 한 건, 처리는 5ms → 앞 요청이 끝난 뒤 다음이 도착해 겹치지 않는다. spread 200건/초(5ms마다)는 처리 시간과 비슷해서 겹쳤다. → hot을 150 / 300 / 500건/초로 다시 (pitfalls 36)

### Redis 명령 수: 락 한 번에 13개, 왕복 4번 ✅

송금 1건 = 계좌 2개 잠금 = 명령 26개 / 왕복 8번. 경합이 없는 spread에서도 같다 = **분산 락의 기본 요금.** spread p50 차이 REDIS 4.77ms − ATOMIC 4.17ms ≈ 0.6ms가 그 값. 왕복 중 1번(풀기 전 `HEXISTS` 확인)은 우리 코드가 넣은 것이라 이번에 제거 (`[core] Redis 락 풀기 전 확인 제거`). 명령 분해와 jar 확인은 `docs/learning/io-and-event-loop.md` 8절

## 선택지 비교

| 방법 | 장점 | 단점 | 이번 측정에서 |
| --- | --- | --- | --- |
| 원자적 UPDATE (조건부 UPDATE) | 왕복·대기 최소, 인프라 없음 | 규칙이 SQL로 감 (행 하나 안의 조건만) | 500건/초에서도 p99 7ms, 실패 0 |
| 비관적 락 (FOR UPDATE) | 복잡한 규칙·여러 행, 공정(FIFO) | 대기 중 DB 커넥션 점유, 데드락 주의 | 500건/초에서 p50 1.26s, VU 한계 |
| 낙관적 락 (@Version) | 충돌 없으면 공짜, 다른 요청에 걸친 수정 | 경합이 크면 재시도 폭증·실패 | 500건/초에서 실패 39% |
| Redis 분산 락 (pub/sub·스핀) | DB 밖 자원, 대기 중 커넥션 안 쥠 | 왕복 비용, Redis 장애점, 락 범위·TTL | 300건/초부터 core OOMKilled |
| 락 없음 | — | lost update | 150건/초부터 잔액 깨짐 |

## 배운 점 / 한계

- **부하 모양이 실험을 결정한다.** 같은 "50건/초"라도 균일 도착은 경합을 거의 안 만든다. 실제 트래픽은 몰려서 온다(버스트) → 실험의 처리량 숫자는 상한이 아니라 "균일 도착일 때"의 숫자
- **원장이 진실, 잔액은 캐시.** 모든 NONE 회차에서 원장 합은 정확했고 잔액만 틀렸다 (원장은 INSERT만, 잔액은 덮어쓰기). 대사(8주 차)가 잡아낼 불일치의 실제 모양
- **실패가 정합성을 깨지는 않았다.** OOMKilled 4회, 503·500 수천 건에도 모든 회차 정합성 ✅ (트랜잭션 롤백)
- 한계: core replicas 1이라 분산 락의 본래 자리(인스턴스 여러 대)는 재지 않았다. 한 번씩만 쟀다(반복·분산 없음). 30초는 짧다. k6 응답 시간에는 같은 클러스터 안 네트워크(약 0.x ms)가 포함
- 후속: REDIS 계열 붕괴의 원인 분석(판독 1), 503·500을 transfer가 어떻게 분류하나(8주 차), `HEXISTS` 제거 후 명령 수 재측정, PESSIMISTIC `lock_timeout`
