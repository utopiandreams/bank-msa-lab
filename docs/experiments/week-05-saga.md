# Week 05. 타행 이체 사가 (오케스트레이션)

> 2026-11-20 클러스터 확인 (S-4). 설계는 `docs/design-drills/04-interbank-transfer.md` → ADR-0004.
> 이 주차의 기록은 "재현 → 해결 → 수치"보다 **설계 기록**에 가깝다. 수치(결과 불명·대사)는 8주 차, 장애 주입은 15·17주 차에 붙인다.

## 문제
타행 이체는 우리 DB(core 원장)와 롤백할 수 없는 외부(결제망 = `bank-mock`)에 걸친다. 둘을 하나의 트랜잭션으로 묶을 수 없다. 외부 송금이 거절되면 이미 빠진 출금을 되돌려야 하고, 외부 송금 결과를 모를 때 되돌리면 이중 지급이 된다.

## 설계 요약 (ADR-0004)
- 지휘자 = `transfer`. 순서: core 타행 출금 → bank-mock 송금 → (거절 시) core 출금 취소
- **피벗 = 외부 송금 성공.** 피벗 앞은 보상, 뒤는 재시도
- 원격 호출마다 호출 **전에** 의도 상태를 커밋한다. 결과 불명은 의도 상태에 남는다 (pitfalls 27)
  `WITHDRAW_REQUESTED → WITHDRAWN → EXTERNAL_BANK_REQUESTED → COMPLETED`
  거절: `FAILED`(출금 거절) / `EXTERNAL_BANK_REJECTED`(= 보상 의도) `→ CANCELLED`
- `EXTERNAL_BANK_REQUESTED`에서는 절대 보상하지 않는다 (보냈을 수도 있음). 8주 차에 결과 조회로 해소
- 보상 = 원래 출금 전표를 가리키는 역분개, `reverses_entry_id` UNIQUE로 한 번만
- 출금하면 고객 예금 → **미정산(`INTERBANK_UNSETTLED`)**. 은행 간 차액결제는 만들지 않아서 성공 건은 미정산에 남는다 (8주 차 대사의 기준)

## 클러스터 확인 (2026-11-20, gateway 경유)

계좌 1개에 100,000원 입금 후, 미정산 0에서 시작.

| 시나리오 | 응답 | 잔액 | core 원장 | 미정산 | 알림 |
| --- | --- | --- | --- | --- | --- |
| 타행 성공 30,000 | 201 `COMPLETED` | 100,000 → 70,000 | `INTERBANK_WITHDRAWAL` 1건 (예금 차변 / 미정산 대변) | 0 → 30,000 | `TRANSFER_COMPLETED` SENT |
| 외부 거절 20,000 (받는 계좌 `999…`) | 201 `CANCELLED`, `ACCOUNT_NOT_FOUND` | 70,000 → 70,000 | 출금 1건 + `INTERBANK_WITHDRAWAL_CANCEL` 1건 (미정산 차변 / 예금 대변, 원래 전표를 가리킴) | 30,000 그대로 | `TRANSFER_CANCELLED` "출금한 금액을 돌려드렸습니다" SENT |
| 성공 건을 같은 고객 키로 재요청 | 200 `COMPLETED` | 그대로 | 새 전표 없음 | 그대로 | 추가 발송 없음 |

- 외부 거절은 400이 아니다. 요청은 정상이었고 출금까지 실제로 일어난 뒤 보상이 돌았다 → 원장에 전표 2개, 잔액과 미정산은 원래대로. **원장은 지우지 않고 반대 전표를 쌓는다**
- core 전표의 멱등 키 = 송금 ID. 고객 키(`Idempotency-Key`)와 서비스 간 키가 분리되어 있다

## 선택지 비교: 오케스트레이션 vs 코레오그래피

같은 타행 이체를 두 방식으로 (코레오그래피 흐름은 개발자가 설명, 2026-11-20):

```
① 오케스트레이션 (구현)                  ② 코레오그래피 (가정)

 고객   transfer    core   bank-mock      고객  transfer   Kafka    core   bank-mock  notification
  │──요청─▶│                               │─요청─▶│
  │        │──출금(REST)─▶│                 │◀─202─│ (처리 중)
  │        │◀────ok──────│                  │       │─출금요청됨─▶│──────▶│ 출금
  │        │──송금(REST)──────▶│            │       │◀────────────│◀출금됨│
  │        │◀────거절──────────│            │       │ (까 보니 타행)
  │        │──취소(REST)─▶│                 │       │──송금(REST)──────────────▶│
  │        │◀────ok──────│                  │       │◀─────거절─────────────────│
  │◀CANCELLED│                              │       │─출금취소요청됨▶│──────▶│ 취소
  │        │─취소됨 이벤트─▶ notification   │       │◀────────────│◀취소됨│
                                            │       │─송금취소됨──▶│──────────────────────▶ 알림
 흐름 = transfer 코드 한 곳                  흐름 = 서비스마다 흩어진 "이 이벤트 오면 이거 해"
 상태 = 상태 머신 하나                       상태 = 서비스별 작은 상태들의 조합 (전체 상태는 어디에도 없음)
```

| 관점 | 오케스트레이션 | 코레오그래피 |
| --- | --- | --- |
| 흐름이 보이는 곳 | transfer 코드 한 곳 | 서비스마다 흩어진 구독 규칙 |
| 전체 상태 | 상태 머신 하나 | 어디에도 없음 → "내 송금 어떻게 됐어요?"에 답하려면 모든 이벤트를 구독하는 조회 모델(프로젝션)을 따로 만들어야 함 |
| 고객 응답 | 동기로 끝 상태까지 (5주 차 결정) | 본질적으로 비동기 (202 "처리 중") |
| 커밋 후 발행 전 장애 | 호출한 쪽이 기다리고 있음 → 타임아웃 = 결과 불명 → 의도 상태에서 같은 키로 재시도, 멱등으로 복구 | **기다리는 쪽이 없음** → 돈은 빠졌는데 송금이 조용히 멈춤 (결과 불명조차 안 됨) → 모든 홉에 Outbox 필수 |
| 멈춘 송금 발견 | 오래된 의도 상태 조회 | 타임아웃 감시자가 필요, 그게 사실상 지휘자 |
| 순서 변경 | transfer만 수정 | 여러 서비스를 함께 수정·배포 |
| 결합 | transfer가 core·bank-mock API를 앎 | 이벤트 계약으로 결합. core 이벤트가 송금 ID 같은 상대의 맥락을 실어 날라야 함 ("출금됨"만으로는 당행·타행을 모름) |
| 잘 맞는 곳 | 보상이 있는 돈 흐름, 단계 3개 이상 | 결과를 알리기만 하는 흐름 |

## 적용한 해결책과 이유
오케스트레이션. 보상 판단에 "지금 어디까지 했나"가 필요하고, 그걸 한 곳(transfer 상태 머신)에서 보는 것이 이중 지급을 막는 가장 확실한 방법이다. 워크플로 엔진(Temporal 등)은 도입하지 않았다. 오케스트레이션 = 영속화된 상태 머신이고, 지금 규모에선 손으로 짠 상태 머신이 설명 가능성이 더 높다.

**우리 시스템은 이미 둘 다 쓴다.** 돈이 움직이는 사가는 오케스트레이션, 송금 결과 알림(transfer → Kafka → notification)은 이벤트 하나에 반응하는 코레오그래피.

## 결과
- 성공·거절(보상)·재요청 세 경로에서 잔액과 미정산이 기대값과 일치 (위 표)
- 전후 수치는 아직 없다: 결과 불명(`EXTERNAL_BANK_REQUESTED`에 멈춤)과 대사는 8주 차, 외부 지연·장애 전파는 15주 차

## 배운 점 / 한계
- "요청함" 상태는 원래 결과 불명이다. API 호출과 DB 트랜잭션을 묶을 수 없으니까. 결과 불명을 따로 두지 않고 의도 상태에 남긴다
- 상태를 나눌지는 "멈춘 송금을 복구 로직이 발견하면 할 일이 다른가"로 정한다
- **한계 1:** 외부 송금 결과 불명이면 지금은 멈춘 채로 남는다 (8주 차 해소 스케줄러)
- **한계 2:** `TransferFinishedEvent`는 커밋 뒤 바로 발행해 유실될 수 있다 (6주 차 Outbox로 재현·해결 예정, 의도적으로 남긴 구멍)
- **한계 3:** 고객 응답이 동기라 외부가 느리면 고객도 느리다 (15주 차 외부 지연 실험의 "전" 상태)
